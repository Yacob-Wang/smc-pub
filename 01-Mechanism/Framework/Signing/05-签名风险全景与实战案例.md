## 3. 5 件套实战案例(6 大场景各 1 个)

### 案例 1:V1 绕过 + DEX 注入(典型模式)

**环境**:Android 6.0(API 23,无 V2 强制),某早期工具类 App,只签 V1

**现象**:
- 用户从非官方渠道下载了同款 App
- 安装后,App 弹广告 / 扣费
- 用户投诉"我装的是官方的,怎么变了"

**分析思路**:
1. 用户提供 APK 文件 → `apksigner verify --print-certs app.apk`
2. 看到 `v1 scheme: true` 但 `v2 scheme: false`
3. 用 `unzip -p app.apk classes.dex | sha256sum` 跟官方对比 → 不一致
4. 用 010Editor 看 APK 头部 → 多了几字节 → **Janus 漏洞**

**根因**:**V1 不保护 ZIP 头部** — 攻击者在 APK 头部塞了一段 DEX 头,旧 Dalvik 把它当作合法 DEX 解析。V1 签名只校验 entry 内部,不校验 entry 之前/之后的字节。

**修复**:
- 用户侧:不要从非官方渠道下载
- 开发者侧:**强制 minSdkVersion ≥ 24**,V2 签名覆盖整个 APK

**修复后验证**:升级到 V2/V3 后,新版本再被注入,签名校验失败(因为 APK 头改了)。

### 案例 2:升级签名不匹配(典型模式)

**环境**:Android 17,某银行 App v5.0 → v6.0 升级,公司 CI 重构换了密钥

**现象**:
```
PackageManager: Installation failed: -25
        at com.android.server.pm.InstallParams.handleStartCopy(...)
InstallPackage: Verification failed: INSTALL_FAILED_UPDATE_INCOMPATIBLE
```

**分析思路**:
1. 错误码 -25 → INSTALL_FAILED_UPDATE_INCOMPATIBLE
2. 跑 `apksigner verify --print-certs v5.0.apk` vs `v6.0.apk` → 证书指纹不同
3. 查 CI 系统的 git log → v6.0 那次发布用了新密钥(老密钥文件被丢了)

**根因**:**老密钥丢了,新密钥签的 v6.0 没有 V3 Proof of Rotation**(Proof 需要老私钥)。

**修复**:
- 短期:Play App Signing 用户 → 联系 Play Console 走 App Signing Key 重置流程(可走通,因为 Play 保留所有历史 key)
- 短期:国内商店用户 → 卸载老版本,装新版本(干净状态,不能升级)
- 长期:**密钥文件多副本备份 + 版本控制 + 异地灾备** + **CI 跑 apksigner rotate 演练**

**修复后验证**:Play App Signing 流程走通,所有用户可平滑升级到 v6.0。

### 案例 3:vbmeta / AVB 签名断裂(典型模式)

**环境**:Android 17,某厂商 OTA 升级 vbmeta 后,部分设备变砖

**现象**:
- 设备开机停在 bootloader 界面
- logcat 无法获取(系统没起来)
- `fastboot oem unlock` 提示"vbmeta signature verification failed"

**分析思路**:
1. 查设备 /vendor 目录 → OTA 包里 vbmeta.img 用错的密钥签
2. 查 OTA 流水线日志 → 密钥文件上次升级时换过,新 vbmeta 用新 key 签
3. 老设备的 bootloader 信任**老 key**,新 vbmeta 校验失败 → 拒绝启动

**根因**:**vbmeta key 跟 bootloader 烧录的"信任根"不匹配**。AOSP 的 AVB 2.0 设计要求:**vbmeta key 一旦确定,不能换**(除非 unlock bootloader 重新锁)。

**修复**:
- 短期:用户进入 bootloader 模式 → `fastboot --disable-verity` 或 `fastboot oem unlock`(用户数据会清空)
- 长期:**vbmeta key 跟 boot ROM 烧录 key 严格同步**,OEM 升级时必须沿用同一把 key

**修复后验证**:老设备解锁后重新刷 OTA,新 vbmeta 走 unlock 路径(不验 vbmeta key,只验 boot.img)。

### 案例 4:Key 失窃 / 误删(典型模式)

**环境**:某游戏公司,CI 系统的 Jenkins 服务器被入侵,release.jks 私钥泄露

**现象**:
- 攻击者用泄露私钥签了"同款 App" + 植入恶意代码
- 用户从非官方渠道下载,看起来是"官方版本"
- 安全团队发现 → 紧急吊销 → 但 App 已经在野升级

**分析思路**:
1. Play Console 异常登录告警 → 查上传历史 → 发现 24 小时内有未知 upload key 的 APK
2. APK 看起来"正常" — 签名验证通过(因为攻击者有 upload key)
3. 报警服务:Play App Signing 的"轮询上传异常"告警

**根因**:**upload key 泄露** + 没有 V3 key rotation + 没有"异常 upload 告警"。

**修复**:
- 紧急:Play Console → App Signing → Reset upload key(需要 Google 团队审核)
- 中期:**Play App Signing 必须用** + V3 Proof of Rotation 提前演练
- 长期:**upload key 用 HSM(硬件安全模块)托管** + **CI 系统 audit log + 异常告警** + **2FA + 最小权限**

**修复后验证**:Play Console 走完 reset upload key 流程,所有老用户下次升级到新签名的 APK,成功(因为 Play 帮你做了 rotate)。

### 案例 5:Play Integrity 失败(典型模式)

**环境**:某银行 v6.0,新机型(三星国行 S24)用户首次启动,提示"设备安全等级不足"

**现象**:
- 银行 App 启动 → Play Integrity API 返回 `MEETS_BASIC_INTEGRITY` 失败
- App 提示"您的设备不在信任列表" → 拒绝服务
- 用户投诉:三星旗舰机居然用不了银行 App

**分析思路**:
1. 查银行服务端日志:Play Integrity verdict = null(无任何 verdict)
2. 查 Google Play 服务端:该机型的 attestation root cert 不在 Google Trust List
3. 查设备:国行三星 S24 用了三星自己的 Knox,没走 Google 标准 Attestation

**根因**:**国行 ROM 经常不通过 Google 认证**(没有 GMS)。Google 不给 Attestation root cert,银行服务端拒绝。

**修复**:
- 短期:银行 App 加 fallback — Play Integrity 失败时,改用其他风控(设备指纹 + 行为分析)
- 长期:银行 App 跟三星/华为谈 OEM 合作,获取 OEM Attestation(替代 Google Attestation)

**修复后验证**:Fallback 流程跑通,国行用户可用银行 App(但风险等级降一档)。

### 案例 6:厂商定制签名校验差异(典型模式)

**环境**:同一 APK(用标准 V2/V3 签)在 MIUI 14 / EMUI 13 / ColorOS 13 三个 ROM 上表现不一致

**现象**:
- MIUI 14:安装成功
- EMUI 13:安装成功
- ColorOS 13:**安装失败** -25(INSTALL_FAILED_UPDATE_INCOMPATIBLE)
- 三星 One UI 6:安装成功

**分析思路**:
1. 错误码 -25 → 升级签名不匹配
2. 但本次是新装,不是升级 → 怀疑 ColorOS 改了 PMS 逻辑
3. 反编译 ColorOS 的 PMS → 发现**强制要求"上次安装的 cert"匹配**(但用户没装过)

**根因**:**ColorOS 13 改了 PMS 的签名校验逻辑**,强制要求"已安装 cert == 即将安装 cert",新装不通过。**这是 ColorOS 的"反盗版"功能**(防止用同一签名升级不同 App)。

**修复**:
- 用户侧:卸载"残留包"重装,或改用其他 ROM
- 开发者侧:**签名统一** + **多套 release key 备用**(不同 ROM 用不同 key)
- OEM 合作:跟 ColorOS 申请"白名单",绕过反盗版

**修复后验证**:多套 key 策略后,所有 ROM 都能装。

## 4. 跨厂商差异速查

### 4.1 国内主要 ROM 差异

| 厂商 | ROM | TEE 实现 | StrongBox | 签名校验 | 备注 |
|------|-----|---------|-----------|---------|------|
| **华为** | EMUI / HarmonyOS | iTrustee(自研 TEE) | inSE(独立芯片) | 标准 PMS | 鸿蒙 NEXT 引入新签名链 |
| **小米** | MIUI / HyperOS | Trusty(Google) | 部分旗舰(13 Pro+) | 标准 PMS | 国行去 Google 服务 |
| **OPPO** | ColorOS | Trusty | 部分旗舰(Find X5+) | **PMS 定制**(反盗版) | 强制 cert 匹配 |
| **vivo** | OriginOS / FuntouchOS | Trusty | 部分旗舰 | 标准 PMS | 跟 OPPO 同源 |
| **三星** | One UI | Knox(自研 TEE) | Knox Vault(独立芯片) | 标准 PMS | 国行去 Google 服务 |
| **谷歌** | Pixel | Trusty(Google 自维护) | Titan M2 | 标准 PMS | 参考实现 |
| **魅族** | Flyme | Trusty | ❌ | 标准 PMS | 较少定制 |
| **一加** | OxygenOS | Trusty | ❌ | 标准 PMS | 国际版标准 |

### 4.2 鸿蒙 NEXT(HarmonyOS NEXT)的特殊签名

**鸿蒙 NEXT** 完全脱离 Android,**引入新的"鸿蒙签名"机制**:

- **HAP(HarmonyOS Ability Package)** 替代 APK
- **新签名链**:`profile + 数字证书 + 权限声明`(比 Android 复杂)
- **强制 HSM 签名** — 鸿蒙开发者必须用华为云 HSM 签 HAP
- **不再兼容 V1-V4** — 鸿蒙 NEXT 完全独立

**稳定性视角**:**鸿蒙 NEXT 不在 Android 签名体系内**。如果你的 App 要鸿蒙 NEXT,必须重新签 HAP,**两套签名链都要维护**。

## 5. 监控 + 治理方案

### 5.1 监控关键指标

| 指标 | 监控方式 | 告警阈值 |
|------|---------|---------|
| **APK 签名校验失败率** | logcat + 抓 `ApkSignatureVerifier.verify` 异常 | > 0.1% 持续 5min |
| **PMS installStage 失败** | PMS 日志 + `dumpsys package` | > 1% 持续 10min |
| **vbmeta 校验失败** | dmesg + `dmesg \| grep -i dm-verity` | 任何一次都告警 |
| **Play Integrity verdict=null** | Play Integrity 回调统计 | > 5% 持续 30min |
| **Key Attestation 失败** | 服务端日志 | > 0.5% 持续 1h |
| **KeyStore2 守护进程崩溃** | `dumpsys keystore2` | 任何一次都告警 |
| **StrongBox 不可用率** | logcat + `StrongBox unavailable` | > 1% 持续 24h |

### 5.2 治理 4 步走

**Step 1:预防(开发期)**
- CI 必须跑 `apksigner verify` —— 不通过禁止发布
- 私钥文件 HSM 托管 + 2FA + 异地备份
- 定期演练 `apksigner rotate` —— 验证 Proof of Rotation 链
- 跨厂商兼容性测试(MIUI / EMUI / ColorOS 各机型)
- V3 强制 + V4 增量安装(>= 30MB 的 App 必加)

**Step 2:检测(线上)**
- 监控关键指标(§5.1 表)
- 异常 APK 上传告警(Play Console)
- 异常设备型号告警(Play Integrity verdict=null)
- 用户报装不上的关键词监控(用户反馈系统)

**Step 3:响应(线上问题)**
- 短期:Play Console / 厂商商店紧急更新
- 中期:服务端降级(Play Integrity fallback / cert 兼容)
- 长期:根因修复 + 复盘(写案例库)

**Step 4:复盘(事后)**
- 5 件套标准化(01 §1.3 模板)
- 决策日志(为什么当时这么决策)
- 案例入知识库(本系列就是案例库)
- 监控规则更新(新风险 → 新告警)

## 6. 总结:整个系列的 5 条 Takeaway

整个系列 5 篇的 5 条 Takeaway:

1. **签名是 Android 安全模型的"信任锚",不是"安全特性"**(01 §7) — 位于 Layer 2,沙箱 / 权限 / Verity 都建立在它之上。架构师如果只关注 App 代码,会在跨层问题上栽跟头。

2. **V2/V3 是当前事实标准,V4 是增量专用,V1 是 fallback**(01 §2.5 + 02 全文) — 新 App 必须 V2+V3,大 App 必须 V2+V3+V4,老 App 升级必须分阶段。`apksigner verify --print-certs` 是排查工具箱必备。

3. **签名校验是 PMS 的"必经门",运行时不做签名校验**(03 §3 + 03 §7) — 所有非系统 APK 都必须过 `VerifyInstaller.verify()`,但 PathClassLoader 信任 PMS 的结果。**安全模型是"PMS 守住,运行时不卡"**。

4. **AndroidKeyStore Key 永不离开 TEE/StrongBox,Key Attestation 是 Key 的"出生证明"**(04 §5) — 银行 App 信任硬件背书 Key 的唯一机制。**服务端必须定期同步 Google Trust List**(3 年一换,过期就 fail)。

5. **线上签名问题 90% 是"非 App 代码问题"**(01 §1.3 + 05 §3) — 签名相关的根因通常隐藏在 PMS / KeyStore / AVB / 厂商定制层。**架构师必须有"跨 4 层 + 跨厂商"的视角,才能一次定位**。

# Prometheus + AlertManager 配置(伪代码,实际以监控系统为准)
groups:
  - name: android_signing
    rules:
      # 1. APK 签名校验失败率
      - alert: ApkSignatureVerifyFailedHigh
        expr: rate(apk_signature_verify_failed_total[5m]) / rate(apk_signature_verify_total[5m]) > 0.001
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "APK 签名校验失败率 > 0.1%"
          runbook: "https://wiki.smc-pub/runbook/apk-signature-failure"

      # 2. PMS installStage 失败
      - alert: PmsInstallStageFailedHigh
        expr: rate(pms_install_stage_failed_total[10m]) / rate(pms_install_stage_total[10m]) > 0.01
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: "PMS installStage 失败率 > 1%"

      # 3. vbmeta 校验失败
      - alert: VbmetaVerificationFailed
        expr: increase(vbmeta_verify_failed_total[5m]) > 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "vbmeta 校验失败 — 设备可能变砖"

      # 4. Play Integrity verdict=null
      - alert: PlayIntegrityVerdictNullHigh
        expr: rate(play_integrity_verdict_null_total[30m]) / rate(play_integrity_request_total[30m]) > 0.05
        for: 30m
        labels:
          severity: warning
        annotations:
          summary: "Play Integrity 5%+ 设备 verdict=null,可能是国行 ROM 异常"

      # 5. Key Attestation 失败
      - alert: KeyAttestationVerifyFailedHigh
        expr: rate(key_attestation_verify_failed_total[1h]) / rate(key_attestation_verify_total[1h]) > 0.005
        for: 1h
        labels:
          severity: warning
        annotations:
          summary: "Key Attestation 失败率 > 0.5% — 可能是 Google Trust List 过期"

      # 6. StrongBox 不可用率
      - alert: StrongBoxUnavailableHigh
        expr: rate(strongbox_unavailable_total[24h]) / rate(strongbox_request_total[24h]) > 0.01
        for: 24h
        labels:
          severity: info
        annotations:
          summary: "StrongBox 不可用率 > 1% — 可能是新机型不支持"
