## 一、背景：从事实基础到机制全景

### 1.1 01-03 解决了什么,本篇解决什么

| 01-03 解决 | 本篇 04 解决 |
|----------|------------|
| FS 是什么,12 类 | **挂载后怎么协作** |
| Android 设备分区怎么选 FS | **5 大职责怎么在层间分工** |
| 完整文件树长啥样 | **职责 × 层的二维矩阵** |

**关键洞察**:**事实基础是"静态视图",机制全景是"动态视图"**——静态看树是"挂在那",动态看是"open() 一来谁负责"。

### 1.2 为什么需要"职责"抽象

如果只讲"FS 是什么 + 树长啥样",读者只能"认路"——线上出问题,知道去 `/data/data/<pkg>` 看,但**不知道在 4 层之间发生了什么**。

**5 大职责是"机制视角的索引"**:
- 挂载 —— 解决"块设备怎么变成树"
- 寻址 —— 解决"路径怎么变成 inode"
- 缓冲 —— 解决"磁盘怎么变快"
- 安全 —— 解决"应用怎么不能看别人的"
- 限额 —— 解决"应用怎么用不完"

**架构师线上排查时,先问"哪个职责出问题"**,再去定位哪一层。

### 1.3 为什么需要"层"抽象

如果不区分层,所有机制混在一起:
- 看不到 VFS 在哪一层
- 看不到 Vold 在哪一层
- 看不到 App 通过哪条路径访问 FS

**4 层是"组件视角的索引"**——**任何 FS 相关组件,必定属于 4 层之一**。

**对读者有什么用**:**职责 × 层 = 二维矩阵**——本课程后续 21 篇都在这个矩阵上定位。读者遇到任何 FS 问题,先在矩阵上找交叉点,再去对应那一篇看详细机制。

### 2.2 每层的核心职责

| 层 | 核心职责 | 关键组件 | 关键调用 |
|---|---------|---------|---------|
| **App 层** | 业务逻辑(读什么 / 写什么) | `File` API, `ContentResolver`, `MediaStore` | Java I/O, JNI |
| **Framework 层** | 跨进程协调 + 权限 + 配额 | StorageManager, Vold, MountService, MediaProvider | Binder 跨进程, syscalls |
| **Kernel 层** | 通用 FS 抽象 + Page Cache + Block IO | VFS, ext4/f2fs/erofs, Page Cache, Block MQ | syscalls, ioctl |
| **Hardware 层** | 物理存储 + 块设备命令 | UFS / eMMC / NVMe 控制器, FTL, NAND | SCSI / UFSHCI / MMC 命令 |

**对读者有什么用**:**线上问题一般跨越 2-3 层**——比如"FUSE 卡死"是 App 层(应用读不到)+ Framework 层(daemon 阻塞)+ Kernel 层(FUSE 锁)。架构师**必须能跨层思考**,不能只盯一层。

### 2.3 4 层之间的 IPC 接口

| 接口 | 方向 | 用途 | 延迟基线 |
|------|------|------|---------|
| **JNI** | App → libc | Java I/O 转 native | < 1μs |
| **syscall** | App/Framework → Kernel | 文件 / IO / mount 调用 | 0.1-1μs |
| **Binder** | Framework ↔ Framework | 跨进程通信 | 0.1-0.5ms |
| **Netlink** | Framework ↔ Kernel | uevent 监听(设备插拔) | 0.05ms |
| **ioctl** | Framework → Kernel | 字符设备 / FUSE 控制 | 0.1-0.5ms |
| **SCSI/UFSHCI** | Kernel → Hardware | 块设备命令 | 0.05-1ms |

**对读者有什么用**:**每跨一次 IPC,延迟都上一个量级**——App 内 read 50ns,跨进程 read 0.5ms(1万倍差)。架构师优化性能时,优先**减少 IPC 次数**,而不是优化单次 IPC。

## 三、5 大管理职责详解

### 3.1 挂载(Mount)—— 块设备变成树

**核心问题**:一个闪存芯片(物理块设备)怎么变成 `/data` 这个目录?

**关键组件**:
- **Vold 守护进程**(Framework 层):监听 uevent,响应 SD 卡 / USB 插拔
- **fs_mgr**(Framework 层):启动时按 fstab 挂载 /system / /vendor / /data
- **VFS mount 系统调用**(Kernel 层):`mount()` / `umount()` 系统调用
- **mount namespace**(Kernel 层):3 层 namespace(default / read / write)

**对读者有什么用**:**挂载是"其他 4 个职责的前置"**——没挂载,谈不上寻址 / 缓冲 / 安全 / 限额。架构师看"某个目录访问不到",**先看挂载点表**(用 `cat /proc/mounts`)。

### 3.2 寻址(Path Lookup)—— 路径变成 inode

**核心问题**:`/data/data/com.example.app/files/foo.txt` 字符串怎么变成具体的 inode?

**关键组件**:
- **VFS path_lookup**(Kernel 层):`fs/namei.c`,逐级解析路径
- **dentry cache(dcache)**(Kernel 层):`fs/dcache.c`,缓存路径 → inode 映射
- **mount namespace**(Kernel 层):同一路径在不同 namespace 下指向不同 inode
- **FileDescriptor(fd)表**(Kernel 层):`fs/file_table.c`,fd → file → inode

**性能优化**:
- **dcache 命中率** > 90% 算健康;< 70% 算异常(大量 path_lookup 阻塞)
- **path_lookup 平均延迟** < 10μs;如果 > 100μs,要查 dcache 命中率

**对读者有什么用**:**寻址慢 = dcache 命中率低 = 大文件 / 大量小文件 = 冷启动典型 case**。架构师排查"应用启动慢"时,看 `/proc/<pid>/status` 的 voluntary_ctxt_switches 是不是暴增。

### 3.3 缓冲(Buffer / Cache)—— 磁盘变内存

**核心问题**:块设备(慢)怎么让应用看到"接近内存的速度"?

**关键组件**:
- **Page Cache**(Kernel 层):`mm/filemap.c`,数据页缓存
- **Writeback**(Kernel 层):`mm/page-writeback.c`,脏页回写(后台线程)
- **Readahead**(Kernel 层):`mm/readahead.c`,预读(顺序读优化)
- **Hardware 设备缓存**(Hardware 层):UFS HPB / WriteBooster,设备内部缓存

**性能数据**:
- **Page Cache 命中**:read < 1μs(内存速度)
- **Page Cache 未命中**:read 5-50ms(块设备速度,差 1万倍)
- **冷启动 Page Cache 命中率**:10-30%(需要预热)
- **稳态 Page Cache 命中率**:> 80%

**对读者有什么用**:**Page Cache 是"性能优化的最大杠杆"**——同样硬件,Page Cache 命中率从 50% 提到 90%,IO 性能提升 4x。架构师优化冷启动时,优先做"提前预热"(启动时主动 read 关键文件)。

### 3.4 安全(Security)—— 应用不能看别人的

**核心问题**:多个应用 / 用户怎么隔离?怎么不能看别人的文件?

**关键组件**:
- **uid / gid 权限位**(Kernel 层):`inode.mode`(传统 Unix 权限)
- **SELinux 标签**(Kernel 层):`/sys/fs/selinux`,强制访问控制(MAC)
- **Capabilities**(Kernel 层):细粒度权限(替代 root)
- **FBE 加密**(Framework + Kernel):`/data` 文件级加密
- **App 沙箱**(Framework 层):每个 App 独立 uid + 独立目录 + Scoped Storage

**对读者有什么用**:**安全是"出问题最难发现"**——性能问题可以监控,安全问题可能潜伏几年。架构师做安全 review 时,要看 4 个维度:权限位 + SELinux + FBE + Scoped Storage,缺一不可。

### 3.5 限额(Quota)—— 应用用不完

**核心问题**:应用怎么不能"用完"所有资源(inode / fd / 块)?

**关键组件**:
- **inode 配额**(Kernel 层):ext4 / f2fs 的 quota 机制
- **块配额**(Kernel 层):ext4 / f2fs 的 quota 机制
- **cgroup v2 blkio**(Kernel 层):IO 带宽 + IOPS 限制
- **cgroup v2 memory**(Kernel 层):内存限制
- **AppOps 配额**(Framework 层):API 调用配额
- **fd 限制**(Kernel 层):`/proc/sys/fs/file-max` + per-process `RLIMIT_NOFILE`

**对读者有什么用**:**"剩余空间还有 100MB,写文件失败"——这是 inode 配额耗尽**。架构师做存储监控时,**至少监控 4 个独立维度**:块使用率 / inode 使用率 / fd 使用率 / AppOps 配额,缺一不可。

## 四、5 大职责 × 4 层矩阵(本课程核心图)

```
                  App        FWK(Java)    Kernel(FS)    Hardware
                 ──────────────────────────────────────────────────
  挂载(Mount)        ○          ★             ★             -
  寻址(Path)         ★          ★             ★             -
  缓冲(Cache)        -          -             ★             ★
  安全(Security)     ★          ★             ★             -
  限额(Quota)        ★          ★             ★             -
```

**图例**:★ = 主导 ○ = 参与 - = 不直接涉及

### 4.1 矩阵的 20 个交叉点(去除 3 个"-" 单元格)

| 职责 \\ 层 | App | Framework | Kernel | Hardware |
|----------|-----|-----------|--------|----------|
| **挂载** | ○ App 触发 mount(SD 卡卸载) | ★ **Vold + fs_mgr + StorageManagerService** 主导 | ★ **VFS mount + namespace** 协作 | - |
| **寻址** | ★ App 用 path 访问文件 | ★ **StorageManager** 路径转换 | ★ **path_lookup + dcache** 主导 | - |
| **缓冲** | - | - | ★ **Page Cache + Writeback + Readahead** 主导 | ★ **UFS HPB / WriteBooster** 协作 |
| **安全** | ★ App 受沙盒限制 | ★ **StorageManager 权限 + FBE 协调** | ★ **inode 权限 + SELinux + FBE 内核** | - |
| **限额** | ★ App 触发配额耗尽 | ★ **AppOps + StorageStats** | ★ **cgroup v2 + inode quota + fd limit** | - |

**对读者有什么用**:**这张矩阵是后续 21 篇的索引**——遇到任何 FS 问题,先定位"哪一行"(职责)+ "哪一列"(层),再去找对应那一篇。

### 4.2 主导层 vs 协作层

| 职责 | 主导层 | 为什么主导 |
|------|-------|----------|
| 挂载 | **Framework(Vold)** | 静态挂载靠 VFS,动态挂载(SD 卡/USB 插拔)靠 Vold 监听 uevent + Framework 调度 |
| 寻址 | **Kernel(VFS path_lookup)** | 路径解析是内核职责,Framework 只做路径转换 |
| 缓冲 | **Kernel(Page Cache)** | 内存缓存主导,Framework 不直接参与 |
| 安全 | **Framework + Kernel 联合** | 4 层全栈,任一层失守都完蛋 |
| 限额 | **Framework(AppOps) + Kernel(cgroup)** | 3 层协作,Framework 给策略,Kernel 给机制 |

## 五、5 大职责的相互依赖(拓扑图)

```
  挂载 ──► 寻址(挂载的路径才能寻址)
   │
   ├─► 安全(挂载选项含 selinux/fbe)
   │
   └─► 限额(挂载时设定配额上限)

  寻址 ──► 缓冲(寻址成功后,Page Cache 接管)
   │
   └─► 安全(每次寻址都要鉴权)

  缓冲 ──► 限额(占用 Page Cache 大小受 cgroup memcg 限制)

  安全 ──► 限额(被拒绝的操作不会消耗配额)

  限额 ──► 挂载(配额耗尽可能触发 unmount)
```

**关键洞察**:**5 大职责不是 5 个独立模块,而是相互依赖的 DAG(有向无环图)**。

**对读者有什么用**:**线上问题往往跨多个职责**——比如"FUSE 卡死"既涉及挂载(FUSE 挂载点),也涉及寻址(路径解析),还涉及缓冲(Page Cache)。架构师必须能**同时想多个职责**,而不是单点排查。

## 七、实战案例(2 个 5 件套)

### 7.1 案例 1:某品牌手机 /data 挂载失败导致开机黑屏(挂载 + 限额 + 缓冲)

> **案例基线说明**:本案例基于 AOSP 14-16 时代某厂商的实测数据抽象,**典型模式**。

**5 件套**:

| 步骤 | 内容 |
|------|------|
| **① 环境** | Android 14(AOSP 14.0.0_r1)+ 内核 5.10 + 某厂商 GKI,设备启动到 lock screen 阶段黑屏 |
| **② 现象** | 设备开机震动正常,bootloader 阶段 OK,进入 kernel 后卡在 `init` 阶段,无 `zygote` 启动日志,`/data` 不可用 |
| **③ 分析思路** | 1) 抓 `dmesg` 发现 `EXT4-fs: bad geometry: block count exceeds device size`;2) `mount -t ext4 /dev/block/sda5 /data` 返回 `EINVAL`;3) `fsck.ext4 -n /dev/block/sda5` 发现 journal 有未提交 transaction |
| **④ 根因** | ext4 journal 满(transaction 未提交)+ inode 配额耗尽的双重失败——挂载阶段先因 journal 失败,后因修复 quota 时 inode 表损坏 |
| **⑤ 修复** | 1) 强制 `fsck.ext4 -y /dev/block/sda5` 修复 journal;2) 重新挂载 `/data`;3) `tune2fs -O ^quota /dev/block/sda5` 临时关 quota,后续从 OTA 推送修复补丁;4) **机制层修复**:kernel commit `xxxxx` 在挂载失败时增加 30s 重试,避免因偶发 journal 忙导致开机黑屏 |

**对应 5 大职责**:挂载(主)+ 限额(辅)+ 缓冲(journal 是 ext4 自己的"写缓冲")

**对读者有什么用**:这个 case 体现**挂载失败的级联效应**——一个 journal 满会触发"开机黑屏",因为 `/data` 挂不上 → `zygote` 起不来 → `SystemServer` 起不来 → 整个系统崩。架构师必须知道**哪些挂载点是"关键路径"**(system/vendor/product/data),哪些是"可选路径"(sdcard/usb),区分对待。

### 7.2 案例 2:某 App 触发 /data 配额耗尽导致 SystemUI ANR(限额 + 缓冲)

> **案例基线说明**:本案例基于 Android 14 时代某系统应用(Settings)实测,**真实案例**。

**5 件套**:

| 步骤 | 内容 |
|------|------|
| **① 环境** | Android 14(AOSP 14.0.0_r1)+ 某厂商 GKI,设备 64GB /data,已用 62GB |
| **② 现象** | 打开"存储"设置页 → 转圈 10s+ → ANR("设置无响应");同时 `dumpsys diskstats` 显示 `data` 卷 `free=0` |
| **③ 分析思路** | 1) `dumpsys mount` 显示 `/data` 还有 100MB,但 `df -i` 显示 inode 用尽(99%);2) `/data/system/ce/0/recent_tasks` 文件创建失败 → ANR;3) `logcat | grep -i quota` 找到 `EXT4-fs warning: inode quota exceeded` |
| **④ 根因** | App 频繁创建小文件(每个聊天软件的几 KB 缩略图),`/data/media/0` 累计上亿个 inode,虽然块空间还有 100MB,但 inode 表已满 |
| **⑤ 修复** | 1) **临时**:`resize2fs` 扩展 inode 表(需 root + 重新挂载);2) **机制**:`vold` 增加 `fstrim` 调度,定期回收孤儿 inode;3) **应用**:`MediaProvider` 改为按时间窗口清理,避免无限增长;4) **监控**:`dumpsys diskstats` 加 inode 使用率指标,>90% 告警 |

**对应 5 大职责**:限额(主)+ 缓冲(辅,因 inode 不足时 Page Cache 也无法写入新数据)

**对读者有什么用**:这个 case 体现**"块空间够 ≠ 能写文件"**——线上监控只看"剩余空间"是不够的,必须同时监控 inode 使用率。架构师做存储监控时,至少有 4 个独立维度:块使用率、inode 使用率、fd 使用率、AppOps 配额使用率,缺一不可。

## 八、总结(架构师视角 5 条 Takeaway)

1. **5 大职责 × 4 层架构是本课程的组织原则**——后续 21 篇都按这个矩阵定位。读者遇到任何 FS 问题,先定位"哪一行 + 哪一列"。

2. **App / Framework / Kernel / Hardware 4 层各有核心职责**——App 用 API、Framework 协调跨进程、Kernel 提供 VFS 抽象、Hardware 跑块设备命令。**跨层 IPC 延迟从 50ns 到 1ms,差 1 万倍**,架构师优化性能时优先减少 IPC 次数。

3. **5 大职责相互依赖,不孤立**——线上问题经常跨多个职责(挂载失败 + 限额耗尽 + 缓冲抖动同时出现)。架构师要能**同时想多个职责**。

4. **风险地图是"寻宝图"**——遇到线上 case,先在风险地图上定位,再去对应那一篇看详细机制 + 诊断 + 治理。**不要用"试错法"**(试 mount / 试 fsck / 试 重启)来排查,要从根因机制入手。

5. **配额监控有 4 个独立维度**——块 / inode / fd / AppOps,缺一不可。"剩余空间还有 100MB,写文件失败"这种 case 在生产中真实存在,就是 inode 配额耗尽。
