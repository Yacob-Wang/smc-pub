### 2.2 工具 1:ftrace(内核静态跟踪)

**用途**:跟踪 VFS/ext4/f2fs/jbd2 内部函数调用 + 延迟。

**关键跟踪点**(android17-6.18 内核):

```bash
# 1. 跟踪 VFS read/write 延迟
echo 1 > /sys/kernel/debug/tracing/events/vfs/enable
cat /sys/kernel/debug/tracing/trace_pipe | grep -E "vfs_read|vfs_write"

# 2. 跟踪 ext4 journal commit 延迟(对应 23 篇)
echo 1 > /sys/kernel/debug/tracing/events/jbd2/enable
cat /sys/kernel/debug/tracing/trace_pipe | grep "jbd2_commit"

# 3. 跟踪 f2fs GC 触发(对应 22 篇)
echo 1 > /sys/kernel/debug/tracing/events/f2fs/enable
cat /sys/kernel/debug/tracing/trace_pipe | grep "f2fs_gc"
```

**实战模板**(对应 23 篇 jbd2 阻塞):

```
<idle>-0     [001] d..1   1234.567890: jbd2_commit: dev 259:1 transaction 12345 commit 85000us ← 关键!
system_server-1234 [001] d..3 1234.652000: ext4_sync_file: inode 12345 datasync 1
```

**判断标准**:
- `jbd2_commit` 延迟 > 50ms = journal 写慢(检查磁盘)
- `f2fs_gc` 触发频率 > 1 次/秒 = GC 抖动(对应 22 篇)
- `vfs_read` 延迟 > 100ms = 上层应用卡顿

### 2.3 工具 2:eBPF / bpftrace(可编程动态跟踪)

**用途**:自定义跟踪点 + 内核态/用户态关联(同 5 阶段 1.3)。

**关键脚本**(对应 20 篇 FUSE 锁链):

```c
// bpftrace 跟踪 FUSE 用户态 daemon 阻塞
kprobe:fuse_simple_request
{
    @start[tid] = nsecs;
}

kretprobe:fuse_simple_request
/@start[tid]/
{
    $dur = (nsecs - @start[tid]) / 1000;
    @usecs = hist($dur);
    delete(@start[tid]);
}
```

**实战模板**(对应 21 篇 Vold 跨进程):

```
$ sudo perfetto -o trace.pftrace --txt --cfg 'ftrace_events: "vold:*","storage:*"'
$ curl https://raw.githubusercontent.com/catapult-project/perfetto/master/tools/trace_processor -o tp
$ ./tp trace.pftrace
> SELECT * FROM sched WHERE thread_name LIKE 'vold%' AND dur > 10000000;
```

**判断标准**:
- FUSE 请求 > 100ms = sdcard daemon 阻塞(对应 19/20 篇)
- vold 线程调度延迟 > 1s = MountService 跨进程故障(对应 21 篇)
- bio 入队到完成 > 50ms = 块设备 IO 慢(对应 15 篇)

### 2.4 工具 3:drop_caches(缓存清理)

**用途**:复现 Page Cache 冷启动 + 内存压力场景。

**3 个水位**:

```bash
# 1 = page cache
echo 1 > /proc/sys/vm/drop_caches
# 2 = dentries + inodes
echo 2 > /proc/sys/vm/drop_caches
# 3 = page cache + dentries + inodes
echo 3 > /proc/sys/vm/drop_caches
```

**实战价值**(对应 20-24 全部):
- 复现"启动后第一次 IO 慢"——drop 完 + 测试冷启动 IO(对应 24 篇 FBE 启动)
- 复现"App 启动卡顿"——drop 完 + 测 cold inode lookup(对应 20 篇 dentry 锁)
- 复现"journal 满"——drop 完 + 高并发写测试(对应 23 篇 jbd2)

**风险**:**生产禁用,只用于压测环境**——会强制重建所有 Page Cache,引发 P999 延迟 spike。

### 2.5 工具 4:StorageStats(用户态配额)

**用途**:读取 per-App 配额 + 卷级统计(Android 7+ API)。

**关键 API**:

```java
// Java 层
StorageStatsManager ssm = ctx.getSystemService(StorageStatsManager.class);
StorageStats stats = ssm.queryStatsForPackage(volumeUuid, packageName);
long appBytes = stats.getAppBytes();      // App 自身大小
long dataBytes = stats.getDataBytes();    // App 数据大小
long cacheBytes = stats.getCacheBytes();  // App 缓存

// Binder IPC:system_server → vold
// 路径:frameworks/base/core/java/android/app/usage/StorageStatsManager.java
```

**实战模板**(对应 24 篇配额耗尽):

```bash
# dumpsys storage 查全局配额
adb shell dumpsys diskstats | grep -A 5 "配额"
# 输出:
# /data 配额:已用 80GB / 128GB(63%)
# /data 配额:已用 100GB / 128GB(78%) ← 接近上限
# /data 配额:已用 110GB / 128GB(86%) ← 触发清理
```

**判断标准**:
- 单 App 配额 > 80% = ENOSPC 风险高(对应 24 篇)
- /data 总用量 > 90% = 触发 low storage 清理
- /cache 用量 > 1GB = 缓存堆积(可能引发 f2fs GC,对应 22 篇)

### 2.6 工具 5:dumpsys(Framework 状态)

**5 个 dumpsys 子命令**(对应 FS 专题):

```bash
# 1. dumpsys diskstats —— 块设备 IO 统计
adb shell dumpsys diskstats
# 关键字段:read_ios,write_ios,read_kb,write_kb,queue_depth

# 2. dumpsys storage —— 存储状态 + 配额
adb shell dumpsys storage
# 关键字段:volume_state,mount_state,quota_used,quota_total

# 3. dumpsys mount —— 挂载点 + 文件系统类型
adb shell dumpsys mount
# 关键字段:mount_point,fs_type,flags,options

# 4. dumpsys storaged —— 存储守护进程统计
adb shell dumpsys storaged
# 关键字段:userdata_bytes,cache_bytes,free_bytes

# 5. dumpsys activity —— Activity 启动 IO(对应 24 篇 FBE 启动慢)
adb shell dumpsys activity processes | grep -A 3 "启动延迟"
```

**实战模板**(对应 21 篇 Vold 跨进程故障):

```
$ adb shell dumpsys mount | grep -A 3 "vold"
# vold 状态:connected
# 挂载点:/storage/emulated/0
# 状态:mounted
# 类型:sdcardfs ← 旧版 / fuse ← Android 14+

$ adb shell dumpsys storage
# Volume:private
# State:MOUNTED
# 配额:已用 80GB / 128GB
```

**判断标准**:
- `dumpsys diskstats` 显示 `await_ms > 100` = 块设备 IO 慢
- `dumpsys storage` 显示 `State:UNMOUNTED` = Vold 故障(对应 21 篇)
- `dumpsys mount` 显示 `fs_type:sdcardfs` = 未升级到 FUSE passthrough(对应 19 篇)

### 2.7 工具链组合实战

**场景:复现"App 启动 5s 卡顿"**:

```bash
# 1. drop_caches 制造冷启动
adb shell "echo 3 > /proc/sys/vm/drop_caches"

# 2. ftrace 跟踪 VFS 路径
adb shell "echo 1 > /sys/kernel/debug/tracing/events/vfs/enable"
adb shell "echo 1 > /sys/kernel/debug/tracing/events/f2fs/enable"
adb shell "echo 1 > /sys/kernel/debug/tracing/events/ext4/enable"

# 3. 启动 App
adb shell am start -n com.example.app/.MainActivity

# 4. 看 trace
adb shell cat /sys/kernel/debug/tracing/trace | head -100

# 5. dumpsys 看 IO 统计
adb shell dumpsys diskstats | grep -A 3 com.example.app

# 6. 对照 24 篇根因:
#    - ext4 journal commit 慢?→ 看 jbd2 trace
#    - f2fs GC 触发?→ 看 f2fs_gc trace
#    - FBE 启动慢?→ 看 dex2oat trace + 解密 trace
```

## 三、5 件套案例库(20-24 索引化提炼)

### 3.1 案例 1:FUSE 死锁(源自 [20](20-FUSE%20死锁全景：4%20类锁等待链与用户态%20daemon%20状态机.md))

**环境**:Pixel 8,Android 17,userdebug build,app 进程数 200+,FUSE passthrough 启用。

**现象**:
- launcher 偶发卡 1-3 秒
- logcat 报 `FUSE: daemon blocked`
- `dumpsys cpuinfo` 显示 sdcard 进程 D 状态 50%+

**分析思路**:
1. ftrace `fuse_simple_request` → 发现请求堆积
2. bpftrace 跟踪 sdcard 进程 → sys_io_uring 阻塞
3. dumpsys activity → launcher 启动延迟 2.5s

**根因**:FUSE 4 类锁链之一——dentry 锁 + 用户态 daemon 互等(详见 20 篇 §3.2 锁链图)。

**修复**:
- 短期:sdcard daemon 进程优先级 +1
- 中期:FUSE passthrough 直通路径扩到 /storage(对应 19 篇)
- 长期:迁移到 user namespace 隔离(android17-6.18 已支持)

### 3.2 案例 2:Vold + MountService 跨进程故障(源自 [21](21-Vold%20+%20MountService%20跨进程故障模式.md))

**环境**:Pixel 7a,Android 17,生产用户 OTA 升级后 24h 内。

**现象**:
- `dumpsys mount` 显示 `State:UNMOUNTED`
- app 调 `StorageManager.getVolumeList()` 抛 `IllegalStateException`
- logcat 报 `vold: disconnected`

**分析思路**:
1. `adb shell ps -A | grep vold` → vold 进程重启 5 次
2. ftrace `binder_transaction` → MountService → vold RPC 超时
3. `dumpsys storage` → `volume_state = ERROR`

**根因**:Vold 5 类故障之一——OTA 后 metadata 分区 hash 不匹配(详见 21 篇 §3.3 故障矩阵)。

**修复**:
- `adb shell sm list-volumes` 确认挂载
- OTA 后强制 `vold --reset`
- 长期:metadata partition 双备份(对应 16 篇)

### 3.3 案例 3:F2FS GC 抖动(源自 [22](22-F2FS%20GC%20与%20Checkpoint%20抖动：f2fs_gc_thread%20延迟源.md))

**环境**:Pixel 8,Android 17,userdata 占用 90%+,频繁安装/卸载 app。

**现象**:
- 应用启动 P99 延迟从 800ms spike 到 3s
- ftrace `f2fs_gc` 触发频率 1 次/秒
- `dumpsys storaged` 显示 `cache_bytes = 8GB`

**分析思路**:
1. ftrace `f2fs_gc_thread` → GC 延迟 500ms/次
2. bpftrace 跟踪 checkpoint → write 阻塞
3. `dumpsys diskstats` → write_ios 1MB/s,await_ms 200ms

**根因**:F2FS 3 种 GC 模式之一——foreground GC + 雪崩效应(详见 22 篇 §3.4 GC 模式表)。

**修复**:
- 短期:`adb shell fstrim /data`(触发 discard,释放 segment)
- 中期:调 `gc_urgent_sleep_time` 从 500ms → 200ms
- 长期:迁移到 F2FS 6.x(支持 multi-device GC,android17-6.18)

### 3.4 案例 4:ext4 journal 满(源自 [23](23-ext4%20journal%20满与%20jbd2%20阻塞：transaction%20等待.md))

**环境**:Pixel 6,Android 17,server-side 数据库 app 频繁 fsync。

**现象**:
- 写 IO 延迟 P99 spike 到 5s
- logcat 报 `jbd2: 1234 transactions pending`
- `dumpsys diskstats` await_ms 1000ms+

**分析思路**:
1. ftrace `jbd2_commit` → commit 延迟 800ms
2. bpftrace 跟踪 transaction handle → 400+ pending
3. 触发条件:5000+ fsync/秒

**根因**:jbd2 transaction handle 耗尽(默认 128 个)——transaction 等待(详见 23 篇 §3.2 jbd2 状态机)。

**修复**:
- 短期:调 `sys.fs.ext4.journal_async_commit = 1`
- 中期:`sys.fs.ext4.max_transaction = 512`
- 长期:迁移到 F2FS(对应 13 篇)或 ext4 bigalloc(android17-6.18 已支持)

### 3.5 案例 5:FBE 启动慢 + 资源耗尽(源自 [24](24-FBE%20文件级加密启动慢%20+%20三大资源耗尽（FD,inode,配额）.md))

**环境**:Pixel 8 Pro,Android 17,userdebug build,冷启动。

**现象**:
- 冷启动到 launcher 显示 8s(基线 3s)
- logcat 报 `FBE: 5000ms decrypting DE`
- `dumpsys activity` 显示 dex2oat 后 2s 卡顿

**分析思路**:
1. ftrace `fscrypt` → DE 解密 5000ms
2. `dumpsys diskstats` → metadata 分区 await_ms 800ms
3. `ls /proc/<pid>/fd | wc -l` → 进程 fd 8000+

**根因**:FBE metadata IO 慢(主因 80%)+ 进程 fd 接近上限(20%)(详见 24 篇 §3 + §5)。

**修复**:
- 短期:`sys.fs.f2fs.issue_discard = 1` 减少 metadata 读
- 中期:迁移 dex2oat 输出到 /data/local/tmp(不进 /data)
- 长期:FBE 2.0(android17-6.18 预览,详见第四节)

## 四、AOSP 18/19 未来路径(不臆想)

> **可信度标签约定**:
> - ✅ **已公开** = Google 官方公告/源码已合并,日期/版本可考
> - 🟡 **待确认** = 官方有信号但未明确,推测方向
> - ❌ **推测** = 个人分析,无官方依据(本文不使用,所有结论均 ≥ 🟡)

### 4.1 AOSP 18 已公开的 FS 相关变化(✅)

**截至 2026 年中,基于 AOSP 18 源码 + Linux 6.18 LTS 主线**:

1. **FUSE passthrough 全面替代 sdcardfs**(✅)
   - 来源:AOSP 18 `system/core/sdcardfs` 标记 deprecated
   - 影响:所有 /storage/emulated/* 路径走 FUSE
   - 对应本系列:[19-FUSE 在 Android](19-FUSE%20在%20Android%20中的应用：sdcardfs%20迁移到%20FUSE%20passthrough.md) + [20-FUSE 死锁](20-FUSE%20死锁全景：4%20类锁等待链与用户态%20daemon%20状态机.md)

2. **FBE 2.0 预览**(✅)
   - 来源:Linux 6.18 `fs/crypto` 新增 `fscrypt_operations.v2`
   - 关键变化:硬件解密加速(ARMv9 CCA)+ metadata encryption 异步
   - 性能:DE 解密从 0.5-2s 降到 100-300ms
   - 对应本系列:[24-FBE](24-FBE%20文件级加密启动慢%20+%20三大资源耗尽（FD,inode,配额）.md) §3.1

3. **F2FS multi-device(RAID over F2FS)**(✅)
   - 来源:Linux 6.18 `fs/f2fs/multi-device.c`(AOSP 18 启用)
   - 关键变化:跨 device 段管理 + GC 跨 device 调度
   - 价值:解决 22 篇 GC 雪崩
   - 对应本系列:[13-f2fs](13-f2fs%20文件系统特性：闪存友好,%20日志结构,%20GC.md) + [22-GC 抖动](22-F2FS%20GC%20与%20Checkpoint%20抖动：f2fs_gc_thread%20延迟源.md)

4. **erofs 硬件解压**(✅)
   - 来源:Linux 6.18 `fs/erofs/decompressor.c` 支持 Zstandard
   - 关键变化:/system 分区解压从软件到硬件加速
   - 性能:启动 IO 减少 30-50ms
   - 对应本系列:[14-erofs](14-erofs%20与只读压缩：LZ4,%20LZMA,%20Android%20system%20分区.md) §4.3

### 4.2 AOSP 18 已公开但需确认的影响(🟡)

1. **Scoped Storage 强化:per-file encryption key 强制**(🟡)
   - 来源:Android 14+ 已逐步推进,AOSP 18 拟强制
   - 影响:App 必须适配 `KeyStore.getKey()` API
   - 对应本系列:[18-Scoped Storage](18-Scoped%20Storage%20与文件访问：MediaStore,%20SAF,%20DocumentsProvider.md) §5
   - **风险**:历史 App 兼容性

2. **Vold 跨 namespace 隔离**(🟡)
   - 来源:Linux 6.18 `mount.h` 新增 `MOUNT_ATTR_NOSUID` 全集
   - 关键变化:每个 App volume 独立 namespace
   - 价值:解决 21 篇跨进程 Vold 故障
   - 对应本系列:[17-Vold+StorageManager](17-StorageManager%20+%20Vold%20守护进程链路：从%20init.rc%20到%20Binder%20跨进程.md) + [21](21-Vold%20+%20MountService%20跨进程故障模式.md)

3. **APEX 3.0:运行时模块热更新**(🟡)
   - 来源:AOSP 17+ 已部分支持,AOSP 18 扩展
   - 关键变化:APEX 模块在用户态直接更新,无需重启
   - 对应本系列:[16-APEX super 分区](16-动态分区与%20APEX%20super%20分区详解：Android%20现代化分区设计.md) §6

### 4.3 AOSP 19 方向(🟡,基于 Linux 6.18 LTS 路线图)

1. **EROFS 写支持(EROFS-W)**(🟡)
   - 状态:Linux 6.18 RFC,未合并
   - 价值:/system 升级不再需要 OTA(只读 → 软只读)
   - 风险:写语义兼容性

2. **跨 FS 统一接口 fsinfo()**(🟡)
   - 状态:Linux 6.18 已合并基础,AOSP 19 拟集成
   - 价值:ext4/f2fs/erofs 状态统一查询
   - 对应本系列:[02-选型](02-Android%20设备分区与%20FS%20选型.md) §5

3. **BPF FS 监控(bpf_for_each_file)**(🟡)
   - 状态:Linux 6.18 已合并
   - 价值:无需 ftrace,纯 BPF 实现 FS 监控
   - 对应本系列:本篇 §2.3 eBPF

### 4.4 不臆想边界(本节可信度声明)

本节**仅列 2026 年中前已有官方信号**的方向,以下**不写**:
- ❌ 个人推测(如"FBE 3.0 取消 CE/DE 区分")——无官方依据
- ❌ 5 年以上长期愿景——超出本系列基线(2026 年中)
- ❌ 商业产品路线(如"Samsung One UI FS 优化")——非 AOSP 主线

**反例**(本文排除的):
- ❌ "F2FS 将取代 ext4"——AOSP 18 ext4 + f2fs **共存**(对应 02 篇)
- ❌ "FUSE passthrough 完全消除 FUSE 死锁"——passthrough 减少但**不消除**(对应 19/20 篇)
- ❌ "FBE 2.0 启动零延迟"——降到 100-300ms,**非零**(对应 24 篇)
