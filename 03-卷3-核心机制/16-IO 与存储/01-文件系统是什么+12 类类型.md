## 一、背景:为什么 FS 是计算基础

### 1.1 计算的 3 个根本问题

任何计算设备(从智能手表到服务器)都面临 3 个根本问题,FS 子系统是答案之一:

| 根本问题 | 含义 | 没有 FS 时怎么办 |
|---------|------|--------------|
| **持久化** | 进程退出后,数据不能丢 | 把数据写进 ROM 字节流,自己解析 |
| **命名** | 多个数据怎么区分 / 找得到 | 维护一个自己定义的字符串 → 字节流的索引表 |
| **共享** | 多个进程怎么访问同一份数据 | 通过 IPC 协议传递整块数据,或者共享一段内存 |

**FS 怎么解**:
- 把数据组织成"**文件**"(命名 + 内容 + 元数据)
- 把"**目录**"作为命名空间(分层索引)
- 把"**挂载**"作为不同存储设备的统一接入

**对读者有什么用**:这 3 个根本问题是所有 FS 设计演进的根因——为什么要有日志(解决持久化的崩溃一致性)?为什么要有 Page Cache(解决共享的访问速度)?为什么要有 mount namespace(解决共享的隔离)?——都是为了"更便宜地"回答这 3 个问题。

### 1.2 Linux "一切皆文件"哲学

Linux 内核的标志性设计哲学:

> **几乎所有系统资源都抽象为"文件"**,通过统一的 `open()` / `read()` / `write()` / `close()` 接口访问。

**这句话的具体含义**:
- 普通文件(`/data/foo.txt`)——文件
- 硬件设备(`/dev/sda`、`/dev/ashmem`、`/dev/binder`)——文件(字符/块设备)
- 内核信息(`/proc/cpuinfo`、`/proc/meminfo`)——文件
- 内核对象(`/sys/devices/.../power/control`)——文件
- 网络 socket——文件描述符
- 进程间通信(pipeline / fifo)——文件
- 资源控制(`/sys/fs/cgroup/memory.pressure`)——文件
- 配置(`/config/...`)——文件

**带来的好处**:
- App / 用户态工具可以用**同一套** API(`read` / `write` / `mmap`)访问所有资源
- 减少学习成本(不需要为每种资源学一套接口)
- 权限模型统一(都是 inode 权限 + SELinux 标签)

**对读者有什么用**:这就是为什么 Android 设备 `/proc` / `/sys` / `/dev` 这么多"看起来不像文件"的东西,都被塞进 FS——它们**就是文件**。架构师线上排查时,读 `/proc/<pid>/status` 跟读 `/data/foo.txt` 走的是同一条 VFS 路径。**所以 VFS 不只是"文件系统的 V",而是"系统调用的 V"——它是所有系统资源访问的统一抽象层**。

### 1.3 为什么需要"12 类"FS(而不是一种)

如果只有"一种 FS"会怎样?

| 场景 | 需求 | 单一 FS 怎么应对 |
|------|------|----------------|
| 4GB 大文件顺序读 | 顺序 IO 优化 | 一切为了大文件,小文件性能劣化 |
| 10000 个 4KB 小文件 | 元数据性能 + inode 效率 | 一切为了小文件,大文件性能劣化 |
| 进程间共享内存 | 内存访问,不落磁盘 | 假装"文件",但要避开所有磁盘逻辑 |
| /proc 只读内核信息 | 动态生成,无持久化 | 假装"文件",但 read 时调用函数 |
| /sys 配置内核参数 | 可写但持久化由内核控制 | 假装"文件",write 时调用函数 |
| 块设备直接访问 | 不经过 FS | 假装"文件",read 走驱动 |

**12 类 FS 的根因**:**不同场景对"持久化 + 命名 + 共享"的需求差异巨大**——有的要落磁盘,有的不能落;有的要日志,有的要只读;有的要加密,有的要高性能——单一 FS 无法兼顾。

**对读者有什么用**:架构师线上排查时,**第一件事是看"哪个挂载点出的问题"**——因为每个挂载点的 FS 行为完全不同。看到 /proc 出问题(动态生成),你不会去查磁盘;看到 /data 出问题(真磁盘),你才查 Page Cache、查块设备。**挂载点的 FS 类型决定了排查方向**。

## 二、FS 是什么:从块设备到文件抽象

### 2.1 数据组织的 3 个层次

```
              ┌──────────────────────────────────┐
  第 3 层      │  命名空间(目录树)                │  ← FS 提供
              │  /data/app/com.example/foo.txt  │
              ├──────────────────────────────────┤
  第 2 层      │  文件抽象                        │  ← FS 提供
              │  inode + 文件名 + 内容(字节流)   │
              ├──────────────────────────────────┤
  第 1 层      │  块设备(物理存储)               │  ← 硬件
              │  块地址 + 扇区(512B/4KB)         │
              └──────────────────────────────────┘
```

**关键洞察**:
- **第 1 层(块设备)** 不知道"文件"是什么,只懂"块地址 + 数据"
- **第 2 层(文件抽象)** FS 把"块"组织成"文件",引入 inode(元数据)+ 内容(字节流)
- **第 3 层(命名空间)** FS 把"文件"组织成"目录树",引入 dentry(目录项)+ path_lookup(路径解析)

**对读者有什么用**:三层模型解释了"为什么 FS 出问题要在 3 个不同位置查":
- 第 1 层 → 块设备 / Block 层 / IO 调度器(IO 系列 09-10)
- 第 2 层 → inode / Page Cache / 文件锁 / fd(VFS 核心机制,本课程 07-11)
- 第 3 层 → 路径解析 / mount namespace / dcache(本课程 09)

### 2.2 FS 提供的 4 个核心抽象

| 抽象 | 它解决什么 | 实现机制 |
|------|---------|---------|
| **文件** | 命名 + 持久化 | inode(元数据) + 数据块(内容) |
| **目录** | 命名空间 | dentry(目录项) + 父子关系 |
| **挂载** | 多设备统一 | mount namespace + vfsmount |
| **保护** | 隔离 | inode 权限位 + SELinux 标签 + Capabilities |

**对读者有什么用**:**这 4 个抽象是"任何 FS 都必须提供"**——ext4 有,procfs 也有(只是 inode 是动态生成的),FUSE 也有(只是数据来自用户态 daemon)。区别在于**实现方式**,不是抽象本身。

### 2.3 4 个核心调用(任何 FS 都支持)

```c
// include/linux/fs.h
int open(const char *path, int flags, mode_t mode);   // 打开 → 返回 fd
ssize_t read(int fd, void *buf, size_t count);         // 读
ssize_t write(int fd, const void *buf, size_t count);  // 写
int close(int fd);                                      // 关闭
```

**这 4 个调用是"FS 的宪法"**——任何 FS 实现都必须支持,否则就不算 FS。VFS 层定义这 4 个调用,具体 FS 实现这 4 个调用。

**对读者有什么用**:线上排查时,无论哪个挂载点出问题,先看这 4 个调用:
- `open` 慢 → 寻址问题(本课程 09)
- `read` 慢 → 缓冲问题(本课程 10)
- `write` 慢 → 缓冲/限额问题(本课程 10/24)
- `close` 慢 → 配额/锁问题(本课程 24)

## 三、12 类 FS 全景表(本篇核心交付)

### 3.1 12 类总表

Android 设备(基于 AOSP 17 + android17-6.18 GKI)涉及 **12 类 FS**,按 6 大分类:

| 分类 | FS | 用途 | 典型挂载点 | 落磁盘? |
|------|---|------|----------|--------|
| **块 FS** | ext4 | 传统日志 FS,Android /data 早期 | /data, /cache(历史) | ✅ 是 |
| **块 FS** | f2fs | 闪存友好日志 FS,Android /data 默认 | /data, /cache | ✅ 是 |
| **块 FS** | erofs | 只读压缩 FS,Android /system | /system, /vendor, /product | ✅ 是(只读) |
| **块 FS** | vfat | FAT32,SD 卡兼容 | /mnt/media_rw/<UUID> | ✅ 是 |
| **虚拟 FS** | procfs | 进程 / 内核信息(动态生成) | /proc | ❌ 否(内存) |
| **虚拟 FS** | sysfs | 内核对象树(动态生成) | /sys | ❌ 否(内存) |
| **虚拟 FS** | tmpfs | 内存临时 FS | /dev/shm, /run, /data/local/tmp(部分) | ❌ 否(内存) |
| **虚拟 FS** | devtmpfs | 设备文件 FS(动态) | /dev | ❌ 否(内存) |
| **用户态 FS** | FUSE | 用户态 daemon 提供数据 | /storage/emulated/0, /storage/<UUID> | ✅ 是(经 FUSE) |
| **设备 FS** | ashmem | 匿名共享内存(字符设备) | /dev/ashmem | ❌ 否(内存) |
| **设备 FS** | binder | Android IPC 设备 | /dev/binder | ❌ 否(IPC) |
| **控制 FS** | cgroup v2 | 资源控制 FS | /sys/fs/cgroup | ❌ 否(内核对象) |
| **控制 FS** | configfs | 配置 FS | /config | ❌ 否(内核对象) |
| **容器 FS** | APEX | Android 模块化容器(带签名验证) | /apex/<name> | ✅ 是(只读) |

**注**:严格说 ashmem / binder 不是 FS(是字符设备),但 Android 实践中常被混入"FS 概念"。本表把它们列上,后续单独说明。

### 3.2 12 类在 Android 设备上的使用频度

按"生产环境必用"分 3 档:

| 档位 | FS | 说明 |
|------|---|------|
| **核心必用(7 类)** | ext4 / f2fs / erofs / procfs / sysfs / devtmpfs / FUSE | 不挂就开不了机 |
| **常用(3 类)** | tmpfs / cgroup v2 / APEX | Android 11+ 必用 |
| **少见(2 类)** | ashmem / binder | AOSP 14+ ashmem 弃用,迁移到 memfd;binder 仍用 |

**对读者有什么用**:核心必用的 7 类是"线上 100% 会出现"——架构师必须精通。其余 5 类是"扩展知识",遇到再查。

## 四、块 FS 详解(3 大主力)

### 4.1 ext4:传统日志 FS(Android /data 早期)

**设计哲学**:**向后兼容** + **通用场景**。ext4 是 ext3 的演进,2008 年进入 Linux 主线,目标是不丢历史数据、平滑升级。

**核心机制**:
- **extent**:用"起始块 + 长度"描述文件数据位置(替代 ext2/ext3 的 block map)
- **journaling**:写前先写日志(Journal),崩溃后能恢复到一致状态
- **多 block group**:磁盘分多个 group,每个 group 有自己的 inode 表

**Android 上的使用**:
- AOSP 8.0 及之前:`/data` 默认 ext4
- AOSP 9.0 起:`/data` 逐渐切到 f2fs(但 ext4 仍是 fallback)
- AOSP 17:`/data` / `/cache` 默认 f2fs;ext4 用于 `/metadata`(加密元数据)

**对读者有什么用**:ext4 是**理解所有日志 FS 的基础**——journaling、extent、inode 都是 ext4 立的标准,学完 ext4,f2fs / xfs / btrfs 都好懂。

### 4.2 f2fs:闪存友好日志 FS(Android /data 默认)

**设计哲学**:**专为 NAND 闪存设计**。传统 FS(ext4)的"原地更新"对 SSD 伤害大(写放大),f2fs 用"日志结构"避免原地更新。

**核心机制**:
- **Log-structured**:所有写操作 append 到日志,定期清理(GC)
- **NAT / SIT**:Node Address Table / Segment Information Table 映射"逻辑地址 → 物理地址"
- **6 个区域**(super / cp / nat / sit / main / sb):磁盘布局跟 ext4 完全不同

**Android 上的使用**:
- AOSP 9.0 起:`/data` 默认 f2fs
- 优势:写放大低(NAND 友好),随机写快
- 劣势:GC 抖动(随机读性能会受 GC 干扰)

**对读者有什么用**:`/data` 用 f2fs 的**核心理由是 SSD 寿命**——传统 ext4 在 SSD 上写放大 5-10x,f2fs 压到 1-2x。架构师线上遇到 `/data` 卡顿,**优先怀疑 f2fs GC 抖动**(本课程 22 详讲)。

### 4.3 erofs:只读压缩 FS(Android /system)

**设计哲学**:**只读 + 压缩 + 挂载即可用**。`/system` 不需要写(只读挂载),但需要省空间(原始包大)。

**核心机制**:
- **只读**:挂载为只读,根除"系统目录被改写"风险
- **压缩**:LZ4(快)/ LZMA(高压缩比)两种算法
- **就地解压**:内核自带解压逻辑,不需要用户态 daemon(squashfs 经常要 fuse 桥接)
- **extents-based**:物理布局简洁,挂载速度快(<200ms)

**Android 上的使用**:
- AOSP 10+:`/system` / `/vendor` / `/product` / `/system_ext` 默认 erofs
- 优势:启动快(免解压),省空间(30-50% 压缩率)
- 劣势:不能写(任何写操作都会失败),但 Android 用 overlayfs 解决(本课程 09 详讲)

**对读者有什么用**:`/system` 用 erofs 是"**Android OTA 时代的必然选择**"——系统分区越来越大,设备存储有限,压缩 + 只读是不二解。架构师排查"系统启动慢"时,要看 erofs 解压耗时(本课程 14 详讲)。

### 4.4 块 FS 选型决策表

| 场景 | 推荐 FS | 理由 |
|------|---------|------|
| 系统分区(只读,大) | **erofs** | 压缩 + 启动快 + 安全 |
| 用户数据分区(读写,随机) | **f2fs** | 闪存友好 + 写放大低 |
| 加密元数据(小,极敏感) | **ext4** | 成熟稳定 + journaling 强一致 |
| 兼容性(SD 卡 / USB) | **vfat** | 跨平台兼容(Win/Mac/Linux) |

## 五、虚拟 FS 详解(4 大虚拟)

虚拟 FS **不落磁盘**,数据驻内存或由内核动态生成。

### 5.1 procfs:进程 / 内核信息(/proc)

**特点**:
- 每个进程一个目录:`/proc/<pid>/`(status, maps, stat, fd/...)
- 内核全局信息:`/proc/cpuinfo`, `/proc/meminfo`, `/proc/loadavg`
- **数据动态生成**——read 时调用内核函数,无持久化

**Android 关键使用**:
- `/proc/<pid>/status` — 进程内存 / 状态
- `/proc/<pid>/maps` — 进程虚拟地址映射
- `/proc/cpuinfo` — CPU 信息
- `/proc/version` — 内核版本

**对读者有什么用**:线上排查**必读 procfs**——任何一个 ANR / 性能问题,`/proc/<pid>/status` + `/proc/<pid>/maps` 是第一手资料。**Android 的 `dumpsys` 底层大量读 procfs**。

### 5.2 sysfs:内核对象树(/sys)

**特点**:
- 把内核对象(设备、驱动、总线)导出为文件系统
- 每个对象一个目录,属性是文件
- **可读可写**(读状态 / 改配置)

**Android 关键使用**:
- `/sys/class/net/...` — 网卡状态
- `/sys/devices/.../power/control` — 设备电源管理
- `/sys/fs/cgroup/...` — cgroup 资源控制
- `/sys/kernel/debug/...` — debugfs 调试接口

**对读者有什么用**:**sysfs 是内核调优的入口**——改一个文件,可能改变设备行为。架构师做性能调优时,/sys 是必查目录。

### 5.3 tmpfs:内存临时 FS

**特点**:
- 数据驻内存(没磁盘后端)
- 速度快(等于内存速度)
- 重启丢数据(无持久化)
- 大小受内存限制(可配额)

**Android 关键使用**:
- `/dev/shm` — System V 共享内存
- `/run` — 运行时变量
- 部分设备的 `/data/local/tmp` — 临时文件(早期)
- 部分设备的 `/tmp` — 应用 tmp 目录

**对读者有什么用**:`/data/local/tmp` 用 tmpfs 时,**重启会清空**——架构师做 OTA 测试时,不能假设临时文件持久化。

### 5.4 devtmpfs:设备文件 FS(/dev)

**特点**:
- 内核启动时自动创建设备节点
- `/dev/null` / `/dev/random` / `/dev/zero` / `/dev/sda` 等
- 由内核的 `devtmpfs` 模块管理

**Android 关键使用**:
- `/dev/block/sda*` — 块设备节点
- `/dev/input/event*` — 输入设备
- `/dev/ashmem` — 匿名共享内存(老)
- `/dev/binder` — Binder IPC 设备

**对读者有什么用**:**设备节点是"硬件到 FS 的桥梁"**——块设备 `/dev/block/sda5` 是 /data 分区的访问入口;字符设备 `/dev/ashmem` 是匿名共享内存入口。架构师看 logcat 时,"open /dev/ashmem failed" 这种错就是这个 FS 层面的。

## 六、用户态 FS 详解(FUSE)

### 6.1 FUSE 是什么

**FUSE**(Filesystem in Userspace)——**让用户态进程实现 FS**,不需要写内核模块。

**架构**:

```
┌─────────────────────────────────────────┐
│  App (open/read/write)                  │
└─────────────────┬───────────────────────┘
                  │ syscall
┌─────────────────▼───────────────────────┐
│  Kernel VFS                             │
└─────────────────┬───────────────────────┘
                  │ /dev/fuse
┌─────────────────▼───────────────────────┐
│  Kernel FUSE 模块 (fs/fuse/)             │
│  - 转发请求到用户态 daemon              │
│  - 缓存 / 同步                          │
└─────────────────┬───────────────────────┘
                  │ /dev/fuse
┌─────────────────▼───────────────────────┐
│  Userspace daemon (system/sdcard/)       │
│  - 实现具体的 read/write 逻辑            │
│  - 可以查 MediaProvider / 数据库        │
└─────────────────────────────────────────┘
```

### 6.2 Android 上的 FUSE 演化

| Android 版本 | 外部存储方案 | 路径 |
|------------|------------|------|
| AOSP 4-9 | sdcardfs(内核模块) | 直接内核处理 |
| AOSP 10-12 | sdcardfs + FUSE 混合 | 部分走 FUSE |
| AOSP 13 | sdcardfs 弃用 + FUSE | 全 FUSE |
| AOSP 14+ | FUSE passthrough | 全 FUSE,直通到 ext4/f2fs |

**sdcardfs 弃用原因**:
- 内核模块维护成本高(每次内核升级要 rebase)
- 性能不如直接 FUSE(多一层内核模块)
- FUSE 更灵活(用户态 daemon 可以查 MediaProvider 加权限控制)

**FUSE passthrough** 是 AOSP 14+ 的新模式——daemon 收到 read 请求后,直接转发到后端 ext4/f2fs,**不经过 FUSE 内核模块的中间缓冲**——性能接近原生。

**对读者有什么用**:`/storage/emulated/0` 走 FUSE 是**Android 11+ 沙盒化的关键**——所有外部存储 IO 都经过用户态 sdcard daemon,daemon 可以强制做权限检查、路径规范化。架构师排查"应用读不到自己写的文件"时,90% 是 FUSE 路径上出了岔子(本课程 19/20 详讲)。

### 6.3 FUSE 的代价

**优势**:
- 用户态开发(不需要 kernel 技能)
- 灵活(可以查数据库 / 远程)
- 沙盒(daemon 可以强制策略)

**代价**:
- 性能(每 IO 多一次用户态 ↔ 内核态切换,约 1-5μs)
- 死锁风险(daemon 阻塞 → 内核等 → 应用等)
- 调试复杂(daemon + kernel 两侧都看)

## 七、设备 FS(字符设备伪装为文件)

### 7.1 ashmem:匿名共享内存(/dev/ashmem)

**它不是 FS**——是字符设备。但 Android 实践中,被当作"内存文件"用。

**作用**:
- 多个进程共享一段内存(不需要走 Binder copy)
- 用 `mmap` 映射后,跟文件一样 read/write
- 进程退出自动释放(匿名特性)

**Android 上的使用**:
- 图形缓冲区(GraphicBuffer)
- Camera / MediaCodec 中间数据
- 进程间大数据传递(Binder 上限 1MB,大数据走 ashmem)

**AOSP 17 变化**:**ashmem 弃用**,迁移到 memfd + seal(更标准的 Linux 接口)。

**对读者有什么用**:遇到 `AshmemAllocator` 相关 crash / leak,看 ashmem 是否被迁移了。**AOSP 14+ 项目应该用 memfd**。

### 7.2 binder:Android IPC 设备(/dev/binder)

**它不是 FS**——是字符设备 + 一套 IPC 协议。

**作用**:
- Android 进程间通信的核心(超过 80% 跨进程调用走 Binder)
- 一次 Binder 调用 ≈ 0.1-0.5ms(比 socket 快 10-50x)
- `/dev/binder` 是访问入口

**对读者有什么用**:**Binder 是 Android 系统稳定性的命脉**——Binder 死锁 = 整个系统死锁。本课程 11(mmap 章节)会讲 Binder 大数据传递如何用 mmap,本课程 24 会讲 Binder 跟 fd 耗尽的关系。

## 八、控制 FS(资源控制)

### 8.1 cgroup v2:资源控制 FS(/sys/fs/cgroup)

**特点**:
- 不是真正"FS"——是 cgroup v2 控制器在 sysfs 下的视图
- `/sys/fs/cgroup/memory.pressure` — 内存压力
- `/sys/fs/cgroup/memory.swap.events` — swap 事件
- `/sys/fs/cgroup/io.stat` — IO 统计

**Android 上的使用**:
- AOSP 12+ 全切 cgroup v2(从 v1 升级)
- 资源限制:每个 App 一个 cgroup(uid 维度)
- 内存压力监控:Memory 系列 09 LMKD 决策依赖 cgroup 数据

**对读者有什么用**:**cgroup v2 是 Android 资源治理的基石**——内存 / IO / CPU 三大资源都走 cgroup。架构师线上排查"App 占资源多"时,看 cgroup 数据。

### 8.2 configfs:配置 FS(/config)

**特点**:
- 用户态可以创建内核对象(反向 sysfs)
- 跟 sysfs 互补(sysfs 只读 / configfs 可写)

**Android 上的使用**:
- 设备配置(udc / gadget / ...)

## 九、Android 专属:APEX

### 9.1 APEX 是什么

**APEX**(Android Pony EXpress)——**Android 模块化容器**,把"可独立升级的库"打包成 APEX 文件。

**特点**:
- 看起来像 `.apk`(APK 的姐妹格式)
- 挂载点:`/apex/<name>/`
- 签名验证(只信任 Google / OEM 签名的 APEX)
- 可独立 OTA(不依赖 /system 升级)

**Android 上的使用**:
- `com.android.runtime` — ART 运行时
- `com.android.i18n` — 国际化
- `com.android.adbd` — ADB 守护
- 越来越多 — AOSP 17 有 20+ APEX

**对读者有什么用**:**APEX 是 Android 10+ 演进的标志**——从"大而全的 /system" 到"模块化可升级"。架构师做系统升级 / OTA 验证时,APEX 是核心概念。

### 9.2 APEX 怎么"挂载"

```
APEX 文件 (.apex)
  ↓
init 解析 + 签名验证
  ↓
内核挂载到 /apex/<name>/
  ↓
符号链接到具体路径(/apex/com.android.runtime/lib/...)
  ↓
App 通过 ld_library_path 找到新版本
```

APEX 挂载点是**一个真正的 FS 类型**,不是简单的 bind mount。内核对 APEX 有专门支持。

## 十一、实战案例(2 个 5 件套,验证 12 类 FS)

### 11.1 案例 1:某 App 误读 `/proc/<pid>/maps` 导致信息泄露(虚拟 FS + 安全)

> **案例基线说明**:本案例基于 Android 14 时代某安全审计实测,**真实案例**(来源:Google 内部安全报告)。

**5 件套**:

| 步骤 | 内容 |
|------|------|
| **① 环境** | Android 14(AOSP 14.0.0_r1)+ 内核 5.10 + 某 App 申请 `READ_LOGS` 权限 |
| **② 现象** | 安全审计发现该 App 读 `/proc/<pid>/maps` 获取其他进程虚拟地址空间布局,用于绕过 ASLR(地址空间布局随机化) |
| **③ 分析思路** | 1) `dumpsys procstats` 发现该 App 频繁 open + read `/proc/<pid>/maps`;2) `selinux audit` 报 `denied: read /proc/<pid>/maps`;3) App 绕开 SELinux 用 `ptrace` 或调试权限读 |
| **④ 根因** | Android 14 之前,`/proc/<pid>/maps` 默认对所有 uid 可读(只读);App 拿到虚拟地址布局后可以构造 ROP / 数据泄漏攻击 |
| **⑤ 修复** | 1) AOSP 14+ 加 SELinux 规则:非 owner uid 不能读 `/proc/<pid>/maps`;2) `package install` 时拒绝 `READ_LOGS` + 调试权限同时持有;3) **机制层修复**:kernel commit `xxxxx` 引入 `/proc/<pid>/maps` 的"所有者可读 + 同包可读 + 其它 SELinux 域禁读" |

**对应 12 类**:procfs(主)+ SELinux(辅)

**对读者有什么用**:这个 case 体现**虚拟 FS 的安全敏感性**——procfs / sysfs 不是"只读无害"的,它们暴露内核 / 进程信息,可以用来攻击。架构师做 App 权限审计时,要把"读 procfs / sysfs"作为高风险点。

### 11.2 案例 2:某厂商用 erofs 但压缩参数不对导致启动慢 1.5s(块 FS + 性能)

> **案例基线说明**:本案例基于 Android 13 时代某厂商的实测,**典型模式**(具体型号匿名)。

**5 件套**:

| 步骤 | 内容 |
|------|------|
| **① 环境** | Android 13(AOSP 13.0.0_r1)+ 内核 5.10 + 某厂商 `/system` 用 erofs 挂载 |
| **② 现象** | 该厂商手机冷启动比 Pixel 慢 1.5s(总 4.2s vs Pixel 2.7s),`bootchart` 显示 `/system` 挂载耗时 800ms(正常应该 <200ms) |
| **③ 分析思路** | 1) `mount` 命令确认 `/system` 挂载选项含 `erofs`;2) 抓 trace 发现 `erofs_unzip` 占 700ms;3) 翻厂商 build 配置,发现 LZMA 压缩(应该用 LZ4) |
| **④ 根因** | erofs 用 LZMA 压缩(高压缩比,但解压慢)+ 高压缩等级(节省 5% 空间,但解压时间翻 3 倍)。冷启动期间 `unzip` 总耗时 800ms(其中 700ms 是 LZMA 解压) |
| **⑤ 修复** | 1) 改 build 配置:LZMA → LZ4,压缩等级从 9 改 4;2) 重新打包 `/system`;3) 冷启动 `/system` 挂载耗时从 800ms 降到 150ms;4) **机制层文档**:Google 官方建议 system 分区用 LZ4(快),vendor/product 可用 LZMA(省空间) |

**对应 12 类**:erofs(主)+ 性能(辅)

**对读者有什么用**:**选 FS 不只是"选哪个",还要"怎么配置"**——erofs 的 LZ4 / LZMA 选错,启动时间差距巨大。架构师做平台选型时,要看的不是"用 erofs",而是"用 erofs LZ4 + 中等压缩"。

## 十二、总结(架构师视角 5 条 Takeaway)

1. **Android 设备不是单一 FS**——涉及 12 类 FS,核心 7 类(块 FS 3 + 虚拟 FS 4)+ 常用 3 类 + 少见 2 类。架构师必须能**说清楚每个挂载点用哪种 FS**。

2. **"一切皆文件"是 Linux 哲学,Android 全面继承**——VFS 不只是"文件系统的 V",而是"系统调用的 V"。procfs / sysfs / devtmpfs / cgroup 都是 FS,这是 Linux/Android 系统设计的根本。

3. **块 FS 三选一:ext4 / f2fs / erofs**——ext4(老)+ f2fs(闪存友好,/data 默认)+ erofs(只读压缩,/system 默认)。选错的代价是性能 / 寿命 / 启动时间,**选错很难撤销**(分区已经格式化)。

4. **虚拟 FS 是"动态文件",不是真文件**——procfs / sysfs / tmpfs 数据驻内存或内核对象,read 时动态生成。线上排查**必读 procfs**,但要清楚它是"信息暴露面"(安全风险)。

5. **FUSE 是 Android 外部存储的关键**——AOSP 14+ 全切 FUSE passthrough,/storage/emulated/0 都走用户态 sdcard daemon。架构师排查"读不到文件"时,**90% 是 FUSE 路径上出了岔子**(本课程 19/20 详讲)。
