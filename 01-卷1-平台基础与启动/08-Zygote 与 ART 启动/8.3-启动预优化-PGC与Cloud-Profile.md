# 8.3 启动预优化:Profile Guided Compilation + Cloud Profile

## 一句话开场

ART 启动后的运行期优化靠 **profile**——`dex2oat` 根据 profile 把"热点方法"提前编译成机器码。Profile 三类来源(系统 boot image / 应用本地 / Play Store Cloud),**任何一类缺失都会让对应 App 冷启动退化 100-300ms**。理解 profile 怎么生成、怎么下发、怎么失效,就能在"装应用后第一次启动慢""OTA 后整机慢""新机第一次开机慢"这三类常见现象里精确定位。

## 1. 核心子问题

1. **Profile** 究竟是什么?文件长什么样?ART 怎么读它?
2. `dex2oat` 在什么时机被调用?触发链是 `PMS → installd → dex2oat` 还是反过来?
3. **Cloud Profile** 的 3 类来源(系统 / App / Play Store)各自怎么下发?
4. 装应用后第一次启动为什么慢?profile 怎么从"无"变成"有"?
5. **boot image profile** 与 **app profile** 的区别?前者怎么影响 Zygote 启动?
6. 国内厂商(华为 Turbo / MIUI 资源预置 / vivo 加速)与 AOSP profile 机制差异?
7. profile 损坏或缺失的退化路径?art 怎么 fallback?
8. AOSP 17 vs AOSP 14 的 profile 机制差异?

## 2. 详细展开

### 2.1 Profile 是什么:ART 启动优化的"使用说明书"

Profile 是 ART 用来**记录方法热度**的数据结构,本质是一组"哪些 class / method 被高频调用"的统计:

```text
# profile 文件结构(简化,实际是 protobuf 格式)
PgoProfile {
  profile_info: [
    {
      dex_location: "system/framework/framework.jar",
      class_id: 0x1234,  # class 索引
      methods: [
        { method_id: 0x5678, hot_count: 1000 },  # 热点:调用 1000 次
        { method_id: 0x5679, hot_count: 200 },   # 温点:调用 200 次
        { method_id: 0x567a, hot_count: 50 },    # 启动期用:调用 50 次
      ]
    },
    ...
  ]
}
```

**3 个热度级别**:
- **hot**:调用 > 1000 次 → `dex2oat` 用 `speed` 模式编译(最优化,体积大)
- **warm**:调用 200-1000 次 → `dex2oat` 用 `speed-profile` 模式编译(平衡)
- **startup**:启动期用到(< 50 次但属于启动路径)→ `dex2oat` 用 `speed-profile` 但标记 startup critical

**所以呢**:
- profile 决定 dex2oat 编译**什么**——没有 profile,dex2oat 不知道哪些方法重要
- 编译产物(oat)比 dex 大 30-50%,**全编译不现实**(framework.oat 全编译 100+ MB)
- profile 让 dex2oat 智能选择"只编译热点"——framework.oat 通常 50-80 MB,因为只编了热点

### 2.2 dex2oat 触发链:从 PMS 到 dex2oat

dex2oat 的调用方是 **installd**(系统服务),installd 又被 **PackageManagerService(PMS)** 调度。完整链路:

```
┌─ dex2oat 触发链 ──────────────────────────────────────────────┐
│ 触发场景 1: 装新 App                                          │
│   PackageInstaller → PMS.installPackage →                     │
│   PackageManagerService.performDexOpt →                       │
│   InstalldNativeService.dexopt →                             │
│   installd fork dex2oat                                       │
│                                                                 │
│ 触发场景 2: 首次开机(boot)                                   │
│   PMS.systemReady → PMS.performBootDexOpt →                  │
│   InstalldNativeService.dexopt →                             │
│   installd fork dex2oat                                       │
│                                                                 │
│ 触发场景 3: OTA 升级                                          │
│   PMS.performBootDexOpt(after OTA) →                         │
│   同上                                                          │
│                                                                 │
│ 触发场景 4: 后台 idle                                         │
│   JobScheduler(idle) → PMS.performIdleDexOpt →               │
│   InstalldNativeService.dexopt →                             │
│   installd fork dex2oat                                       │
│                                                                 │
│ 触发场景 5: 手动 adb 触发                                     │
│   adb shell cmd package compile -m speed-profile <pkg>      │
│   → PMS.performDexOpt → 同上                                  │
└─────────────────────────────────────────────────────────────────┘
```

**关键代码**(简化):

```java
// path: frameworks/base/services/core/java/com/android/server/pm/PackageManagerService.java
// commit: android-17.0.0_r1
public void performDexOpt(PackageInfo pkg, int compilationReason) {
    // 1. 检查是否需要 dexopt(根据 install reason / time / profile 状态)
    if (!shouldPerformNewDexOpt(pkg, compilationReason)) return;

    // 2. 调 installd.dexopt
    String[] commands = new String[] {
        "dexopt",
        pkg.applicationInfo.sourceDir,        // apk 路径
        pkg.applicationInfo.dataDir,          // data 路径
        "speed-profile",                       // compilation mode
        pkg.applicationInfo.packageName,
    };
    try {
        mInstaller.dexopt(commands);
    } catch (InstallerException e) {
        Slog.w(TAG, "Failed to dexopt " + pkg.packageName, e);
    }
}
```

```cpp
// path: system/installd/InstalldNativeService.cpp
// commit: android-17.0.0_r1
binder::Status InstalldNativeService::dexopt(const std::string& apk_path,
                                              const std::string& instruction_set,
                                              const std::string& compiler_filter,
                                              ...) {
    // 1. 拼 dex2oat 命令行
    std::string cmd = "dex2oat";
    cmd += " --dex-file=" + apk_path;
    cmd += " --oat-file=" + oat_path;
    cmd += " --compiler-filter=" + compiler_filter;
    if (has_profile) {
        cmd += " --profile-file=" + profile_path;
    }

    // 2. fork dex2oat 进程执行
    pid_t pid = fork();
    if (pid == 0) {
        execl("/system/bin/dex2oat", "dex2oat", ..., nullptr);
    }

    // 3. 等待 dex2oat 完成
    waitpid(pid, &status, 0);

    return binder::Status::ok();
}
```

**关键点**:
- `compiler_filter` 是 dex2oat 的核心参数,决定编译模式
- 5 种 `compiler_filter`(从快到慢):`verify-none` / `interpret-only` / `space` / `speed-profile` / `speed`
- 默认 `speed-profile`(AOSP 17 沿用)——只在 profile 标记的热点上做 AOT 编译

### 2.3 装应用后第一次启动为什么慢

**装应用 X 后,启动 X 的耗时分布**:
1. PMS 安装 X(`installPackage`)
2. PMS 调度 `performDexOpt(X)` → installd 调 dex2oat
3. dex2oat 编译 X 的 dex → 生成 `/data/dalvik-cache/<arch>/X.oat`
4. 这次 dex2oat 跑**几秒到几十秒**(取决于 X 的大小)
5. **首次启动 X** 时,ART 直接 mmap X.oat,启动快

**首次启动 X 时的耗时变化**:
- 如果**装 X 时已经跑过 dex2oat**:启动快(~200-400ms)
- 如果**装 X 时没跑过 dex2oat**(`pm install --no-dexopt`):首次启动会触发 lazy dex2oat,启动慢 1-3 秒

**所以呢**:
- **装应用后第一次启动**慢,根因可能是 dex2oat 没在装时跑,而被推迟到首次启动
- 大型 App(微信、抖音、王者)装时 dex2oat **必须**完成,否则用户首次打开等待 5-10 秒
- **线上常见 OEM 优化**:装应用时**并行**触发 dex2oat,不让用户等

### 2.4 boot image profile:Zygote 启动的"使用说明书"

8.2 讲过 boot image(`/system/framework/boot.{art,oat,vdex}`)是 Zygote 启动的"数据底座"。但**boot image 怎么决定要编译什么**?靠 **boot image profile**——这是一组描述"Zygote 启动时哪些方法会被调用"的 profile 数据。

**boot image profile 来源**:
1. **编译时 profile**:Google 在 AOSP build 阶段对 framework 跑一次"模拟启动",收集热点
2. **AOSP 17 新增**:boot image profile 可以来自**线上设备**的统计数据(类似 App Cloud Profile)

**boot image profile 怎么影响 Zygote 启动**:
- 编译 boot image 时,dex2oat 根据 boot image profile 决定**编哪些 method**
- 启动时,Zygote mmap boot.oat,**只**调用 profile 标记的方法
- profile 缺失 / 失效 → boot image 没编那几个方法 → 运行时解释执行 → 启动慢 50-150ms

**🟡 待联网确认**:AOSP 17 的 boot image profile 上线细节,以 release notes 为准。

### 2.5 Cloud Profile:Play Store 的"助攻"

Cloud Profile 是 AOSP 14+ 引入的机制,目的是**让大量设备"复用"少数设备的 profile 统计**:

```
┌─ Cloud Profile 流程 ─────────────────────────────────────────┐
│                                                                │
│  ① 设备 A 运行 App X,profile 记录热点                          │
│     ↓ (OTA / Background)                                       │
│  ② 设备 A 把 profile 上传到 Google 云端(脱敏)                  │
│                                                                │
│  ③ 设备 B 安装 App X(从未运行过)                              │
│     ↓ (Play Store 推送 App 时,顺带推送 profile)                │
│  ④ 设备 B 的 PackageManager 收到 profile + App                │
│     ↓                                                          │
│  ⑤ installd 跑 dex2oat,用 Cloud Profile 优化编译              │
│     ↓                                                          │
│  ⑥ 设备 B 启动 X:首次启动就快 100-300ms                       │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

**3 类 Cloud Profile 来源**:
1. **系统 profile**:Google 维护的 framework / 系统 app profile
2. **应用 profile**:Play Store 上架时附带(开发者上传或自动生成)
3. **OEM profile**:OEM 在工厂预置 profile(华为 / 小米 / vivo 都有)

**🟡 待联网确认**:Cloud Profile 在 AOSP 17 的传输协议与脱敏规则,以官方文档为准。

**对启动的意义**:
- 新机第一次装 + 启动某 App,**第一次启动就快**——因为 Cloud Profile 让 dex2oat 编了热点
- 没有 Cloud Profile 的设备,需要先跑一次 X,生成 profile,然后**第二次启动**才快
- **OTA 后首启**:旧 profile 可能因 framework API 变化而失效,需要重新生成

### 2.6 国内厂商定制:Turbo / 预置 / 加速

国内厂商(华为、小米、OPPO、vivo)的 profile 优化比 AOSP 更激进,典型做法:

| 厂商 | 机制 | 做法 | 稳定性影响 |
|---|---|---|---|
| 华为 | GPU Turbo / 预编译 | 工厂预置 framework 扩展类的 profile + 预编译 | 升级 framework 时必须重生成,否则触发 ART 启动崩 |
| 小米 | MIUI 资源预置 | 把常用 App 的 profile 预置到 `/system/pre_loaded_app/` | App 升级后预置 profile 失效,首次启动慢 100-200ms |
| OPPO | Hyper Boost | App 启动期 CPU 频率提升 + profile 预加载 | CPU 频率提升可能让 thermal 限频,触发卡顿 |
| vivo | vivo 加速 | 工厂预置 + 智能预编译 | 类似小米 |

**🟡 待联网确认**:具体 OEM 优化措施与触发条件,以各厂商公开发布说明为准。

**共性问题**:
- **OTA 后 profile 失效**:framework 改 → 所有 OEM 预置 profile 失效 → 整机启动退化 1-3 秒
- **App 升级后 profile 失效**:App dex 改了 → 预置 profile 错位 → 首次启动退化 100-500ms
- **预置 profile 文件损坏** → ART 启动崩,需要重刷

### 2.7 profile 损坏或缺失的退化路径

```
profile 状态    →  dex2oat 决策       →  App 启动表现
─────────────────────────────────────────────────────
profile 存在     →  按 profile 编译    →  快(~200-400ms)
profile 缺失     →  解释执行 / 全编译  →  慢(interpret: +300ms;全编:启动慢,运行快)
profile 损坏     →  拒绝加载,fallback  →  同缺失
profile 版本错   →  同上
─────────────────────────────────────────────────────
```

**所以呢**:
- 装新 App 后第一次启动慢,**先看 profile 状态**:`dumpsys package <pkg> | grep profile`
- profile 文件路径:`/data/misc/profiles/cur/<uid>/<pkg>/primary.prof`
- 手动触发 dex2oat:`adb shell cmd package compile -m speed-profile <pkg>`
- 强制清除 profile:`adb shell pm clear <pkg>`(同时清应用数据)

### 2.8 AOSP 17 vs AOSP 14 的 profile 差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| Cloud Profile 范围 | 应用为主 | 应用 + boot image | 增强 |
| 默认 compiler_filter | speed-profile | speed-profile(参数略调) | 不变 |
| 后台 dex2oat 触发 | idle job | idle job(加强调度) | 增强 |
| Profile 加密 | 设备密钥 | 设备密钥 + 完整性校验 | 强化安全 |
| Profile 大小限制 | 1MB / app | 2MB / app(扩容) | 增强 |
| 装应用并行 dex2oat | 实验 | 稳定 | 增强 |

> **🟡 待联网确认**:`Profile 大小限制 2MB` 的具体值,以 AOSP 17 release notes 为准。

## 4. 实战案例

### 案例 1:某厂商预置 profile 损坏,装应用后首次启动崩(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 panda,8GB RAM)
- 复现步骤:装某银行 App(代号 SafeBank),首次启动后 3 秒崩

**现象**:
```log
# logcat -b crash
DEBUG   : installd: dexopt starting for com.safebank.app
DEBUG   : dex2oat: Loading profile: /system/pre_loaded_app/com.safebank.app.prof
ERROR   : dex2oat: Failed to parse profile: invalid magic
ERROR   : dex2oat: Aborting compilation
DEBUG   : installd: Falling back to interpret-only
ERROR   : art: VerifyError at App.onCreate
        com.safebank.app.MainActivity.onCreate
FATAL   : Process com.safebank.app crashed
```

**分析思路**:
1. 关键日志 `invalid magic` + 位置 `Loading profile` → 预置 profile 损坏
2. 查 `/system/pre_loaded_app/`:`md5sum com.safebank.app.prof`
3. 对照同型号其他设备:profile hash 应该一致 → 当前设备不一致 → 文件损坏
4. 触发场景:工厂镜像烧录时 IO 异常(常见于生产线),profile 文件被部分写入

**根因**:
- 厂商预置 profile 用工厂烧录工具一次性写入,出错时**只写了部分**
- dex2oat 拒绝加载(版本校验 + magic 校验双重失败)→ fallback 到 interpret-only
- interpret-only 模式下,某些用了 AOT 特有指令的 class verify 失败 → VerifyError → crash

**修复**:
- 短期:用户 adb 修复:`adb shell cmd package compile -m speed-profile com.safebank.app` → 重新生成 profile
- 长期:工厂烧录工具加 profile **校验和**校验 + 烧录后回读验证
- **不可**:OEM 推送 profile 修复包,因为 profile 路径 `/system/pre_loaded_app/` 是只读分区

**修复原理**:
- profile 是 protobuf 格式,**有 magic + version header**
- 任何损坏(包括部分写入)都会被 dex2oat 拒绝,fallback 到 interpret-only
- interpret-only 是**最安全**的回退,但**不保证所有 class 都能运行**——某些依赖 AOT 编译产物的代码会 verify 失败

### 案例 2:OTA 升级 framework 后,所有 App 启动退化 200-500ms(典型模式)

**环境**:
- Android 版本:AOSP 14 → AOSP 17 OTA
- 设备:Pixel 8(8GB RAM)
- 复现步骤:OTA 升级后,装应用 + 启动,3 次中位数

**现象**:
- OTA 升级前:某 App 冷启动 350ms
- OTA 升级后:某 App 冷启动 750ms
- 多次启动后,逐渐回到 380ms(本地 profile 重新生成)

**分析思路**:
1. 关键现象:OTA 后**首次启动慢,后续启动恢复正常** → 高度怀疑 profile 失效
2. 检查:`adb shell dumpsys package <pkg> | grep Profile` → 显示 `Status: cleared`
3. 解释:OTA 升级后,PMS 自动清除所有应用 profile(因为 framework 变了)
4. 应用启动时,ART 没 profile → interpret-only → 启动慢 400ms
5. 启动后,ART 自动采集 profile → **第二次启动** 时,dex2oat 用新 profile 重编译 → 启动快

**根因**:
- AOSP 17 强化了 profile 的 framework 依赖校验
- framework 改了 → 旧 profile 失效 → 强制清空
- 装应用时没有并行 dex2oat(取决于 OEM 实现)
- 用户首次启动 App 体验差

**修复**:
- 短期:**预加载 + 并行 dex2oat**:`adb shell cmd package compile -m speed-profile -f <pkg>` 在后台触发
- 中期:Cloud Profile 推送(8.3 §2.5 详述)——但只对 Play Store 装的应用有效
- 长期:incremental OTA,只更新变化的 framework 部分 → 减少 profile 失效的应用范围

**修复原理**:
- profile 失效是**设计内行为**——framework 改了,旧 profile 不安全
- 但**用户体验**差,需要从 OEM 侧补:
  - OTA 后立刻后台跑 dex2oat 重建 profile(用户无感)
  - Cloud Profile 让首次启动就用上别人的 profile

## 5. Takeaway

1. **Profile 是 ART 启动优化的"使用说明书"**——没 profile,dex2oat 不知道该编什么;有 profile,只编热点,启动快。
2. **`dex2oat` 由 `installd` fork,被 `PMS` 调度**——装新 App / 首次开机 / OTA 升级 / idle 时都会触发。
3. **装应用后第一次启动慢的根因** = 装时没跑 dex2oat + profile 缺失,fallback 到 interpret-only。
4. **Cloud Profile 让新机第一次启动 App 就快**——AOSP 14+ 引入,Play Store 推送时顺带推 profile。
5. **国内厂商(华为/小米/OPPO/vivo)的预置 profile 是"银弹"**——首次启动快,但**升级 framework 后失效**,整机启动退化 1-3 秒。
6. **profile 损坏会 fallback 到 interpret-only,可能导致 VerifyError 崩溃**——案例 1 的根因。
7. **AOSP 17 强化了 profile 校验**——OTA 升级后,所有应用 profile 自动清空,首次启动退化 200-500ms。
8. **profile 关键路径**:`/data/misc/profiles/cur/<uid>/<pkg>/primary.prof` + `/system/pre_loaded_app/*.prof`(OEM 预置)

## 附录 D:工程基线表(可调参数)

| 参数 | 典型默认 | 选用准则 | 踩坑提醒 |
|---|---|---|---|
| `dalvik.vm.image-dex2oat-flags` | speed-profile | 性能优先:speed;平衡:speed-profile;体积优先:space | speed 编译最慢且占空间最多,小内存设备别用 |
| `pm.dexopt.bg-dexopt-scheduling` | true | 调试时改 false,让 dexopt 跑前台;线上保持 true 后台跑 | false 会让 App 启动退化 200-500ms |
| `pm.dexopt.install_bg-dexopt` | true | 装应用时并行触发 dexopt | false 后用户首次启动退化 1-3 秒 |
| `pm.dexopt.first-boot` | true | 首次开机跑全量 dexopt | false 后首次开机快,但应用启动都慢 |
| `dalvik.vm.dex2oat-Xms` / `-Xmx` | 256M / 512M | 编译大型 App(< 200MB)时调到 1G | 调大后 dex2oat 编译时占内存更多,可能 OOM |
| `dalvik.vm.dex2oat-threads` | CPU 核数 | 编译时与开机争 CPU,小内存设备调到 2-4 | 调大反而让 dex2oat 与 Zygote 启动争抢 CPU |
| `dalvik.vm.dex2oat-resolve-startup-strings` | true | 启动期字符串解析优化 | false 后 App 启动慢 50-150ms |
| Cloud Profile 推送(`cmd profile install`) | 手动 | 调试时手动推;OEM 线上不开放 | 误推错 profile 会让 App 崩溃 |
