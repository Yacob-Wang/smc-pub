# 8.4 启动类加载优化:deferred class load / lazy verification

## 一句话开场

**8.1 §2.4 讲 Zygote 启动时 80% 时间在 `preloadClasses`,但并非所有 class 都必须在 Zygote 启动期 eager 加载**。AOSP 提供 `preloaded-classes` + `lazy-preloaded-classes` 两层机制:前者 Zygote 启动时加载,后者第一次 App fork 后才加载。本节讲清这个权衡——`preload` 越多 Zygote 启动越慢,`lazy` 越多首个 App 启动越慢,**配置不当会触发首次类加载 VerifyError 崩**。

## 1. 核心子问题

1. `preloaded-classes` 文件长什么样?9000+ class 是怎么挑出来的?
2. **lazy-preloaded-classes** 是什么?与 `preloaded-classes` 的执行时序?
3. **verify** 是什么?为什么 ART 启动期要 verify 一遍?
4. **lazy verification**(AOSP 14+ 的 `verifyAtRuntime` 策略)怎么用?
5. **PIC(Position Independent Code)** 编译如何与 lazy verification 联动?
6. **判定准则**:哪些 class 必须 eager preload,哪些可以 lazy?
7. preload 阶段 OOM 怎么解决?OEM 常见做法?
8. AOSP 17 vs AOSP 14 的 deferred class load 差异?

## 2. 详细展开

### 2.1 preloaded-classes 文件:9000+ class 的"必须清单"

`frameworks/base/config/preloaded-classes`(源码)在 AOSP 编译时会被复制到设备的 `/system/etc/preloaded-classes`。这个文件是**纯文本**,每行一个 class 全限定名,ZygoteInit.preloadClasses() 逐行 `Class.forName()` 触发加载:

```text
# /system/etc/preloaded-classes (片段,AOSP 17)
# Auto-generated by frameworks/base/tools/preload/WritePreloadedClassList.java
android.app.Activity
android.app.ActivityManager
android.app.ActivityManagerNative
android.app.ActivityThread
android.app.Application
android.app.ApplicationErrorReport
...
# framework 关键类,约 8000 个
java.lang.Object
java.lang.String
java.lang.System
java.lang.Thread
...
# core-oj 核心类,约 1500 个
java.io.File
java.io.InputStream
java.net.URL
...
```

**文件特征**:
- 注释行以 `#` 开头,运行时跳过
- 排序:**按 dex 内部的 class 索引排序**,不是字母序——为了 preload 时**按 dex 顺序读**,提高 page cache 命中率
- 一个 class 一行,**不能跨行**
- 文件大小:AOSP 17 约 **400-500 KB**(9000+ 行)

**关键问题:class 是怎么挑出来的?**

`frameworks/base/tools/preload/WritePreloadedClassList.java` 是生成这个文件的工具。它跑 4 步:

```
┌─ preloaded-classes 生成流程(在 AOSP build 阶段) ──────────────┐
│ ① 对 framework.jar / core-oj.jar / services.jar / am.jar       │
│    跑一次"启动模拟"——执行 framework 关键路径                  │
│ ② 收集所有被 Class.forName / ClassLoader.loadClass 触发       │
│    加载的 class                                                 │
│ ③ 加白名单:core-oj 全部 / framework 关键 7000+ / 反射常用类  │
│ ④ 排序(按 dex 索引)+ 写到 frameworks/base/config/preloaded-classes │
└─────────────────────────────────────────────────────────────────┘
```

**所以呢**:
- `preloaded-classes` 里的 class **不是 Google 随便挑的**,是基于"framework 启动模拟"实证出来的
- OEM 在这个文件**追加**自家 framework 扩展类,可能让 Zygote 启动退化 50-200ms
- OEM **错误地移除**这个文件里的 class,会让第一个 App 启动退化 100-300ms
- 改动这个文件**需要重新跑** `WritePreloadedClassList`,否则排序错乱 → page cache 命中率降低

### 2.2 lazy-preloaded-classes:把"次重要"的 class 推迟

`frameworks/base/config/lazy-preloaded-classes`(AOSP 14+ 引入)是**第二层** class 列表。它的 class 在 Zygote 启动期**不**加载,而是**第一次 App fork 时**才加载。

```text
# /system/etc/lazy-preloaded-classes (片段,AOSP 17)
# 包含"使用频次中等,启动期可推迟"的 class
android.accessibilityservice.AccessibilityService$1
android.accounts.AccountManager$1
android.animation.ValueAnimator$1
...
# 约 500-1000 个 class
```

**lazy preload 的执行时机**:

```java
// path: frameworks/base/core/java/com/android/internal/os/ZygoteInit.java
// commit: android-17.0.0_r1
public static void main(String[] argv) {
    // 1. eager preload:preloaded-classes 的全部
    preloadClassesFromFile(PRELOADED_CLASSES_FILE);

    // 2. lazy preload 调度器:Zygote 启动时**只装载** lazy 列表的索引,
    //    实际加载延后到第一次 fork 子进程
    if (ENABLE_LAZY_PRELOAD) {
        LazyClassLoader.setup(PRELOADED_LAZY_CLASSES_FILE);
    }
}

static class LazyClassLoader {
    // 在 forkAndSpecialize 之后,被新进程拉起时执行
    static void preloadAfterFork() {
        // 加载 lazy-preloaded-classes 里的 class
        preloadClassesFromFile(PRELOADED_LAZY_CLASSES_FILE);
    }
}
```

**所以呢**:
- Zygote 启动时,`preload` 节省 100-300ms(因为 lazy 的 500-1000 个 class 不在启动期加载)
- 第一个 App fork 后,该 App 进程**内部**多花 50-200ms 加载 lazy class
- **效果**:Zygote 启动快 + 第一个 App 启动略慢,但后续 App fork 时 lazy class 已加载,启动快

### 2.3 verify 是什么:Class.forName 触发的校验链

ART 在 `Class.forName(name, true, null)` 加载 class 时,会做**4 步校验**:

```
┌─ Class.forName 触发的校验链 ──────────────────────────────────┐
│ ① 链接(Link):把 class 的 constant pool / method / field 关联  │
│ ② 验证(Verify):检查字节码是否符合 JVM 规范                    │
│ ③ 准备(Prepare):为 static field 分配内存 + 设默认值           │
│ ④ 初始化(Initialize):执行 <clinit>(static block)            │
└─────────────────────────────────────────────────────────────────┘
```

**verify 是最耗时的一步**:
- 简单的 class:verify 1-5ms
- 复杂的 class(如 `ActivityThread`、`Handler`、`Looper`):verify 10-30ms
- 包含大量反射 / 泛型 / 内部类的 class:verify 30-100ms

**preload 阶段的 verify 实际表现**(8.1 案例 2 已讲):
- 9000+ class 加载完,verify 累计耗时 200-500ms
- 某个 class verify 失败 → `VerifyError` → Zygote 启动崩

**VerifyError 的常见 4 类原因**:

| 错误 | 根因 | 修复 |
|---|---|---|
| `IllegalAccessError` | class 引用了不可见的 class / method | 重新编译 framework,确保 class 可见性一致 |
| `IncompatibleClassChangeError` | interface / abstract 方法签名变了 | 同步更新所有引用方 |
| `NoSuchFieldError` / `NoSuchMethodError` | 字段 / 方法被删除 | 同步更新 dex |
| `ClassCircularityError` | 类的初始化循环依赖 | 重构类依赖图 |

### 2.4 lazy verification:AOSP 14+ 的"双层校验"

AOSP 14 引入 **verifyAtRuntime** 策略(由 `dalvik.vm.dex2oat-flags` 控制),让某些 class 的 verify **不**在 dex2oat 时做,而在运行时第一次调用时做。

**5 种 `compiler_filter` 对 verify 的影响**:

| compiler_filter | 启动期 verify | 运行期 verify | 启动速度 | 运行速度 |
|---|---|---|---|---|
| `verify-none` | 跳过 | 跳过 | 最快 | 最慢 |
| `interpret-only` | 跳过 | 运行时解释 | 快 | 慢 |
| `space` | 部分(只 verify critical) | 剩余运行期 | 中 | 中 |
| `speed-profile` | 部分 | 剩余运行期 | 中 | 快 |
| `speed` | 全部 | 跳过 | 慢 | 最快 |

**AOSP 17 默认 `speed-profile`**——这意味着:
- 启动期只 verify 一部分 class(boot image 里的)
- 剩余 class 的 verify 在运行期触发
- 运行期 verify 触发时,如果遇到 VerifyError,**App 进程崩**,但 Zygote 不会受影响

**所以呢**:
- `speed-profile` 让 Zygote 启动快 100-200ms(因为部分 verify 跳过)
- 但**部分 class 的 VerifyError 推迟到运行期**——这意味着 Zygote 启动期看不到错误,首次 App 启动才暴露
- 案例 1(下)的"装应用后首次启动崩"很可能就是这种情况

### 2.5 PIC(Position Independent Code)与 lazy 联动

AOSP 14+ 还引入了 **PIC 编译**(`--compile-pic`),让 AOT 编译产物的代码段可重定位,从而:
- 多个 App 进程可以**共享**同一份 AOT 编译产物(节省内存)
- 启动期可以**不必**链接所有 method,运行时再链接

**PIC 的代价**:
- AOT 编译时间多 10-20%(因为要支持重定位)
- 运行期 method 第一次调用时多 1-3ms(链接开销)
- 但**长期收益**大:多 App 进程共享 AOT 编译产物,整机内存省 100-300MB

**🟡 待联网确认**:`--compile-pic` 在 AOSP 17 的具体行为,以 release notes 为准。

### 2.6 判定准则:哪些 class 必须 preload,哪些可以 lazy

这一节给"线上调 preloaded-classes"的具体准则,而不是空话"看情况"。

| 判定条件 | 建议归类 | 理由 |
|---|---|---|
| framework / core-oj 中的 class | ✅ eager preload | 几乎所有 App 都会用到,不分 App 类型 |
| 系统服务启动期用到的 class(`am.jar` / `services.jar`) | ✅ eager preload | system_server 启动必用 |
| 反射常用的 class(Annotation / Reflect / Proxy) | ✅ eager preload | 反射调用频繁,运行时 verify 代价大 |
| 业务 App 自己 dex 里的 class | ❌ 不在 preloaded-classes | Zygote 不应该知道 App 私有 class |
| framework 中**仅**某些场景用的 class | 🟡 lazy preload | 比如 `AccessibilityService`、`AccountManager` 内的回调 class |
| 第三方 framework 扩展(厂商加的) | 🟡 OEM 自行决策 | 8.1 §4 案例 2 的根因:加太多 → Zygote OOM |
| OTA 升级后才用到的 class | 🟡 lazy preload | 旧 profile 不包含,新 class 推迟到第一个 App fork |
| 与其他 class 强耦合(初始化顺序敏感) | ✅ eager preload | lazy 后顺序错乱,可能 NPE |

**判定公式**:
```
preload 价值 > preload 成本 → eager preload
preload 价值 < preload 成本 → lazy preload
preload 价值 ≈ preload 成本 → 看 Zygote 启动预算

其中:
preload 价值 = (App 启动省的时间) × (App 启动频次)
preload 成本 = Zygote 启动多花的时间 + Zygote 内存多占的
```

**举例**:
- `android.util.Log`(高频,所有 App 用):preload 价值极高,必 eager
- `android.speech.tts.TextToSpeech` 内回调 class(低频,仅无障碍 / 语音 App 用):preload 价值低,改 lazy
- `android.app.Notification$Builder`(高频):preload 价值高,eager

### 2.7 preload 阶段 OOM 的治理

8.1 §4 案例 2 已讲过 OEM 在 preloaded-classes 加太多 class 触发 OOM。补充治理手段:

| 手段 | 做法 | 副作用 |
|---|---|---|
| **扩 Zygote Java heap** | `setprop dalvik.vm.zygote.max-heap-size 128M` | 整机可用内存少 64MB |
| **移 lazy** | 把 OEM 自加的 1000+ class 移到 `/system/etc/lazy-preloaded-classes` | 第一个 App 启动慢 50-200ms |
| **拆分 boot image** | 不让 framework.jar 全量进 boot image,只留核心 | 后续 App 启动慢 100-300ms |
| **pre-dex2oat 优化** | 让 dex2oat 提前编译 OEM 扩展类,而不是 `Class.forName` 加载 dex | build 阶段时间多 30-60 秒 |
| **关闭 preload** | `setprop ro.zygote.disable_preload_classes true` | Zygote 启动快 1.5 秒,但所有 App 第一次启动慢 200-500ms |

### 2.8 AOSP 17 vs AOSP 14 的 deferred class load 差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| preloaded-classes 数量 | 7500 | 9000-12000 | +30% |
| lazy-preloaded-classes 数量 | 500-800 | 500-1000 | 略增 |
| verify 策略 | speed-profile | speed-profile(参数略调) | 不变 |
| PIC 编译 | 默认开启 | 默认开启 | 不变 |
| preload 阶段 OOM 处理 | 自动 lazy 化 | 增强(更智能) | 增强 |
| OEM 扩展支持 | 手动维护 preloaded-classes | 增加 `vendor_preloaded-classes` 机制 | 增强 |

## 4. 实战案例

### 案例 1:OEM 在 preloaded-classes 误加不存在的 class,Zygote 启动崩(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:某品牌中端机(代号 tiger,6GB RAM)
- 复现步骤:刷 OEM 提供的"性能优化包"后,重启设备,卡开机动画 30 秒后自动重启

**现象**:
```log
# logcat -b crash
DEBUG   : ZygoteInit: Preloading classes...
DEBUG   : ZygoteInit: ...Loaded 8500 classes
ERROR   : ZygoteInit: Error preloading class com.oem.boost.PerformanceHelper
        java.lang.ClassNotFoundException: com.oem.boost.PerformanceHelper
            at java.lang.ClassLoader.loadClass(ClassLoader.java:641)
            at java.lang.Class.forName(Class.java:400)
            at com.android.internal_os_ZygoteInit.preloadClasses(ZygoteInit.java:947)
WARN    : ZygoteInit: ...continue despite error
DEBUG   : ZygoteInit: ...Loaded 9500 classes
ERROR   : ZygoteInit: Error preloading class com.oem.boost.SuperResolver
        java.lang.NoClassDefFoundError: com/oem/boost/PerformanceHelper
            ... 8 frames
WARN    : ZygoteInit: ...continue despite error
DEBUG   : ZygoteInit: ...Loaded 11000 classes
DEBUG   : ZygoteInit: Preloading resources...
ERROR   : art: VerifyError at ZygoteInit.preloadClasses
        java.lang.VerifyError: Bad type on operand stack
            at com.oem.boost.SuperResolver.<clinit>
FATAL   : ZygoteInit: Error preloading classes
```

**分析思路**:
1. 关键日志 `Error preloading class` 出现多次,共 3 处
2. 第 1 处是 `ClassNotFoundException`,但被 ZygoteInit **catch 住,继续 preload**——这是关键
3. 第 2 处是 `NoClassDefFoundError`,因为前一个 class 加载失败导致
4. 第 3 处是 `VerifyError`,因为 `SuperResolver` 引用了 `PerformanceHelper` 类的静态字段
5. 实际崩溃在 `VerifyError`,**不是 ClassNotFoundException**——这是 zygote 启动崩的"延迟触发"模式

**根因**:
- OEM 的"性能优化包"在 `/system/etc/preloaded-classes` 加了 3 个自家 class
- 第一个 class `com.oem.boost.PerformanceHelper` **实际上不存在**——OEM 改了 framework 但忘了 push 这个 class
- preload 时第一个 class 抛 `ClassNotFoundException` 被忽略
- 第二个 class 引用第一个 → `NoClassDefFoundError`,被忽略
- 第三个 class 的 `<clinit>` 引用第一个 → 运行时 verify 时才暴露 → `VerifyError` → Zygote 启动崩

**修复**:
- 短期:从 `/system/etc/preloaded-classes` 删除 3 个 OEM class
- 中期:OEM 改 build 流程,**确保 preloaded-classes 里加的 class 在 framework.jar 里都存在**
- 长期:AOSP 17 强化了 preload 阶段的错误处理,会在第一个 class 失败时就 abort,而不是延迟到 verify

**修复原理**:
- `ClassNotFoundException` 不一定能立刻导致崩溃——Java 的 lazy linking 让 class 错误可以延后
- 但 `<clinit>(static initializer)` 是**类加载时立即执行**的,任何 class 引用错误都会立刻 verify 失败
- 这就是为什么"第一个 class 加载失败"+"第三个 class 引用第一个"会变成 `VerifyError`

### 案例 2:某厂商把 system_server 启动期用的 class 错误移到 lazy,首启慢 800ms(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌旗舰(代号 dragon,12GB RAM)
- 复现步骤:OEM 自家"性能优化"build 目标,改 preloaded-classes 配置

**现象**:
- Zygote 启动时间从 1500ms 优化到 900ms(优化 40%)
- 但 **system_server 启动时间从 3500ms 退化到 4300ms**(退化 800ms)
- 整机 boot time:稍微慢 200ms(因为 system_server 启动退化幅度 > Zygote 优化幅度)

**分析思路**:
1. Zygote 启动变快 600ms,但 system_server 启动退化 800ms
2. 怀疑 OEM 把 system_server 启动期用的 class 误移到 lazy
3. 检查 OEM 修改:`diff <(adb shell cat /system/etc/preloaded-classes) < 标准 AOSP 14`
4. 发现 OEM 把 `android.app.ActivityManager`,`android.app.WindowManagerGlobal` 等 200+ class 移到 lazy

**根因**:
- system_server 启动时需要 ActivityManager、WindowManagerGlobal 等(它要注册服务)
- 这些 class 从 lazy 加载时,system_server 内部要触发**第二次** ClassLoader.loadClass → 慢 1-3ms × 200+ 次
- 累加 800ms

**修复**:
- 短期:恢复 200+ class 到 preloaded-classes
- 中期:OEM 用 Perfetto 跑 system_server 启动 trace,标出每个 class 加载耗时,再决定哪些移 lazy
- 长期:AOSP 17 的 `WritePreloadedClassList` 工具增加了"system_server 启动模拟"路径

**修复原理**:
- preloaded-classes 不是孤立文件,它与 system_server / PMS / AMS 启动链路**强耦合**
- 移走某个看似"不常用"的 class,如果它在 system_server 启动路径上,就会拖累整机启动
- OEM 改这个文件**必须**用 Perfetto 跑完整的 boot trace 验证

## 5. Takeaway

1. **`preloaded-classes` 决定 Zygote 启动期加载哪些 class**——9000+ 个是 AOSP build 阶段"启动模拟"实证出来的,不是 Google 随便挑的。
2. **`lazy-preloaded-classes` 让"次重要"的 class 推迟到第一个 App fork 后**——节省 Zygote 启动时间 100-300ms,代价是第一个 App 启动慢 50-200ms。
3. **verify 失败会触发 Zygote 启动崩**——9000+ class 任何 verify 错误都让 Zygote 死在 preload 阶段。
4. **`speed-profile` 让部分 verify 推迟到运行期**——意味着 Zygote 启动期看不到 VerifyError,**装应用后首次启动才暴露**。
5. **OEM 改 preloaded-classes 是高危操作**——加多了 Zygote OOM,加错了 verify 崩,移错了 system_server 启动退化。
6. **判定公式**:`preload 价值 = App 启动省的时间 × App 启动频次`;`preload 价值 > preload 成本 → eager,反之 lazy`。
7. **PIC 编译 + lazy verification 联动**——AOSP 14+ 默认开启,多 App 共享 AOT 编译产物,整机内存省 100-300MB。
8. **AOSP 17 默认 speed-profile**——preloaded-classes 9000+,lazy-preloaded-classes 500-1000,这是稳定的折中。
