# 10.7 启动时间测量:am start -W / logcat / Perfetto

## 一句话开场

**3 类启动时间测量工具**(am start -W / logcat + bootstat / Perfetto + gfxinfo)各自适用场景不同——**am start -W 看 12 字段 + LaunchState / logcat 看 7 个时间点 / Perfetto 看 Choreographer 4 大回调**。3 类工具配合 = **30 秒定位 App 启动慢的根因**。本节讲清 3 类工具的实战用法 + 30 秒 SOP,让读者能在线上 30 秒内定位 App 启动慢的 5 类根因(10.1-10.5 详述)。

## 1. 核心子问题

1. `am start -W` 的 12 字段怎么读?LaunchState 怎么用?
2. `logcat` 7 个时间点(am_create_task 等)怎么用?怎么抓?
3. `Perfetto` 怎么抓 App 启动 trace?怎么读 Choreographer 4 大回调?
4. `dumpsys gfxinfo` 怎么读?`View measure` / `View draw` 字段怎么用?
5. **30 秒定位 SOP** 怎么走?3 类工具怎么配合?
6. `Macrobenchmark` 是什么?怎么测 First Image?
7. 工具选择原则:什么场景用什么工具?
8. AOSP 17 vs AOSP 14 的测量工具差异?

## 2. 详细展开

### 2.1 工具 1:`am start -W`(快速 12 字段)

**`am start -W`** 是最常用的 App 启动测量工具——一行命令拿到 12 字段。

**用法**:

```bash
adb shell am start -W -n com.example.app/.MainActivity
```

**输出**(AOSP 17,12 字段):

```
Status: ok
LaunchState: COLD
Activity: com.example.app/.MainActivity
ThisTime: 1234
TotalTime: 1500
WaitTime: 1500
Intent: ...
UserId: 0
DisplayId: 0
BaseIntent: ...
Stack: ...
Task: ...
```

**字段含义**(10.6 §2.5 已讲,本节重复 3 个最常用):

| 字段 | 含义 |
|---|---|
| `LaunchState` | 启动类型(COLD / WARM / HOT) |
| `ThisTime` | TTID(Activity 第一次绘制开始) |
| `TotalTime` | 接近 TTFD(Activity 完全 ready) |

**对读者有什么用**:
- **am start -W 是最便宜的测量工具**——一行命令,无副作用
- **ThisTime 反映 Cold Start 数字**——线上 App 性能基线
- **LaunchState 帮助确认测量的是哪种启动**——避免 Cold / Warm / Hot 混测

**限制**:
- 只看 12 字段——看不到 Choreographer 细节
- 不看 First Image——看不到异步内容加载
- 看不到 memory / cpu——要其他工具

### 2.2 工具 2:`logcat` + `bootstat`(7 个时间点)

**`logcat -s ActivityTaskManager,ActivityManager`** 看 7 个时间点 + `getprop ro.boottime.*` 看 4 个时间点。

**用法**:

```bash
# 1. 启动前清空 logcat
adb logcat -c

# 2. 启动 App
adb shell am start -n com.example.app/.MainActivity

# 3. 看 logcat
adb logcat -d -s ActivityTaskManager,ActivityManager,ActivityThread | head -200

# 4. 看 bootstat 时间点
adb shell getprop ro.boottime.system_server
adb shell getprop ro.boottime.ams_ready
adb shell getprop ro.boottime.first_frame_drawn
adb shell getprop ro.boottime.boot_completed
```

**logcat 关键事件**(7 个时间点,10.1 §2.6 已讲):

| 事件名 | 含义 |
|---|---|
| `am_create_task` | 任务栈创建 |
| `am_new_intent` | Intent 处理 |
| `am_proc_start` | 进程 fork 开始 |
| `am_proc_bound` | 进程 attach 到 AMS |
| `am_create_activity` | Application + Activity onCreate 完成 |
| `am_resume_activity` | Activity onResume |
| `Displayed` | 整机第一帧显示 |

**对读者有什么用**:
- **logcat 看 7 个时间点**——比 am start -W 更细
- **getprop 看 4 个 ro.boottime.***——量化进程级时间
- **关键拐点**:`am_proc_bound` 是 Framework / App 边界

**限制**:
- logcat 抓的是离散事件——看不到 Choreographer 细节
- `ro.boottime.*` 是单值——被覆盖只能看最近 1 次

### 2.3 工具 3:`Perfetto` + `dumpsys gfxinfo`(Choreographer 细节)

**`Perfetto`** 是 Android 11+ 的新一代 trace 工具——可以抓全栈 trace,包括 Choreographer 4 大回调。

**用法**:

```bash
# 1. 启动 perfetto(后台)
adb shell perfetto -o /data/local/tmp/trace.pb -t 10s \
  sched freq idle am wm view gfx info ss \
  --app com.example.app

# 2. 拉取 trace
adb pull /data/local/tmp/trace.pb

# 3. 在 Perfetto UI 打开
# https://ui.perfetto.dev
```

**Perfetto 关键事件**:

| 事件名 | 含义 |
|---|---|
| `Choreographer#doFrame` | 整帧耗时 |
| `Choreographer#doInput` | input 回调 |
| `Choreographer#doAnimation` | animation 回调 |
| `Choreographer#doTraversal` | traversal 回调 |
| `Choreographer#doCommit` | commit 回调 |
| `am_*` 启动事件 | 10.1 §2.6 详述 |

**`dumpsys gfxinfo`** 看 View 树构建 + 帧耗时:

```bash
adb shell dumpsys gfxinfo com.example.app | head -50
# 关键字段:
#   - View measure: <N>ms
#   - View layout: <N>ms
#   - View draw: <N>ms
#   - Janky frames: <N> (<P>%)
#   - 50th / 90th / 95th / 99th percentile
```

**对读者有什么用**:
- **Perfetto 是最细的测量工具**——看 Choreographer 4 大回调
- **`dumpsys gfxinfo` 看 jank**——50th / 99th percentile
- **Perfetto 跨进程**——能看到 App / system_server / SurfaceFlinger 跨进程 trace

**限制**:
- **Perfetto trace 文件大**——几 MB-几十 MB
- **`dumpsys gfxinfo` 只能看本进程**——跨进程不行
- **Perfetto 抓 trace 影响性能**——线上不要抓

### 2.4 30 秒定位 SOP(关键!)

**3 类工具配合的 30 秒 SOP**:

```
[T0] 用户报告"App 启动慢"
  ↓
[1] am start -W 看 LaunchState + ThisTime(5 秒)
  - LaunchState = COLD / WARM / HOT → 决定是哪一种启动
  - ThisTime 数字 → 决定 Cold Start 基线
  - 如果 ThisTime 健康(800-1500ms)但用户感觉慢 → 走 [2]
  - 如果 ThisTime 异常(> 2000ms) → 走 [3]
  ↓
[2] 用户感觉慢 = First Image 慢(10.6 案例 1)
  - 看 Perfetto 抓首屏内容加载
  - 检查首屏 RecyclerView / ImageView 异步加载
  - 用骨架屏 + 预加载优化
  ↓
[3] ThisTime 异常(> 2000ms)
  - 抓 logcat 看 7 个时间点(5 秒)
  - am_proc_bound → am_create_activity 差值大 → 10.3 详述
  - am_create_activity → am_resume_activity 差值大 → 10.3 案例 1 详述
  - am_resume_activity → Displayed 差值大 → 10.4 / 10.5 详述
  ↓
[4] 抓 Perfetto(10 秒)
  - 看 Choreographer 4 大回调耗时
  - 看 Choreographer#doTraversal 是否 > 16.67ms
  - 哪个回调慢 → 跳到对应章节
  - input > 20ms → 触摸事件 IO 阻塞(10.5 案例 2)
  - animation > 50ms → 动画值计算慢
  - traversal > 200ms → View 树构建慢(10.4)
  - commit > 50ms → GPU 提交慢
  ↓
[5] 抓 dumpsys gfxinfo(5 秒)
  - 看 View measure / layout / draw 耗时
  - 看 Janky frames 比例
  - 哪个字段异常 → 跳到对应章节
  - measure > 200ms → View 树深(10.4 案例 1)
  - layout > 100ms → ConstraintLayout 复杂
  - draw > 500ms → onDraw 慢(10.4 案例 2 / 10.5 案例 1)
  ↓
[T30] 完成定位
```

**对读者有什么用**:
- **30 秒定位 App 启动慢的根因**——3 类工具配合
- **每个工具负责不同维度**——am start -W 数字 + logcat 7 拐点 + Perfetto 4 回调
- **遇到异常字段 → 跳到对应章节**——10.1-10.5 各自的 30 秒 SOP

### 2.5 工具 4:`Macrobenchmark` 库(测 First Image)

**`Macrobenchmark`** 是 Jetpack 库,可以测 First Image / 完整启动时间。

**用法**(伪代码):

```kotlin
// path: app/src/androidTest/java/.../StartupBenchmark.kt
class StartupBenchmark {
    @get:Rule
    val rule = MacrobenchmarkRule()

    @Test
    fun startup() {
        rule.measureRepeated(
            packageName = "com.example.app",
            metrics = listOf(StartupTimingMetric()),
            compilationMode = CompilationMode.DEFAULT,
            startupMode = StartupMode.COLD,
            iterations = 5,
        ) {
            pressHome()
            startActivityAndWait()
        }
    }
}
```

**Macrobenchmark 测的是什么**:
- `StartupTimingMetric`:报告 5 个指标(Time to Initial Display / Time to Full Display / ...)
- 编译模式:DEFAULT / FULL / PARTIAL
- 启动模式:COLD / WARM / HOT

**对读者有什么用**:
- **Macrobenchmark 是 lab 环境的标准化测量**——开发期常用
- **比 am start -W 更准确**——可以控制编译模式 + 启动模式
- **可测 First Image**——通过 Time to Full Display 指标

**限制**:
- 只能在 lab 跑——不能线上
- 编译模式与用户实际不同——结果可能失真

### 2.6 工具选择原则

| 场景 | 推荐工具 | 原因 |
|---|---|---|
| 线上快速归因 | `am start -W` + `logcat` | 一行命令,无副作用 |
| 30 秒定位 App 启动慢 | 3 类工具配合 | 见 2.4 SOP |
| lab 深度调查 | `Perfetto` + `gfxinfo` | 跨进程 + 详细 |
| 标准化测 First Image | `Macrobenchmark` | Jetpack 标准 |
| 历史数据回顾 | `getprop ro.boottime.*` + `bootstat` | 落盘 + 可读 |

### 2.7 AOSP 17 vs AOSP 14 的测量工具差异

| 工具 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| `am start -W` | 9 字段 | 12 字段 | +3 |
| `logcat` 启动事件 | 7 个 | 7 个 | 无变化 |
| `Perfetto` | 稳定 | 稳定 + 增强 | +Systrace 兼容 |
| `dumpsys gfxinfo` | 15 字段 | 18 字段 | +3 |
| `Macrobenchmark` | 1.1.0 | 1.2.0 | +StartTimeMetric |
| 启动后事件追踪 | 启动期 | 启动期 + 启动后 1 分钟 | +feature |

> **🟡 待联网确认**:Macrobenchmark 1.2.0 StartTimeMetric 为待联网确认,实际以 Android Jetpack 1.2.0 release notes 为准。

## 4. 实战案例

### 案例 1:某 App 启动慢 2s,30 秒 SOP 定位到 Perfetto 回调超时(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:用户报告某 App 启动"慢 2 秒"

**30 秒定位过程**:

**T0:用户报告"App 启动慢 2 秒"**

**T5:am start -W**(5 秒):
```bash
$ adb shell am start -W -n com.example.app/.MainActivity
ThisTime: 1800   ← 异常(基线 500-1500ms)
TotalTime: 2200   ← 异常
LaunchState: COLD
```
**结论**:ThisTime 1800ms 异常,Cold Start。

**T10:logcat 看 7 个时间点**(5 秒):
```bash
$ adb logcat -d -s ActivityTaskManager | grep -E "am_"
am_proc_start: ...     ← T+0
am_proc_bound: ...     ← T+200ms(基线 50-150ms,略慢)
am_create_activity: ...  ← T+1000ms(基线 200-400ms,异常大!)
am_resume_activity: ...  ← T+1200ms
Displayed: ...         ← T+1800ms
```
**结论**:`am_proc_bound → am_create_activity` 差值 800ms——Application 初始化慢(10.3 详述)。

**T20:Perfetto 抓 trace**(10 秒):
```
Choreographer#doFrame: 50ms (正常)
Choreographer#doInput: 5ms
Choreographer#doAnimation: 8ms
Choreographer#doTraversal: 700ms  ← 异常
  measure: 80ms
  layout: 50ms
  draw: 600ms   ← onDraw 慢!
```

**T30:定位结论**:
- `am_create_activity` 慢 = Application.onCreate 慢
- `Choreographer#doTraversal` 慢 = View 树 draw 慢
- **根因**:Application.onCreate + View 树 onDraw 都慢(组合)

**修复方向**:
- Application.onCreate 优化(10.3 详述)
- View 树 onDraw 优化(10.4 / 10.5 详述)
- 预估可降 600-1000ms

### 案例 2:某 App 启动"健康"但 jank 30%,30 秒 SOP 定位到 onTouch IO(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:某品牌中端机(代号 eagle,4GB RAM)
- 复现步骤:用户报告"App 滑动卡顿",但 am start -W 健康

**30 秒定位过程**:

**T0:用户报告"App 滑动卡顿"**

**T5:am start -W**(5 秒):
```bash
$ adb shell am start -W -n com.example.app/.MainActivity
ThisTime: 800    ← 健康
TotalTime: 1200  ← 健康
```
**结论**:am start -W 健康——问题不在启动期,在运行期。

**T10:dumpsys gfxinfo 看 jank**(5 秒):
```bash
$ adb shell dumpsys gfxinfo com.example.app | head -50
Stats since gfxinfo reset:
  Total frames rendered: 60
  Janky frames: 18 (30.00%)   ← 异常
  50th percentile: 12ms
  99th percentile: 35ms     ← 异常
```
**结论**:jank 30%——运行期有性能问题。

**T20:Perfetto 抓 trace**(10 秒):
```
Choreographer#doFrame: 30ms
  Choreographer#doInput: 25ms   ← 异常(input 回调慢)
    OnTouchListener.onTouch: 25ms   ← 自定义监听器
      SharedPreferences.commit: 20ms  ← 同步 IO!
```

**T30:定位结论**:
- jank 30% = Choreographer 跳帧
- 跳帧在 input 回调 = OnTouchListener 慢
- OnTouchListener 慢 = SharedPreferences 同步 IO
- **根因**:触摸事件处理中同步 IO 阻塞主线程(10.5 案例 2)

**修复方向**:
- onTouch 中只 record,不 IO
- SharedPreferences 改 apply() 替代 commit()
- 预估可降 jank 30% → < 5%

## 5. Takeaway

1. **3 类测量工具**(`am start -W` / `logcat` + `bootstat` / `Perfetto` + `gfxinfo`)各自适用场景不同,**3 类配合 = 30 秒定位 App 启动慢的根因**。
2. **`am start -W` 是最便宜的测量**——一行命令拿到 12 字段(LaunchState / ThisTime / TotalTime / WaitTime 等)。
3. **`logcat` 看 7 个时间点**(`am_create_task` / `am_new_intent` / `am_proc_start` / `am_proc_bound` / `am_create_activity` / `am_resume_activity` / `Displayed`)——比 am start -W 更细。
4. **`Perfetto` 看 Choreographer 4 大回调**——最细的测量,适合 lab 深度调查。`dumpsys gfxinfo` 看 View measure / layout / draw 耗时 + jank 比例。
5. **30 秒定位 SOP**:am start -W(5s)→ logcat(5s)→ Perfetto(10s)→ dumpsys gfxinfo(5s)→ 5 秒分析。
6. **`Macrobenchmark`** 是 Jetpack 标准化测量工具,适合 lab 测 First Image 指标——但不能线上。
7. **`am start -W` 健康 ≠ App 不慢**——可能是 First Image 慢(10.6 案例 1)或 jank(案例 2)。
8. **AOSP 17 vs AOSP 14 的测量工具差异**:`am start -W` 9 字段 → 12 字段,`gfxinfo` 15 字段 → 18 字段,`Perfetto` + Systrace 兼容。
