# 10.6 首帧定义:First Frame / First Image / Cold / Warm / Hot Start

## 一句话开场

**App 启动性能有 5 种"启动"**(Cold / Warm / Hot / Lukewarm / Ambient)和 **4 种"首帧"**(TTID / TTFD / First Frame Drawn / First Image),**混用这些概念 = 优化方向错**——优化 Cold Start 不能直接降低用户感知的"App 慢"——用户感知是"看到 App 内容"即 First Image。本节讲清 5+4 个概念的精确定义、关系、对应测量工具。

## 1. 核心子问题

1. **5 种"启动"**(Cold / Warm / Hot / Lukewarm / Ambient)各自怎么定义?
2. **4 种"首帧"**(TTID / TTFD / First Frame Drawn / First Image)各自怎么定义?
3. **TTID / TTFD / First Image 三者关系**?
4. **用户感知的真正起点**是哪个?
5. 为什么"App 启动慢"的优化方向**不是直接降 Cold Start 数字**?
6. `am start -W` 输出的 12 字段分别代表什么?
7. 启动期 LaunchState 枚举值怎么对应 5 种启动?
8. AOSP 17 vs AOSP 14 的启动概念差异?

## 2. 详细展开

### 2.1 5 种"启动"的概念辨析

**5 种"启动"** 按"应用进程是否在"区分:

| 启动类型 | 定义 | 进程状态 | 典型耗时(SM8550) |
|---|---|---|---|
| **Cold Start** | 进程不在,需从 0 启动 | 进程不在 | 800-2000ms |
| **Lukewarm Start** | 进程在但 Activity 不在,需重启 Activity | 进程在后台 | 500-1000ms |
| **Warm Start** | 进程在,Activity 在但被 onStop,需 onStart / onResume | 进程在 + Activity 栈有 | 300-700ms |
| **Hot Start** | 进程在,Activity 在前台 onResume,需重新显示 | 进程在 + Activity onResume | 100-300ms |
| **Ambient Start** | 后台进程被低优先级唤醒,需快速 ready | 进程在 + 低优先级 | < 100ms |

**关键洞察**:
- **Cold Start 是最重的**——进程 fork + Application.onCreate + Activity onCreate 全走
- **Lukewarm Start 次重**——进程在,Activity onCreate 要重走
- **Warm Start 较轻**——只需要 onStart / onResume
- **Hot Start 最轻**——只需要 surface 重新显示
- **Ambient Start 是后台预热场景**——App 在后台被预热,前台拉起时已经 ready

**对读者有什么用**:
- **用户感知的"App 启动慢"主要是 Cold Start 慢**——其他启动用户感知不强
- **优化时优先优化 Cold Start**——其他启动的优化空间小
- **"App 启动慢"的指标要看 Cold Start 数字**——不要被 Warm Start 数字误导

### 2.2 4 种"首帧"的概念辨析

**4 种"首帧"** 按"用户感知"区分:

| 首帧类型 | 定义 | 触发时机 | 用户感知 |
|---|---|---|---|
| **TTID**(Time To Initial Display) | Activity 第一次绘制的开始 | onCreate 完成后 | 用户看到第一帧前 |
| **TTFD**(Time To Full Display) | Activity 所有内容绘制完成 | onResume + 完整 layout | 用户看到完整首屏 |
| **First Frame Drawn** | 第一帧实际绘制到屏幕 | ViewRootImpl 完成第一帧 | 屏幕有像素 |
| **First Image** | 用户能看到 App 的具体内容 | 应用层宣告"内容可见" | 用户感知"App 起来了" |

**关键洞察**:
- **TTID 是 Activity 级别的**——Activity 第一次绘制
- **TTFD 是 Activity 完整的**——所有 view 都绘制完成
- **First Frame Drawn 是 ViewRootImpl 级别的**——第一帧像素到屏幕
- **First Image 是用户感知**——内容真正可读

**对读者有什么用**:
- **`am start -W` 输出的 ThisTime = TTID**——是 Activity 开始绘制的时间
- **`am start -W` 输出的 TotalTime = 接近 TTFD**——接近完整首屏时间
- **`ro.boottime.first_frame_drawn` = First Frame Drawn**——第一帧像素到屏幕
- **First Image 没有统一指标**——各厂商自定义(如 Apollo 性能平台的"首图时间")

### 2.3 TTID / TTFD / First Image 三者关系

**3 个首帧的时序关系**:

```
[am start] 触发
  ↓
[T0] Activity 创建开始
  ↓
[onCreate] Application.onCreate + Activity.onCreate
  ↓
[T1] TTID = Activity 第一次绘制开始
  ↓
[Choreographer 调度 traversal]
  ↓
[T2] First Frame Drawn = 第一帧像素到屏幕
  ↓
[完整 layout / 异步内容加载]
  ↓
[T3] TTFD = Activity 所有内容绘制完成
  ↓
[应用层宣告"内容可见"]
  ↓
[T4] First Image = 用户能看到 App 的具体内容

时序差值(线上实测 SM8550):
T1 - T0 = TTID = 500-1500ms(Cold Start)
T2 - T0 = First Frame Drawn = 600-1700ms
T3 - T0 = TTFD = 800-2000ms
T4 - T0 = First Image = 1000-3000ms(如果有异步内容)
```

**关键洞察**:
- **TTID 到 First Frame Drawn 差值 50-200ms**——是 Choreographer 等待 VSYNC
- **First Frame Drawn 到 TTFD 差值 200-500ms**——是后续 layout / 异步内容
- **TTFD 到 First Image 差值 200-1000ms**——是业务侧"宣告内容可见"逻辑

**对读者有什么用**:
- **优化"App 慢"实际优化的是 First Image**——用户感知的真正起点
- **TTID 数字小不等于 App 不慢**——可能 TTFD / First Image 慢
- **`am start -W` 只能看 TTID**——其他用 Perfetto / 自定义埋点

### 2.4 用户感知的真正起点:First Image

**用户感知的"App 慢"是 First Image 慢**,不是 TTID 慢。

**例子**:
- 微信启动:TTID 800ms,但 First Image 2000ms(聊天列表 + 头像 + 消息气泡)
- 美团启动:TTID 1000ms,但 First Image 2500ms(推荐卡片 + 价格 + 距离)
- 抖音启动:TTID 1200ms,但 First Image 3000ms(视频预览图 + 文字 + 头像)

**为什么 First Image 慢**:
- **首屏内容是异步加载的**——Activity onCreate 完后,RecyclerView 还没数据
- **网络图片还没回来**——Glide / Picasso 异步加载
- **数据库查询还没完成**——Room / SQLite 异步

**对读者有什么用**:
- **优化"App 慢"应该优化 First Image**——不是 Cold Start 数字
- **网络图片懒加载**——首屏 1-2 个占位符 + 异步填充
- **数据预加载**——Application.onCreate 中预读核心数据
- **骨架屏**——首屏先显示骨架,内容回来后替换

### 2.5 `am start -W` 输出的 12 字段含义

**`am start -W -n <pkg>/.MainActivity` 输出**(AOSP 17):

```
Status: ok
LaunchState: COLD
Activity: com.example.app/.MainActivity
ThisTime: 1234
TotalTime: 1500
WaitTime: 1500
```

**12 字段含义**:

| 字段 | 含义 | 对应概念 |
|---|---|---|
| `Status` | 启动成功 / 失败 | — |
| `LaunchState` | 启动类型(COLD / WARM / HOT) | 5 种启动的子集 |
| `Activity` | 启动的 Activity | — |
| `ThisTime` | 启动到 Activity 第一帧绘制 | TTID |
| `TotalTime` | 启动到 Activity 完全 ready | 接近 TTFD |
| `WaitTime` | 启动到系统调度完成 | TotalTime + AMS 调度 |
| `Intent` | 启动的 Intent | — |
| `UserId` | 用户 ID(0 / 10 / ...) | — |
| `DisplayId` | 显示 ID | — |
| `BaseIntent` | 原始 Intent | — |
| `Stack` | Activity 栈 | — |
| `Task` | Task ID | — |

**对读者有什么用**:
- **ThisTime = TTID**——是 `am start -W` 最常用的指标
- **TotalTime 接近 TTFD**——但不等同(还要看应用层异步)
- **WaitTime 含 AMS 调度**——比 TotalTime 多 AMS 排队时间
- **LaunchState = COLD / WARM / HOT**——区分 3 种最常见的启动

### 2.6 AOSP 17 vs AOSP 14 的启动概念差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| LaunchState 枚举 | COLD / WARM / HOT | COLD / WARM / HOT | 无变化 |
| Lukewarm Start | 不在 LaunchState | 仍不在 LaunchState | 无变化 |
| Ambient Start | 实验 | 稳定 | +feature |
| `am start -W` 字段 | 9 字段 | 12 字段 | +3 字段 |
| First Image 指标 | 厂商自定义 | 厂商自定义 | 无变化 |
| `ro.boottime.first_frame_drawn` | 写入 | 写入 | 无变化 |

> **🟡 待联网确认**:LaunchState 枚举值为待联网确认,实际以 AOSP 17 build 为准。

| 启动类型 | 进程 | Activity | 典型耗时(SM8550) | 优化空间 |
|---|---|---|---|---|
| Cold Start | 不在 | 不在 | 800-2000ms | 大 |
| Lukewarm Start | 在后台 | 不在 | 500-1000ms | 中 |
| Warm Start | 在 | onStop | 300-700ms | 小 |

| First Image | 用户感知"App 起来了" | 优化首屏内容 |

## 4. 实战案例

### 案例 1:某 App am start -W ThisTime 800ms 但用户感觉"App 慢 3s",定位 First Image 慢(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:用户报告某 App 启动"慢 3 秒",但 am start -W 显示 800ms

**现象**:
```bash
$ adb shell am start -W -n com.example.app/.MainActivity
ThisTime: 800
TotalTime: 1200
WaitTime: 1200
```
**关键观察**:ThisTime 800ms 健康(基线 800-2000ms),但用户感觉慢 3s。

**分析思路**:
1. 关键观察:am start -W 数字健康,用户感知的"慢"不在 TTID
2. 抓 Perfetto trace,看 First Frame Drawn 之后的事件
3. 发现 First Frame Drawn 后,RecyclerView 异步加载数据 1500ms
4. 数据回来后才显示完整首屏(First Image)
5. **首屏内容 = RecyclerView + 图片(网络) + 数据库查询**
6. **根因**:首屏内容是异步加载,ThisTime 不算这部分

**根因**:
- App 首屏 = `RecyclerView` 显示 10 个 Item
- 每个 Item 包含:网络图片(Glide 异步) + 数据库查询(Room 异步) + 业务数据(网络异步)
- 异步加载完成后才"可见"
- 文件路径:`src/com/example/app/MainActivity.java:onCreate` + 业务逻辑
- 修复方法:用骨架屏 + 预加载

**修复**:
- 短期:首屏先用骨架屏占位,内容异步回来后替换
- 中期:Application.onCreate 中预读核心数据(数据库 warm up)
- 长期:用 `Macrobenchmark` 测 First Image 指标,定制首屏策略

**修复原理**:
- **用户感知的"App 慢"实际是 First Image 慢,不是 Cold Start 慢**
- **ThisTime 800ms 健康 ≠ 用户感觉不慢**
- **优化方向应是 First Image,不是 Cold Start**

### 案例 2:某 App 启动期热启动被误判为冷启动,定位 Process.kill 后台进程(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:某品牌中端机(代号 eagle,4GB RAM)
- 复现步骤:用户报告某 App 启动"慢 1.5s",OEM 误判为 Cold Start 慢

**现象**:
```bash
$ adb shell am start -W -n com.example.app/.MainActivity
ThisTime: 1500
TotalTime: 1700
LaunchState: COLD
```
**关键观察**:LaunchState = COLD——但 App 实际在后台(LMKD 杀进程后才 COOL 启动)。

**分析思路**:
1. 关键观察:LaunchState = COLD,启动慢 1.5s
2. 检查 `dumpsys activity processes | grep <pkg>`
3. 发现 `<pkg>` 进程**不在**——被 LMKD 杀了
4. 进一步看 `dumpsys meminfo | grep <pkg>`——应用占内存 800MB,远超阈值
5. 抓 `lmkd` 日志,发现 LMKD 频繁杀进程
6. **根因**:App 占内存过大,后台频繁被杀,导致每次启动都走 Cold Start 路径

**根因**:
- App 内存占用 800MB(线上均值 200-400MB)
- 8.6 已讲:LMKD 触发条件是 RSS > `oom_adj` 阈值
- 8GB 设备阈值约 600MB → App 800MB 触发 LMKD
- 后台 App 频繁被杀 → 每次启动都 Cold Start
- 文件路径:`src/com/example/app/...` 多处
- 修复方法:用 leakcanary + 减少内存占用

**修复**:
- 短期:用 `am profile start` profile 内存,找泄漏
- 中期:减少 Bitmap 缓存 / Glide 内存配置
- 长期:8.6 Zygote 内存治理 + LMKD 联动优化

**修复原理**:
- **冷启动慢未必是 onCreate 慢**——也可能是被频繁杀进程
- **优化"App 慢"应该从内存治理入手**——而不是 onCreate 优化
- 8.6 详述 Zygote 内存治理

## 5. Takeaway

1. **5 种"启动"**(Cold / Warm / Hot / Lukewarm / Ambient)按"进程 + Activity 是否在"区分——Cold Start 最重,Hot Start 最轻。
2. **4 种"首帧"**(TTID / TTFD / First Frame Drawn / First Image)按"用户感知"区分——**用户感知的真正起点是 First Image**。
3. **TTID / TTFD / First Frame Drawn / First Image 时序差值**:TTID 到 First Frame Drawn 50-200ms,First Frame Drawn 到 TTFD 200-500ms,TTFD 到 First Image 200-1000ms。
4. **`am start -W` 输出的 12 字段含义**:ThisTime = TTID,TotalTime 接近 TTFD,WaitTime 含 AMS 调度。
5. **优化"App 慢"应优化 First Image,不是 Cold Start 数字**——ThisTime 健康 ≠ 用户感觉不慢。
6. **冷启动慢未必是 onCreate 慢**——也可能是 LMKD 频繁杀进程(案例 2),或业务侧首屏内容异步加载慢(案例 1)。
7. **LaunchState = COLD / WARM / HOT** 区分 3 种最常见的启动。
8. **AOSP 17 vs AOSP 14 的启动概念差异**:`am start -W` 9 字段 → 12 字段,LaunchState 枚举无变化。
