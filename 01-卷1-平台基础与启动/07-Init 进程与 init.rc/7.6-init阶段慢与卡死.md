## 一句话开场

「慢」和「卡死」看起来是程度差别，实际是两类问题——**慢是资源争抢，要看分布；卡死是依赖断裂，要看最后一条日志**。用错方法，两边都查不出来。

## 1. 核心子问题

1. 怎么在三十秒内判断当前是「慢」还是「卡死」？
2. init 阶段的耗时大头通常在哪几处？
3. 哪些命令会真正阻塞 init 的单线程主循环？
4. 服务启动风暴是怎么形成的，为什么它比单个慢服务更难查？
5. 卡死的依赖断裂点有哪几类？怎么快速收敛？
6. 进不了 adb 的时候，现场从哪里取？
7. 有哪些成熟的优化手段？各自的代价是什么？
8. 哪些「慢」是设计内的、不该去优化？

## 2. 详细展开

### 2.1 先分诊：慢还是卡死

这一步决定后面走哪条路，不能跳过。

| 判据 | 慢 | 卡死 |
|---|---|---|
| 最终能否进系统 | 能，只是久 | 不能，或反复重启 |
| `ro.boottime.*` | 有完整序列，某段空档大 | 序列在某处**戛然而止** |
| `dmesg` 里 init 日志 | 持续推进到最后 | 停在某条之后再无输出 |
| 现象 | 开机久但会好 | 停在动画 / boot loop |

最快的一招是看 `ro.boottime` 序列是否完整：

```bash
adb shell getprop | grep ro.boottime | sort -t: -k2 -n
```

**能取到属性说明已经进系统了，那就是「慢」**；取不到、连不上 adb，按「卡死」处理，转 2.5 的取证路径。

一个反复出现的判断陷阱重申一遍（7.3 讲过）：**开机动画在转不代表系统在推进**。bootanimation 起得比 `post-fs-data` 早，它转得再欢，后面的阶段也可能早就停了。

### 2.2 慢：耗时大头在哪

按线上经验，init 阶段的耗时集中在下面几处。

**第一类：阻塞主循环的命令**（7.2 详列过）

init 主循环是单线程的，这些命令执行期间整个启动链路停摆：

| 命令 | 阻塞原因 | 典型量级 |
|---|---|---|
| `exec` | 同步等子进程退出 | 取决于被执行的程序 |
| `wait_for_prop` | 无超时等待 | 0 到 ∞ |
| `mount_all` | 挂载 + 可能触发 fsck | 数十毫秒到数分钟 |
| `insmod` | 内核模块加载 | 单个几毫秒，但数量多 |
| `restorecon_recursive` | 遍历打标签 | 随文件数线性增长 |

**第二类：一次性的现场编译**

- sepolicy 未命中预编译，现场合并 CIL（7.5）
- odsign 校验 + dex2oat 重编译 ART artifact（7.3 案例 2）

这两类的共同特征是**只在刷机或 OTA 后的首次开机出现**。

**第三类：服务启动风暴**

`on boot` 里的 `class_start core` / `class_start main` 会把同一 class 的服务几乎同时 fork 出来。几十个进程同时启动，抢 CPU、抢 IO、抢内存带宽，每个都比单独启动时慢。

风暴的难查之处在于：**逐个看每个服务都不算慢，但总耗时就是下不来**。看单点耗时会一无所获，必须看并发度和资源水位。这时候单靠 `ro.boottime.*` 不够了，要上 Perfetto boot trace 看 CPU / IO 的时间线。

**第四类：GKI 下的 vendor 模块加载**

GKI 架构把大量驱动做成了独立 ko，开机要逐个 insmod。单个不慢，但数量可达上百个，累积效应明显，且它们串在关键路径上。相关机制见卷 1 第 2 章。

### 2.3 慢：定位方法

```bash
# 1. 导出全部时间点
adb shell getprop | grep ro.boottime > boottime.txt

# 2. 按值排序，算相邻差值，找空档
#    注意：属性记的是"时刻"不是"耗时"
```

**关键在于找空档而不是找大值**。`ro.boottime.<服务名>` 记的是该服务被启动的时刻，两个相邻时刻之间的差，才是那段时间里发生的事情的耗时。

找到空档后：

1. 用空档两端的服务名去 rc 里 `grep`，确定这段属于哪个阶段。
2. 在该阶段内用 kmsg 打点法二分（7.3 的 SOP）。
3. 怀疑是风暴而非单点时，转 Perfetto boot trace。

### 2.4 卡死：依赖断裂的五个高频点

卡死的本质是某个等待永远等不到。按出现频率排：

1. **`post-fs-data` 卡住**（7.3 详述）。`/data` 挂不上或解不开，链条是 `/data` 挂载 → FBE 解密 → KeyMint HAL → vendor 分区 → SELinux 域。
2. **`wait_for_prop` 等不到**。无超时，写它的服务没起来或没设那个属性，就永久挂起。
3. **`critical` 服务反复失败**。7.2 讲过，超过窗口内的失败次数会触发重启进 bootloader，表现为 boot loop。
4. **HAL 起不来**。多因 SELinux 域没配对（7.5）或 VINTF 声明缺失，被依赖它的阶段一起拖住。
5. **服务依赖环**。A 等 B 的属性，B 等 A 的 socket。这类最隐蔽，因为两边看起来都「在运行」。

### 2.5 卡死：现场从哪里取

进不了 adb 时，按这个顺序尝试：

```bash
# 1) 有时 adb 还在，只是框架没起来 —— 先试
adb shell dmesg | grep "init:"

# 2) adb 不通，重启后取上次的内核日志
adb shell cat /sys/fs/pstore/console-ramoops-0
# 或
adb shell cat /proc/last_kmsg

# 3) 都没有 —— 只能靠串口 / fastboot 侧手段
```

拿到 `dmesg` 后的核心动作只有一个：**找最后一条 init 日志**。它所在的 `on` 段就是卡住的阶段，对照 7.3 的资源前提表就知道缺什么。

如果能进 adb，补两条：

```bash
# 谁在 restarting —— 反复崩溃的服务
adb shell getprop | grep init.svc | grep -v stopped | grep -v running

# 有没有 SELinux 拦截
adb shell dmesg | grep avc
```

### 2.6 优化手段与各自的代价

按性价比排序，每一条都有代价，不存在白给的优化。

| 手段 | 做法 | 代价 |
|---|---|---|
| **延后非关键服务** | 从 `class main` 挪到 `class late_start` | 该功能首次可用时间变晚 |
| **改按需启动** | 去掉自启，由使用方 `ctl.start` | 首次调用有冷启动延迟 |
| **拆解阻塞命令** | `exec` 改为 `service` + `oneshot` | 失去同步语义，需自行处理时序 |
| **给 `wait_for_prop` 兜底** | 改为带超时的等待逻辑 | 超时后的降级路径要设计 |
| **精简 insmod** | 合并模块或延后加载非必要驱动 | 依赖关系要重新梳理 |
| **缩小 restorecon 范围** | 避免全量 `restorecon_recursive /data` | 遗漏会导致标签错误 |

有两条**不该去优化**的，识别出来能省很多无用功：

- **首启的现场编译**（sepolicy 现编、odsign/dex2oat）。这是设计内行为，做启动性能基线时应当把「刷机/OTA 后首启」与「常规启动」分成两条曲线，否则会把正常现象追成劣化。
- **`mount_all` 触发的 fsck**。它是数据完整性的保障，不能为了开机快而绕过。真正该做的是查清 `/data` 为什么会脏。

## 3. 关键产出

### SOP：init 阶段问题的分诊流程

```
能进系统吗？
├─ 能 ──→ 「慢」
│         1. getprop | grep ro.boottime，排序算差值
│         2. 找最大空档，定位到阶段
│         3. 阶段内 kmsg 打点二分
│         4. 单点找不到 → Perfetto boot trace 看并发与资源
│
└─ 不能 ──→ 「卡死」
          1. 取 dmesg / pstore / last_kmsg
          2. grep "init:"，找最后一条
          3. 对照资源前提表，确定缺什么
          4. grep avc 排除 SELinux
          5. getprop init.svc 找 restarting 的服务
```

### SOP：启动性能基线的建立

1. 固定测试条件：同机型、同版本、同电量区间、同温度区间。
2. 区分三条曲线：**刷机后首启** / **OTA 后首启** / **常规重启**。三者不可混算。
3. 每条曲线取多次重启的中位数，不用单次值。
4. 记录分段数据而非只记总时长，否则劣化时无法定位。
5. 分段边界建议用：bootloader 交接、init 二阶段开始、`post-fs-data` 完成、zygote 启动、`sys.boot_completed`。

### SOP：rc 改动的启动风险自检

提交前逐条过：

1. 新增的命令里有没有 `exec` / `wait_for_prop` / `mount_all`？在关键路径上吗？
2. 涉及 `/data` 的操作，是否在 `post-fs-data` 及之后？（7.3）
3. 新服务是否漏了 `oneshot`？（7.2）
4. 新服务是否配了 SELinux 域，`ps -Z` 验证过吗？（7.5）
5. 新属性是否声明了 context 并授了 `set_prop`？（7.4）
6. 有没有引入 `critical`？失败重启的后果评估过吗？

## 4. 实战案例

### 案例 1：一个服务拖慢整机 1.2 秒，但它自己只跑了 80 毫秒

**现象**：某版本开机比上版慢 1.2 秒左右。逐个服务看耗时，没有任何一个明显变慢。

**排查**：`ro.boottime` 序列显示，空档出现在 `on post-fs-data` 中段。kmsg 打点二分后，定位到一条新增的 `exec` 命令——它调用的脚本本身只跑 80 毫秒。

**根因**：这条 `exec` 阻塞了 init 主循环 80 毫秒，但它卡住的位置正好在几十个服务即将并发启动之前。这 80 毫秒把整条启动流水线的时间轴整体后移，而后移之后恰好撞上了另一个资源峰值窗口，产生了远超 80 毫秒的连锁放大。

**修复**：改为 `service` + `oneshot`，让它异步执行，不占主循环。

**教训**：init 主循环上的阻塞，**代价不等于它自己的耗时**。在关键路径上，任何同步等待都要按「它会把后面所有事情推迟多久」来评估，而不是按它自身耗时。

### 案例 2：boot loop 的根因在一条看似无关的属性

**现象**：某批次机器约 2% 概率开机后反复重启，其余正常。

**排查**：取 pstore 日志，最后一条 init 日志停在一个 `critical` 服务启动之后。`getprop init.svc` 取不到（进不了系统），只能从 dmesg 看到该服务反复被拉起。再往前翻，找到一条 `avc: denied ... tclass=property_service`。

**根因**：该服务启动时要写一个属性，写被 SELinux 拒绝；服务把写失败当致命错误退出；因为标了 `critical`，init 重试若干次后触发重启进 bootloader。2% 的概率来自一个时序竞争——SELinux 策略在特定时序下才会命中那条拒绝。

**修复**：补 `set_prop` 权限；同时去掉该服务的 `critical` 标记，因为它并非系统必需。

**教训**：`critical` 是把「单点故障」升级为「整机不可用」的开关，只应给真正不可或缺的服务。排查 boot loop 时，从最后一条 init 日志往前翻 avc，是高命中率的固定动作。

## 5. Takeaway

- 先分诊：能进系统是「慢」，进不去是「卡死」。两者方法完全不同，混着查会两头落空。
- 慢看分布，卡死看最后一条日志。
- `ro.boottime.*` 记的是时刻不是耗时，要看**相邻差值形成的空档**。
- init 主循环上阻塞的代价不等于自身耗时——它会把整条流水线后移，可能引发连锁放大。
- 服务启动风暴的特征是「每个都不慢、总时间就是长」，单点分析无效，必须看并发与资源水位。
- 卡死的五个高频点：`post-fs-data`、`wait_for_prop`、`critical` 服务反复失败、HAL 起不来、服务依赖环。
- 首启的现场编译（sepolicy / odsign）和 fsck 属于设计内行为，不该当劣化去优化。启动基线必须区分首启与常规启动。
- `critical` 把单点故障升级成整机不可用，慎用。
