## 一句话开场

属性服务是个**读写高度不对称**的系统——读是完全无锁的共享内存访问，不走任何 IPC；写必须经由 init 的一个 socket 串行处理。理解这个不对称，就理解了它的性能特征和它的故障形态。

## 1. 核心子问题

1. 属性存在哪儿？为什么 `getprop` 快到可以在热路径上随便调？
2. 为什么读不需要锁也不会读到撕裂的值？
3. 写为什么非要绕一圈 init？谁有权限写？
4. `ro.` / `persist.` / `ctl.` / `init.svc.` 这些前缀分别是什么语义？
5. `persist.` 属性为什么必须等到 `/data` 就绪之后才能加载？
6. 新加一个 vendor 属性，为什么 `setprop` 不报错但值没变？
7. 属性空间会不会用完？用完了什么表现？
8. `wait_for_prop` 底层是怎么等的——轮询还是唤醒？

## 2. 详细展开

### 2.1 存储布局：一组按 SELinux 上下文切分的共享内存文件

属性不是存在某个进程的堆里，而是一组 mmap 出来的文件：

```bash
adb shell ls -l /dev/__properties__/
# u:object_r:default_prop:s0
# u:object_r:debug_prop:s0
# u:object_r:vendor_default_prop:s0
# u:object_r:exported_system_prop:s0
# ... 几十个
```

**每个文件对应一个 SELinux 上下文**，而不是一个属性。哪个属性落在哪个文件里，由 `property_contexts` 决定：

```bash
# path: system/sepolicy/private/property_contexts
ro.build.version.sdk    u:object_r:exported_system_prop:s0
persist.sys.            u:object_r:system_prop:s0
vendor.               u:object_r:vendor_default_prop:s0
```

这样切分的目的是**权限粒度**：SELinux 规则作用在文件上，于是「哪个域能写哪类属性」就能被精确表达。这一设计直接导致了 2.6 要讲的那类静默失败。

每个文件内部是一棵 **trie（前缀树）**，因为属性名天然带层级（`ro.build.version.sdk`）。节点结构在 `bionic/libc/system_properties/` 下：

- `prop_bt`：trie 的分支节点，按名字的一段做索引
- `prop_info`：叶子节点，存实际的值和一个序列号

### 2.2 读路径：无锁，靠序列号做一致性

读属性完全不走 IPC。每个进程在启动时把这些文件以**只读**方式 mmap 进自己的地址空间，之后 `__system_property_get` 就是纯粹的内存遍历。

一致性靠 `prop_info` 里的序列号（seqlock 思路）：

```cpp
// 概念示意，实际实现见 bionic/libc/system_properties/system_properties.cpp
// 写：先把序列号置为奇数（表示"正在改"），改完再加 1 变回偶数
// 读：读前取序列号，读后再取一次
//     若两次不等，或为奇数，说明读期间发生了写 —— 重试
```

所以：

- **读没有系统调用，没有锁，没有 IPC**。这是 `getprop` 能被大量代码在热路径上调用的原因。
- **读到的一定是某个完整的旧值或新值**，不会是半新半旧的撕裂值。
- 极端情况下读会**自旋重试**。写得极其频繁时，读方会被拖慢——这是属性风暴的次生影响之一。

### 2.3 写路径：串行经过 init

写完全是另一回事。普通进程没有权限直接改那块共享内存（它们是只读映射的），必须发请求给 init：

```
应用/服务
  → __system_property_set()
    → 连接 /dev/socket/property_service
      → init 的 property service
        → SELinux 权限检查
        → 更新共享内存（写方唯一，无需互斥）
        → 触发匹配的 property action
```

关键推论：

- **写是串行的**，全系统的属性写请求都排在 init 这一个点上。
- **写比读贵几个数量级**：一次 socket 往返 + 一次 SELinux 检查 + 可能的 action 排队。
- 这解释了 7.2 里提到的属性触发风暴为什么危险——每一次 `setprop` 都是对 init 主循环的一次打扰。

需要留意 AOSP 11 之后的一个改动：属性写请求的处理被移到了独立线程以避免阻塞 init 主循环，但**属性 action 的执行仍然回到主循环**。也就是说写请求本身不再卡住 init，但它触发的 action 依旧排队串行执行。

### 2.4 前缀语义

| 前缀 | 语义 | 注意点 |
|---|---|---|
| `ro.` | 只读，**只能设置一次** | 第二次设置会被拒绝并打日志，不是覆盖 |
| `persist.` | 持久化到 `/data/property/` | 依赖 `/data`，见 2.5 |
| `ctl.` | 控制命令，非存储 | `ctl.start` / `ctl.stop` / `ctl.restart` |
| `init.svc.<名>` | init 维护的服务状态 | 只读，值为 `stopped`/`running`/`restarting` |
| `sys.` | 系统运行时状态 | 如 `sys.boot_completed` |
| `vendor.` | vendor 分区专用 | Treble 要求 vendor 代码只用这个前缀 |
| `debug.` | 调试用 | 通常 user 版受限 |

`ctl.` 是最特别的一个——它不存值，而是当命令用：

```bash
setprop ctl.start mediaserver   # 等价于 init 里的 start mediaserver
setprop ctl.stop mediaserver
```

`adb shell start` / `stop` 本质就是设 `ctl.` 属性。**这是异步的**：`setprop ctl.start foo` 返回时 foo 通常还没起来，要确认得去轮询 `init.svc.foo`。把它当同步调用是很常见的错误，见案例 2。

### 2.5 persist 属性与 `/data` 的依赖

`persist.` 属性存在 `/data/property/` 下，于是产生一条硬依赖：**`/data` 没就绪，persist 属性就读不到**。

这正是 7.3 里 `on late-init` 序列中那一项的由来：

```bash
trigger post-fs-data              # /data 就绪
trigger load_persist_props_action # 才能加载 persist 属性
trigger zygote-start
```

顺序不能换。由此得到两个实用结论：

- **`post-fs-data` 之前的任何逻辑都不能依赖 `persist.` 属性**，那时它们全是空值。这类 bug 表现为「开机早期读到默认值，后期又变了」，行为随机不好复现。
- **清除 `/data` 会丢掉所有 persist 属性**。恢复出厂后某些定制行为失效，根因常在这里。

### 2.6 静默失败：新属性没在 property_contexts 里声明

这是 OEM 定制中最高频的一类属性问题，值得单独讲。

现象是：`setprop vendor.foo.bar 1` 命令返回成功，`getprop vendor.foo.bar` 却是空的。

原因是属性名没有匹配到任何 `property_contexts` 条目，或匹配到了但调用方的 SELinux 域没有写权限。此时 init 会拒绝这次写入，但 **`setprop` 命令行工具不一定把失败清楚地报给你**。

排查手段：

```bash
# 看属性的 SELinux 上下文；查不到上下文说明没声明
adb shell getprop -Z vendor.foo.bar

# 看有没有被 SELinux 拦下
adb shell dmesg | grep -i "avc.*property"
adb logcat | grep -iE "avc|property_service"
```

修复要同时做两件事，缺一不可：

1. 在对应分区的 `property_contexts` 里声明属性名及其上下文；
2. 在 sepolicy 里给调用方的域授予 `set_prop` 权限。

只做第一步是最常见的半吊子修法——属性有了上下文，但写它的进程依然被拒。SELinux 侧的详细排查见卷 1 第 5 章。

### 2.7 属性空间是有上限的

每个上下文文件的 `prop_area` 有固定大小（默认 128 KB 量级），装不下就会失败。

正常设备远用不完，但两种情况会撞上：

- **动态生成属性名**。比如按包名或按设备序列号拼出属性名，每个都占一个 trie 叶子，越跑越多。
- **测试或调试代码遗留的循环 setprop**。

表现为某个时刻起所有新属性都设不进去，日志里出现属性区域满的报错。排查时注意 `prop_area` 只增不减——**属性删不掉**，即使值设为空，trie 节点依然占位。

### 2.8 `wait_for_prop` 的等待方式

7.2 说过 `wait_for_prop` 无超时，这里补上它怎么等。

它不是轮询，而是基于属性区域里的**全局序列号 + futex 唤醒**：等待方在序列号上挂起，任何属性写入都会推进序列号并唤醒等待者，等待者醒来检查目标属性是否满足条件，不满足就继续挂起。

所以它的开销很低，**但也正因为低开销、无超时，它才敢被放在关键路径上，也才会在依赖不满足时无声地永久等待**。7.3 案例 2 里的 `wait_for_prop odsign.verification.done 1` 就是这种。

## 3. 关键产出

### SOP：排查 setprop 不生效

1. `getprop -Z <属性名>` 看上下文。取不到 → 没在 `property_contexts` 声明。
2. `dmesg | grep -i "avc.*property"` 看是否被 SELinux 拒绝。
3. 确认前缀语义：是不是 `ro.` 属性在尝试第二次设置。
4. 确认时机：是不是 `persist.` 属性在 `post-fs-data` 之前被读取。
5. 以上都排除后，查属性空间是否耗尽。

### SOP：确认服务是否真的起来了

不要依赖 `setprop ctl.start` 的返回：

```bash
setprop ctl.start my_service
# 轮询直到 running，或超时退出
for i in $(seq 1 50); do
    [ "$(getprop init.svc.my_service)" = "running" ] && break
    sleep 0.1
done
getprop init.svc.my_service
```

值为 `restarting` 说明服务在反复崩溃，转去查 SELinux 与依赖，而不是继续等。

### SOP：给新 vendor 属性做上线前检查

1. 属性名以 `vendor.` 开头（Treble 要求）。
2. 在 `vendor_property_contexts` 里声明。
3. sepolicy 里给写方域加 `set_prop`。
4. 刷机后 `getprop -Z` 确认上下文正确。
5. 用非 root 的实际调用方进程验证一次写入，不要只用 adb root 测——权限域不同。

## 4. 实战案例

### 案例 1：persist 属性在开机早期读到空值

**现象**：某定制功能开关用 `persist.vendor.feature.enabled` 控制，用户关掉后重启，功能在开机初期仍然生效几秒，之后才关闭。

**排查**：读该属性的代码位于一个在 `on post-fs` 阶段启动的服务里。

**根因**：`persist.` 属性要等 `load_persist_props_action`，而它排在 `post-fs-data` 之后。服务启动时读到空值，走了默认的「开启」分支；等属性真正加载进来，另一条监听逻辑才把它关掉。

**修复**：把该服务的启动时机后移到 `on boot`，并在读不到属性时选择保守默认值而非功能默认值。

**教训**：凡是读 `persist.` 的代码，都要问一句「它可能在 `/data` 就绪前被执行吗」。

### 案例 2：把 `ctl.start` 当同步调用，导致偶发初始化失败

**现象**：某厂测脚本约 5% 概率失败，报连不上服务的 socket。

**排查**：脚本里 `setprop ctl.start diag_service` 之后立刻就去连它的 socket。

**根因**：`ctl.` 是异步的，init 收到请求后 fork 服务，服务再自己创建 socket 并监听。在负载高的机器上这段耗时会拉长，超过脚本的隐含假设。

**修复**：改为轮询 `init.svc.diag_service` 到 `running`，再加一层对 socket 可连接性的重试。

**教训**：`init.svc.<名>` 变成 `running` 只表示**进程已被 fork 且未退出**，不表示它内部初始化完成。要严格同步，只能由服务自己置一个就绪属性，由调用方 `wait_for_prop` 等待。

## 5. Takeaway

- 读走共享内存、无锁无 IPC；写走 init socket、串行且带 SELinux 检查。读便宜，写贵。
- 属性文件按 SELinux 上下文切分，不是按属性切分——这是权限粒度的设计，也是静默失败的来源。
- 新属性必须同时做两件事：`property_contexts` 声明 + sepolicy 授权。只做一件是最常见的半吊子修法。
- `ro.` 只能设一次；`persist.` 依赖 `/data`，`post-fs-data` 之前一律读不到。
- `ctl.` 是异步命令。`init.svc.<名>` 为 `running` 只代表进程活着，不代表初始化完成。
- 属性只增不减，动态拼接属性名迟早撞上空间上限。
- `wait_for_prop` 基于序列号 + futex，开销低但无超时——低开销正是它敢被放在关键路径上的原因，也是它能无声挂死的原因。
