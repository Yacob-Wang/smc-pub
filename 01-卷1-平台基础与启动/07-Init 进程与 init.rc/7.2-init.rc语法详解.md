# 7.2 init.rc 语法：service / action / on / import

## 一句话开场

init.rc 是一门只有 **4 类顶层语句**（`on` / `service` / `import` / `subsystem`）的声明式小语言——但它跑在 PID 1 的单线程主循环里，**一条 `exec` 写错就能让整机开机卡住**。

## 1. 核心子问题

1. init.rc 到底有几个文件、按什么顺序加载？为什么改了 `/vendor/etc/init/` 却不生效？
2. 四类顶层语句各自解决什么问题？边界在哪？
3. `service` 段的选项集怎么记？哪些选项直接关系稳定性？
4. `on` 的触发器有几种？事件触发和属性触发的语义差别是什么？
5. `import` 为什么是**延迟解析**的？加载顺序怎么确定？
6. 内建命令里**哪些会阻塞 init 主循环**？这是启动性能的第一杀手。
7. 哪些写法会导致 boot loop？怎么在提交前就发现？
8. Parser 的实现模型（SectionParser）长什么样？出错时 init 是跳过还是崩？

## 2. 详细展开

### 2.1 文件布局与加载顺序

第一个反直觉的事实：**`/init.rc` 早就不存在了**。AOSP 9 起主脚本搬到了 `/system/etc/init/hw/init.rc`，其余按分区拆散。

`LoadBootScripts()`（`system/core/init/init.cpp`）决定了加载顺序：

```cpp
// path: system/core/init/init.cpp
// commit: android-14.0.0_r1
static void LoadBootScripts(ActionManager& action_manager, ServiceList& service_list) {
    Parser parser = CreateParser(action_manager, service_list);

    std::string bootscript = GetProperty("ro.boot.init_rc", "");
    if (bootscript.empty()) {
        parser.ParseConfig("/system/etc/init/hw/init.rc");
        if (!parser.ParseConfig("/system/etc/init")) {
            late_import_paths.emplace_back("/system/etc/init");
        }
        parser.ParseConfig("/system_ext/etc/init");
        if (!parser.ParseConfig("/vendor/etc/init")) {
            late_import_paths.emplace_back("/vendor/etc/init");
        }
        if (!parser.ParseConfig("/odm/etc/init")) {
            late_import_paths.emplace_back("/odm/etc/init");
        }
        if (!parser.ParseConfig("/product/etc/init")) {
            late_import_paths.emplace_back("/product/etc/init");
        }
    } else {
        parser.ParseConfig(bootscript);   // 调试用：cmdline 指定单一脚本
    }
}
```

| 顺序 | 路径 | 归属 | 挂载时机风险 |
|---|---|---|---|
| 1 | `/system/etc/init/hw/init.rc` | AOSP 主脚本 | 一阶段已挂载 |
| 2 | `/system/etc/init/` | 系统组件 | 一阶段已挂载 |
| 3 | `/system_ext/etc/init/` | 系统扩展 | 可能延后 |
| 4 | `/vendor/etc/init/` | vendor HAL | **可能尚未挂载** |
| 5 | `/odm/etc/init/` | ODM 定制 | **可能尚未挂载** |
| 6 | `/product/etc/init/` | 产品定制 | 可能延后 |

**`late_import_paths` 是这里最容易踩的坑**：如果解析时对应分区还没挂上（动态分区、A/B OTA 场景常见），init 不会报错，而是把路径塞进 `late_import_paths`，等 `mount_all` 完成后再补一次解析。后果是 **vendor 的 rc 文件生效时机比预期晚**，依赖它的 service 会在早期触发器里找不到。

> **🔴 警告**：`ro.boot.init_rc` 只用于调试。它一旦设置，上面 6 个路径**全部不加载**——设备只会跑你指定的那一个脚本。

同一目录内的文件按**文件名字典序**解析（`Parser::ParseConfigDir` 里显式 `std::sort`，对应 AOSP bug 31996208）。所以 `init.aaa.rc` 一定早于 `init.zzz.rc`。**不要依赖这个顺序表达依赖关系**——用触发器。

### 2.2 四类顶层语句

```
on <trigger> [&& <trigger>]*      # Action：一组按序执行的命令
    <command>
    <command>

service <name> <path> [<arg>]*    # Service：一个受 init 监管的进程
    <option>
    <option>

import <path>                     # Import：引入另一个 rc 文件或目录

subsystem <name>                  # 仅 ueventd.rc 使用，设备节点子系统
    <option>
```

四者的分工可以用一句话区分：**`service` 声明「有什么进程」，`on` 声明「什么时候做什么」，`import` 声明「还要读哪些文件」**。

语法层面还有三条通用规则：

- `#` 开头是注释；`\` 结尾续行
- 参数含空格要用 `"` 包起来
- 支持属性展开：`${ro.product.device}`，带默认值写 `${some.prop:-fallback}`

### 2.3 service 段：选项集与稳定性含义

`service` 的选项有 30 多个，按稳定性相关度分组记忆效率最高。

**第一组：身份与权限**

| 选项 | 作用 | 配错的后果 |
|---|---|---|
| `user <name>` | 运行用户 | 权限不足，服务反复重启 |
| `group <g> [<g>...]` | 附加组 | 访问设备节点失败 |
| `capabilities [<cap>...]` | Linux capability | 特权操作被拒 |
| `seclabel <label>` | SELinux 域 | **avc denied → 服务起不来** |

**第二组：生命周期**

| 选项 | 作用 | 稳定性含义 |
|---|---|---|
| `class <name>` | 归入服务类 | 决定被哪个 `class_start` 拉起 |
| `disabled` | 不随 class 自动启动 | 需显式 `start <name>` |
| `oneshot` | 退出后不重启 | **缺它 = 退出即重启，可能形成死循环** |
| `critical [window=N] [target=T]` | 关键服务 | 窗口期内反复挂 → **重启到 bootloader** |
| `restart_period <sec>` | 重启间隔 | 默认 5s，压制重启风暴 |
| `timeout_period <sec>` | 运行超时后杀掉 | 防止服务挂死 |
| `reboot_on_failure <target>` | 失败即重启整机 | 慎用 |
| `onrestart <command>` | 重启时附带执行 | 常用于联动重启 zygote |

**第三组：资源与优先级**

| 选项 | 作用 |
|---|---|
| `priority <nice>` | nice 值（-20 ~ 19） |
| `ioprio <class> <prio>` | IO 优先级（rt / be / idle） |
| `oom_score_adjust <v>` | LMK / OOM killer 权重 |
| `rlimit <res> <cur> <max>` | 资源上限 |
| `task_profiles <p> [<p>...]` | cgroup 归属（取代旧的 `writepid`） |
| `memcg.limit_in_bytes` 等 | memcg 限制 |

**第四组：通信端点**

| 选项 | 作用 |
|---|---|
| `socket <name> <type> <perm> [<u> [<g> [<seclabel>]]]` | 由 init 预创建 socket，服务通过 `ANDROID_SOCKET_<name>` 环境变量拿 fd |
| `file <path> <type>` | 预打开文件描述符 |
| `interface <iface> <instance>` | 声明提供的 HIDL/AIDL 接口，供 `interface_start` 使用 |

一个典型例子（zygote 的骨架，已精简）：

```
service zygote /system/bin/app_process64 -Xzygote /system/bin --zygote --start-system-server
    class main
    priority -20
    user root
    group root readproc reserved_disk
    socket zygote stream 660 root system
    socket usap_pool_primary stream 660 root system
    onrestart write /sys/power/state on
    onrestart restart audioserver
    onrestart restart media
    onrestart restart netd
    onrestart restart wificond
    task_profiles ProcessCapacityHigh MaxPerformance
    critical window=${zygote.critical_window.minute:-off} target=zygote-fatal
```

这段里有两个值得注意的设计：

- **`onrestart restart <x>` 链**：zygote 一旦重启，依赖它的一批服务必须跟着重启，否则会持有失效的 Binder 引用。这解释了为什么"zygote 挂一次，系统看起来像重启了一遍"。
- **`critical window=`**：zygote 反复崩溃时直接重启到 `zygote-fatal` 目标，避免设备停在半死不活的状态。

**服务状态的可观测性**：init 会为每个服务维护属性 `init.svc.<name>`，取值 `stopped` / `running` / `restarting`。这是排查服务起没起来的第一手段：

```bash
adb shell getprop | grep init.svc | grep -v stopped
```

### 2.4 action 段：事件触发与属性触发

`on` 后面跟触发器，触发器只有两类：

```
on early-init                          # 事件触发
on property:sys.boot_completed=1       # 属性触发
on boot && property:ro.debuggable=1    # 组合（事件 + 属性）
```

**组合规则很严格**：最多一个事件触发器，可以有任意多个属性触发器，用 `&&` 连接。**不支持 `||`，不支持否定**。想表达"或"只能写多个 `on` 段。

内建的启动事件触发器顺序（由 `SecondStageMain` 入队 + `init.rc` 里的 `trigger` 命令串联）：

```
early-init
    ↓
init
    ↓
late-init  ──┬─→ early-fs
             ├─→ fs                 (mount_all)
             ├─→ post-fs
             ├─→ late-fs            (mount_all --late)
             ├─→ post-fs-data       (/data 可用，加密解锁后)
             ├─→ zygote-start
             ├─→ early-boot
             └─→ boot
```

选错触发器是新手最常见的错误。三条经验规则：

| 你要做的事 | 该用的触发器 | 原因 |
|---|---|---|
| 写 `/sys` 节点、设内核参数 | `on early-init` / `on init` | 越早越好，不依赖文件系统 |
| 访问 `/data` | `on post-fs-data` | 之前 `/data` 未解密挂载 |
| 起需要网络/包管理的服务 | `on boot` 或更晚 | 依赖已就绪 |
| 开机完成后的收尾动作 | `on property:sys.boot_completed=1` | 不占用启动关键路径 |

**属性触发的语义**要特别注意：它是**边沿触发 + 启动时补齐**。属性每次变成目标值都会触发一次；init 解析完 rc 后也会检查当前值，已满足则立即入队。这意味着：

> **🟡 提示**：`on property:x=1` 的 action 可能在一次开机中被执行**多次**——只要属性被反复设成 1。所有属性触发的 action 都应当写成幂等的。

### 2.5 import：为什么是延迟解析

`import` 看起来像 C 的 `#include`，实际语义完全不同——**它不是就地展开，而是登记到队列，等当前文件解析完再处理**。

```cpp
// path: system/core/init/import_parser.cpp
// commit: android-14.0.0_r1
Result<void> ImportParser::ParseSection(std::vector<std::string>&& args,
                                        const std::string& filename, int line) {
    if (args.size() != 2) {
        return Error() << "single argument needed for import\n";
    }
    auto conf_file = ExpandProps(args[1]);
    if (!conf_file.ok()) {
        return Error() << "Could not expand import: " << conf_file.error();
    }
    LOG(INFO) << "Added '" << *conf_file << "' to import list";
    if (filename_.empty()) filename_ = filename;
    imports_.emplace_back(std::move(*conf_file), line);
    return {};
}

void ImportParser::EndFile() {
    auto current_imports = std::move(imports_);
    imports_.clear();
    for (const auto& [import, line_num] : current_imports) {
        parser_->ParseConfig(import);   // 当前文件解析完才递归进去
    }
}
```

三个直接后果：

1. **同一文件里 `import` 的位置无关紧要**——写在开头和结尾效果一样。
2. **被 import 的文件里的定义"晚于"当前文件**，但由于 action 靠触发器排序、service 靠 class 排序，这通常不影响行为。
3. `import` 支持属性展开，所以能写 `import /vendor/etc/init/hw/init.${ro.hardware}.rc` 这种按机型分流的写法。

### 2.6 内建命令：哪些会阻塞 init

这是本节**与启动性能最相关的部分**。init 主循环是单线程的：执行 action 里的命令时，它无法响应 epoll 事件，也无法回收退出的子进程。

常用命令按是否阻塞分类：

| 阻塞主循环 | 说明 | 非阻塞替代 |
|---|---|---|
| `exec <seclabel> [<user>...] -- <cmd>` | **fork 并等待退出**，最危险 | `exec_background` |
| `wait <path> [<timeout>]` | 等文件出现，默认超时 5s | 改用属性触发 |
| `wait_for_prop <name> <value>` | 等属性变成指定值，**无超时** | 改用 `on property:` |
| `mount_all <fstab> [--early\|--late]` | 挂载全部分区 | 拆分 early/late |
| `insmod [-f] <path> [<options>]` | 加载内核模块 | 延后到 `on boot` |
| `umount_all` / `swapon_all` | 同上 | — |

| 不阻塞 | 说明 |
|---|---|
| `start` / `stop` / `restart <service>` | 只改状态，实际 fork 在主循环里 |
| `class_start` / `class_stop` / `class_reset` | 批量操作服务类 |
| `setprop` / `write` / `chmod` / `chown` / `mkdir` | 快速 syscall |
| `trigger <event>` | 入队另一个触发器 |
| `exec_background` | fork 后不等待 |

> **🔴 警告**：`wait_for_prop` **没有超时**。如果目标属性因为某个服务启动失败而永远不会被设置，init 主循环就永久卡死——表现为开机停在某一帧，`adb` 也连不上。这是 OEM 定制里最典型的开机 hang 成因之一。

判断一条 action 是否在关键路径上，看它挂在哪个触发器下：`early-init` 到 `boot` 之间的全部算关键路径，`on property:sys.boot_completed=1` 之后的不算。

### 2.7 Parser 的实现模型

`Parser` 本身只做分词和分派，真正的语义交给注册的 `SectionParser`：

```cpp
// path: system/core/init/init.cpp
// commit: android-14.0.0_r1
Parser CreateParser(ActionManager& action_manager, ServiceList& service_list) {
    Parser parser;
    parser.AddSectionParser(
        "service", std::make_unique<ServiceParser>(&service_list, GetSubcontext(), std::nullopt));
    parser.AddSectionParser("on", std::make_unique<ActionParser>(&action_manager, GetSubcontext()));
    parser.AddSectionParser("import", std::make_unique<ImportParser>(&parser));
    return parser;
}
```

`SectionParser` 接口有四个回调，对应一个段的生命周期：

| 回调 | 时机 |
|---|---|
| `ParseSection` | 遇到段首行（`service foo /bin/foo`） |
| `ParseLineSection` | 段内每一行（选项或命令） |
| `EndSection` | 段结束（遇到下一个段首或文件尾） |
| `EndFile` | 整个文件解析完（`ImportParser` 在这里递归） |

**出错行为是理解排查手感的关键**：解析错误**不会让 init 崩溃**，只会 `LOG(ERROR)` 后跳过这一行或这一段，然后继续。所以一个拼错的选项名不会有任何显式失败，只是服务行为悄悄不对。

```bash
# 解析期的所有报错都在 kmsg 里，且只在开机早期出现
adb shell dmesg | grep -E "init: (Could not|error|Unable)"
```

### 2.8 会引发 boot loop 的四类写法

| 写法 | 后果 | 正确做法 |
|---|---|---|
| 服务缺 `oneshot`，且进程正常退出 | init 无限重启它，CPU 打满 | 一次性任务加 `oneshot` |
| `critical` 服务依赖尚未就绪的资源 | 窗口期内崩满次数 → 重启到 bootloader | 移到更晚的触发器，或去掉 `critical` |
| `wait_for_prop` 等一个永不出现的属性 | init 主循环永久阻塞 | 改 `on property:` 异步响应 |
| `on property:x=1` 的 action 里又 `setprop x 1` | 自触发死循环 | action 写成幂等，避免自赋值 |

## 3. 关键产出

### SOP：验证一个 rc 改动是否被正确解析

```bash
# 1. 确认文件被加载（解析期日志只在开机早期，必须重启后立刻抓）
adb reboot && adb wait-for-device
adb shell dmesg | grep -i "init:" | grep -iE "import|could not|error"

# 2. 确认 service 被注册（未注册则 getprop 无输出）
adb shell getprop init.svc.<your_service>
# stopped / running / restarting；无输出 = 根本没解析到

# 3. 确认服务实际在跑
adb shell ps -A | grep <your_service>

# 4. 手动拉起，观察是否立刻退出
adb shell start <your_service>
adb shell getprop init.svc.<your_service>
```

### SOP：定位一条 action 拖慢了启动

```bash
# 1. 抓开机 trace（init 的 action 执行有 atrace 埋点）
adb shell perfetto -o /data/misc/perfetto-traces/boot.pftrace \
    -t 30s -b 64mb sched freq idle am wm gfx view binder_driver

# 2. 看各触发器阶段耗时
adb shell getprop | grep -E "ro.boottime"

# 3. init 自身的耗时统计（AOSP 会把超过阈值的命令打到 kmsg）
adb shell dmesg | grep -E "init: Command .* took .*ms"
```

最后一条最实用：init 会把执行超时的内建命令主动打印出来，形如
`init: Command 'wait_for_prop vendor.foo.ready 1' action=boot ... took 8213ms`。
**开机慢的第一步永远是 grep 这一行。**

### SOP：确认服务的 SELinux 域是否配对

```bash
# 服务起不来但看不出原因时，先怀疑 seclabel
adb shell dmesg | grep avc | grep <your_service>
adb shell ps -AZ | grep <your_service>   # 看实际落到哪个域
```

## 4. 实战案例

### 案例 1：一条 `wait_for_prop` 让整机开机卡死 90s

**现象**：某 OEM 版本升级后，约 3% 的设备开机停在开机动画，90s 后自行恢复。

**定位**：
- `adb shell dmesg | grep "took"` 抓到
  `init: Command 'wait_for_prop vendor.sensors.ready 1' action=boot took 89732ms`
- 追 `vendor.sensors.ready` 的写入方，发现由 sensor HAL 在初始化完成后 `setprop`
- sensor HAL 在部分硬件批次上初始化失败，属性永远不写

**根因**：`on boot` 里用了阻塞式 `wait_for_prop` 等待一个**可能失败**的外部条件。init 主循环被独占，后续所有 action 与服务启动全部排队。90s 是上层的看门狗兜底重试时间，不是 `wait_for_prop` 自己超时——**它根本没有超时**。

**修复**：
- 把 `on boot` 里的 `wait_for_prop` 删掉
- 依赖 sensor 的动作改挂在 `on property:vendor.sensors.ready=1` 下
- sensor HAL 增加失败路径，失败时也写属性（写成 `0` 并另设错误码属性）

**Takeaway**：**关键路径上不放阻塞等待**。需要等待时，用属性触发把同步等待改写成异步响应。

### 案例 2：缺一个 `oneshot` 导致 CPU 常年多占 8%

**现象**：某定制版本待机功耗偏高，`top` 显示一个 vendor 的一次性配置脚本每秒都在出现。

**定位**：
- `adb shell getprop init.svc.vendor_cfg` 在 `running` / `restarting` 之间反复跳
- 该服务是个 shell 脚本，做完配置就正常 `exit 0`
- init 默认语义是「服务退出即重启」，于是它每 5 秒被拉起一次（`restart_period` 默认值）

**根因**：rc 里声明了 `service` 却没写 `oneshot`。作者以为「跑完就结束」，但 init 认为「服务不该退出」。

**修复**：加 `oneshot`。更彻底的做法是——一次性动作根本不该声明成 `service`，直接用 `on <trigger>` + `exec_background` 更合适。

**Takeaway**：`service` 表达的是**长期存在的进程**。一次性任务要么加 `oneshot`，要么别用 `service`。

## 5. Takeaway

1. **`/init.rc` 已不存在**，主脚本在 `/system/etc/init/hw/init.rc`，其余按 system_ext / vendor / odm / product 分区拆散。
2. **分区没挂上时解析会被推迟**到 `late_import_paths`——vendor rc 生效比预期晚是常见坑。
3. 同目录内按**文件名字典序**解析；不要用文件名表达依赖，用触发器。
4. 四类语句分工：`service` 说有什么进程，`on` 说何时做什么，`import` 说还读哪些文件，`subsystem` 只给 ueventd 用。
5. **`oneshot` 决定服务退出后是否重启**——漏写是重启风暴的头号成因。
6. **`critical` 服务反复崩溃会把设备重启到 bootloader**，加它之前先确认依赖已就绪。
7. 触发器**只支持 `&&`，不支持 `||` 和否定**；最多一个事件触发器 + 任意个属性触发器。
8. **属性触发是边沿触发且会重复执行**，所有属性 action 都必须幂等。
9. **`exec` / `wait` / `wait_for_prop` / `mount_all` / `insmod` 阻塞 init 单线程主循环**，其中 `wait_for_prop` 无超时，最危险。
10. **解析错误不会让 init 崩**，只 `LOG(ERROR)` 后跳过——拼错的选项名是静默失效的。
11. 排查开机慢的第一条命令：`dmesg | grep "init: Command .* took"`。
12. 排查服务起没起来的第一条命令：`getprop init.svc.<name>`。
