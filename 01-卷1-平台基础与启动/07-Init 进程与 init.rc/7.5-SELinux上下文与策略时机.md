## 一句话开场

SELinux 在 init 的**第二次 exec** 时就已加载完毕并进入 enforcing——这意味着从 `early-init` 开始的每一条命令、每一个服务都已经在策略约束之下，**「开机早期还没有 SELinux」是个常见的错误直觉**。

## 1. 核心子问题

1. 策略文件在哪几个分区？为什么要拆开？
2. 策略是编译好的还是开机现编的？现编要多久？
3. 加载发生在启动链路的哪一刻？在它之前 init 处于什么状态？
4. init 加载完策略后为什么要再 exec 一次自己？
5. 服务的 SELinux 域是怎么定的？`seclabel` 和文件上下文推导的优先级？
6. 一条 `avc: denied` 日志的六个字段分别怎么读？
7. 为什么有些 denial 不致命、有些直接 boot loop？
8. `restorecon` 在启动序列的哪一步跑？为什么 `/data` 的要单独跑？

## 2. 详细展开

### 2.1 策略为什么是拆开的

Treble 要求 system 和 vendor 能独立升级，策略也必须跟着拆：

```bash
adb shell ls /system/etc/selinux/
# plat_sepolicy.cil  plat_file_contexts  plat_property_contexts ...

adb shell ls /vendor/etc/selinux/
# vendor_sepolicy.cil  precompiled_sepolicy  vendor_file_contexts ...
```

分片大致是 `plat`（system）/ `system_ext` / `product` / `vendor` / `odm` 五份，各自用 CIL（Common Intermediate Language）描述，最终要合并成一份二进制策略交给内核。

**拆分带来的核心约束**：vendor 侧的策略不能引用 plat 侧的私有类型。这是 Treble 接口稳定性的要求，也是 OEM 最常撞墙的地方——想给自家服务开个访问 system 私有资源的口子，会在编译期被 neverallow 规则拦下。

### 2.2 预编译与现场编译

合并 CIL 是有成本的，所以 AOSP 做了缓存：

- **预编译命中**：vendor 分区里带一份 `precompiled_sepolicy`，同时带上编译时各分片的哈希。开机时 init 比对当前各分片的哈希，一致就直接加载这份二进制策略。
- **未命中则现场编译**：任一分片哈希对不上（典型场景是只 OTA 了 system 而 vendor 没动，或开发期单独刷了 system），就要在设备上跑一次 CIL 合并编译。

现场编译是**实打实的开机耗时**，在中低端机上可达数百毫秒到秒级。它的特征很好认：只在刷完某一个分区后的首次开机出现，之后恢复正常。把它误判成性能劣化是常见的乌龙——和 7.3 案例 2 的 odsign 是同一类现象。

### 2.3 加载时刻：init 的第二次 exec

7.1 讲过 init 会 exec 自己三次。第二次就是为 SELinux 准备的：

```cpp
// path: system/core/init/main.cpp
int main(int argc, char** argv) {
    // ...
    if (!strcmp(argv[1], "selinux_setup")) {
        return SetupSelinux(argv);
    }
    if (!strcmp(argv[1], "second_stage")) {
        return SecondStageMain(argc, argv);
    }
    // ...
}
```

`SetupSelinux()` 做完策略加载后，做了一件关键的事：

```cpp
// path: system/core/init/selinux.cpp（概念流程）
// 1. 读取并合并各分区策略分片
// 2. 通过 selinux_android_load_policy 交给内核
// 3. 用 setexeccon 把下一次 exec 的目标域设为 u:r:init:s0
// 4. exec 自己，argv[1] = "second_stage"
```

**为什么必须再 exec 一次**：进程的安全上下文在 `execve` 时才会发生转换。init 在加载策略前跑在 kernel 初始域里，只有重新 exec 一次，它才能真正落到 `u:r:init:s0` 这个域上。加载完策略却不 exec，init 自己就成了策略之外的例外。

**时序推论**：这一切发生在 `SecondStageMain()` 之前，而 `early-init` 事件是在 `SecondStageMain()` 里才排队的。所以——

> 从 `early-init` 开始，所有 rc 命令与服务都已运行在 enforcing 的策略之下。

### 2.4 服务域是怎么定的：两条路径

一个由 init 拉起的服务，最终跑在哪个域，有两种确定方式。

**路径一：rc 里显式写 `seclabel`**

```bash
service my_daemon /vendor/bin/my_daemon
    class main
    seclabel u:r:my_daemon:s0
```

显式指定，优先级最高。多用于那些可执行文件位置特殊、或需要精确控制的场景。

**路径二：不写 `seclabel`，由可执行文件的上下文推导**

这是绝大多数服务的方式。内核在 `execve` 时按策略里的 `type_transition` 规则做转换：

```
源域（init）+ 目标文件类型（my_daemon_exec）
    → type_transition → 新域（my_daemon）
```

对应的策略写法：

```
# file_contexts 里给可执行文件打类型
/vendor/bin/my_daemon    u:object_r:my_daemon_exec:s0

# te 文件里声明域并建立转换
type my_daemon, domain;
type my_daemon_exec, exec_type, vendor_file_type, file_type;
init_daemon_domain(my_daemon)
```

**最高频的故障就出在这条路径上**：`file_contexts` 漏了那一行，或者刷机后文件上下文没被正确应用。此时可执行文件的类型不是 `my_daemon_exec`，`type_transition` 匹配不上，**服务会继承 init 的域跑在 `u:r:init:s0` 里**。

这个后果很微妙：它不是「起不来」，而是**起来了但域不对**。短期看可能一切正常（init 域权限很大），但策略里针对 `my_daemon` 写的规则一条都不生效，而 neverallow 检查又可能在别处炸掉。排查时必须养成习惯：

```bash
adb shell ps -Z | grep my_daemon
# 期望看到 u:r:my_daemon:s0
# 若是 u:r:init:s0 —— file_contexts 有问题
```

### 2.5 读懂一行 avc denied

```
avc: denied { read write } for pid=1234 comm="my_daemon"
    name="foo" dev="dm-5" ino=98765
    scontext=u:r:my_daemon:s0
    tcontext=u:object_r:vendor_data_file:s0
    tclass=file permissive=0
```

按这个顺序读：

| 字段 | 含义 | 用途 |
|---|---|---|
| `{ read write }` | 被拒的权限 | 要授予什么 |
| `comm=` | 进程名 | 谁在访问 |
| `scontext=` | 源域 | **主语**：谁 |
| `tcontext=` | 目标上下文 | **宾语**：访问什么 |
| `tclass=` | 客体类别 | file / dir / sock_file / property_service 等 |
| `permissive=0` | 是否被真正拦截 | 0 = 已拦截，1 = 仅记录 |

拼成一句话就是策略规则本身：

```
allow my_daemon vendor_data_file:file { read write };
```

`audit2allow` 就是干这个的机械转换。但**不要直接采信它的输出**——它只会照抄 denial，不判断这个访问是否本就不该发生。正确顺序是先问「为什么要访问这个」，再决定是加规则还是改代码。

两个采集渠道：

```bash
adb shell dmesg | grep avc              # 内核环形缓冲，会被冲掉
adb logcat -b events | grep avc         # 更完整，但需要 auditd 在跑
```

开机早期的 denial 只能靠 `dmesg` 或 `pstore`，因为那时 logd 还没起来。

### 2.6 哪些 denial 会致命

不是所有 denial 都要立刻修，但有几类必须优先：

- **`critical` 服务的 denial**。7.2 讲过 `critical` 服务反复失败会触发重启进 bootloader，直接 boot loop。
- **`post-fs-data` 依赖链上的 denial**。KeyMint 等 HAL 被拦，`/data` 解密不了，卡在 7.3 说的那个高频点。
- **属性写被拒**（`tclass=property_service`）。表现为 7.4 讲的静默失败，最难查——没有任何功能报错，只是值没变。

相对不急的是那些运行期偶发、且有降级路径的 denial，但它们仍然是噪声源，会淹没真正重要的告警。

### 2.7 restorecon 与 `/data`

策略里的 `file_contexts` 描述「文件应该是什么上下文」，但已经躺在磁盘上的文件不会自动更新，需要 `restorecon` 把标签刷上去。

系统分区是只读的，上下文在构建镜像时就打好了。**`/data` 是可写的，必须在运行时刷**——这就是它要在 `post-fs-data` 阶段处理的原因：

```bash
on post-fs-data
    # /data 已挂载解密，此时才能刷标签
    restorecon_recursive /data
    ...
```

两个实践要点：

- `restorecon_recursive /data` 在文件数极多时很慢，是 7.3 提到的 `post-fs-data` 变慢成因之一。
- OTA 修改了 `file_contexts` 后，首次开机需要刷更多文件，比平常慢——又一个「首启慢是正常的」场景。

## 3. 关键产出

### SOP：新增一个 vendor 服务的 SELinux 检查清单

1. `file_contexts` 里给可执行文件声明 `*_exec` 类型。
2. te 文件里 `type` 声明域 + `init_daemon_domain()` 建立转换。
3. 刷机后 `ps -Z | grep <服务名>`，确认域是 `u:r:<域名>:s0` 而非 `u:r:init:s0`。
4. `ls -Z /vendor/bin/<可执行文件>`，确认类型是 `*_exec`。
5. 跑一遍完整功能，`dmesg | grep avc` 收集 denial。
6. 逐条判断 denial 的合理性后再补规则，不要直接套 `audit2allow` 输出。

### SOP：定位开机期的 avc denied

1. 能进 adb：`adb shell dmesg | grep avc`。进不去：取 pstore / last_kmsg（卷 1 第 4 章）。
2. 按 `scontext` 分组，先看 init 域和各 HAL 域的。
3. 对每条确认 `tclass`：`property_service` 归 7.4 的排查路径，`file`/`dir` 走文件上下文排查。
4. 结合 7.3 的阶段定位，判断这条 denial 是否落在关键路径上。

### SOP：临时排除 SELinux 因素

仅限 userdebug / eng 版本，用于快速验证「是不是 SELinux 导致的」：

```bash
adb shell setenforce 0      # 临时转 permissive，重启失效
adb shell getenforce        # 确认当前模式
```

转 permissive 后问题消失，即可确认是策略问题。**这只是判定手段，不是修复手段**——permissive 下 denial 仍会被记录，正好用来一次性收齐所有需要补的规则。

## 4. 实战案例

### 案例 1：服务跑在 init 域，问题在三个月后才暴露

**现象**：某 vendor 服务上线三个月一直正常，某次 system 侧升级后突然大量功能失效。

**排查**：`ps -Z` 显示它跑在 `u:r:init:s0`。

**根因**：`file_contexts` 里漏了该可执行文件的条目，域转换从未发生。它一直借着 init 域的宽松权限运行，所以功能正常。system 升级收紧了 init 域的部分权限后，这些访问才开始被拒。

**修复**：补 `file_contexts` 条目与 `init_daemon_domain()`，把服务落到自己的域，再按实际需要补最小权限集。

**教训**：功能正常不等于配置正确。`ps -Z` 应当进入新服务的上线检查清单——这类问题的潜伏期可以很长，而爆发时机往往在升级后，最难归因。

### 案例 2：属性写被拒，表现为一个完全无关的功能异常

**现象**：某机型的省电策略偶发不生效，日志里查不到任何报错。

**排查**：顺着代码找到策略生效依赖 `vendor.power.mode` 这个属性，实测 `getprop` 一直是空。回到 `dmesg`，找到 `avc: denied { set } ... tclass=property_service`。

**根因**：属性在 `vendor_property_contexts` 里声明了，但写它的进程所在域没有 `set_prop` 权限——正是 7.4 说的那个「半吊子修法」。

**修复**：给该域补 `set_prop` 权限。

**教训**：SELinux 的失败大量是**静默**的。功能异常但日志干净时，把 `dmesg | grep avc` 作为固定动作，而不是等到怀疑 SELinux 才去看。

## 5. Takeaway

- 策略在 init 第二次 exec（`SetupSelinux`）时加载完成，早于 `early-init`。**开机全程都在 enforcing 之下**。
- 加载后必须 exec 自己，因为安全上下文只在 `execve` 时转换。
- 服务域两条路径：`seclabel` 显式指定，或由可执行文件的 `*_exec` 类型经 `type_transition` 推导。后者漏配的后果是服务**继承 init 域**——不报错、但策略全部失效。
- `ps -Z` 确认域，`ls -Z` 确认文件类型，这两条应当进上线检查清单。
- avc denial 读法：`scontext` 是主语，`tcontext` 是宾语，`tclass` 是客体类别，拼起来就是 allow 规则。
- `audit2allow` 只做机械转换，不判断访问是否合理，输出必须人工过一遍。
- 致命的 denial 有三类：`critical` 服务的、`post-fs-data` 依赖链上的、以及 `tclass=property_service` 的静默失败。
- 预编译策略未命中会在设备上现场编译，和 odsign、restorecon 一样，都属于「首启慢是正常的」范畴。
