# 11.1 开机时间的测量与阶段拆分:bootchart / bootstat / Perfetto boot trace

## 一句话开场

**4 类开机时间测量工具**(bootchart / bootstat / Perfetto boot trace / dumpsys + last_kmsg)各自适用场景不同——bootchart 看系统级 timeline / bootstat 看 10+ 个 ro.boottime.* / Perfetto 看跨进程 trace / dumpsys + last_kmsg 看崩现场。**4 类工具配合 = 30 秒定位"开机慢 5 秒"的具体根因**。

## 1. 核心子问题

1. **bootchart** 是什么?它能看什么?
2. **bootstat** 的 10+ 个 ro.boottime.* 时间点怎么读?
3. **Perfetto boot trace** 怎么抓?怎么读?
4. **dumpsys bootstat** 和 **dumpsys activity processes** 怎么配合?
5. **`adb pull /sys/fs/pstore/console-ramoops`** 怎么用(last_kmsg)?
6. **30 秒定位 SOP** 怎么走?4 类工具怎么配合?
7. **5 个阶段拆分的标准基线**(Bootloader / Kernel / Init / Zygote / SystemServer)各自耗时?
8. AOSP 17 vs AOSP 14 的测量工具差异?

## 2. 详细展开

### 2.1 开机时间 5 个阶段:从硬件上电到桌面

**"开机时间"是 5 个阶段的总和**,本节给 5 个阶段的标准基线和"在哪个阶段慢"的归因:

```
[5 个阶段]
 1. Bootloader(Power On → Kernel 入口)
   ro.boottime.init 上游
   ↓
 2. Kernel(head.S → start_kernel → /init 启动)
   ro.boottime.init (Unix epoch)
   ↓
 3. Init(/init → main → LoadBootScripts → 关键 action)
   ro.boottime.zygote (init 启动 zygote 完)
   ↓
 4. Zygote + SystemServer(app_process → fork system_server → 50+ 服务)
   ro.boottime.system_server
   ro.boottime.ams_ready
   ro.boottime.wms
   ro.boottime.ims
   ↓
 5. Launcher(选 home app → fork Launcher → fallback home → 桌面 ready → boot_completed)
   ro.boottime.first_frame_drawn
   ro.boottime.boot_completed
```

**5 个阶段的标准基线**(SM8550,AOSP 17 默认配置):

| 阶段 | 标准基线 | 异常阈值 | 典型根因 |
|---|---|---|---|
| Bootloader | 1-3s | > 5s | AVB 校验 / OEM logo 慢 |
| Kernel | 1-3s | > 5s | 内核 initcall 慢 / mount 慢 |
| Init | 1-3s | > 5s | init.rc action 卡死 / odsign 等待 |
| Zygote + SystemServer | 2-4s | > 6s | preload 慢 / 服务启动慢 |
| Launcher + boot_completed | 2-5s | > 8s | PMS 扫描 / 第三方 SDK 自启 |
| **总耗时** | **7-18s** | **> 25s** | 多个阶段慢叠加 |

**对读者有什么用**:
- **"开机慢 X 秒"先定位在哪个阶段**——用 `ro.boottime.*` 差值
- **总耗时 18s 内是健康**——> 25s 是"用户能感知的慢"
- **每个阶段慢的根因不一样**——不能用同一个 SOP 修

### 2.2 工具 1:bootchart(系统级 timeline)

**bootchart** 是 AOSP 自带的系统级启动 timeline 工具——把"哪个进程在哪个时间点做了什么事"画成一张图。

**bootchart 的工作机制**:

```
[内核启动]
内核启动时,bootchart 在 /proc 写 2 个采样文件
  /proc/bootchart/header  ← 时间戳 + CPU 频率
  /proc/bootchart/entries ← 进程/线程采样事件
  ↓
[init 启动]
init 进程在 init.rc 启动时启用 bootchart
  on boot
    write /proc/bootchart/stop 0  ← 启动采样
  on property:sys.boot_completed=1
    write /proc/bootchart/stop 1  ← 停止采样
  ↓
[boot_completed]
停止采样
  ↓
[采集工具]
bootchart 工具把采样数据转换为 SVG / HTML
  system/core/init/bootchart.cpp + tools/bootchart/
  ↓
[输出]
bootchart.svg / bootchart.html
```

**bootchart 的典型输出图**:

```
┌────────────────────────────────────────────────────────┐
│          Bootloader        Kernel          Init         │  ← 时间线
│  ████                  █████              █████        │
│  ████                  █████              █████        │
│  ──────────────────────────────────────────────────────  │
│          Zygote          SystemServer      Launcher     │
│                    ████████                            │
│                    ████████                            │
│                    ────────────                        │
│                    ████████                            │
│  CPU: 100% / 80% / 60% / 40% / 20%  ← CPU 利用率          │
└────────────────────────────────────────────────────────┘
```

**bootchart 启用方法**(OEM / userdebug build):

```bash
# 1. userdebug build
adb root
adb shell setprop persist.sys.bootchart true

# 2. 重启
adb reboot

# 3. 等到 boot_completed
adb wait-for-device
adb shell while [[ -z $(getprop sys.boot_completed) ]]; do sleep 1; done

# 4. 拉取采样数据
adb shell ls -la /data/bootchart/
# 输出:tps.txt  ps.txt  pkglog

# 5. 用工具生成 SVG
host $ tools/bootchart/parser.py
# 输出:bootchart.svg
```

**对读者有什么用**:
- **bootchart 是"全局视角"**——能看 5 个阶段总耗时 + CPU 利用率
- **适合 lab 复现**——不能线上抓(占用存储)
- **看 CPU 利用率**——能定位 IO 阻塞 / CPU 争抢
- **详细工具**——11 章 D03 详述

### 2.3 工具 2:bootstat(ro.boottime.* 埋点)

**bootstat** 是 AOSP 系统的"启动时间埋点"——把 10+ 个关键时间点写到 ro.boottime.* system property。

**bootstat 的 10+ 个时间点**:

| 时间点 | 写入者 | 含义 |
|---|---|---|
| `ro.boottime.init` | init 进程 | init 进程启动时间 |
| `ro.boottime.servicemanager` | init | servicemanager 启动时间 |
| `ro.boottime.zygote` | init | zygote 启动时间 |
| `ro.boottime.zygote64` | init | 64-bit zygote 启动时间 |
| `ro.boottime.system_server` | SystemServer | system_server fork 时间 |
| `ro.boottime.pms` | PackageManagerService | PMS 第一次扫描完成 |
| `ro.boottime.ams_ready` | ActivityManagerService | AMS systemReady() |
| `ro.boottime.wms` | WindowManagerService | WMS 启动完成 |
| `ro.boottime.ims` | InputManagerService | IMS 启动完成 |
| `ro.boottime.first_frame_drawn` | WindowManagerService | 第一帧上屏 |
| `ro.boottime.boot_completed` | ActivityManagerService | boot_completed 写入 |
| `ro.boottime.launcher` | Launcher | Launcher Activity 起来 |
| `ro.boottime.locked` | ActivityManagerService | 锁屏状态 |

**bootstat 的命令行**:

```bash
# 1. 看所有时间点
adb shell getprop | grep boottime
# 期望:13 行左右输出

# 2. dumpsys bootstat
adb shell dumpsys bootstat
# 输出:ro.boottime.* + 历史数据(last 5 boots)

# 3. dumpsys bootstat --reset
adb shell dumpsys bootstat --reset
# 重置 bootstat(仅 OEM 用)

# 4. dumpsys bootstat --historian
# 启动 bootstat historian(Grafana,详细分析)
```

**bootstat 差值归因**:

```bash
# 1. 总耗时
TOTAL=$(adb shell getprop ro.boottime.boot_completed - $(adb shell getprop ro.boottime.init))

# 2. Zygote fork 耗时
ZYGOTE=$(adb shell getprop ro.boottime.zygote - $(adb shell getprop ro.boottime.init))

# 3. SystemServer 启动耗时
SYSTEM=$(adb shell getprop ro.boottime.ams_ready - $(adb shell getprop ro.boottime.system_server))

# 4. Launcher 启动耗时
LAUNCHER=$(adb shell getprop ro.boottime.boot_completed - $(adb shell getprop ro.boottime.first_frame_drawn))
```

**对读者有什么用**:
- **bootstat 是"30 秒定位"的第一步**——一行命令看 13 个时间点
- **差值归因**——哪个阶段慢一目了然
- **dumpsys bootstat 看历史**——最近 5 次启动的对比
- **详细使用**——9.5 §2.2 详述

### 2.4 工具 3:Perfetto boot trace(跨进程 trace)

**Perfetto** 是 Android 11+ 的新一代 trace 工具——能抓**跨进程**全栈 trace,包括 init / zygote / system_server / Launcher。

**Perfetto boot trace 抓取命令**:

```bash
# 1. 后台抓 30 秒 boot trace
adb shell perfetto -o /data/local/tmp/boot_trace.pb -t 30s \
  -c system/core/init/boot_traces.cfg \
  sched freq idle am wm view gfx info ss

# 2. 拉取 trace
adb pull /data/local/tmp/boot_trace.pb

# 3. 在 Perfetto UI 打开
# https://ui.perfetto.dev
# 加载 boot_trace.pb

# 4. 看 5 个阶段的 trace
# 5. 看每个进程的 CPU / 线程
# 6. 看每个服务的启动时间
```

**boot_traces.cfg**(AOSP 内置配置):

```
# path: system/core/init/boot_traces.cfg
# 5 个 trace category:
sched: {
  # 进程调度
}
freq: {
  # CPU 频率
}
idle: {
  # CPU idle 状态
}
am: {
  # ActivityManagerService 事件
}
wm: {
  # WindowManagerService 事件
}
```

**Perfetto 关键事件**(按 5 阶段):

| 阶段 | 关键事件 | 含义 |
|---|---|---|
| Bootloader | 无 Perfetto | bootchart 才有 |
| Kernel | `sched:sched_process_exec` | 进程启动 |
| Init | `am:am_create_task` | 任务栈创建 |
| Zygote | `am:am_proc_start` | 进程 fork 开始 |
| SystemServer | `am:am_proc_bound` | 进程 attach |
| Launcher | `am:am_create_activity` | Activity onCreate |
| Boot Completed | `am:Displayed` | 第一帧显示 |

**对读者有什么用**:
- **Perfetto 是"最细的测量"**——跨进程 + 详细 + 可视化
- **抓 trace 一次 30 秒**——线上不抓(影响性能)
- **适合 lab 复现 + 深度调查**——11 章 D01 详述

### 2.5 工具 4:dumpsys + last_kmsg(崩现场 + 当前状态)

**dumpsys** 是 Android 的"全系统状态"查询工具——能看 system_server / bootstat / activity / window 等所有服务状态。

**dumpsys 关键命令**(开机调查 4 件套):

```bash
# 1. dumpsys bootstat
adb shell dumpsys bootstat
# 期望:ro.boottime.* 时间点 + 历史数据

# 2. dumpsys activity activities
adb shell dumpsys activity activities | head -100
# 期望:ActivityRecord + FallbackHome + Launcher 状态

# 3. dumpsys activity processes
adb shell dumpsys activity processes | head -100
# 期望:ProcessRecord + 启动类型(COLD/WARM/HOT)

# 4. dumpsys package
adb shell dumpsys package | head -50
# 期望:Package 列表 + BOOT_COMPLETED receiver 数量
```

**last_kmsg**(内核 + 早期 init 日志):

```bash
# 1. 拉取 last_kmsg(内核侧 + 早期 init 侧)
adb pull /sys/fs/pstore/console-ramoops
# 输出:last_kmsg.txt

# 2. 关键日志
grep -E "init:|zygote:|system_server" last_kmsg.txt

# 3. 看内核 panic / oom
grep -E "Kernel panic|Out of memory" last_kmsg.txt
```

**对读者有什么用**:
- **dumpsys 是"当前状态"**——看哪些服务在跑 / 哪些包没 ready
- **last_kmsg 是"崩现场"**——如果系统崩了,这里有最早的错误日志
- **4 件套配合**——dumpsys bootstat(时间点) + dumpsys activity(进程) + dumpsys package(包) + last_kmsg(崩现场)

### 2.6 30 秒定位 SOP(关键!)

**"开机慢 5 秒"30 秒定位 SOP**:

```
[T0] 用户报告"开机慢 5 秒"
  ↓
[1] adb shell getprop | grep boottime(5 秒)
  - 输出 13 个时间点
  - 算总耗时 boot_completed - init
  - 算各阶段差值(7.1 算)
  - **第一步定位:在哪个阶段慢**
  ↓
[2] adb shell dumpsys bootstat(3 秒)
  - 看历史数据(最近 5 次启动)
  - 看本次启动时间点是否异常
  ↓
[3] adb shell dumpsys activity activities(3 秒)
  - 看 FallbackHome 是否在跑(launcher 没 ready?)
  - 看 launcher 进程状态
  ↓
[4] 抓 Perfetto boot trace(10 秒,后台)
  - adb shell perfetto -o /data/local/tmp/trace.pb -t 30s ...
  - adb pull /data/local/tmp/trace.pb
  - 加载到 Perfetto UI
  - **第二步定位:具体哪个服务/哪个函数慢**
  ↓
[5] adb shell dumpsys package(3 秒)
  - 看 BOOT_COMPLETED receiver 数量
  - 看 Package 列表
  ↓
[6] adb pull /sys/fs/pstore/console-ramoops(3 秒,仅在崩场景)
  - last_kmsg 找 panic / oom
  ↓
[T30] 完成定位
  - 慢在 Bootloader → 6.x
  - 慢在 Kernel → 6.x
  - 慢在 Init → 7.x
  - 慢在 Zygote / SystemServer → 8.x / 9.x
  - 慢在 Launcher / boot_completed → 10.0
  - 慢在资源峰值 → 11.6
```

**对读者有什么用**:
- **30 秒定位"开机慢"的根因**——4 类工具配合
- **每个阶段慢的归因**——6-10 章 + 11.6 各有 30 秒 SOP
- **Perfetto 跨进程**——能看 init / zygote / system_server / Launcher 全部细节

### 2.7 4 类工具的对比与选择

| 工具 | 适用场景 | 输出粒度 | 性能影响 | 落地难度 |
|---|---|---|---|---|
| **bootchart** | lab 复现 + 全局视角 | 系统级 timeline | 中(占用存储) | 中(需 userdebug) |
| **bootstat** | 线上快速归因 | 13 个时间点 | 极小 | 极小(一行命令) |
| **Perfetto boot trace** | lab 深度调查 | 跨进程 + 详细 | 大(几 MB) | 大(需 host UI) |
| **dumpsys + last_kmsg** | 当前状态 + 崩现场 | 状态 + 日志 | 极小 | 极小 |

**工具选择原则**:

```
"开机慢"用户报告
  ↓
线上 / 量产?
  ├─ 线上 → bootstat(5 秒)
  └─ lab → bootchart + Perfetto
  ↓
看哪个阶段慢?
  ├─ Bootloader / Kernel → 看 last_kmsg
  ├─ Init → 看 init.rc 日志
  ├─ Zygote / SystemServer → 看 Perfetto + 8.x 9.x
  ├─ Launcher / boot_completed → 看 dumpsys activity + 10.0
  └─ 资源峰值 → 看 Perfetto + 11.6
```

### 2.8 AOSP 17 vs AOSP 14 的测量工具差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| bootstat ro.boottime.* | 11 个 | 13 个 | +2 (locked / launcher) |
| Perfetto 支持 | 稳定 | 稳定 + 增强 | +boot_traces.cfg |
| bootchart 工具 | 稳定 | 稳定 | 无变化 |
| dumpsys bootstat 字段 | 30 | 35 | +5 |
| 线上 bootstat 写入开销 | 极小 | 极小 | 无变化 |
| Perfetto trace 文件大小 | 5-50 MB | 5-50 MB | 无变化 |

## 4. 实战案例

### 案例 1:某设备 boot time 慢 10s,30 秒 SOP 定位到 PMS 第一次扫描阻塞(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:用户装某第三方 App(代号 TestApp)后,首次开机 28s(基线 18s)

**30 秒定位过程**:

**T5:bootstat**(5 秒):

$ adb shell getprop | grep boottime

```

**结论**:`init → pms` 差值 6.1s 异常——PMS 第一次扫描慢。

```

- `init → pms` 差值 6.1s = PMS.scanDirTracedLI 5.8s

- PMS 第一次扫描 TestApp apk 5.0s(9.3 §2.1 详述 rollback 校验)

- PMS 扫描优化(9.3 §2.1)
- 第三方 SDK 自启 OEM 批次启动优化(10.0 §2.7)
- 预估可降 10s → 18s(基线)

### 案例 2:某设备 boot time 慢 5s,30 秒 SOP 定位到 IO 争抢(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:某品牌中端机(代号 eagle,4GB RAM)
- 复现步骤:用户首次开机 23s(基线 18s)

**30 秒定位过程**:

**T5:bootstat**(5 秒):
```bash
$ adb shell getprop | grep boottime
[ro.boottime.init]: [1738234567.890]
[ro.boottime.zygote]: [1738234569.000]    ← 1.1s(基线 0.5-1s,稍长)
[ro.boottime.system_server]: [1738234570.500]
[ro.boottime.pms]: [1738234573.000]    ← 2.5s(基线 1-2s,稍长)
[ro.boottime.ams_ready]: [1738234574.000]
[ro.boottime.first_frame_drawn]: [1738234578.000]
[ro.boottime.boot_completed]: [1738234582.000]  ← 整机 14.1s

# 差值:
# init → zygote: 1.1s (稍长)
# zygote → system_server: 1.5s (正常)
# system_server → pms: 2.5s (稍长)
# pms → ams_ready: 1.0s (正常)
# ams_ready → first_frame_drawn: 4.0s (基线 2-3s,长)
# first_frame_drawn → boot_completed: 4.0s (基线 1-3s,稍长)
```

**结论**:多阶段都稍长,总耗时 14.1s vs 基线 18s 少 4s(实际慢 5s 来自分布)。

**T8:dumpsys bootstat**(3 秒):
```bash
$ adb shell dumpsys bootstat | head -50
# 列出 13 个时间点
# 历史对比:本次启动比上次启动慢 5s
```

**T11:dumpsys activity activities**(3 秒):
- 列出 ProcessRecord 50+,发现 8 个 process IO wait 高

**T21:Perfetto boot trace**(10 秒):
```
SystemServer 启动期:
  - iowait: 4.0s (总 IO 等待)
  - reads on /system: 3.5s
  - reads on /data: 0.5s
Init 启动期:
  - reads on /system: 1.5s
```

**T24:dumpsys package**(3 秒):
```bash
$ adb shell dumpsys package | wc -l
5000  ← 5000 行包列表
$ adb shell pm list packages | wc -l
450  ← 450 个包
```

**T30:定位结论**:
- 多阶段都稍长 = IO 争抢(系统级)
- iowait 4s + 5000 行 package 列表 = IO 读取慢
- **根因**:eMMC / UFS IO 性能不足 + 大量包读取

**根因**:
- 4GB 设备 + eMMC 5.1 + 450 包 = IO 性能不足
- reads on /system 3.5s 主导
- 修复方法:换 UFS 3.1 / 减少包数 / 优化 IO 调度器

**修复**:
- 短期:eMMC → UFS 升级
- 中期:预加载关键 dex(8.3 详述)
- 长期:优化 IO 调度器 + 减少开机期 IO

**修复原理**:
- **多阶段都稍长 = IO 争抢**——不是单点慢
- 4GB + eMMC + 大量包 = 经典 IO 性能问题
- 这是 11.6 § 详述的"开机期 IO 争抢治理"场景

## 5. Takeaway

1. **4 类测量工具**(bootchart / bootstat / Perfetto / dumpsys + last_kmsg)各自适用场景不同——**4 类配合 = 30 秒定位"开机慢"**。
2. **5 个阶段标准基线**(Bootloader 1-3s / Kernel 1-3s / Init 1-3s / Zygote+SystemServer 2-4s / Launcher+boot_completed 2-5s),**总耗时 7-18s 是健康**。
3. **bootstat 是 30 秒定位的第一步**——一行命令看 13 个时间点,差值归因"哪个阶段慢"。
4. **bootchart 是 lab 全局视角**——用户级 timeline,看 CPU 利用率,适合复现。
5. **Perfetto boot trace 是 lab 深度调查**——跨进程 + 详细,看具体哪个服务/哪个函数慢。
6. **dumpsys + last_kmsg 是当前状态 + 崩现场**——线上用 dumpsys,崩了用 last_kmsg。
7. **"开机慢 5 秒"通常不是单点慢**——多阶段都稍长 = IO 争抢(案例 2);单阶段特别慢 = 具体服务/具体函数(案例 1)。
8. **AOSP 17 vs AOSP 14 的差异**:`ro.boottime.*` 11 → 13 +locked / launcher;`dumpsys bootstat` 30 → 35 字段;Perfetto 稳定。
