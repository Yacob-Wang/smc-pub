# 11.6 开机期资源峰值:内存 / IO / CPU 争抢治理

## 一句话开场

开机期是 Android 系统中**资源最紧张的时间窗口**——SystemServer 启动期内存峰值可达 1.5-2GB、IO 突发读可达 200-500 MB/s、CPU 8 核全开,任何一个资源被挤占都会拖慢开机或引发稳定性问题。本节讲清 3 类资源(内存 / IO / CPU)各自的峰值特征、争抢检测与治理手段。

## 1. 核心子问题

本节回答以下 8 个问题:

1. **开机期内存峰值**多大?AOSP 17 实测 1.5-2GB(8GB 设备),包含 framework + system_server + zygote + 多个 service
2. **LMKD 触发**是什么?`updateOomLevels` 计算 adj 0-15 进程的内存阈值,内存达到阈值触发杀进程
3. **内存争抢**的根因?SystemServer 内部 service 内存泄漏 + 应用预加载占用 + 启动器 Activity 加载
4. **IO 突发读**的峰值?eMMC 设备 200-500 MB/s,UFS 设备 1-2 GB/s;开机期主要读 /system /vendor /data 分区
5. **IO 争抢**的根因?dex2oat + 资源加载 + ContentProvider + 日志写入 + 多个 dex 加载并发
6. **CPU 饱和**的判定?`top -m 5` 看 load average;8 核 CPU 全部 user% > 80% 即饱和
7. **CPU 调度问题**的根因?`init` 进程 + SystemServer + 多个 service + dex2oat 线程全部在抢 CPU
8. **资源争抢治理**的优先级?先看 IO(40% 案例),再看 CPU(35% 案例),最后看内存(25% 案例)

## 2. 详细展开

### 2.1 内存峰值与 LMKD 触发

开机期内存峰值是 Android 系统的"必考题"——SystemServer 启动期间会同时加载 framework-res.apk + 多个 service + zygote fork + launcher 进程,内存峰值一般出现在 `boot_progress_ams_ready` 前后。

```
开机期内存峰值分布(AOSP 17 + 8GB 设备,典型值)
┌────────────────────────────────────────┐
│ 阶段                  内存占用          │
├────────────────────────────────────────┤
│ Pre-SystemServer      ~600 MB           │
│   - kernel + init + zygote             │
│   - surfaceflinger + bootanim          │
├────────────────────────────────────────┤
│ SystemServer 启动期    ~1500 MB (峰值)  │
│   - system_server (Java heap + native) │
│   - 60+ 个 system service 加载         │
│   - PMS 扫描 / dex2oat                 │
├────────────────────────────────────────┤
│ boot_completed         ~1200 MB         │
│   - launcher 启动                      │
│   - 后台预加载应用                      │
├────────────────────────────────────────┤
│ 稳定态(> 5 分钟)       ~800-1000 MB    │
│   - 释放部分缓存                       │
│   - LMKD 收敛 adj 等级                 │
└────────────────────────────────────────┘
```

| 资源类型 | 8GB 设备峰值 | 6GB 设备峰值 | 4GB 设备峰值 | 风险等级 |
|----------|--------------|--------------|--------------|----------|
| SystemServer Java heap | 512 MB | 384 MB | 256 MB | 高 |
| SystemServer native | 256 MB | 192 MB | 128 MB | 中 |
| 全部 service 进程 | 800 MB | 600 MB | 400 MB | 高 |
| zygote + 预加载类 | 400 MB | 300 MB | 200 MB | 中 |
| framework-res.apk 加载 | 80 MB | 80 MB | 80 MB | 低 |
| 启动器 Activity | 200 MB | 150 MB | 100 MB | 中 |
| **合计** | **~2.2 GB** | **~1.7 GB** | **~1.2 GB** | - |

LMKD 触发: 当内存低于 `MemAvailable` 阈值时,`lmkd` 守护进程按 `oom_adj_score` 从高到低杀进程,直到内存恢复到安全线。开机期 adj 主要分布:

| adj 范围 | 含义 | 开机期实例 | 杀进程影响 |
|----------|------|------------|------------|
| 0-2 | 前台 / 可见 / 关键服务 | launcher / system_server | **永不杀** |
| 3-5 | 重要后台 / 感知 | input / window | **通常不杀** |
| 6-9 | 普通后台 | AudioFlinger / Camera | 杀后重新拉起慢 |
| 10-13 | 缓存后台 | 已 cached 的 service | 杀后立即拉起 |
| 14-15 | 不可见后台 | 空进程 | 杀无影响 |

### 2.2 IO 争抢与 eMMC/UFS 调度

开机期 IO 是**最容易触发争抢的资源**——多个 service 同时启动,各自触发 dex2oat / 资源加载 / ContentProvider,IO 设备瞬间被打满。eMMC 设备尤其严重,UFS 设备稍好。

```
IO 争抢根因(8GB + eMMC 设备,实测)
┌────────────────────────────────────────┐
│ 1. dex2oat 并发 (35% IO)               │
│    - 启动期 100+ 应用同时 dex2oat       │
│    - 每个 dex2oat 单次读 50-200 MB     │
│    - eMMC 4GB/s 极限被打满             │
├────────────────────────────────────────┤
│ 2. 资源加载 (20% IO)                   │
│    - framework-res.apk 加载 80 MB      │
│    - launcher 资源加载 50 MB           │
│    - 多 service 同时加载资源           │
├────────────────────────────────────────┤
│ 3. ContentProvider (15% IO)            │
│    - 应用第一次启动触发 ContentProvider │
│    - 主线程 onCreate 阻塞等 DB 读      │
├────────────────────────────────────────┤
│ 4. 日志写入 (10% IO)                   │
│    - logcat buffer 写满触发同步         │
│    - 开机期 100+ log 源并发写          │
├────────────────────────────────────────┤
│ 5. SELinux 校验 (5% IO)                │
│    - init 阶段 SELinux 策略加载         │
│    - 校验大量文件触发 IO                │
├────────────────────────────────────────┤
│ 6. 其他 (15% IO)                       │
│    - crypto 校验 / OTA 检查 / 网络     │
└────────────────────────────────────────┘
```

| 设备类型 | 顺序读 | 顺序写 | 随机读 | 开机期可用带宽 |
|----------|--------|--------|--------|----------------|
| eMMC 5.1 | 250 MB/s | 125 MB/s | 20 MB/s | < 50 MB/s (争抢后) |
| UFS 2.1 | 850 MB/s | 250 MB/s | 80 MB/s | < 200 MB/s (争抢后) |
| UFS 3.1 | 1800 MB/s | 500 MB/s | 200 MB/s | < 500 MB/s (争抢后) |
| UFS 4.0 | 4200 MB/s | 2800 MB/s | 600 MB/s | < 1500 MB/s (争抢后) |

### 2.3 CPU 争抢与调度策略

CPU 争抢是开机期**最隐蔽的资源问题**——表面看每个进程 CPU 占用都不高,但 8 核饱和时系统切换开销激增,实际执行进度被拖慢。

```
CPU 争抢根因(8 核 CPU + 4GB 设备,实测)
┌────────────────────────────────────────┐
│ 1. dex2oat 线程 (30% CPU)              │
│    - AOSP 17 默认开 4 个 dex2oat 线程  │
│    - 4 线程各占 1 核 100%              │
├────────────────────────────────────────┤
│ 2. SystemServer 主线程 (20% CPU)       │
│    - SystemServer 启动期主线程忙       │
│    - 调度 binder 回调 / service 启动   │
├────────────────────────────────────────┤
│ 3. PMS 扫描 (15% CPU)                  │
│    - 扫描 /data/app 全部应用           │
│    - 校验签名 / dex2oat 调度           │
├────────────────────────────────────────┤
│ 4. Zygote GC (10% CPU)                 │
│    - 引用类加载触发 concurrent GC       │
│    - Stop-The-World 卡 10-50ms         │
├────────────────────────────────────────┤
│ 5. surfaceflinger (10% CPU)            │
│    - boot animation 渲染                │
│    - BufferQueue 合成                   │
├────────────────────────────────────────┤
│ 6. 其他 service (15% CPU)              │
│    - AudioFlinger / Camera / Sensor     │
│    - 50+ 后台 service 共占              │
└────────────────────────────────────────┘
```

| 调度策略 | 优先级 | 用途 | 风险 |
|----------|--------|------|------|
| `SCHED_NORMAL` | 0 | 普通线程 | 默认 |
| `SCHED_BATCH` | -2 | 后台批处理 | dex2oat / logcat |
| `SCHED_IDLE` | -20 | 最低优先级 | 空闲时跑 |
| `SCHED_FIFO` / `RR` | 1-99 | 实时线程 | 音视频 / SurfaceFlinger |
| `cgroup` bg / fg / sys_bg / system | N/A | cgroup 调度 | bg 任务降权 |

### 2.4 资源争抢检测

资源争抢检测的 3 个常用工具:

| 工具 | 检测目标 | 输出 | 解读 |
|------|----------|------|------|
| `dumpsys meminfo` | 内存 | 每进程 PSS / 类别占用 | 找内存峰值进程 |
| `vmstat 1` | 内存 + IO | `si/so` (swap) `bi/bo` (block IO) | swap > 0 即内存紧张 |
| `top -m 5` | CPU | 每进程 CPU% / load average | load > 核数 = 饱和 |
| `iostat 1` | IO | `r/s w/s await util` | util > 80% = IO 饱和 |
| `perfetto` | 全栈 | trace 文件 | 看关键路径时间戳 |
| `bootchart` | 开机 | HTML 报告 | 早期 init 阶段时间分布 |

### 2.5 资源争抢治理 SOP

**内存争抢治理 5 步**:
```bash
# 第 1 步:dumpsys meminfo 看大内存进程
adb shell dumpsys meminfo | head -30
# 找 PSS > 200MB 的开机期进程

# 第 2 步:看 framework-res.apk 加载
adb logcat -d | grep -E 'framework.*res.apk'
# 加载耗时 > 500ms 视为异常

# 第 3 步:看 service 是否有内存泄漏
adb shell dumpsys meminfo <service_name> | grep -E 'Java Heap|Native Heap'
# Java Heap 增长 > 50MB 视为泄漏

# 第 4 步:触发 GC 验证
adb shell am send-trim-memory <pid> COMPLETE
# 内存没释放 = 泄漏,释放了 = 临时占用

# 第 5 步:看 LMKD 是否误杀
adb logcat -d | grep -E 'lowmemorykiller'
# adj >= 12 的 service 被杀视为误杀
```

**IO 争抢治理 5 步**:
```bash
# 第 1 步:vmstat 1 看 block IO
adb shell vmstat 1
# bi+bo > 设备极限的 80% 即争抢

# 第 2 步:iostat 看 await 时间
adb shell iostat 1
# await > 50ms 视为争抢

# 第 3 步:看 dex2oat 是否在争抢 IO
adb logcat -d | grep -E 'dex2oat.*ms'
# 100+ dex2oat 同时跑 = 争抢

# 第 4 步:查 IO 调度器
adb shell cat /sys/block/sda/queue/scheduler
# 改 deadline / cfq 看是否改善

# 第 5 步:启用 EROFS 镜像
adb shell df -h /system
# 文件系统类型是 erofs 即启用
```

**CPU 争抢治理 5 步**:
```bash
# 第 1 步:top 看 CPU 占用
adb shell top -m 5 -n 1
# 找 CPU > 80% 的进程

# 第 2 步:看 load average
adb shell uptime
# load > 8 核数 = 饱和

# 第 3 步:看 dex2oat 线程数
adb shell ps -A | grep dex2oat | wc -l
# > 4 = 过多

# 第 4 步:看 cgroup 配置
adb shell cat /dev/cpuctl/cpu.shares
# 调整 bg/fg cgroup 权重

# 第 5 步:看 schedtune 配置
adb shell cat /proc/sys/kernel/sched_tune_sched_boost
# 调整 boost 值
```

## 4. 实战案例

### 案例 1:某 4GB 设备 SystemServer 启动期 OOM 频繁

**背景**:
- 设备:某 SoC 平台 4GB RAM,出厂 13
- 现象:用户报开机慢(28s)+ 偶发开机后立即弹出"应用已停止运行"
- 现场数据:`dumpsys meminfo` 显示 system_server 占用 380 MB,接近 4GB 设备极限

**调查过程**:
1. 抓 meminfo,看到 system_server Java Heap 280 MB + Native 100 MB,合计 380 MB
2. 抓 boot_progress 时间戳,`ams_ready` 在 12s,`boot_completed` 在 24s,差 12s
3. 抓 logcat,看到 `ActivityManager: Process system_server has died` 在 22s 出现
4. 看 dropbox,`system_server_crash` 现场,栈顶在 `ResourceManager.getValue`
5. 查 framework-res.apk 加载耗时:1.8s(同基线 8GB 设备 0.5s)

**根因**:
- 4GB 设备上 framework-res.apk 加载耗时长(IO 慢 + 内存少)
- 加载过程占用大量内存,触发 LMKD 误判
- system_server 即将完成时被 LMKD 标记为可疑,实际未杀但留下 OOM 痕迹
- 用户感知:开机 24s 完成 + 部分应用 crash

**修复**:
- framework-res.apk 拆成多个 split apk(只加载主包)
- 启动期禁用 LMKD 对 system_server 的检查
- **总节省:开机时间从 24s → 18s(节省 6s),应用 crash 率从 5% → 0.5%**

### 案例 2:某 8 核设备 8 核 CPU 但开机慢

**背景**:
- 设备:某 OEM 8GB RAM 设备,8 核 CPU,出厂 14
- 现象:用户报开机慢(30s),用户认为"8 核 CPU 应该秒开"
- 现场数据:`top -m 5` 显示开机期 5 个进程 CPU > 80%

**调查过程**:
1. 抓 `top -m 5 -n 1`,看到 5 个进程 CPU 占用:
   - system_server 95%
   - dex2oat 92% / 89% / 88% (4 个 dex2oat 线程)
   - surfaceflinger 78%
2. 8 核 CPU 总占用 = 8 核 × 平均 80% = 640% CPU 时间
3. 但单核极限是 100%,意味着每个核都接近饱和
4. 抓 perfetto,看 `boot_progress_pms_start` → `ams_ready` 时间差 18s
5. 看 dex2oat log,4 个 dex2oat 线程各跑了 12s,合计 48s,但实际只跑 12s(并行)

**根因**:
- 4 个 dex2oat 线程 + system_server + surfaceflinger 抢占 6 个核
- 剩下 2 个核被其他 60+ service 抢
- CPU 调度器无法合理分配,导致"8 核都不够用"
- 实际瓶颈在**调度开销**而非 CPU 算力

**修复**:
- dex2oat 线程数从 4 减到 2(`setprop ro.sys.dexopt.threads 2`)
- 启动期 service 降级到 `SCHED_BATCH`
- 关键 service 升到 `cgroup:/dev/cpuctl/bg`
- **总节省:开机时间从 30s → 22s(节省 8s)**

## 5. Takeaway

1. **资源争抢是开机期最隐蔽的根因**——表面看"开机慢"但实际是 IO/CPU/内存三者争抢,直接套用 11.4 优化效果有限
2. **内存峰值 1.5-2GB 是 8GB 设备典型值**——4GB 设备易吃紧,需要拆 framework-res.apk + 启动期禁用部分 LMKD 检查
3. **LMKD 触发是按 oom_adj_score**——adj 0-2 永不杀,adj 14-15 杀无影响;开机期 service adj 主要在 6-9 区间
4. **IO 争抢 35% 案例来自 dex2oat 并发**——100+ 应用同时 dex2oat 是 eMMC 设备的杀手,UFS 设备可放宽到 4-6 线程
5. **eMMC 设备极限 250 MB/s 读,UFS 3.1 是 1800 MB/s**——同一段代码在 eMMC / UFS 设备表现差 7 倍,优化需按设备分级
6. **CPU 争抢 30% 案例是 dex2oat 线程**——4 个 dex2oat 线程 + system_server 就占 6 核,8 核设备瞬间饱和
7. **资源争抢检测 3 件套:dumpsys meminfo + vmstat/iostat + top -m 5**——三件套能定位 80% 资源争抢问题
8. **CPU 调度问题是"调度开销"而非"算力不够"**——8 核 CPU 全部 user% > 80% 实际是调度瓶颈,需要降级部分 service 到 SCHED_BATCH
9. **dex2oat 线程数是开机期关键调优参数**——4 核 / 4GB 设备建议 2 线程,8 核 / 8GB 设备建议 3 线程
10. **EROFS 镜像能直接降低 IO 30%**——AOSP 13+ 默认启用,4GB eMMC 设备必须验证是否启用
