# 6.5 Kernel cmdline 与 dtb：设备树 + 内核参数

## 一句话开场

**Kernel 启动参数的"4 个来源 + 3 层 dtb 加载"决定了 Kernel 看到什么硬件、做什么行为**——错误配置 → 启动后 init 跑错、SELinux 模式错、log 抓不到。boot hang 调查必须**先确认 cmdline 和 dtb 正确**。

按 AOSP 17 默认：

- **cmdline 来源优先级**：DTB chosen > bootloader 注入 > CONFIG_CMDLINE > atags
- **dtb 加载顺序**：主 dtb（boot 分区）→ dtbo（dtbo 分区）→ 后处理（运行期修改）

## 1. cmdline 的 4 个来源

### 1.1 优先级排序（高 → 低）

| 优先级 | 来源 | 典型值 | 用途 |
|---|---|---|---|
| 1 | DTB `/chosen` 节点 | `console=ttyMSM0,115200` | 设备树 + ABL 注入 |
| 2 | Bootloader 注入 | `androidboot.hardware=qcom` | ABL fastboot 配置 |
| 3 | `CONFIG_CMDLINE` | `CONFIG_CMDLINE="earlyprintk"` | 内核编译时默认 |
| 4 | atags | (几乎不用) | legacy ARM 模式 |

**Kernel 选择 cmdline 的实际逻辑**（`arch/arm64/kernel/setup.c`）：

```c
// 1. DTB /chosen 节点的最高优先级
if (of_property_read_string(of_chosen, "bootargs", &cmdline)) {
    // 2. 没找到则用 Bootloader 注入的
    strlcpy(cmdline, boot_command_line, COMMAND_LINE_SIZE);
}
// 3. 也没找到则用 CONFIG_CMDLINE
// 4. 最后 fallback 到 atags
```

### 1.2 AOSP 17 默认 cmdline（Pixel 8 SM8550）

```bash
$ adb shell cat /proc/cmdline
console=ttyMSM0,115200n8
androidboot.console=ttyMSM0
androidboot.hardware=qcom
androidboot.boot_devices=soc/1d84000.ufshc
androidboot.serialno=...
androidboot.slot_suffix=_a
androidboot.bootloader=b1c1-0.4-12345678
androidboot.ramdump=0x80000000,0x100000000
androidboot.fp_sensor=goodix
androidboot.dtbo_idx=1
androidboot.dtbo_size=4096
androidboot.dtb_idx=0
androidboot.dtb_size=4096
androidboot.bootconfig=
androidboot.veritymode=enforcing
androidboot.verifiedbootstate=green
androidboot.keystore=0
androidboot.avb_version=2.0
```

### 1.3 cmdline 关键参数分类

| 类别 | 参数 | 用途 |
|---|---|---|
| **console** | `console=ttyMSM0,115200n8` | printk 输出串口 |
| **早期调试** | `earlyprintk` / `earlycon` | 早期 printk 开关 |
| **initcall** | `initcall_debug` | 打印每个 initcall 耗时 |
| **printk** | `printk.time=1` | printk 带时间戳 |
| **panic** | `panic=10` | 10s 后 reboot on panic |
| **androidboot.hardware** | `qcom` / `mtk` | 平台标识（驱动匹配用） |
| **androidboot.slot_suffix** | `_a` / `_b` | A/B 分区槽位 |
| **androidboot.veritymode** | `enforcing` / `disabled` | AVB 模式 |
| **androidboot.serialno** | device serial | 设备唯一标识 |
| **dtbo** | `androidboot.dtbo_idx=N` | 设备树 overlay 索引 |
| **OEM 私参** | `vendor.*` / `oem.*` | 厂商自定义参数 |

## 2. cmdline 错误 → 启动后行为异常

### 2.1 5 类常见 cmdline 错误

| 错误类型 | 现象 | 调查 |
|---|---|---|
| 1. 整段 cmdline 缺失 | Kernel 启动后 init 行为异常 | dmesg 没"Kernel command line" |
| 2. 关键参数拼错 | "console=" 没生效，dmesg 丢失 | cat /proc/cmdline 检查 |
| 3. OEM 私参不兼容 | 驱动加载失败 | initcall_debug 找 initcall 失败 |
| 4. AVB 模式错 | 启动后 SELinux 异常 | veritymode 参数值 |
| 5. androidboot.slot_suffix 错 | 启动到 A/B 错槽 | fastboot getvar current-slot |

### 2.2 实战：console= 错导致 dmesg 丢失

```bash
# 错误 cmdline：console=ttyMSM_xxx（错误端口）
# Kernel 启动后所有 printk 丢到不存在的端口
# 用户看到 dmesg 是空的（实际上 Kernel 跑了，但 log 丢了）

# 调查：
adb shell cat /proc/cmdline
# 看到 "console=ttyMSM0_xxx" → console 参数错

# 修复：ABL 重新注入正确 cmdline
fastboot oem cmdline set "console=ttyMSM0,115200n8"
fastboot reboot
```

## 3. 设备树（DTB）的 3 层加载机制

### 3.1 设备树的 3 个组成

| 组成 | 内容 | 位置 |
|---|---|---|
| **主 DTB** | 设备硬件描述（CPU/内存/总线/外设） | `boot` 分区 |
| **DTBO** | 设备树 overlay（OEM 定制） | `dtbo` 分区 |
| **运行时修改** | Kernel 启动后修改 DTB | `runtime` |

### 3.2 DTB 加载流程

```
ABL 加载主 DTB
  ↓
ABL 加载 DTBO（按 dtbo_idx 索引）
  ↓
ABL 用 DTBO overlay 主 DTB（合并节点）
  ↓
ABL 跳到 Kernel，x0 = 合并后 DTB 地址
  ↓
Kernel 解析 DTB（head.S → setup_arch）
```

### 3.3 DTBO Overlay 机制

DTBO 设备树 overlay 是 **"差分"机制**——只包含要修改的节点：

```dts
// dtbo 1（Pixel 8 印度版 · 双卡）
/dts-v1/;
/plugin/;

&{/soc/i2c@3580000} {
    sim_detect: sim-detect@20 {
        compatible = "qcom,sim-detect";
        reg = <0x20>;
        sim-slots = <2>;
    };
};

// dtbo 2（Pixel 8 美国版 · 单卡）
&{/soc/i2c@3580000} {
    sim_detect: sim-detect@20 {
        compatible = "qcom,sim-detect";
        reg = <0x20>;
        sim-slots = <1>;
    };
};
```

**Overlay 优先级**（高 → 低）：
1. Bootloader 加载顺序（dtbo_idx）
2. DTB 主节点
3. Kernel 编译时 defaults

### 3.4 dtbo 损坏 → Kernel 早期 panic

```bash
# 调查
adb shell dmesg | grep -i "of:"
# 看到 "of: ... parse failed" → DTBO 损坏
# 看到 "Machine model: ..." → DTBO OK

# 修复：重新刷 dtbo
fastboot flash dtbo dtbo.img
fastboot reboot
```

## 4. cmdline 注入的 4 种方式

### 4.1 编译时注入

```bash
# Kernel 配置
CONFIG_CMDLINE="console=ttyMSM0,115200n8 earlyprintk"
# 注意：通常 AOSP 17 用 dtb /chosen，CONFIG_CMDLINE 留空
```

### 4.2 ABL fastboot 注入

```bash
# 临时修改 cmdline
fastboot oem cmdline add "initcall_debug printk.time=1"
# 注意：不是所有 ABL 都支持 oem cmdline
```

### 4.3 通过 bootconfig 注入（Android 12+）

```bash
# 1. 启用 bootconfig
CONFIG_BOOT_CONFIG=y
CONFIG_BOOT_CONFIG_FORCE=y

# 2. 创建 bootconfig 镜像
mkbootconfig -o bootconfig.img "androidboot.bootconfig=initcall.debug=1"

# 3. 刷入 bootconfig 分区
fastboot flash bootconfig bootconfig.img
```

### 4.4 通过 Kernel 模块参数注入

```c
// 驱动模块的 cmdline 参数
module_param(debug_level, int, 0644);
MODULE_PARM_DESC(debug_level, "Debug level: 0=off, 1=basic, 2=verbose");

// cmdline 加 vendor.debug_level=2
```

## 5. cmdline 调试实战

### 5.1 调查 cmdline 是否正确

```bash
# 1. 完整 cmdline
adb shell cat /proc/cmdline
# 对比 AOSP 17 默认值，检查关键参数

# 2. Kernel 看到的 cmdline（早期）
adb shell dmesg | grep "Kernel command line"
# 看 Kernel 启动时实际解析的 cmdline

# 3. init 看到的 cmdline
adb shell getprop | grep "ro.boot"
# ro.boot.hardware / ro.boot.serialno 等
```

### 5.2 实战：抓 last_kmsg 失败 → console= 错

```bash
# 现象：设备启动到桌面但 dmesg 完全空
# 调查步骤：
# 1. cat /proc/cmdline
adb shell cat /proc/cmdline
# 输出：console=ttyMSM_xxx,115200n8

# 2. 确认 console 设备
adb shell ls /dev/ttyMSM*
# 没看到 ttyMSM_xxx → console 设备不存在

# 3. 修复 cmdline
fastboot oem cmdline set "console=ttyMSM0,115200n8"
fastboot reboot

# 4. 验证
adb shell dmesg | head -10
# 看到 dmesg → 修好
```

### 5.3 实战：androidboot.slot_suffix 错 → A/B 槽位错乱

```bash
# 现象：device 启动后 fastboot getvar current-slot 错乱
# 调查：
adb shell getprop ro.boot.slot_suffix
# 看到 "_a" 但实际 active 是 _b

# 修复：
fastboot set_active b
fastboot reboot
```

## 6. cmdline 安全注意事项

### 6.1 不能在 cmdline 暴露的 3 类信息

| 类型 | 风险 | 替代方案 |
|---|---|---|
| **用户密码 / 密钥** | 任何用户 `cat /proc/cmdline` 都能看 | 写到 root-only 文件 |
| **调试后门** | 攻击者可禁用 SELinux | 用 module_param |
| **OEM 私钥** | OTA 升级签名泄露 | 用 Keystore 硬件隔离 |

### 6.2 启动期 cmdline 修改的检测

Kernel 启动期会打印 cmdline hash，攻击者改 cmdline 可被检测：

```bash
# dmesg 抓 cmdline hash
adb shell dmesg | grep "Kernel command line"
# [    0.020000] Kernel command line: console=ttyMSM0,115200n8 ...

# 攻击者改了后：
adb shell dmesg | grep "Kernel command line"
# 看到不一样 → cmdline 被改

# 进一步检测：cmdline hash（Kernel 5.x+）
# CONFIG_CMDLINE_HASH=y 会在启动时打印 hash
```

## 7. Takeaway

- **cmdline 4 来源**：DTB chosen > Bootloader > CONFIG_CMDLINE > atags
- **dtb 3 层加载**：主 dtb → dtbo overlay → 运行时修改
- **5 类 cmdline 错误**：整段缺失 / 关键拼错 / OEM 私参不兼容 / AVB 模式错 / 槽位错
- **4 种 cmdline 注入**：CONFIG_CMDLINE / ABL oem cmdline / bootconfig / module_param
- **实战关键**：boot hang 调查前**先确认 cmdline + dtb 正确**（cat /proc/cmdline + dmesg "Machine model"）
- **安全禁忌**：cmdline 不能放密码 / 调试后门 / OEM 私钥
