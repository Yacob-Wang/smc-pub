# 6.6 启动失败案例：Kernel panic / boot loop / hung task

## 一句话开场

**启动期 3 类典型失败：Kernel panic（直接死）、boot loop（反复重启）、hung task（卡死）**——3 类的调查 SOP 各不相同，但都靠 **last_kmsg + pstore + ramdump** 三件套起手。

实战中 80% 的启动失败能用以下 5 步定位：

1. 抓 last_kmsg（看 panic / hang 信息）
2. 抓 pstore（看 console log）
3. 抓 ramoops（看 early log）
4. 抓 ramdump（Kernel panic 现场）
5. 抓 dropbox（用户空间异常）

## 1. Kernel panic 调查 SOP

### 1.1 Kernel panic 的 3 大类型

| 类型 | 触发位置 | 现象 |
|---|---|---|
| **硬件探测失败** | start_kernel → setup_arch | dmesg 卡"setup_arch" |
| **资源不足** | start_kernel → mm_init | "Bad page state" |
| **致命异常** | do_basic_setup → initcall | "Oops: ... in initcall" |

### 1.2 调查 6 步

```bash
# 步骤 1: 抓 last_kmsg
adb shell cat /proc/last_kmsg > last_kmsg.txt
# 关键：找最后 3-5 行 Call trace

# 步骤 2: 抓 pstore
adb shell ls /sys/fs/pstore/ > pstore_list.txt
adb shell cat /sys/fs/pstore/console-ramoops-0 > console.log 2>/dev/null

# 步骤 3: 抓 ramoops
adb shell cat /sys/fs/pstore/dmesg-ramoops-0 > ramoops.log 2>/dev/null

# 步骤 4: 抓 ramdump（需要 OEM 工具）
# Pixel / 三星 / 高通平台各有 ramdump 工具
edl.py --loader prog_firehose_ddr.elf --memory=ramdump --output=ramdump.bin

# 步骤 5: 抓 dropbox 系统日志
adb shell dumpsys dropbox --print > dropbox.txt

# 步骤 6: 抓 bootstat 启动耗时
adb shell dumpsys bootstat > bootstat.txt
```

### 1.3 实战案例 1：Kernel panic at setup_arch（cmdline 损坏）

**现场**：
- 设备卡开机 logo，20s 后 reboot
- last_kmsg 显示：
```
[    0.050000] Kernel command line: console=ttyMSM0 console=ttyMSM0 console=ttyMSM0 ...
[    0.060000] Kernel panic - not syncing: malformed cmdline
```

**根因**：cmdline 包含重复的 `console=` 参数，且长度溢出（> COMMAND_LINE_SIZE=2048）。

**修复**：
```bash
# 1. 抓取 ABL 当前 cmdline
fastboot oem cmdline get > current_cmdline.txt

# 2. 修正 cmdline（去掉重复）
fastboot oem cmdline set "console=ttyMSM0,115200n8 androidboot.hardware=qcom ..."

# 3. 重新启动验证
fastboot reboot
```

### 1.4 实战案例 2：Kernel panic at mm_init（内存探测失败）

**现场**：
- Pixel 8 高配版（12GB RAM）启动卡第一屏
- last_kmsg：
```
[    0.300000] memblock_add: [0x40000000, 0x80000000)
[    0.350000] memblock_add: [0x80000000, 0x100000000)
[    0.400000] Kernel panic - not syncing: Failed to add memory region
```

**根因**：SoC 内存大小识别错误，memblock_add 失败。

**修复**：
```bash
# 1. 通过 ABL 重置内存大小
fastboot oem memcfg 0xc0000000  # 12GB

# 2. 或修改 DTB memory 节点
# 重新编译 DTB
make ARCH=arm64 dtbs
fastboot flash dtb boot.img-dtb
```

## 2. Boot loop 调查 SOP

### 2.1 Boot loop 的 4 个判定阶段

按 PBL / XBL / ABL / Kernel 4 段判定：

```
PBL 阶段 boot loop:
  - 现象: 按电源键无任何反应 → 设备没启动
  - 调查: 硬件（PMIC / 电池 / SoC）
  - 概率: 10%

XBL 阶段 boot loop:
  - 现象: 卡 "Qualcomm / MediaTek" logo
  - 调查: 9008 模式 + Sahara ramdump
  - 概率: 15%

ABL 阶段 boot loop:
  - 现象: 卡开机动画第一屏，20s 后重启
  - 调查: serial log + last_kmsg
  - 概率: 30%

Kernel 阶段 boot loop:
  - 现象: 卡白屏 / 反复重启
  - 调查: dmesg + initcall_debug
  - 概率: 45%
```

### 2.2 BootLoop 5 步调查法

```bash
# 步骤 1: 确认阶段
adb shell dmesg | head -50
# 看到 "Booting Linux" → Kernel 阶段
# 看到 "Run /init" → init 阶段
# 看到 "Calibrating delay" → 早期启动

# 步骤 2: 抓 last_kmsg
adb shell cat /proc/last_kmsg > last_kmsg.txt
# 关键: 找 "reboot reason"

# 步骤 3: 抓 bootstat
adb shell dumpsys bootstat
# 看 "boot complete" 时间

# 步骤 4: 抓 dropbox
adb shell dumpsys dropbox --print | grep "boot"
# 看 "boot_anomaly_count"

# 步骤 5: 启用 initcall_debug
# 修 ABL cmdline 加 initcall_debug，重启
fastboot oem cmdline add "initcall_debug"
fastboot reboot
```

### 2.3 实战案例 3：Boot loop at do_basic_setup（驱动 initcall 失败）

**现场**：
- 某 OEM 设备启动卡 logo
- 启用 initcall_debug 后 dmesg：
```
[    1.500000] calling  i2c_adap_i2c_init+0x0/0x100 @ 800
[    1.600000] initcall i2c_adap_i2c_init+0x0/0x100 returned 0 after 100000 usecs ← 100ms 异常
[    1.700000] calling  qcom_i2c_probe+0x0/0x200 @ 850
                                                  ← 卡这里
```

**根因**：i2c 总线 hang（外设不响应）。

**调查**：
```bash
# 1. 启用 i2c 调试
fastboot oem cmdline add "i2c.debug=1 dyndbg"

# 2. 重启
fastboot reboot

# 3. 抓 dmesg
adb shell dmesg | grep i2c
# 看到 "i2c: timeout waiting for bus" → i2c 总线无响应
```

**修复**：
- 检查硬件（i2c 外设焊接）
- 或在 cmdline 加 `i2c.skip_broken=1` 跳过该外设（临时）

## 3. Hung task 调查 SOP

### 3.1 Hung task 的 3 大类型

| 类型 | 触发位置 | 现象 |
|---|---|---|
| **D-state 进程** | process hung in D state | "INFO: task ... blocked for more than 120s" |
| **D-state IO** | iowait stuck | "task ... blocked for more than 120s" + "iowait" |
| **死锁** | mutex / spinlock deadlock | "possible circular locking dependency detected" |

### 3.2 调查 4 步

```bash
# 步骤 1: 抓 hung_task 警告
adb shell dmesg | grep "INFO: task"
# 输出:
# [120.000000] INFO: task kworker/u8:1:123 blocked for more than 120s

# 步骤 2: 看堆栈
adb shell dmesg | grep -A 30 "blocked for more"
# 看到具体堆栈，确认卡在哪个函数

# 步骤 3: 启用 lockdep（debug 锁死锁）
# ABL cmdline 加 lockdep=on
# 启动后 dmesg 会自动检测锁死锁

# 步骤 4: 抓 ramdump
# hung_task 的现场需要 ramdump 工具
```

### 3.3 实战案例 4：Hung task at IO subsystem

**现场**：
- 设备启动到桌面后 5 分钟卡死
- dmesg：
```
[300.000000] INFO: task kworker/u8:1:123 blocked for more than 120s.
[300.050000] "echo 0 > /proc/sys/kernel/hung_task_timeout_secs" disables this message.
[300.100000] Call trace:
[300.150000]  __switch_to+0x...
[300.200000]  blk_queue_enter+0x...
[300.250000]  blk_mq_get_tag+0x...
[300.300000]  blk_mq_alloc_request+0x...
[300.350000]  __blk_mq_alloc_request+0x...
[300.400000]  blk_mq_submit_bio+0x...
[300.450000]  submit_bio+0x...
[300.500000]  ext4_writepages+0x...
[300.550000]  ext4_do_writepages+0x...
```

**根因**：eMMC / UFS 设备 hang，IO 请求超时。

**调查**：
```bash
# 1. 启用 IO 调试
adb shell echo 1 > /proc/sys/vm/block_dump
adb shell cat /proc/diskstats

# 2. 抓 IO trace
adb shell perfetto -o /data/local/tmp/trace.perfetto-trace -t 10s sched freq idle am_ps_wakelock

# 3. 分析：eMMC 是否在 IO 队列卡死
```

**修复**：
- 硬件：检查 eMMC/UFS 物理连接
- 软件：升级 eMMC 驱动

## 4. 5 个万能调试开关

### 4.1 必加的 5 个 cmdline 开关

```bash
# 启动失败时，ABL cmdline 加以下 5 个：

initcall_debug          # 打印每个 initcall 耗时（排查 initcall hang）
printk.time=1           # printk 带时间戳（看清 dmesg 时间线）
earlycon                # 早期 console（head.S 阶段输出）
CONFIG_DEBUG_PAGEALLOC  # 启用 page alloc 调试
CONFIG_LOCKDEP          # 启用锁死锁检测
```

### 4.2 通过 fastboot 临时修改 cmdline

```bash
# 1. 加开关
fastboot oem cmdline add "initcall_debug printk.time=1"

# 2. 验证
fastboot oem cmdline get

# 3. 重启
fastboot reboot

# 4. 抓 dmesg
adb shell dmesg > dmesg_with_debug.txt
```

## 5. 3 大 ramdump 工具对比

### 5.1 OEM 工具

| 厂商 | 工具 | 抓取命令 |

| 高通 | Sahara / Firehose | `edl.py --loader prog_firehose_ddr.elf --memory=ramdump` |
| MTK | MTK RAMDump | `mtk_ramdump_tool.exe` |

### 5.2 ramdump 解析

```bash
# 用 GDB + vmlinux 解析 ramdump
gdb-multiarch vmlinux
(gdb) target remote | python parse_ramdump.py ramdump.bin
(gdb) bt

```

## 6. Takeaway

- **3 类启动失败**：Kernel panic（直接死） / boot loop（反复重启） / hung task（卡死）
- **5 步调查 SOP**：last_kmsg → pstore → ramoops → ramdump → dropbox
- **5 个万能 cmdline 开关**：initcall_debug + printk.time + earlycon + CONFIG_DEBUG_PAGEALLOC + CONFIG_LOCKDEP
- **3 大 ramdump 工具**：Sahara（高通）/ MTK RAMDump / fastboot oem ramdump（Pixel）
- **实战核心**：先确认 cmdline 和 dtb 正确 → 再看 dmesg 哪行卡 → 启用 initcall_debug 定位 initcall
