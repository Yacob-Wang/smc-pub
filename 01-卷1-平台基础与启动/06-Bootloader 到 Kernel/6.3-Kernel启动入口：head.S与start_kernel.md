# 6.3 Kernel 启动入口：head.S / start_kernel

## 一句话开场

**Linux Kernel 启动的本质 = start_kernel 函数的 30+ 调用顺序**——理解这条主线，90% 的 boot hang 都能定位到具体函数。**dmesg 的"卡哪一行"就是 start_kernel 卡的"哪一步"**。

按 AOSP 17 + Linux 6.18 + ARM64 架构，start_kernel 调用链如下（**实测耗时基线**）：

```
head.S
  ↓ (汇编 · 20ms)
__primary_switched
  ↓
start_kernel  ← C 函数入口
  ├ lockdep_init              (0ms · 锁依赖检测)
  ├ boot_cpu_init             (1ms)
  ├ setup_arch                (200ms · 解析 cmdline)
  ├ mm_init                   (300ms · 内存子系统)
  ├ sched_init                (5ms · 调度器)
  ├ init_IRQ                  (5ms · 中断子系统)
  ├ time_init                 (10ms · 时间子系统)
  ├ console_init              (50ms · printk 接管)
  ├ calibrate_delay           (500ms · 延迟校准，🔴 风险)
  ├ calibrate_cpufreq         (100ms)
  ├ page_alloc_init           (100ms)
  ├ vfs_caches_init           (50ms)
  ├ do_basic_setup            (800ms · 🔴 驱动 initcall)
  ├ do_initcalls              (200ms)
  └ rest_init                 (50ms)
      └ kernel_init
          └ run_init_process("/init")  ← 启动第一个用户进程
```

**总耗时 ~2.4s**（dmesg 出现"Kernel command line"开始到"Run /init"结束）。

## 1. head.S：汇编入口的 6 个最小职责

### 1.1 head.S 的 6 步汇编流程

```asm
// arch/arm64/kernel/head.S · Linux 6.18
ENTRY(stext)
    // 1. 关闭 IRQ/FIQ/SError（防早期中断）
    msr    daifset, #DAIF_PROCCTX
    
    // 2. 验证 CPU 类型
    bl     __lookup_processor_type
    
    // 3. 验证设备树 magic
    ldr    x4, =__fdt_pointer
    ldr    x5, [x0]              // 读 DTB 前 4 字节
    cmp    x5, #FDT_MAGIC        // 0xd00dfeed
    b.ne   __secondary_hang       // 不匹配 → 死循环
    
    // 4. 创建临时页表（identity mapping）
    adrp    x6, idmap_pg_dir
    ...
    bl     __create_page_tables
    
    // 5. 跳到 __primary_switched
    br     x8                     // 间接跳转
    
    // 6. 跳到 start_kernel（C 入口）
    b     start_kernel
```

### 1.2 head.S 阶段的 5 个调试开关

| 开关 | 用途 | 配置选项 |
|---|---|---|
| `earlycon` | 早期串口输出（在 console_init 之前） | `CONFIG_SERIAL_EARLYCON` |
| `earlyprintk` | 早期 printk（基于 earlycon） | `CONFIG_EARLY_PRINTK` |
| `EFI_RUNTIME_WRAPPERS` | EFI runtime 支持 | `CONFIG_EFI_RUNTIME_WRAPPERS` |
| `STATIC_RODATA` | 静态只读段保护 | `CONFIG_STRICT_KERNEL_RWX` |
| `DEBUG_LL` | 汇编级早期 printk（无 console） | `CONFIG_DEBUG_LL` |

**实操命令**：
```bash
# 抓取 head.S 阶段的日志（dmesg 之前）
adb shell cat /sys/fs/pstore/console-ramoops-0  # 需要 ramoops 配置
# 或通过串口（如果有）：
minicom -D /dev/ttyUSB0 -b 115200
```

## 2. start_kernel 的 30+ 调用顺序

### 2.1 完整调用栈（Linux 6.18 + ARM64）

```c
// init/main.c · Linux 6.18
asmlinkage __visible void __init __no_sanitize_address start_kernel(void)
{
    // ===== 阶段 1: 极早期（< 10ms）=====
    lockdep_init();                      // 锁依赖检测
    smp_setup_processor_id();            // SMP CPU ID
    boot_cpu_init();                     // 当前 CPU 标记为 boot CPU
    init_thread_xid();                   // 主线程 xid
    hypervisor_check();                  // 检查虚拟化环境
    
    // ===== 阶段 2: 架构初始化（~200ms）=====
    setup_arch(&command_line);           // ★ 解析 cmdline
    //  ├ parse_early_param()              // early 阶段参数
    //  ├ setup_machine_fdt()              // DTB 设备树匹配
    //  ├ arm64_memblock_init()            // memblock 内存管理
    //  ├ paging_init()                    // 页表建立
    //  └ unflatten_device_tree()          // DTB 展开为 device_node 树
    
    // ===== 阶段 3: 内存子系统（~300ms）=====
    mm_init();                           // ★
    //  ├ page_ext_init()
    //  ├ memblock_dump_all()
    //  ├ kmem_cache_init()                // slab 分配器
    //  ├ page_alloc_init()                // 页分配器
    //  └ vmemmap_populate_print_info()
    
    // ===== 阶段 4: 调度器（~5ms）=====
    sched_init();                        // 创建 idle 进程
    //  ├ rq_init()
    //  ├ init_sched_fair_class()
    //  └ init_idle()                      // 0 号进程（idle）
    
    // ===== 阶段 5: 中断子系统（~5ms）=====
    init_IRQ();                          // ARM64 GICv3 初始化
    //  ├ irq_init()
    //  ├ gic_init()
    //  └ set_handle_irq()
    
    // ===== 阶段 6: 时间子系统（~10ms）=====
    time_init();                         // ★ clocksource
    //  ├ of_clk_init()
    //  ├ clocksource_probe()
    //  └ timer_probe()
    
    // ===== 阶段 7: 早期控制台（~50ms）=====
    console_init();                      // ★ 注册 printk console
    //  ├ register_console()
    //  └ earlycon_unregister()           // 早期 console 卸载
    
    // ===== 阶段 8: 延迟校准（~500ms · 🔴 高风险）=====
    calibrate_delay();                   // ★ BogoMIPS 校准
    //  ├ calibrate_delay_converge()
    //  └ cpu_calibrate_loop()             // 紧循环测 CPU 频率
    
    // ===== 阶段 9: CPU 频率（~100ms）=====
    calibrate_cpufreq();
    
    // ===== 阶段 10: VFS 缓存（~50ms）=====
    vfs_caches_init();
    //  ├ dcache_init()
    //  ├ inode_init()
    //  └ files_init()
    
    // ===== 阶段 11: 信号（< 5ms）=====
    signals_init();
    
    // ===== 阶段 12: 架构无关基础（< 5ms）=====
    cpuset_init();
    cgroup_init();
    taskstats_init();
    delayacct_init();
    
    // ===== 阶段 13: 调度器 fork 准备（< 5ms）=====
    check_bugs();                        // CPU bug 检查
    sfi_init_late();
    oops_init();
    
    // ===== 阶段 14: ACPI 资源管理（< 10ms）=====
    acpi_subsystem_init();
    arch_post_acpi_subsys_init();
    
    // ===== 阶段 15: 随机数种子（< 5ms）=====
    random_init();
    
    // ===== 阶段 16: 驱动 initcall（~800ms · 🔴 高风险）=====
    do_basic_setup();
    //  └ do_initcalls();
    //     └ for each __initcall_entry:
    //         fn();
    //     // ★★ 大部分驱动、设备总线、文件系统在这里初始化 ★★
    
    // ===== 阶段 17: 启动 init 进程（~50ms）=====
    rest_init();
    //  ├ call_usermodehelper_init()       // usermodehelper 准备
    //  ├ preempt_enable()
    //  ├ mark_readonly()
    //  └ kernel_init();                   // ★ 启动 init
    //     └ run_init_process("/init");    // execve("/init")
}
```

### 2.2 30+ 函数的关键程度分级

| 阶段 | 函数 | 耗时基线 | 关键程度 | 失败现象 |
|---|---|---|---|---|
| 2 | `setup_arch` | 200ms | ★★★ | 卡"Booting Linux"不进入下一步 |
| 3 | `mm_init` | 300ms | ★★ | 卡内存初始化 / Bad page state |
| 4 | `sched_init` | 5ms | ★ | 调度器 hang（极少） |
| 5 | `init_IRQ` | 5ms | ★ | 中断未初始化完（极少） |
| 6 | `time_init` | 10ms | ★ | 时间子系统卡（极少） |
| 7 | `console_init` | 50ms | ★★ | "无 dmesg" 盲启动 |
| 8 | `calibrate_delay` | 500ms | ★★★ | 卡 "Calibrating delay loop..." |
| 10 | `vfs_caches_init` | 50ms | ★ | VFS 初始化失败（极少） |
| 16 | `do_basic_setup` | 800ms | ★★★ | 卡 "Loading module" / initcall hang |
| 17 | `rest_init` | 50ms | ★ | init 进程启动失败 |

## 4. 5 个常见 boot hang 点

### 4.1 卡 "Booting Linux on physical CPU" → head.S 失败

**根因**：
- CPU 类型验证失败（lookup_processor_type 找不到）
- DTB magic 验证失败（FDT_MAGIC 不匹配）
- 临时页表创建失败（__create_page_tables）

**调查**：
```bash
# 1. 确认 DTB 是否有效
adb shell dmesg | grep -i "machine model"
# 看到 "Machine model: ..." → DTB OK
# 没看到 → DTB 损坏或 magic 不匹配

# 2. 通过 earlycon 抓 log
# ABL cmdline 加 earlycon:
# console=ttyMSM0,115200n8 earlycon
# 看到 "Booting Linux on physical CPU" → head.S 跑到这
# 没看到 → head.S 早期就 fail
```

### 4.2 卡 "Kernel command line:" → setup_arch 失败

**根因**：
- cmdline 解析失败（malformed 字符串）
- DTB 设备树匹配失败（machine_desc 不匹配）
- 内存探测失败（memblock_add 失败）

**调查**：
```bash
# 1. 确认 cmdline 内容
adb shell cat /proc/cmdline
# 看到完整 cmdline → 解析 OK
# 看到部分 / 缺字符 → cmdline 被截断

# 2. 启用 cmdline 解析 debug
# ABL cmdline 加 initcall_debug
```

### 4.3 卡 "Calibrating delay loop..." → calibrate_delay 失败

**根因**：
- 紧循环测 CPU 频率失败（timer 不准）
- 早期 timer 异常（arch_timer 没启）
- 内存屏障导致 hang

**调查**：
```bash
# 1. 检查 dmesg 卡在哪一行
# "Calibrating delay loop... 638.72 BogoMIPS (lpj=1277440)" ← 成功
# "Calibrating delay loop..." 长时间不动 ← calibrate_delay hang

# 2. OEM cmdline 加 cpu_calibrate_loop 跳过
# 但需要确认是否硬件 timer 异常
```

### 4.4 卡 "Loading module" / initcall hang → do_basic_setup 失败

**根因**：
- 某个驱动 initcall 阻塞（I/O hang / mutex 死锁）
- 设备探测失败（设备树节点指向不存在的设备）
- 文件系统挂载失败（rootfs 找不到）

**调查**：
```bash
# 1. 启用 initcall_debug（关键开关）
# ABL cmdline 加 initcall_debug
# 启动后会打印每个 initcall 的耗时

# 2. 看 dmesg 最后几行（卡哪个 initcall）
# "calling  i2c_adap_i2c_init+0x0/0x100 @ 100" ← 启动 i2c init
# 然后卡住 → i2c 驱动有问题

# 3. 用 printk 时间戳定位
# ABL cmdline 加 printk.time=1
```

### 4.5 卡 "Run /init" 之前 → kernel_init 失败

**根因**：
- init 可执行文件找不到（rootfs 未挂载）
- init 二进制损坏
- ramdisk 损坏

**调查**：
```bash
# 1. 确认 init 二进制存在
adb shell ls -la /init
# 看到 /init → file 存在
# 看到 "No such file or directory" → rootfs 挂载失败

# 2. 检查 init 版本
adb shell /init --version
```

## 5. initcall_debug 启动慢分析

### 5.1 启用 initcall_debug

在 ABL cmdline 加 `initcall_debug`：

```bash
# 1. 通过 bootconfig（Android 12+）
adb shell setprop persist.boot.enable.initcall_debug 1
adb shell setprop persist.boot.initcall_debug.verbose 1
adb shell reboot

# 2. 或临时通过 ABL fastboot 设置
fastboot oem cmdline add "initcall_debug"
```

### 5.2 启动后 dmesg 解析

```bash
# 抓 initcall 耗时
adb shell dmesg | grep "initcall"
# 输出示例：
# [    0.050000] calling  acpi_init+0x0/0x100 @ 1
# [    0.051000] initcall acpi_init+0x0/0x100 returned 0 after 1000 usecs
# [    1.500000] calling  i2c_init+0x0/0x200 @ 800
# [    1.550000] initcall i2c_init+0x0/0x200 returned 0 after 50000 usecs
# → i2c_init 耗时 50ms，超过 10ms 需调查
```

### 5.3 慢 initcall TOP10 分析

```bash
# 按耗时排序
adb shell dmesg | grep "returned 0 after" | \
  awk '{print $NF, $0}' | sort -rn | head -10
# 输出：
# 250000 returned 0 after 250000 usecs ← 250ms 慢
# 150000 returned 0 after 150000 usecs ← 150ms
# 100000 returned 0 after 100000 usecs ← 100ms
```

## 6. Takeaway

- **start_kernel 是 boot hang 调查的"主线剧本"**：dmesg 哪一行 → 对应哪个函数
- **30+ 调用顺序**：极早期（10ms）→ 架构（200ms）→ 内存（300ms）→ 调度（5ms）→ 中断（5ms）→ 时间（10ms）→ console（50ms）→ calibrate（500ms）→ do_basic_setup（800ms）→ rest_init（50ms）
- **5 个常见 hang 点**：head.S / setup_arch / calibrate_delay / do_basic_setup / kernel_init
- **🔴 高风险函数**：setup_arch（cmdline 错）、calibrate_delay（timer 错）、do_basic_setup（驱动 initcall 错）
- **initcall_debug 必备**：排查"启动卡某阶段但不知道卡哪"的杀手锏
- **dmesg 时间锚点**：从 0ms 到 1500ms（Run /init）每 100ms 应该有进展，否则就是 hang
