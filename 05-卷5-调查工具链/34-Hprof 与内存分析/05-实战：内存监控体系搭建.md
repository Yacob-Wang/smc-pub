## 1. 背景:为什么需要自动化内存监控

### 1.1 "被动修"模式的 3 大痛点

04 SOP 流程图的工作模式是"被动修":

**3 大痛点**:
1. **响应延迟**——用户先发现 OOM,投诉到客服,客服反馈到开发,平均 24h
2. **现场丢失**——OOM 发生后现场可能丢失,无 hprof 难复现
3. **团队放大**——每个新人都要重新学 SOP,无法规模化

**架构师视角**:
- → 所以:**"被动修"模式在 10+ 人团队不可持续**——必须升级为"主动防"
- → 所以:**监控体系的核心价值 = "5min 报警 + 30min 自动定位 + 1h 修复"**——把 24h 缩短到 5min
- → 所以:**监控是"治理"的基础设施**——没有数据,一切治理都是猜

### 1.2 监控体系的 3 大价值

**3 大价值**:
1. **早发现**——线上 OOM 在 5min 内报警,不等用户投诉
2. **快定位**——自动 dump + 解析 + 报告,30min 内定位到 6 大案例之一
3. **可治理**——历史趋势 + 报警阈值 + 容量规划,形成"治理基线"

**架构师 3 句话总结**:
1. **"监控 = 治理基础设施"**——没有监控的稳定性是"听天由命"
2. **"5min 报警 + 30min 定位"**——这是 24h → 5min 的核心价值
3. **"治理基线是终态"**——从"报警驱动"到"永不发生"是演进方向

## 2. 4 层监控架构:采集 / 上报 / 存储 / 报警 Dashboard

### 2.1 全景图:从设备到 Dashboard 的数据流

```
[Android 设备]
  │ 第 1 层:数据采集
  ├─ dumpsys meminfo(每 5min 一次)
  ├─ perfetto heapprofd(每 30min 60s 采样)

  ↓
[第 2 层:数据上报]

  └─ 压缩 / 批量 / 重试
  │
  ↓
[第 3 层:数据存储]
  ├─ Prometheus(时序数据库,主用)
  ├─ InfluxDB(时序数据库,备选)
```

**架构师视角**:
- → 所以:**4 层架构是行业标准**——采集 / 上报 / 存储 / 报警,缺一不可
- → 所以:**第 1 层是数据源,决定"能监控什么"**——见 §2.2
- → 所以:**第 4 层是"看到",决定"能多快响应"**——见 §2.5

### 2.2 第 1 层:数据采集(dumpsys / perfetto / LeakCanary / 业务埋点)

**4 大数据源**:

| 数据源 | 采集频率 | 数据量 | 工具 |
|-------|---------|--------|------|
| **dumpsys meminfo** | 5min / 次 | 1-2KB / 次 | adb / 自动化脚本 |
| **perfetto heapprofd** | 30min / 60s 采样 | 50-200MB / 60s | perfetto daemon |
| **LeakCanary 灰度** | 实时(onDestroy 后 5s) | 200KB-2MB / 报告 | LeakCanary SDK |
| **业务埋点 OOM / LMKD** | 实时(事件触发) | 1-5KB / 事件 | 业务代码 + 监控 SDK |

**架构师视角**:
- → 所以:**4 大数据源覆盖 04 §1.1 6 大案例的全部监控点**——Java Heap / Native / Leak / 分配速率 / OOM 频率
- → 所以:**采集频率决定"数据精度"vs"性能开销"**——5min 平衡点
- → 所以:**dumpsys 必装(任何阶段),perfetto 灰度装(线上 10% 灰度)**

### 2.3 第 2 层:数据上报(本地 → 后端)

**3 种上报方式**:

| 方式 | 协议 | 频率 | 适用 |
|------|------|------|------|
| **HTTP POST** | HTTPS | 实时 / 5min | 简单场景,小团队 |
| **OpenTelemetry SDK** | OTLP | 实时 | 中大型团队,可观测性统一 |
| **批量 + 压缩** | HTTPS | 5min 批量 | 数据量大,弱网场景 |

**典型 HTTP POST 代码**(Android 端):
```java
// MemoryReporter.kt - dumpsys meminfo 上报
class MemoryReporter(private val api: String) {
  fun report() {
    val memInfo = collectMemInfo()  // dumpsys meminfo 解析
    val json = JSONObject().apply {
      put("pkg", "com.example.app")
      put("java_heap_mb", memInfo.javaHeap)
      put("native_heap_mb", memInfo.nativeHeap)
      put("graphics_mb", memInfo.graphics)
      put("leak_count", memInfo.leakCount)
      put("timestamp", System.currentTimeMillis())
    }
    // 异步上报
    Thread {
      URL(api).openConnection().apply {
        requestMethod = "POST"
        setRequestProperty("Content-Type", "application/json")
        doOutput = true
        outputStream.use { it.write(json.toString().toByteArray()) }
      }
    }.start()
  }
}
```

**架构师视角**:
- → 所以:**上报 5min 频率平衡实时性 vs 流量**——5min 间隔,弱网容忍
- → 所以:**批量 + 压缩省 80% 流量**——gzip 压缩,单条 1KB → 200B
- → 所以:**失败重试 3 次**——监控链路不可靠是常态

### 2.4 第 3 层:数据存储(Prometheus / InfluxDB)

**2 大时序数据库选型**:

| 维度 | Prometheus | InfluxDB |
|------|-----------|----------|
| **拉/推模型** | 拉(pull) | 推(push) |
| **生态** | 云原生标准,AlertManager 配套 | 时序数据库,自定义 Query |
| **写入吞吐** | 中等 | 高 |
| **查询语言** | PromQL | Flux / InfluxQL |
| **小团队(< 10 人)** | ✅ 推荐 | ⚠️ 重 |
| **大型团队(> 50 人)** | ✅ 多机房 | ✅ 多机房 |

**Prometheus 选型依据**:
- **拉模型**——客户端无需主动 push,Prometheus server 定期拉取
- **PromQL**——成熟查询语言,支持聚合 / 阈值 / 趋势
- **AlertManager**——配套告警系统,直接对接飞书 / 钉钉

**架构师视角**:
- → 所以:**小团队用 Prometheus 即可**——单实例 7-30 天数据足够
- → 所以:**大型团队加 OpenTelemetry Collector 中转**——统一多语言 / 多数据源
- → 所以:**数据保留 7-30 天**——7 天日常,30 天排查

### 2.5 第 4 层:报警 + Dashboard(Grafana)

**Grafana Dashboard 5 大面板**:

1. **Java Heap 时间序列**——折线图,看趋势

4. **分配速率**——热力图,看高峰时段
5. **OOM 频率**——单值 + 趋势,看 P99

**AlertManager 报警规则示例**:
```yaml

  - name: memory_alerts
    rules:
      - alert: JavaHeapHigh
```

## 3. 5 大关键指标

### 3.1 指标 1:Java Heap 总占用

**采集方式**:`dumpsys meminfo` 解析 `Java Heap` 字段
**采集频率**:5min / 次
**存储时长**:30 天
**告警阈值**:**> 200MB 持续 5min 警告,> 300MB 持续 5min 失败**

**为什么是这个阈值**:
- 普通 app Java Heap 80-150MB
- 中度 app 150-200MB
- 重度 app 200-300MB
- > 300MB 必有问题

**架构师视角**:
- → 所以:**Java Heap 是 04 §1.1 6 大案例的"通用告警"**——4 类泄漏都触发 Java Heap 涨
- → 所以:**200MB 阈值是行业经验值**——Android Vitals 2024 数据

### 3.2 指标 2:Native Heap + Graphics 总占用

**采集方式**:`dumpsys meminfo` 解析 `Native Heap` + `Graphics` 字段
**采集频率**:5min / 次
**存储时长**:30 天
**告警阈值**:**Native Heap > 200MB 警告,> 300MB 失败;Graphics > 100MB 警告,> 200MB 失败**

**为什么是这个阈值**:
- Bitmap 加载 + 解码 + 缓存 = Native + Graphics 大头
- 普通 app 100-200MB
- 图库 / 相机 app 200-400MB(正常)
- > 400MB 必有泄漏

**架构师视角**:
- → 所以:**Native Heap 是 04 案例 2 (Bitmap) / 案例 5 (Native 句柄)的告警**——两个都触发
- → 所以:**Graphics > 100MB 必查**——图库 app 也要看

### 3.3 指标 3:Leak 数量(LeakCanary 自动检测)

**采集方式**:LeakCanary SDK 自动检测 + HTTP 上报
**采集频率**:实时(onDestroy 后 5s)
**存储时长**:30 天
**告警阈值**:**> 0 立即报警**

**为什么是 0**:
- Leak 是"确定性 bug"——出现就是 bug,不是抖动
- 立即报警可让开发 5min 内介入

**架构师视角**:
- → 所以:**Leak 数 0 容忍**——1 个就报,不延迟
- → 所以:**LeakCanary 灰度 10%**——Release 包也开灰度(可关闭 Release 默认)
- → 所以:**Leak 报告 200KB-2MB**——含 hprof,直接分析

### 3.4 指标 4:分配速率(perfetto heapprofd 采样)

**采集方式**:perfetto heapprofd `heap_profile_allocation` 聚合
**采集频率**:30min / 60s 采样
**存储时长**:7 天(数据量大)
**告警阈值**:**分配速率 > 10MB/s 持续 60s 警告,> 50MB/s 持续 60s 失败**

**为什么是这个阈值**:
- 普通 app 分配速率 1-5MB/s
- 高频分配 app(图库 / 列表滑动)5-15MB/s
- 抖动 + 持续 > 10MB/s 必有优化空间
- > 50MB/s 必有泄漏 / 频繁创建

**架构师视角**:
- → 所以:**分配速率是"早期预警"**——OOM 之前先报警
- → 所以:**perfetto 灰度 10% 即可**——5-15% 开销可控
- → 所以:**采样 60s 足够**——太短数据不准,太长文件爆炸

### 3.5 指标 5:OOM / LMKD 频率(业务埋点)

**采集方式**:业务代码捕获 OOM / LMKD 事件 + 上报
**采集频率**:实时(事件触发)
**存储时长**:90 天(长期分析)
**告警阈值**:**OOM 率 > 0.1% 立即报警;LMKD 率 > 1% 警告**

**为什么是这个阈值**:
- Android Vitals 标准:OOM 率 < 0.1% 算"健康"
- > 0.1% 进入"次健康",需要关注
- > 0.47% 进入"黄色阈值",影响商店评分
- > 1% 必有问题

**架构师视角**:
- → 所以:**OOM 率是"用户感知"指标**——其他指标是"预警",这个是"真痛"
- → 所以:**OOM 事件必报**——Throwable 截 stack + 业务参数
- → 所以:**LMKD 率高是"次健康"**——不立即 OOM 但要关注

## 5. 6 类报警阈值设计

### 5.1 案例 1 Activity 泄漏:Leak 数 > 0 立即报警

**监控点**:
- 指标:Leak 数量(LeakCanary SDK)
- 阈值:> 0 立即报警
- 持续时间:0s(立即)

**告警规则**:
```yaml
- alert: ActivityLeakDetected
  expr: leak_count{app="com.example.app", type="Activity"} > 0
  for: 0m
  annotations:
    summary: "Activity 泄漏立即处理"
    runbook: "参考 04 §2.1 修复 commit: mHandler.removeCallbacksAndMessages(null)"
```

**架构师视角**:
- → 所以:**Activity 泄漏是"确定性 bug"**——0 容忍
- → 所以:**修复模式固定**:`mHandler.removeCallbacksAndMessages(null)`
- → 所以:**单 commit 修复时间 5min**

### 5.2 案例 2 Bitmap 暴涨:Native Heap > 300MB 报警

**监控点**:
- 指标:Native Heap(perfetto 持续采样)
- 阈值:> 300MB 持续 5min 警告,> 500MB 持续 5min 失败
- 持续时间:5min

**告警规则**:
```yaml
- alert: NativeHeapHigh
  expr: native_heap_mb{app="com.example.app"} > 300
  for: 5m
  annotations:
    summary: "Native Heap > 300MB 持续 5min,可能是 Bitmap 暴涨"
    runbook: "参考 04 §2.2 修复 commit: setImageBitmap(null) + recycle()"
```

**架构师视角**:
- → 所以:**Native Heap 是 Bitmap 暴涨的"早期信号"**——Java Heap 不涨但 Native 涨
- → 所以:**300MB 阈值是经验值**——图库 / 相机 app 200-400MB 正常
- → 所以:**单 commit 修复时间 30min**——需要找适配器逻辑

### 5.3 案例 3 Handler 堆积:切后台 Java Heap 释放 < 50% 报警

**监控点**:
- 指标:切后台后 Java Heap 释放比例
- 阈值:释放 < 50% 持续 3 次切后台
- 持续时间:3 个切后台周期

**告警规则**:
```yaml
- alert: HandlerAccumulation
  expr: java_heap_release_ratio{app="com.example.app"} < 0.5
  for: 3
  annotations:
    summary: "切后台 Java Heap 释放 < 50%,可能是 Handler 消息堆积"
    runbook: "参考 04 §2.3 修复 commit: WeakReference 包裹 Activity"
```

**架构师视角**:
- → 所以:**Handler 堆积是"切后台不释放"的根因**——其他泄漏也会
- → 所以:**50% 阈值是经验值**——正常切后台释放 70-80%
- → 所以:**3 次切后台避免误报**——单次可能抖动

### 5.4 案例 4 静态缓存:Java Heap 后台增长 > 10MB/h 报警

**监控点**:
- 指标:后台 1h Java Heap 增长
- 阈值:> 10MB/h 持续 3h
- 持续时间:3h

**告警规则**:
```yaml
- alert: StaticCacheGrowing
  expr: delta(java_heap_mb{app="com.example.app"}[1h]) > 10
  for: 3h
  annotations:
    summary: "后台 Java Heap 持续增长 > 10MB/h,可能是静态缓存未清"
    runbook: "参考 04 §2.4 修复 commit: 改用 LruCache"
```

**架构师视角**:
- → 所以:**静态缓存是"慢漏"**——单次增长不大但持续累加
- → 所以:**3h 阈值避免抖动**——单次增长可能是缓存预热
- → 所以:**增长速率是关键**——绝对值阈值不适用

### 5.5 案例 5 Native 句柄:fd 数 > 1000 报警

**监控点**:
- 指标:lsof fd 数
- 阈值:> 1000 持续 5min
- 持续时间:5min

**告警规则**:
```yaml
- alert: NativeHandleLeak
  expr: open_fds{app="com.example.app"} > 1000
  for: 5m
  annotations:
    summary: "open fd > 1000 持续 5min,可能是 Cursor / IO 句柄未关"
    runbook: "参考 04 §2.5 修复 commit: cursor.use { } Kotlin"
```

**架构师视角**:
- → 所以:**fd 累积是 Native 句柄泄漏的"早期信号"**——OOM 之前先报警
- → 所以:**1000 阈值是经验值**——正常 app < 200
- → 所以:**StrictMode 必开**——开发期就能捕到

### 5.6 案例 6 跨进程泄漏:ServiceConnection 数 > 50 报警

**监控点**:
- 指标:ServiceConnection 数量(LeakCanary watch)
- 阈值:> 50 持续 5min
- 持续时间:5min

**告警规则**:
```yaml
- alert: ServiceConnectionLeak
  expr: service_connection_count{app="com.example.app"} > 50
  for: 5m
  annotations:
    summary: "ServiceConnection 累积 > 50,可能是 bindService 没 unbind"
    runbook: "参考 04 §2.6 修复 commit: unbindService(mConn)"
```

**架构师视角**:
- → 所以:**ServiceConnection 累积是"慢漏"**——每次 bind 都 +1
- → 所以:**50 阈值是经验值**——正常 app < 10
- → 所以:**自定 watcher**——LeakCanary 默认不 watch ServiceConnection

### 5.7 6 类阈值速查表

| 案例 | 监控点 | 阈值 | 持续时间 | 修复模式 |
|------|-------|------|---------|---------|
| **1 Activity 泄漏** | Leak 数量 | > 0 | 0s | mHandler.remove |
| **2 Bitmap 暴涨** | Native Heap | > 300MB | 5min | setImageBitmap(null) |
| **3 Handler 堆积** | 切后台释放比例 | < 50% | 3 次切后台 | WeakReference |
| **4 静态缓存** | 后台增长速率 | > 10MB/h | 3h | LruCache |
| **5 Native 句柄** | fd 数 | > 1000 | 5min | cursor.use |
| **6 跨进程泄漏** | ServiceConnection 数 | > 50 | 5min | unbindService |

## 6. 持续优化:从"报警"到"预防"

### 6.1 Level 1 报警驱动(被动修)

**核心**:监控报警 → 人工介入 → 修复
**响应时间**:5min 报警 + 30min 定位 + 1h 修复
**适用阶段**:小型团队 / 监控 0 → 1
**投入产出比**:50x

**架构师视角**:
- → 所以:**Level 1 是"基础"**——必须有,但不是终态
- → 所以:**90% 团队停在 Level 1**——能覆盖大部分 case

### 6.2 Level 2 趋势预警(主动防)

**核心**:趋势分析 → 提前预警 → 主动优化
**响应时间**:1 周趋势 → 提前 1 周预警
**适用阶段**:中等团队 / 监控 1 → 2
**投入产出比**:20x

**关键能力**:
- **历史趋势对比**——同比 / 环比
- **异常检测**——基于历史数据的阈值
- **趋势预测**——线性回归 / 季节性分析

**架构师视角**:
- → 所以:**Level 2 是"治理"**——从"被动修"到"主动防"
- → 所以:**趋势预警需要"时间窗"**——至少 1 周历史数据

### 6.3 Level 3 治理基线(永不发生)

**核心**:Code Review + 静态检查 → 从源头杜绝
**响应时间**:0(永不发生)
**适用阶段**:大型团队 / 监控 2 → 3
**投入产出比**:10x

**关键能力**:
- **Lint 规则**——自动检测 `static Handler` / `static Map` 等危险模式
- **Code Review CheckList**——Review 时必查 6 大修复模式
- **LeakCanary 集成到单测**——CI 跑 LeakCanary,失败阻断合并

**架构师视角**:
- → 所以:**Level 3 是"终态"**——0 报警,0 OOM
- → 所以:**静态检查 + 治理基线是 Level 3 核心**——Code Review 必查清单
- → 所以:**"6 大修复模式"是治理基线的核心**——每个新人都要背

### 6.4 Level 4 容量规划(成本控制)

**核心**:基于趋势预测容量 / 优化成本
**响应时间**:季度规划
**适用阶段**:大型团队 / 监控 3 → 4
**投入产出比**:5x

**关键能力**:
- **内存使用趋势**——线性回归预测未来 3-6 月
- **优化 ROI 排序**——按"投入 / 节省"排序
- **资源预算**——季度容量规划

**架构师视角**:
- → 所以:**Level 4 是"战略层"**——稳定性 = 商业竞争力
- → 所以:**容量规划需要"业务感知"**——纯技术团队做不到

### 6.5 4 级演进路径速查

| Level | 状态 | 响应时间 | 投入 | 适用 |
|-------|------|---------|------|------|
| **L1 报警驱动** | 被动修 | 5min | 1-2 天 | 任何 |
| **L2 趋势预警** | 主动防 | 1 周 | 8-17 天 | 10+ 人 |
| **L3 治理基线** | 永不发生 | 0 | 20-30 天 | 30+ 人 |
| **L4 容量规划** | 商业竞争力 | 季度 | 持续 | 50+ 人 |

**架构师铁律**:
- **"L1 是入门,L2 是骨干,L3 是终态"**——99% 团队应做到 L3
- **"L4 是商业问题"**——纯技术团队可不做

## 7. 端到端实战 + 1 周运营数据

### 7.1 案例背景:某 IM app 内存监控从 0 到 1

**环境**:
- 团队规模:25 人(中等)
- 方案:Prometheus + Grafana(§4.2)
- 部署周期:8 天
- 投入:2 个 SRE 工程师 + 1 个 Android 工程师

### 7.2 Step 1-3:第 1 层数据采集 + 第 2 层上报

**第 1 层:数据采集**(`MemoryReporter.kt`):
```kotlin
class MemoryReporter(private val api: String) {
  fun report() {
    val memInfo = collectMemInfo()  // dumpsys meminfo 解析
    val json = JSONObject().apply {
      put("pkg", "com.example.im")
      put("java_heap_mb", memInfo.javaHeap)
      put("native_heap_mb", memInfo.nativeHeap)
      put("graphics_mb", memInfo.graphics)
      put("leak_count", memInfo.leakCount)
      put("oom_count", memInfo.oomCount)
      put("timestamp", System.currentTimeMillis())
    }
    Thread {
      URL(api).openConnection().apply {
        requestMethod = "POST"
        setRequestProperty("Content-Type", "application/json")
        doOutput = true
        outputStream.use { it.write(json.toString().toByteArray()) }
      }
    }.start()
  }
}
```

**第 2 层:上报**:
- 5min 一次
- gzip 压缩
- 失败重试 3 次

### 7.3 Step 4-5:第 3 层存储 + 第 4 层报警 Dashboard

**第 3 层:Prometheus 配置**(`prometheus.yml`):
```yaml
scrape_configs:
  - job_name: 'android_memory'
    scrape_interval: 30s
    static_configs:
      - targets: ['<server>:9100']
```

**第 4 层:Grafana Dashboard + Alert**:
- 5 大面板(Java Heap / Native / Leak / 分配速率 / OOM 频率)

### 7.4 Step 6-7:阈值 + 1 周运营数据

**部署后 1 周运营数据**(2024-Q3 真实数据,脱敏后):

| 指标 | 部署前 | 部署后 1 周 | 变化 |
