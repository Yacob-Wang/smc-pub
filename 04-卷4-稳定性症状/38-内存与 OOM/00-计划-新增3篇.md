## 三、26.7 outline：`07-proc节点文件深度解读-11大文件从读到诊断.md`

### 一句话定位
**11 个 `/proc` 内存节点文件逐一讲透——读什么字段、看什么数算异常、对应内核哪个函数、是哪个机制的产物。**

### 章节结构（6 节 + 4 附录）

#### §1 背景:为什么 proc 节点文件要单写一篇（300-500 字）
- 1.1 工程师的困惑:看到 `proc/slabinfo` 100+ 行,哪个字段是泄漏信号?
- 1.2 三大覆盖空白:33 章 03 篇只给速查(3 行/文件),没讲"怎么读 / 什么数算异常 / 对应哪个内核机制"
- 1.3 本篇 11 文件的选取标准:bugreport 抓取 + 工程师 80% 取证时间都花在这 11 个上

#### §2 系统级账本:proc/meminfo / proc/vmstat / proc/zoneinfo
- 2.1 `/proc/meminfo` 4 段(全局 / Buddy / DMA / Slab)字段表 + 异常阈值
  - **关键阈值**:MemFree < 100MB 紧,MemAvailable < 1GB 触发 lmkd 高频,CmaFree=0 已无 CMA,Cached > 50% 总内存触发回收
  - **对应内核**:`fs/proc/meminfo.c` → 读 `vm_stat[]` `nr_free_pages()` 等
- 2.2 `/proc/vmstat` 155 个 VM 计数器
  - **3 大类**:页面分配(pgalloc/pgfree)、回收(pgscan/pgsteal)、压缩(compact_*/migrate_*)
  - **OOM 关键指标**:`pgscan_kswapd / pgsteal_kswapd`(回收效率)/ `allocstall_*`(直接回收)/ `oom_kill`(杀进程)
  - **实战样本**:`pgscan_kswapd=2620134 / pgsteal_kswapd=2544671 = 97% 回收效率`
- 2.3 `/proc/zoneinfo` Node/Zone/Page 3 层地图
  - **关键字段**:min / low / high / promo(4 个水线)
  - **实战样本**:Normal zone `free=22915` 略低于 `low=7626` → 已穿过 low 水位

#### §3 分配器层:proc/slabinfo / proc/buddyinfo / proc/pagetypeinfo
- 3.1 `/proc/slabinfo` 内核 slab 分配器
  - **3 大泄漏信号**:`dentry` / `inode` / `task_struct` 长期不释放
  - **实战样本**:`tsk_l_cache=1184` / `tranmem_task_struct=4110` / `dm_bufio_buffer-4-25=2626`(dm-verity 缓存,正常)
- 3.2 `/proc/buddyinfo` Buddy 分配器各 order 空闲块
  - **碎片判断**:`order-0` 大量空闲 + `order-N` 0 空闲 = 严重碎片
  - **实战样本**:节选 12 列(每个 order 4 块,共 11 order)
- 3.3 `/proc/pagetypeinfo` 按 migratetype 分类(节略,只讲用途)

#### §4 虚拟地址层:proc/vmallocinfo
- 4.1 `/proc/vmallocinfo` 全部 vmalloc/ioremap 映射
  - **5 大来源**:`vmalloc` / `ioremap` / `vmap` / `pcpu_mem_zalloc` / `persistent_ram_new`
  - **实战样本**:`copy_process`(fork 栈)1.2 万次 × 20KB = 240MB;`ioremap_prot` 8KB × 4 万次 = 320MB(驱动注册)
  - **泄漏判断**:同名 caller 数量异常增长 = 泄漏

#### §5 内存压力 + zRAM:proc/pressure/memory / proc/zraminfo / proc/shmemstat / proc/loadavg
- 5.1 `/proc/pressure/memory` PSI some/full avg10
  - **阈值**:`some avg10 > 20%` 系统已卡,`full avg10 > 5%` 内存吃紧
- 5.2 `/proc/zraminfo` zRAM 块设备状态(空文件,讲"为什么空")
- 5.3 `/proc/shmemstat` shmem 统计(空文件,讲"为什么空")
- 5.4 `/proc/loadavg` 负载,1 行(轻量,跟内存关系)

#### §6 实战案例（2 个,均用 0xffffff13 样本）
- 6.1 案例 A:从 `proc/meminfo` `CmaFree=0` 推断"拍照/视频大块 DMA 分配会失败"
- 6.2 案例 B:从 `proc/vmstat` `pgscan_kswapd=2620134` + `proc/zoneinfo` `free<low` 推断"系统刚经历一波内存压力但扛住了"

#### §7 总结:5 条 Takeaway
- 11 文件的"看 / 不看" 速查矩阵
- 4 大诊断信号(回收效率 < 90% / allocstall > 100 / oom_kill > 0 / CmaFree = 0)
- 跟 15 章 07 篇(内存压力检测)的衔接

#### 附录

- B 路径对账表
- C 量化数据自检表
- D 工程基线表

## 四、26.8 outline：`08-dumpsys-meminfo全设备级与procstats解读.md`

### 一句话定位
**15 章 06 篇只讲 dumpsys meminfo 单进程 PSS,本篇补"全设备级 12 大 OOM adjustment 分组" + "dumpsys procstats 5 大状态"——把 AMS 内存账本的全貌补完。**

### 章节结构（5 节 + 4 附录）

#### §1 背景:为什么 dumpsys_meminfo 要分两篇讲(300-400 字)
- 1.1 15.06 已讲:单进程 PSS 6 大模块(Java/Native/Graphics/Code/Stack/Other)
- 1.2 本篇补:全设备级 `Total RSS by OOM adjustment` 12 大分组(Native / System / Persistent / Persistent Service / Foreground / Visible / Perceptible / Perceptible Low / A Services / Home / Previous / Cached)
- 1.3 跟 15.06 互补不重复:本篇**不重复**单进程解读,只讲"全设备视角" + "dumpsys procstats"

#### §2 dumpsys_meminfo 全设备级:Total RSS by OOM adjustment
- 2.1 12 大分组与 adj 体系映射
  - **adj=-1000** Native / System
  - **adj=0-100** Persistent / Persistent Service
  - **adj=100-200** Foreground
  - **adj=200-300** Visible
  - **adj=300-500** Perceptible / Perceptible Low
  - **adj=500-700** A Services / Home
  - **adj=700-1000** Previous / Cached
- 2.2 工程师的"全设备视角"诊断思路
  - **3 大信号**:
    1. `system_server` > 1GB → 怀疑 AMS 内部组件泄漏
    2. `Cached` > 30% 总内存 → 触发 lmkd 优先杀后台
    3. `Foreground + Visible > 50%` 总内存 → 前台应用过度占用
- 2.3 实战样本:0xffffff13 抓取
  - `system_server` 733MB(8GB 设备正常)
  - `Foreground + Visible = 3.3GB` 占 43% → **前台应用内存偏紧**
  - `Cached = 2.3GB` 偏大 → **lmkd 优先杀 Cached 组**

#### §3 dumpsys_procstats 解读
- 3.1 5 大状态字段含义
  - `Persistent`(系统持久服务)
  - `Top`(当前前台 Activity)
  - `Imp Fg`(重要前台)
  - `Bnd Fgs`(绑定前台服务)
  - `Fgs`(前台服务)
  - `Service`(普通服务)
  - `Receiver`(广播接收者)
  - `(Last Act)`(最近活跃)
- 3.2 怎么用:不同时刻的"百分比快照"看 adj 误配
  - **典型 adj 误配**:某进程长期占 adj 900+(perceptible)但应该被降到 950+(previous)没降 = 泄漏
- 3.3 实战样本
  - `com.transsion.overlaysuw` TOTAL 21% 全部 Top → 正常(前台上拉 UI)
  - `com.transsion.kolun.aiservice` 1000 用户 TOTAL 12% 全部 Bnd Fgs → **可疑**:AI service 不该占 Bnd Fgs 这么久
  - `com.google.android.gms` TOTAL 20% 分 5 个子状态 → 正常(GMS 多 binder)

#### §4 单进程 vs 全设备级:什么时候用哪个
- **单进程 PSS(15.06)**:定位"某个 App 内存怎么涨的"
- **全设备级(本篇)**:定位"系统全局内存压力 / 杀进程优先级"
- **procstats(本篇)**:定位"adj 误配 / 进程状态百分比异常"

#### §5 实战案例
- 5.1 案例 A:从 0xffffff13 抓取目录 `dumpsys_meminfo` 看 `system_server 733MB` → 推断 8GB 设备健康
- 5.2 案例 B:从 `dumpsys_procstats` 看 `kolun.aiservice` 12% Bnd Fgs → 推断 AI service 持有 binder 引用未释放

#### §6 总结:5 条 Takeaway
- 12 大 OOM adjustment 分组速记口诀
- 3 大诊断信号阈值
- 跟 15.06 / 15.13(adj 体系)的衔接

## 五、26.9 outline：`09-平台特有调试工具-MTK-mmstat-ion-dmabuf-gpu-memory解读.md`

### 一句话定位
**Pixel/AOSP 公开文档基本脱钩的 vendor 平台工具:MTK `mmstat2` 4 大 trace、ION/DMA buffer、GPU memory、zRAM 状态——AOSP 调通后必须再过这关才能上产线。**

### 章节结构（6 节 + 4 附录）

#### §1 背景:为什么 vendor 工具要单写一篇(300-400 字)
- 1.1 smc-pub 主线是 Pixel 7/8(AOSP 公开基线),但产线 70% 设备是 MTK/高通/三星
- 1.2 vendor 工具的共同特点:**只在 bugreport 抓取,不开源,文档稀缺**——smc-pub 缺位最严重
- 1.3 本篇 4 类工具:MTK mmstat / ION / DMA / GPU memory

#### §2 MTK mmstat / mmstat2 4 大 trace ⭐核心
- 2.1 `mmstat_trace_meminfo` 13 个字段(节拍采样)
  - **13 字段含义**:`memfree / memavailable / cached / swapcached / swaptotal / anon / file / dirty / ..`
  - **节拍**:1s 一次(用户态 mmstat 进程)
- 2.2 `mmstat_trace_vmstat` 8 个关键指标
  - `pgscan / pgsteal / allocstall / compact_*` —— 跟 `/proc/vmstat` 子集对齐
- 2.3 `mmstat_trace_buddyinfo` 12 个 order 空闲块
  - **碎片判断**:看 order-0 vs order-N 比例变化
- 2.4 `mmstat_trace_proc` 每进程 4 元组(adj / oom_score_adj / RSS_kB / swap_kB)
  - **核心价值**:**时间序列看进程 adj 变化和 PSS 涨速**
- 2.5 实战样本(0xffffff13):
  - `mmstat_trace_proc: 1981(system_server),-900,651732,0` → adj=-900 PSS 651KB
  - 10 个采样点(135s → 147s)看 system_server PSS:651732 → 1029416 → 1008464 → 883176,**先涨后跌**,说明 AMS 清理一波

#### §3 ION 内存历史
- 3.1 `/d/ion/ion_heap_debug` + `ion_history` 路径
  - **5 大 heap**:`system` / `system_contig` / `cgpu` / `secure` / `carveout`
  - **历史记录**:ION 分配 / 释放 / 失败事件
- 3.2 实战样本:0xffffff13 抓取 `ion_history` / `sys_ion_history` 都是 0 字节
  - **3 大可能根因**:
    1. MTK 这版内核 ION 历史 buffer 没开(debugfs 默认关)
    2. 抓取脚本没权限(root 才能读)
    3. 设备重启后历史被清(只保存最近 N 条)
  - **怎么验证**:`adb shell ls -la /d/ion/` → 看是否存在;`adb shell cat /proc/cmdline | tr '\0' '\n' | grep ion`

#### §4 DMA / dmabuf
- 4.1 `/d/dma_buf/bufinfo` + `new_dma_bufinfo`
  - **关键字段**:`size / fd_count / exp_name / flags / ...`
  - **实战样本**:0xffffff13 `new_dma_bufinfo` 64KB(13 行)—— GPU / Camera / 视频解码的 buffer 详情
- 4.2 `dma_bufinfo` 0 字节:同 ION,可能是 debugfs 路径变了(AOSP 17 拆 `dma_buf/bufinfo` 到 `dma_buf/bufinfo`)
- 4.3 泄漏信号:`exp_name=`<具体驱动>`` 数量持续增长 = 该驱动泄漏

#### §5 GPU memory
- 5.1 Mali GPU 内存
  - `mali_gpu_memory` 0 字节:Mali 驱动没装 `memtrack` 接口
  - 替代:`new_gpu_memory` 461B(0xffffff13 抓取到 6 行)
- 5.2 实战样本:`new_gpu_memory` 节选
  ```
  PID    Size    RSS     PSS     Swap    Process
  ...
  ```
  - 看 GPU 内存最大进程(一般是 SurfaceFlinger / SystemUI)
- 5.3 zRAM 状态:`zram0_bdstat` 27B
  - **关键字段**:`Num_read / Num_write / ...`
  - 0xffffff13 zRAM 几乎没用(SwapFree ≈ SwapTotal),意味着 zRAM 没启用或没工作

#### §6 实战案例 + 0 字节文件判别方法学
- 6.1 案例:0xffffff13 13 个 0 字节文件分类
  - **抓取失败**(`mmstat` 0 vs `mmstat2` 45KB):脚本试了 2 次,只有 1 次成功
  - **功能未启用**(`lowmemorykiller_adj/minfree`):设备用 lmkd 不再用 LMK
  - **平台没编译**(`mali_gpu_memory`):Mali memtrack 没装
  - **运行时无数据**(`sys_mem_log`):mem_log 触发条件未命中
- 6.2 通用判别 3 步法:`路径是否存在` → `权限` → `触发条件`

#### §7 总结:5 条 Takeaway
- 4 大 vendor 工具的"看 / 不看" 速查矩阵
- 0 字节文件的 4 大根因速记
- 跟 15.05(Native 堆)、Pixel AOSP 公开工具的衔接
