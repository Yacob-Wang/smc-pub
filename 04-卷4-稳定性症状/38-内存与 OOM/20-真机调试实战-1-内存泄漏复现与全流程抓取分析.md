## 2. Step 1:5min 评估

### 2.1 4 步评估

```bash
# 1.1 看 logcat 异常名(15 秒)
$ adb logcat -d AndroidRuntime:E *:S | grep -A 30 "FATAL EXCEPTION"
```

**输出**(假设):
```
FATAL EXCEPTION: main
Process: com.example.camera, PID: 12345
java.lang.OutOfMemoryError: Out of memory on a 8388608-byte allocation by Bitmap
    at android.graphics.Bitmap.nativeCreate(Native Method)
    at android.graphics.Bitmap.createBitmap(Bitmap.java:1000)
    at com.example.camera.ImageLoader.decode(ImageLoader.java:45)
```

**关键识别**:
- `Out of memory on a 8388608-byte allocation by Bitmap` ← **类型 3 Bitmap 泄漏**(对应 26.2 §5)
- `8388608 bytes = 8MB` ← **1080p Bitmap 大小**(ARGB_8888)
- `nativeCreate` ← **Bitmap 在 native 分配**(AOSP 8+ 机制)

```bash
# 1.2 看 dumpsys_meminfo 单进程 Graphics 涨速(30 秒)
$ adb shell dumpsys meminfo com.example.camera | grep -E "Pss Total|Native Heap|Java Heap|Graphics|Threads"
```

**输出**(假设):
```
Pss Total: 480000
  Native Heap: 80000
  Java Heap: 100000
  Graphics: 300000        ← ⚠️ 300MB(正常 < 50MB)
```

**关键识别**:`Graphics: 300MB` 远超正常 — **Bitmap 泄漏典型信号**

```bash
# 1.3 看 proc/meminfo 系统级(30 秒)
$ adb shell cat /proc/meminfo | grep -E "MemAvailable|CmaFree"
```

**输出**:
```
MemAvailable: 4430020 kB    ← 健康
CmaFree: 0 kB              ← ⚠️ 链 3(对应 26.5 §2.3)
```

**关键识别**:`CmaFree=0` 加重问题

```bash
# 1.4 拉 APM 历史数据(2 分钟)
# 如果已经集成 26.13 APM SDK
$ adb shell am broadcast -a com.example.apm.DUMP_HISTORY
# 拉最近 1h 数据
```

**关键识别**:`Graphics` 涨速 = 8MB/打开一次相机 = **每次新建 8MB Bitmap 没回收**

### 2.2 30 秒决策

**初判**:**P0-1 Java OOM 闪退**(对应 26.12 §3)+ 类型 3 Bitmap 泄漏(对应 26.2 §5)

**复现策略**:反复打开相机 → 触发 5 次以上 → 抓 dumpsys + hprof

## 3. Step 2:15min 复现

### 3.1 复现脚本

```bash
# 3.1 启动 App
$ adb shell am start -n com.example.camera/.MainActivity
# 等待 App 完全启动
$ sleep 5

# 3.2 模拟"打开相机"操作
$ adb shell am start -a android.media.action.IMAGE_CAPTURE
$ sleep 3
$ adb shell input keyevent KEYCODE_BACK
$ sleep 2

# 3.3 重复 5 次
for i in 1 2 3 4 5; do
    echo "=== 第 $i 次 ==="
    adb shell am start -a android.media.action.IMAGE_CAPTURE
    sleep 3
    adb shell input keyevent KEYCODE_BACK
    sleep 2
done
```

### 3.2 实时监控

```bash
# 在另一个终端,持续监控 dumpsys meminfo
$ watch -n 5 "adb shell dumpsys meminfo com.example.camera | grep Graphics"
```

**预期输出**(每次打开涨 8MB):
```
Graphics: 32000 KB    ← 第 1 次
Graphics: 40000 KB    ← 第 2 次
Graphics: 48000 KB    ← 第 3 次
Graphics: 56000 KB    ← 第 4 次
Graphics: 64000 KB    ← 第 5 次
```

**复现成功**:`Graphics` 单调涨 8MB / 次,5 次后 64MB(假设 App 原本 0)

### 3.3 拉 logcat 实时

```bash
# 在另一个终端,持续监控 FATAL EXCEPTION
$ adb logcat -c  # 清空
$ adb logcat | grep -E "FATAL EXCEPTION|Out of memory"
```

**预期**:第 5-6 次后出现 `Out of memory on a N-byte allocation by Bitmap`

## 4. Step 3:5min 抓现场(5 件套 + hprof)

### 4.1 5 件套采集(对应 26.6 §2)

```bash
# 4.1 系统级
$ adb shell cat /proc/meminfo > /tmp/proc-meminfo.txt
$ adb shell cat /proc/vmstat > /tmp/proc-vmstat.txt
$ adb shell cat /proc/zoneinfo > /tmp/proc-zoneinfo.txt

# 4.2 进程级
$ adb shell dumpsys meminfo com.example.camera > /tmp/meminfo-pkg.txt
$ adb shell dumpsys meminfo > /tmp/meminfo-all.txt
$ adb shell dumpsys procstats > /tmp/procstats.txt

# 4.3 抓 hprof
$ adb shell am dumpheap com.example.camera /data/local/tmp/camera-oom.hprof
# 等待 5-10s(应用暂停,触发 Full GC)
$ adb pull /data/local/tmp/camera-oom.hprof /tmp/

# 4.4 抓 bugreport
$ adb shell bugreport /data/local/tmp/camera-bugreport.zip
```

## 5. Step 4:30min 分析(dumpsys + hprof)

### 5.1 dumpsys 解读(对应 26.8 §2)

```bash
# 5.1 看全设备级
$ cat /tmp/meminfo-all.txt | grep -A 20 "Total RSS by OOM adjustment"
```

**输出**(假设):
```
Total RSS by OOM adjustment:
  2,350,340K: Native
        214,917K: surfaceflinger (pid 1351)
        199,676K: zygote64 (pid 1241)
        ...
    733,068K: System
        733,068K: system (pid 1981)
  1,787,672K: Foreground
        294,820K: com.transsion.overlaysuw (pid 4127 / activities)
        ...
  1,535,564K: Visible
        268,980K: com.transsion.launcher3 (pid 4793)
  ...
  2,295,548K: Cached
        ...
```

**关键识别**:`system_server` 733MB 健康(8GB 设备 9.5%),其他正常

### 5.2 hprof 引用链分析(对应 26.10 §5)

**Step 1**:打开 `camera-conv.hprof` 在 MAT 中

**Step 2**:Leak Suspects Report

```
Leak Suspects:
  1024 instances of "com.example.camera.MainActivity" (1 instance leaked)
  Retained Heap: 89,200,000 bytes (35.7% of total)

  Leak path:
  ┬─ com.example.camera.App @ 0x12345
  │    ├─ com.example.camera.BitmapCache (static field)
  │    │    └─ java.util.LinkedHashMap
  │    │         └─ com.example.camera.MainActivity
  │    │              └─ android.widget.ImageView
  │    │                   └─ android.graphics.Bitmap @ 0xabcd (1080×1920 8MB)
  │    │                        └─ DirectByteBuffer (native 8MB)
```

**关键识别**:
- `BitmapCache` static field 持有 Activity → **典型 Bitmap 泄漏**(对应 26.2 §5)
- `LinkedHashMap` = LRU 缓存,但没容量上限
- `DirectByteBuffer` = Bitmap 像素在 native

**Step 3**:Dominator Tree

```
Total: 250 MB
├─ MainActivity (主 Activity,30MB)
│    ├─ BitmapCache (8 千个 Bitmap,150MB)        ← 释放这个能省 60% 内存
│    │    ├─ Bitmap @ 0x12345 (1080p 8MB)
│    │    ├─ Bitmap @ 0x12346 (1080p 8MB)
│    │    └─ ... (8 千个)
│    └─ Handler mHandler (1MB)
├─ Application Context (50MB)
│    └─ OkHttpClient (20MB)
└─ Glide MemoryCache (70MB)
```

**关键识别**:`BitmapCache` 占 150MB retained → **直接根因**

**Step 4**:OQL 查所有 Bitmap

```sql
SELECT toString(cl.@name), 
       @displayName,
       @shallowSize,
       @retainedSize
FROM android.graphics.Bitmap $cl
     , $cl.@displayName $obj
WHERE $obj.@retainedSize > 1000000
ORDER BY @retainedSize DESC
LIMIT 20
```

**输出**:
```
com.example.camera.Bitmap @ 0xabcd  8192  8388608    ← 8MB Bitmap
com.example.camera.Bitmap @ 0xabce  8192  8388608
... 1023 行(8MB × 1024 = 8GB,但实际 retained 60MB)
```

**关键发现**:**1024 个 8MB Bitmap,总 retained 60MB** = 每次打开相机新建 1 个 8MB Bitmap,旧的不回收

### 5.3 引用链分析

```
[Bitmap 引用链]
Bitmap @ 0xabcd (8MB)
  ↑
ImageView.mDrawable (持有 Bitmap)
  ↑
MainActivity (持有 ImageView)
  ↑
BitmapCache.cacheList (LinkedHashMap,持有 Activity)
  ↑
App.cache (static field,持有 BitmapCache)
  ↑ ← ← ← GC Root(static field 是 GC Root)
```

**关键事实**:**`App.cache` 是 static field,是 GC Root**——BitmapCache 永远不会被 GC,所以 Bitmap 永远不被回收。

### 6.2 中期修复(1-3 天)

**错误代码**(典型):
```java
public class App extends Application {
    private static BitmapCache cache = new BitmapCache();  // 静态字段,问题根源

    public void onCreate() {
        // 加载相机预览
        Bitmap preview = BitmapFactory.decodeStream(stream);
        cache.put("last_photo", preview);  // Activity 引用进 cache
    }
}

class BitmapCache {
    private Map<String, Bitmap> cacheList = new HashMap<>();
    public void put(String key, Bitmap bitmap) {
        cacheList.put(key, bitmap);  // 无容量上限
    }
}
```

**修复 1:LruCache 容量上限**(推荐)
```java
public class App extends Application {
    // 限制 10MB 容量
    private LruCache<String, Bitmap> cache = new LruCache<>(10 * 1024 * 1024) {
        @Override
        protected int sizeOf(String key, Bitmap value) {
            return value.getByteCount();  // 8MB per Bitmap
        }
    };

    public void onCreate() {
        Bitmap preview = BitmapFactory.decodeStream(stream);
        cache.put("last_photo", preview);
        // LruCache 自动 LRU 淘汰,最多 10MB
    }
}
```

**修复 2:Bitmap 不缓存进静态字段**(更彻底)
```java
public class App extends Application {
    // 只缓存路径,Bitmap 按需解码
    private LruCache<String, String> pathCache = new LruCache<>(100);

    public Bitmap getBitmap(String key) {
        String path = pathCache.get(key);
        if (path == null) return null;
        return BitmapFactory.decodeFile(path);  // 临时 Bitmap
    }
}
```

**修复 3:用 Glide / Coil 自动管理 Bitmap**(最简单)
```gradle
dependencies {
    implementation 'com.github.bumptech.glide:glide:4.16.0'
}
```

```java
// 替代手动管理
Glide.with(activity)
    .load(url)
    .placeholder(R.drawable.placeholder)
    .into(imageView);
// Glide 自动管理 Bitmap 生命周期,onDestroy 释放
```

**修复 4:Bitmap 复用池**(高级)
```java
// 使用 BitmapPool 复用 Bitmap,减少 alloc
BitmapFactory.Options options = new BitmapFactory.Options();
options.inBitmap = bitmapPool.acquire();
options.inMutable = true;
Bitmap reused = BitmapFactory.decodeStream(stream, null, options);
```

## 8. 总结:5 条 Takeaway

读这篇应能回答:

1. **"30 分钟闭环怎么走?"** ——
   - Step 1 5min 评估(看 logcat + dumpsys)
   - Step 2 15min 复现(脚本 + 反复触发)
   - Step 3 5min 抓现场(5 件套 + hprof)
   - Step 4 30min 分析(MAT 找引用链)
   - Step 5 10min 给方案(短期 + 中期 + 长期)
   - **30 分钟内出短期方案**,完整根因 1-3 天

2. **"Bitmap 泄漏怎么识别?"** ——
   - logcat:`Out of memory on a N-byte allocation by Bitmap`(类型 3)
   - dumpsys:Graphics > 50MB(8GB 设备)
   - dumpsys:Graphics 涨速 > 5MB/min
   - hprof:BitmapCache static field 持有 Activity

3. **"5 步剧本里最容易卡哪步?"** ——
   - Step 2 复现:可能因设备差异复现不了(需多设备验证)
   - Step 4 分析:MAT 学习曲线陡,新工程师不熟
   - **最关键**:Step 3 抓 hprof 必须在 OOM 前抓(应用已死抓不到)

4. **"短期 vs 中期 vs 长期方案怎么分?"** ——
   - 短期(< 5min 生效):am force-stop + 调阈值
   - 中期(1-3 天):代码 patch(LruCache 容量上限 / Glide / BitmapPool)
   - 长期(1-2 周):APM SDK 集成 + 自动化告警

5. **"为什么 BitmapCache static field 是 GC Root?"** ——
   - static field 由 Class 对象持有,Class 对象是 GC Root
   - Class 对象 → static field → BitmapCache → Activity → ImageView → Bitmap
   - 整个链都不被 GC,Bitmap 永远不释放
   - **修复**:用 LruCache 容量上限 / 用 Glide / 用 WeakReference

### E.1 复现脚本 `reproduce_bmp_leak.sh`

```bash
#!/bin/bash
# reproduce_bmp_leak.sh
# 用途:模拟用户打开相机 5 次,触发 Bitmap 泄漏 OOM
# 用法:./reproduce_bmp_leak.sh com.example.camera

set -e
PACKAGE="${1:?Usage: $0 <package_name>}"
LOOPS="${2:-5}"

echo "=== 启动 $PACKAGE ==="
adb shell am start -n "$PACKAGE/.MainActivity" 2>/dev/null
sleep 5

echo "=== 模拟打开相机 $LOOPS 次 ==="
for i in $(seq 1 $LOOPS); do
    echo "--- 第 $i 次 ---"
    adb shell am start -a android.media.action.IMAGE_CAPTURE 2>/dev/null
    sleep 3
    adb shell input keyevent KEYCODE_BACK
    sleep 2

    # 每次抓 dumpsys meminfo
    echo "[第 $i 次] Graphics:"
    adb shell dumpsys meminfo "$PACKAGE" | grep -E "Pss Total|Graphics"
done

echo "=== 复现完成,等待 OOM(可选)==="
```

### E.2 抓现场脚本 `capture_oom_scene.sh`

```bash
#!/bin/bash
# capture_oom_scene.sh
# 用途:OOM 现场 5 件套 + hprof 采集
# 用法:./capture_oom_scene.sh com.example.camera

set -e
PACKAGE="${1:?Usage: $0 <package_name>}"
OUT_DIR="${2:-/tmp/memory-oom-$(date +%Y%m%d-%H%M%S)}"
mkdir -p "$OUT_DIR"

echo "=== 5 件套采集: $PACKAGE ==="

# 1. 系统级
adb shell cat /proc/meminfo > "$OUT_DIR/proc-meminfo.txt"
adb shell cat /proc/vmstat > "$OUT_DIR/proc-vmstat.txt"
adb shell cat /proc/zoneinfo > "$OUT_DIR/proc-zoneinfo.txt"
adb shell cat /proc/slabinfo > "$OUT_DIR/proc-slabinfo.txt"
echo "✓ 系统级 4 文件"

# 2. 进程级
adb shell dumpsys meminfo "$PACKAGE" > "$OUT_DIR/meminfo-pkg.txt"
adb shell dumpsys meminfo > "$OUT_DIR/meminfo-all.txt"
adb shell dumpsys procstats > "$OUT_DIR/procstats.txt"
echo "✓ 进程级 3 文件"

# 3. hprof
echo "=== 抓 hprof(会触发 Full GC,应用暂停 5-10s)==="
adb shell am dumpheap "$PACKAGE" /data/local/tmp/oom.hprof
sleep 10
adb pull /data/local/tmp/oom.hprof "$OUT_DIR/"
echo "✓ hprof 拉到 $OUT_DIR/oom.hprof"

# 4. hprof-conv
echo "=== hprof-conv 转换 ==="
hprof-conv "$OUT_DIR/oom.hprof" "$OUT_DIR/oom-conv.hprof"
echo "✓ 转换完成 $OUT_DIR/oom-conv.hprof"

# 5. bugreport
echo "=== bugreport(5-10min)==="
adb shell bugreport /data/local/tmp/bugreport.zip
sleep 60
adb pull /data/local/tmp/bugreport.zip "$OUT_DIR/"
echo "✓ bugreport 拉到 $OUT_DIR/bugreport.zip"

echo "=== 5 件套采集完成 ==="
echo "  输出目录:$OUT_DIR"
ls -lh "$OUT_DIR/"
```

```bash
#!/bin/bash

echo "3. 选 Leak Suspects Report → Finish"
```
