# 8.5 Zygote fork 慢 / Zygote crash 调查

## 一句话开场

**Zygote 启动慢的 3 类根因**(preload GC / waitFor 阻塞 / OAT 重新校验)与 **crash 的 4 类根因**(preload OOM / class 加载失败 / OAT 损坏 / seccomp 误配),用 `kill -3` + `debuggerd` + bootstat 三个工具**30 秒内**能定位。整机调查的完整 SOP 留给第 11 章,本节只讲 Zygote 内部视角。

## 1. 核心子问题

1. Zygote 启动慢的 3 类代码点分别在哪?怎么区分?
2. Zygote 反复 fork 慢 vs 单次 fork 慢,排查思路有何不同?
3. Zygote crash 的 4 类根因分别有什么 logcat 关键词?
4. `SIGQUIT` + `debuggerd` + `tombstoned` 三个抓栈工具怎么配合?
5. `ro.boottime.zygote` / `init.svc.zygote` / `ro.boot.bootloader` 三类属性怎么用?
6. Zygote 在 epoll_wait 时,如何用 SIGQUIT 抓栈?
7. Zygote crash 后,如何拿到 tombstone(rotten tombstone 是什么)?
8. Zygote 反复崩的 critical window 怎么联动 init(7.2 已讲 service 声明,本节讲触发流程)?

## 2. 详细展开

### 2.1 Zygote fork 慢的 3 类根因

Zygote 进程内部,`runSelectLoop` 收到 fork 请求时,处理路径是:

```
fork 请求
  ↓
[1] 解析参数 (ZygoteConnection.readArguments)
  ↓
[2] 校验参数 (uid / gid / seinfo / namespace 等)
  ↓
[3] 准备 fork (resetNiceName / applyUidSecurityPolicy 等)
  ↓
[4] nativeForkAndSpecialize (真正 fork 在这里)
  ↓
[5] 子进程 specialize (Class.forName / setSchedulingPolicy)
```

**3 类根因在哪个步骤**:

| 根因类别 | 发生在 | 单次 fork 慢的耗时 | 反复 fork 慢的耗时 |
|---|---|---|---|
| **① preload GC** | 步骤 5 之后(Zygote 端) | +100-300ms | 持续 +100-300ms |
| **② waitFor 阻塞** | 步骤 4(Zygote 端) | +500ms-30s | 持续 +500ms-30s |
| **③ OAT 重新校验** | 步骤 4 之前(Zygote 端) | +1-5s | 第一次慢,后续快 |

**① preload GC**:
- 8.1 §2.3 讲过 Zygote 启动期会主动 GC 一次,但**运行期还会再次 GC**
- 当 Zygote 的 Java heap 接近上限(64MB),ART 会触发 concurrent GC → 阻塞所有 fork 请求
- **特征**:logcat 报 `art: Concurrent GC` + 单次 fork 慢但**持续**慢
- **根因**:Zygote 自己或某个 fork 出去的进程写了大量 Java 对象,触发 GC

**② waitFor 阻塞**:
- `waitFor` 在 Zygote 端是 `Os.poll(pollFds, -1)` 的封装,**理论上应该立即返回**
- 但当 Zygote 自己也持锁(比如正在处理上一个 fork 请求),**新 fork 请求会卡在锁上**
- **特征**:logcat 报 `ClassLinker wait` / `Class loading blocked` + 单次 fork 慢但**孤立**
- **根因**:ClassLinker 死锁(8.2 §4 案例 2 已讲)

**③ OAT 重新校验**:
- 步骤 4 之前,Zygote 会校验 OAT 文件完整性
- 第一次 fork 时,OAT 校验**特别慢**(因为要 page fault 加载整个 OAT)
- **特征**:logcat 报 `art: ImageSpace: Loading oat file` + 第一次慢,后续快
- **根因**:Zygote 进程被 swap out,OAT 文件被换出内存,首次 fork 触发 page fault

### 2.2 Zygote fork 慢 vs 整机 App 启动慢:怎么分诊

Zygote fork 慢的特征是"所有 App 第一次启动都慢",而**单 App 启动慢**的根因通常在 App 自己(冷启动逻辑、ContentProvider 初始化等)。**30 秒分诊 SOP**:

```bash
# 步骤 1:看 Zygote 启动时间(若本身启动就慢 → 8.1/8.2 范围)
adb shell getprop ro.boottime.zygote
adb shell getprop ro.boottime.zygote64
# 期望:< 2.5 秒(SM8550 AOSP 17)
# 超过 3 秒:Zygote 启动慢,转 8.1 §3 调查清单

# 步骤 2:看 Zygote 是否在 epoll_wait
adb shell ps -A -o PID,NAME,WCHAN | grep zygote
# 期望:WCHAN = poll 或 ep_poll
# 若 WCHAN = 其他(如 futex_wait):Zygote 卡在某把锁上,转 8.5 §2.4 抓栈

# 步骤 3:抓 Zygote 栈(对 Zygote 进程发 SIGQUIT)
adb shell ps -A | grep zygote | awk '{print $2}' | head -1
# 拿到 zygote PID
adb shell kill -3 <zygote_pid>
adb logcat -d -t 100 -b main | grep -A 50 "zygote.*signal"
# 期望:看到线程栈,主线程在 epoll_wait

# 步骤 4:看 Zygote 内存
adb shell dumpsys meminfo zygote
# 期望:Java Heap < 80MB
# 超过 150MB:8.6 内存治理
```

### 2.3 Zygote crash 的 4 类根因

**4 类根因按发生概率从高到低**:

| # | 根因 | 发生场景 | logcat 关键词 | 修复方向 |
|---|---|---|---|---|
| 1 | **preload OOM** | OEM 加 class 太多 / 4GB 设备 / OTA 后 | `OutOfMemoryError: Java heap space` in `ZygoteInit.preload` | 8.1 §4 案例 2 / 扩 heap / 移 lazy |
| 2 | **class 加载失败** | preloaded-classes 拼错 / framework.jar 与 OAT 不一致 | `ClassNotFoundException` / `NoClassDefFoundError` / `VerifyError` | 8.4 §4 案例 1 / 检查 preloaded-classes |
| 3 | **OAT 损坏** | OEM 误 push framework.jar 不重 dex2oat | `Could not load image space` / `bad elf magic` | 8.2 §4 案例 1 / 重 dex2oat |
| 4 | **seccomp 误配** | OEM 改 SELinux / sepolicy 漏配置 | `seccomp violation` / `audit: ... denied` | 检查 sepolicy / 用 `audit2allow` 修复 |

**每类的进一步诊断**已在 8.1/8.2/8.4 案例中给出,本节不重复。

### 2.4 抓栈工具链:SIGQUIT + debuggerd + tombstoned

**3 个工具的分工**:

| 工具 | 作用 | 触发方式 | 输出位置 |
|---|---|---|---|
| `SIGQUIT`(kill -3) | 让目标进程打印所有线程栈到 logcat | `adb shell kill -3 <pid>` | logcat tag = `DEBUG` |
| `debuggerd` | 接 attach 进程,生成详细 backtrace + 寄存器 | `debuggerd -b <pid>`(主动)或 crash 时自动 | `/data/tombstones/tombstone_<N>` |
| `tombstoned` | 接收 debuggerd 输出的 daemon,管理 tombstone 文件 | 自动 | `/data/tombstones/` |

**SIGQUIT 用法**(对 Zygote 抓栈):

```bash
# 1. 找到 Zygote PID
adb shell ps -A | grep zygote
# 输出:
#   zygote   123  1  123456 56789 ... poll    0000000000 S
# 2. 发 SIGQUIT
adb shell kill -3 123
# 3. 等 1-2 秒,看 logcat
adb logcat -d -b main -s DEBUG -t 50
```

**期望看到**:
```

  | group="main" sCount=1 ucsCount=0 flags=1 obj=0x74a8c000 self=0x...
  | sysTid=123 nice=-20 cgrp=bg sched=0/0 handle=0x...

  | stack=0x7f9b8c0000-0x7f9b8e0000 stackSize=8MB
  | held mutexes=

  ...
```

**关键看**:
- 主线程在 `ZygoteServer.runSelectLoop` 的 `Os.poll` → **正常**
- 主线程在 `ClassLoader.loadClass` → **卡在 class 加载**
- 主线程在 `ClassLinker.VerifyClass` → **卡在 verify(8.2 §4 案例 2)**
- USAP 线程在 `forkAndSpecialize` → **USAP 池在跑**

**debuggerd 用法**(生成 tombstone):

```bash
# 主动:不杀进程的情况下抓栈
adb shell debuggerd -b <pid>
# 输出:/data/tombstones/tombstone_00(自动编号)

# 拉 tombstone 到 PC
adb pull /data/tombstones/tombstone_00 ./
```

**tombstone 内容**(节选):
```
Tombstone written to: /data/tombstones/tombstone_00
Build fingerprint: 'Pixel_8/...'
ABI: 'arm64'
pid: 123, tid: 456, name: zygote64  >>> /system/bin/app_process64
signal 11 (SIGSEGV), code 0 (SI_USER), fault addr 0x0000000000000010
    r0  0000007b9b8c0000  r1  0000000000000000  r2  0000007b9b8c1234
    ...
stack:
    0000007b9b8c0000  0000007b9b8c1000  0000000000000000
    #00 pc 0000000000421234  /system/lib64/libart.so (art::ClassLinker::DefineClass+184)
    #01 pc 0000000000422345  /system/lib64/libart.so (art::ClassLinker::LoadClass+560)
    ...
```

**关键看**:
- `signal 11 (SIGSEGV)` + `libart.so` + `ClassLinker` → ART 内部崩溃
- `signal 6 (SIGABRT)` + `art::Runtime::Abort` → ART 主动 abort
- `signal 4 (SIGILL)` + 任意 → 非法指令,OAT 损坏

**rotten tombstone**(失效 tombstone):
- 当 Zygote 启动时 OAT 已损坏,**根本进不到 dump tombstone 阶段**——Zygote 直接 abort
- 这种情况 tombstones 文件夹是空的(rotten = 腐烂,形容现场没保存)
- **必须用 `last_kmsg` 或 `pstore`**(持久化内核日志)拿现场
- 这就是 7.6 强调的"kernel panic 现场只能从 last_kmsg 取"——Zygote 启动崩同理

### 2.5 bootstat 怎么打 Zygote 阶段耗时

`ro.boottime.*` 是一组属性,记录 Zygote / system_server / 各 service 的启动时刻:

```bash
# 看所有 boottime 属性
adb shell getprop | grep ro.boottime
# 输出(节选):
# [ro.boottime.zygote]: [1738234567.890]
# [ro.boottime.zygote64]: [1738234567.892]
# [ro.boottime.system_server]: [1738234570.123]
# [ro.boottime.persist.sys.timezone]: [1738234567.500]
```

**关键时序**:
- `ro.boottime.zygote` - `ro.boottime.init`:Zygote 启动耗时(应 1-2.5 秒)
- `ro.boottime.system_server` - `ro.boottime.zygote`:system_server fork 后到 ready 的耗时(应 1-3 秒)
- 整机 boot time - `ro.boottime.system_server`:system_server 启动完后到 sys.boot_completed 的耗时(应 5-15 秒)

**Zygote 反复 crash 时**:
- `ro.boottime.zygote` 会被覆盖成**最后一次** Zygote 启动的时刻
- **看不到之前的 crash**——必须用 last_kmsg
- 配合 `init.svc.zygote` 看服务状态:
  ```bash
  adb shell getprop init.svc.zygote
  # 输出:running / stopped / restarting
  ```

### 2.6 Zygote 反复崩的 critical window 联动

7.2 §已讲过 `critical window=${zygote.critical_window.minute:-off} target=zygote-fatal` 的 service 声明。本节讲**触发流程**:

```
Zygote 启动 1
  ↓ 任意 crash
init 收到 SIGCHLD
  ↓
执行 onrestart 链(7.2 已列)
  ↓
重新 start zygote
  ↓
Zygote 启动 2
  ↓ 又 crash
init 收到 SIGCHLD
  ↓
检查 critical window:
  ├─ 距上次 zygote 启动 < critical_window.minute?
  │   ├─ 是 → 累加 "critical 计数"
  │   └─ 否 → 重置
  ↓
critical 计数 >= 4(默认值):
  ↓
reboot zygote-fatal 目标
  ↓
整机重启到 recovery / bootloader
```

**🟡 待联网确认**:critical 计数 4 是 AOSP 17 默认值,以 `init/service.cpp` 实际行为为准。

**线上常见现象**:
- Zygote 反复崩 4 次,每次间隔 1 分钟内 → 整机重启
- 整机重启后 Zygote 又崩(因为根本问题没修) → 无限重启
- **这类问题只能** `last_kmsg` 或 `pstore` 拿现场

## 4. 实战案例

### 案例 1:某 App 冷启动 200-500ms 抖动,定位 Zygote preload GC(典型模式)

**环境**:
- Android 版本:AOSP 14(API 34)
- 设备:Pixel 7(8GB RAM)
- 复现步骤:反复打开/关闭微信,观察冷启动时间分布

**现象**:
- 微信冷启动耗时分布:**350ms / 480ms / 800ms / 400ms**(3 次中位 400ms,但偶尔出现 800ms)
- 这种"偶发慢"是 Zygote fork 慢的典型特征

**分析思路**:
1. 抓 Zygote SIGQUIT,发现主线程在 `Class.forName` 卡 100-300ms
2. 同时 `adb logcat -d -s art` 报 `art: Concurrent GC paused 250ms`
3. 找 GC 触发原因:`adb shell dumpsys meminfo zygote` → Java Heap 已 60MB(接近 64MB 上限)
4. 找谁在占 heap:`adb shell dumpsys meminfo --local zygote` → 某个静态 Map 占 30MB

**根因**:
- Zygote 的 Java heap 默认 64MB
- OEM 在 framework 扩展中放了一个**静态 Map 缓存**,key 是包名,value 是 dex 编译信息
- 该 Map 长期持有 reference,占 30MB Java heap
- Zygote 在空闲期(用户没操作)会触发 concurrent GC,GC 暂停时间随 heap 占用而增加
- 暂停期间所有 fork 请求排队

**修复**:
- 短期:扩 heap → `setprop dalvik.vm.zygote.max-heap-size 96M`
- 中期:OEM 改用 LRU cache + 限制最大 size
- 长期:8.6 Zygote 内存治理详述

**修复原理**:
- Zygote 是**所有 App 进程的祖宗**,它的 heap 状态直接影响每次 fork
- 静态 Map 是 Java 内存泄漏的高发模式,OEM framework 扩展里常见
- 扩 heap 是临时缓解,根本解法是减少 Zygote 自己的常驻对象

### 案例 2:某设备 Zygote 反复崩 4 次后整机重启,last_kmsg 找到 seccomp 误配(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:装某第三方安全 App(代号 SecureGuard)后重启,卡开机动画 60 秒,自动重启到 recovery

**现象**:
- /data/tombstones/ 空 → rotten tombstone
- 整机重启 4 次后停在 recovery 模式
- 屏幕提示"系统已崩溃,请恢复出厂设置"

**分析思路**:
1. 4 次崩 → critical window 触发 zygote-fatal
2. tombstone 是空的 → 必须从 last_kmsg 取
3. `adb pull /sys/fs/pstore/console-ramoops` 拿到 last_kmsg
4. 关键片段:
   ```
   init: zygote (pid 123) exited with status 1
   init: critical: too many crashes in 5 minutes, rebooting
   ...
   last_kmsg:
   type=1400 audit(1738234567.890:123): avc: denied { transition } for
   scontext=u:r:zygote:s0 tcontext=u:r:appdomain:s0 tclass=process
   ...
   zygote: seccomp: reject syscall 220 (clock_nanosleep)
   ...
   zygote: signal 31 (SIGSYS), code 0 (SI_KERNEL)
   ```
5. 关键信号 `SIGSYS` + seccomp 拒绝 + audit denied → **seccomp 误配**

**根因**:
- SecureGuard 在它的 sepolicy 模块里加了 `zygote` 域的 seccomp filter
- 它的 filter 误把 `clock_nanosleep` 列入黑名单
- Zygote 启动时调用 `clock_nanosleep`(8.1 §2.3 preload 后 sleep),被 seccomp 拒绝 → SIGSYS
- 4 次反复崩 → zygote-fatal

**修复**:
- 短期:卸载 SecureGuard,重启设备
- 中期:SecureGuard 改 sepolicy 规则,移除 `clock_nanosleep` 限制
- 长期:OEM 在 init 启动时加 seccomp 规则**白名单校验**,避免误配

**修复原理**:
- seccomp 是 Android 9+ 强制启用的**系统调用白名单**
- Zygote 的 seccomp profile 在 `system/sepolicy/private/zygote.te` 定义
- 任何第三方 sepolicy 模块**添加** zygote 域的规则,都可能误配
- 调试方法:`adb shell setenforce 0` 临时关闭 sepolicy,验证是否是 seccomp 问题

## 5. Takeaway

1. **Zygote fork 慢的 3 类根因**:preload GC(持续慢)/ waitFor 阻塞(孤立慢)/ OAT 重新校验(首次慢)——单次慢 vs 反复慢是分诊关键。
2. **Zygote crash 的 4 类根因**:preload OOM / class 加载失败 / OAT 损坏 / seccomp 误配——4 个 logcat 关键词直接对应。
3. **`kill -3` + `debuggerd -b` + `tombstoned` 是抓栈三件套**:`kill -3` 给 logcat,`debuggerd -b` 给 tombstone,`tombstoned` 守护 tombstone 文件。
4. **rotten tombstone**(空 tombstones 文件夹)= Zygote 启动崩,必须从 `last_kmsg` / `pstore` 取。
5. **`ro.boottime.zygote` 是单值,被覆盖**——反复崩时看不到历史,必须用 last_kmsg。
6. **`critical window=zygote-fatal` 触发 4 次反复崩后整机重启**——这是设计内行为,不是 bug。
7. **8.5 与 11 章分工**:8.5 只管"已知是 Zygote 问题,精确定位到 Zygote 内部";11 章管"整机启动慢 5 秒,可能是 Zygote / system_server / PMS / 任何一个服务慢"。
8. **seccomp 误配是 OEM 改 framework 时最常引入的隐形问题**——加 sepolicy 规则时**必须**在真机全路径验证 boot 流程。
