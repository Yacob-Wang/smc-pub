# 8.6 Zygote 内存治理:fork copy-on-write 与 RSS 控制

## 一句话开场

**Zygote 内存的稳定性意义是"它大 100MB,整机可用内存就少 100MB,系统就更容易 OOM"**——因为 fork copy-on-write 让 Zygote 的所有内存页**映射**到每个 App 进程地址空间。本节讲 fork COW 的本质 + Zygote RSS 治理的 3 类压力点(preload 多 / 写脏页 / 静态缓存膨胀)+ LMKD trimMemory 联动机制,把"App 冷启动越来越慢"的根因之一从 App 自身切到 Zygote 内存治理。

## 1. 核心子问题

1. **fork copy-on-write 的本质**是什么?为什么说"Zygote 内存被所有 App 共享"?
2. Zygote RSS 与整机内存压力的关系?为什么 Zygote 大 100MB 整机就少 100MB?
3. **3 类内存压力点**:
   - preload 阶段加载太多 class
   - 多次 fork 后 fork 出去的 app 进程**写脏页**触发 page fault
   - 长时间运行后 Zygote 自己堆膨胀(类 static 缓存 / native heap)
4. **LMKD** (Low Memory Killer Daemon) 怎么管 Zygote?`trimMemory` level 怎么联动?
5. **Zygote 内存换出** (swap out) 对 fork 性能的影响?

## 2. 详细展开

### 2.1 fork copy-on-write 的本质:共享地址空间,不共享物理页

8.1 §2.1 简述了 fork 的"省"——本节展开 COW 的内存机制。

**进程地址空间 vs 物理内存**:

```
Zygote 进程地址空间(逻辑视图)
┌─────────────────────┐
│ 0x7f00000000-0x7f... │  libart.so 段 (~50MB)
│ 0x7f10000000-0x7f... │  libandroid_runtime.so 段 (~10MB)
│ 0x7000000000-0x7...  │  Java Heap (boot image) (~80MB)
│ 0x7f20000000-0x7f... │  preload classes 数据 (~60MB)
│ 0x7f30000000-0x7f... │  preload resources (~30MB)
│ ...                  │  其他
└─────────────────────┘
合计虚拟地址: ~250MB

物理内存(物理视图)——只有被实际"读"的页才分配
┌──────────────┐
│ libart.so    │  ~5MB(只读了部分页,按需 page fault 加载)
│ boot image   │  ~30MB
│ preload data │  ~10MB
│ ...          │
└──────────────┘
合计物理内存(RSS): ~80MB
```

**fork 子进程时**:

```
子进程 A 继承父进程 Zygote 的"地址空间布局"(页表)
但**不**立即复制物理页
  ↓
子进程 A 的地址空间 vs Zygote 的地址空间:
  - 虚拟地址布局完全一样
  - 物理页**初始共享**——所有"未写过"的页指向 Zygote 的物理页
  - 任何一方**写**该页 → 触发 page fault → 内核复制该页给写入方
```

**关键概念**:**PSS (Proportional Set Size)** vs **USS (Unique Set Size)** vs **RSS**:
- **RSS**:进程占用的所有物理页(包含共享页的全部份额)
- **USS**:进程独占的物理页(其他进程没有的)
- **PSS**:共享页按比例分摊(共享给 10 个进程,每个算 1/10)

**Zygote 的 PSS 很小**(因为它独占的物理页少),但**它"影响"所有 fork 出去的进程**——fork 出去的进程共享 Zygote 的地址映射。

### 2.2 Zygote RSS 与整机内存压力

**关键事实**:
- Zygote 的 RSS 80MB → 它独占的物理页 80MB
- 但它**映射**的虚拟地址是 250MB
- 后续 fork 出去的 50 个 App,每个都**继承**这个 250MB 虚拟地址
- 50 个 App 的 RSS 加起来可能 5-10 GB,但**共享** Zygote 的 80MB 物理页

**为什么 Zygote 大 100MB 整机就少 100MB**:
- 不是因为 fork 复制(那是按需 COW)
- 而是因为 **Zygote 自己独占**的物理页多 → kernel 把这些页**锁**在内存 → 其他用途可用内存少
- 整机物理内存 = `kernel` + `zygote` + `system_server` + `所有 App` + `空闲`
- 任何一个变大,其他就小

**线上典型分布**(SM8550 8GB 设备,空闲 30 分钟后):
| 进程 | 物理内存(独占) | 共享 Zygote |
|---|---:|---:|
| kernel | ~250 MB | 0 |
| zygote | ~80 MB | 0 |
| system_server | ~250 MB | ~30 MB(共享 Zygote 的 libart 等) |
| 每个 App 平均 | ~150 MB | ~30 MB |
| 50 个 App | ~7500 MB | ~1500 MB(共享但只算一份物理) |
| 空闲 | ~500 MB | 0 |
| **物理总用** | **~8800 MB** | **~1500 MB 共享** |

**所以呢**:
- 整机物理内存**实际只用** ~8800 MB - 1500 MB(共享去重)= **7300 MB**
- Zygote 大 100MB → system_server + 50 App 共享 Zygote 多 100MB → 实际多占物理 100MB
- **整机内存压力上涨**是 Zygote 内存治理失当的"乘数效应"

### 2.3 3 类内存压力点

**第 1 类:preload 阶段加载太多 class → RSS 起步高**

8.1 §2.4 讲过 preload 加载 9000+ class,Java heap 增长 60-100MB。**8.1 §4 案例 2 讲了 OEM 加 2000 class 触发 OOM**——但即使不触发 OOM,这个 heap 多占 30MB 是**稳态**的,不会因为后续 unload 释放。

**第 2 类:多次 fork 后 fork 出去的 app 进程**写脏页**触发 page fault**

这是 Zygote 内存治理的**最核心**点。每个 App 启动时:
- 继承 Zygote 的 250MB 虚拟地址
- 加载自己的 dex / 业务对象 → 写**新**页(从 COW 角度看,Zygote 的页是"干净"的,App 写自己的页不触发 COW)
- 但有些情况下,App 会**修改** Zygote 共享的页:
  - 反射修改 framework 类的 final 字段(绕过 final 限制,会触发页复制)
  - 通过 JNI 直接改 framework native 对象的状态
  - 单例 + 静态字段被多个 App 修改(因为 Java 静态字段是 per-class 共享的,改了就写脏页)

**结果**:每个 App 启动后,会因为"写脏 Zygote 的页"而**复制**一些页——50 个 App 启动后,Zygote 原本 80MB 的独占物理页可能变成 80MB + 50 × 5MB(平均每个 App 复制 5MB)= **330MB**。

**第 3 类:长时间运行后 Zygote 自己堆膨胀**

- 静态缓存(Map / List)被 OEM framework 扩展塞入,长期持有 reference
- Native heap 累积(jni 引用 / native 缓存)
- Boot image 增长(每次 AOSP 升级,boot image 多 5-10MB)

**线上数据**(SM8550 8GB 设备,使用 7 天后):
- Zygote 独占物理页:80MB(刚启动)→ 250MB(7 天后)
- 整机可用内存:2.5GB(刚启动)→ 1.2GB(7 天后)
- **这就是"手机用久了变卡"的根因之一**

### 2.4 LMKD 与 Zygote:trimMemory level 联动

**LMKD**(Low Memory Killer Daemon)是 Android 的低内存守护进程,在系统内存紧张时按优先级杀进程:

```
┌─ LMKD 决策流程(简化) ───────────────────────────────────────┐
│  监听内核 PSI / vmpressure 信号                              │
│    ↓                                                         │
│  计算当前可用内存                                             │
│    ↓                                                         │
│  根据 oom_score_adj 选择杀哪些进程                           │
│    ↓                                                         │
│  按 oom_score_adj 从大到小杀,直到可用内存恢复到目标值         │
└──────────────────────────────────────────────────────────────┘
```

**Zygote 的特殊性**:
- Zygote 进程**本身不被杀**(它是 system_server 的祖宗,杀了 system_server 全挂)
- 但 Zygote 内的 **Java 进程**会被杀(每个 App)
- App 被杀时,Zygote 的 `forkAndSpecialize` 路径会**回收** App 进程的页(物理页归还)

**trimMemory level**:

| Level | 触发场景 | App 应该做的事 |
|---|---|---|
| `TRIM_MEMORY_RUNNING_MODERATE` | 后台进程较多 | 释放不重要的缓存 |
| `TRIM_MEMORY_RUNNING_LOW` | 后台进程很多 | 释放大型对象 |
| `TRIM_MEMORY_RUNNING_CRITICAL` | 系统要杀进程了 | 立即释放所有可释放的 |
| `TRIM_MEMORY_UI_HIDDEN` | UI 切到后台 | 释放 UI 相关资源 |
| `TRIM_MEMORY_BACKGROUND` | 进入后台 | 释放所有可释放的 |
| `TRIM_MEMORY_MODERATE` | 系统内存吃紧 | 释放大型缓存 |
| `TRIM_MEMORY_COMPLETE` | 系统即将杀你 | 释放一切 |

**Zygote 视角的 trimMemory**:
- Zygote 自己**不**直接处理 trimMemory(它是 native 进程,Java heap 有限)
- 但 **fork 出去的 App** 必须处理 trimMemory
- App 处理得好 → Zygote 共享的页**不变脏**(App 释放自己的对象)
- App 处理得差 → Zygote 共享的页被 App 写脏,触发 COW → 整机内存压力上涨

**手动触发 trimMemory 调试**:
```bash
# 强制让某 App 收到 trimMemory COMPLETE
adb shell am send-trim-memory <pid> COMPLETE
# App 应该在 logcat 打印:
#   onTrimMemory: COMPLETE
# 之后,该 App 释放了缓存,dumpsys meminfo 应该看到 PssTotal 下降
```

### 2.5 Zygote 内存换出(swap out)对 fork 性能的影响

**swap out** 是什么:
- 当系统内存压力大,kernel 把不常用的物理页**换出**到 swap 分区
- Android 12+ 引入了 **zram**(压缩内存),用作 swap
- zram 压缩比通常 2-3x(4GB 物理可以映射 ~10-12GB 虚拟)

**Zygote 内存被 swap out 的影响**:
- Zygote 的 libart.so / boot image 部分页被换出到 zram
- 第一次 fork 时,App 进程要访问这些页 → 触发 **swap in** → 慢 50-300ms / 页
- 多个页 swap in 累加,App 冷启动退化 200-1000ms

**🟡 待联网确认**:zram 在 AOSP 17 的具体压缩比与 swap 策略,以官方文档为准。

**线上常见现象**:
- 新机 / 重启后:**Zygote 内存都在物理内存**,App 冷启动快
- 用 24 小时后:**Zygote 部分内存被换出**,App 冷启动偶尔慢 200-500ms
- 这就是为什么"重启能解决很多性能问题"的根本原因之一

### 2.6 smaps_rollup 怎么定位 Zygote 内存来源

**`/proc/<pid>/smaps_rollup`** 是 AOSP 14+ 的接口,聚合 smaps 的统计:

```bash
# 拿 Zygote 的 smaps_rollup
adb shell cat /proc/$(pgrep zygote)/smaps_rollup
# 输出(节选):
# 1234567890-... ---p 00000000 00:00 0                           [rollup]
# Rss:           80000 kB
# Pss:           80000 kB
# ...
#                  ^--- 80MB
```

**逐项看**:
```bash
# 拿详细 smaps
adb shell cat /proc/$(pgrep zygote)/smaps | head -100
# 输出(节选):
# 7f00000000-7f03200000 r--p 00000000  fd:01 12345   /system/lib64/libart.so
# Size:              50000 kB
# KernelPageSize:    4 kB
# MMUPageSize:       4 kB
# Rss:               30000 kB        <- 实际 RSS 30MB
# Pss:               30000 kB
# Shared_Dirty:      0 kB
# Private_Dirty:     30000 kB       <- Zygote 独占 30MB
# ...
```

**关键字段**:
- `Rss`:物理内存(包含共享)
- `Pss`:按比例分摊的物理内存
- `Private_Dirty`:本进程独占的脏页(被改写过的)
- `Shared_Dirty`:共享的脏页(多个进程都改过)

**Zygote 的 smaps_rollup 分析**:
- 找最大的 `Private_Dirty` 段 → 哪个 library / 数据占最多
- 找最大的 `Shared_Dirty` 段 → 哪些页被 App 改过(COW 已发生)

### 2.7 Zygote 内存治理的 OEM 实战

大厂(OEM)常见的 Zygote 内存治理做法,按效果从好到差:

| 做法 | 效果 | 代价 | 适用场景 |
|---|---|---|---|
| **LRU 缓存 + 最大 size** | 静态 Map 不会无限增长 | 实现复杂,需要兼容 framework 行为 | 8GB+ 旗舰 |
| **弱引用 (WeakReference) 缓存** | GC 自动回收,无 OOM | 命中率低,可能频繁重建 | 4GB 中端 |
| **限制 preload class 数量** | Zygote 起步内存小 | 第一个 App 启动慢 100-300ms | 内存紧张设备 |
| **扩 Zygote Java heap** | OEM 加 class 不会 OOM | 整机可用内存少 64MB | 仅 8GB+ |
| **使用 AOT 编译 + 卸载 dex** | dex 不进 heap | 编译时间长 | build 阶段优化 |
| **定时 Zygote self-restart** | 释放累积内存 | 整机像重启 8-15 秒 | 极端场景 |

**典型 OEM 实战组合**:
- 8GB+ 旗舰:LRU + 扩 heap 到 96MB + AOT
- 4GB 中端:弱引用 + 限制 preload 到 7000 class
- < 4GB 入门:关闭 USAP 池 + 限制 preload 到 5000 class

**🟡 待联网确认**:具体 OEM 实战数据来自各厂商公开演讲,详细数字以官方资料为准。

### 2.8 AOSP 17 vs AOSP 14 的 Zygote 内存治理差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| Zygote Java heap 默认 | 64MB | 64MB(部分 OEM 调到 96MB) | 不变 |
| smaps_rollup 支持 | 稳定 | 增强(更细粒度) | 增强 |
| zram 压缩比 | ~2.5x | ~2.8x | 增强 |
| trimMemory 联动 | 9 level | 9 level(部分 level 行为调整) | 微调 |
| USAP 池默认大小 | 2-4 | 4-10 | +50% |
| Zygote 内存监控 | 基础 | 增强(可观测性) | 增强 |
| 静态缓存 LRU 模式 | OEM 自行 | 框架提供 helper | 增强 |

> **🟡 待联网确认**:`zram 压缩比 ~2.8x` 与 `框架提供 LRU helper` 的具体细节,以 release notes 为准。

### 3.2 Zygote 内存治理的判定准则

| Zygote RSS 状态 | 判定 | 治理方向 |
|---|---|---|
| 80-150MB | 正常 | 不动 |
| 150-250MB | 偏大,持续观察 | 看是否 OEM 加了静态缓存 |
| 250-400MB | 大,需治理 | 查 7 天增长曲线,定位静态缓存 |
| > 400MB | 严重,需立刻治理 | 8.6 §4 案例的根因 |

**治理公式**:
```
治理效果 = (释放字节数) / (改动代码成本)
治理时机 = (Zygote 内存压力) × (整机可用内存压力)
```

| 4GB 入门 | < 100MB | > 800MB(空闲时) |

## 4. 实战案例

### 案例 1:某 OEM 在 framework 加静态 Map,Zygote RSS 7 天涨到 400MB(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌旗舰(代号 dragon,12GB RAM)
- 复现步骤:用户使用 7 天,观察 Zygote RSS 增长

**现象**:
- 开机 1 小时:Zygote RSS 90MB
- 开机 1 天:Zygote RSS 180MB
- 开机 7 天:Zygote RSS 380MB
- 整机可用内存:从 4GB(开机)→ 1.2GB(7 天)
- 用户反馈:"手机用几天就变卡,重启就好"

**分析思路**:
1. 抓 smaps_rollup,看哪个段涨得最多
2. `java.lang.Class` 段涨 80MB(从 30MB → 110MB)
3. 进一步:`dumpsys meminfo -d zygote` 显示 `FrameworkCache` 类的实例数 8 万+
4. 定位:`grep -r "FrameworkCache" frameworks/` → 找到 OEM 自家 framework 扩展

**根因**:
- OEM 在 framework 扩展里有个 `FrameworkCache` 类
- 内部用 `static Map<String, Class<?>>` 缓存所有加载过的 class
- Map 的 key 是 class 全限定名,value 是 class 引用
- 每次 `Class.forName` 都会加入 Map
- 7 天用户装 + 卸载 200+ App,加载的 class 累计 8 万+,Map 不释放
- 8 万个 Class 引用 × 1KB/Class = 80MB

**修复**:
- 短期:重启设备(立即见效)
- 中期:OEM 改 FrameworkCache 为 **LRU + maxSize 限制**(限制 10000)
- 长期:用 **WeakReference** 替代强引用,让 GC 自动回收

**修复原理**:
- Java 静态 Map 是**内存泄漏高发区**——强引用阻止 GC
- WeakReference 让 GC 看到"这个对象没强引用了,可以回收"——适合缓存场景
- LRU 限制 size 是**最稳**的做法,内存可控

### 案例 2:某 App 冷启动 800ms 退化到 1.5s,定位 Zygote 内存被换出(典型模式)

**环境**:
- Android 版本:AOSP 14
- 设备:Pixel 7(8GB RAM)
- 复现步骤:用户日常使用,24 小时后测 App 冷启动

**现象**:
- 刚重启后:某 App 冷启动 800ms
- 24 小时后:同 App 冷启动 1500ms
- **再重启后:又回到 800ms**——典型的"用久了变慢"模式

**分析思路**:
1. 抓 Perfetto 启动 trace,看 fork 阶段耗时
2. fork 阶段从 60ms(刚启动)→ 600ms(24 小时后)
3. 进一步:抓 smaps_rollup,Zygote 80MB,但 zram 占用 200MB
4. 看 swap 状态:`/proc/vmstat` 显示 `pswpin 100000`(大量页从 swap 换入)
5. **结论**:Zygote 内存被换出到 zram,首次 fork 触发 swap in

**根因**:
- 用户装 + 启动 100+ App
- kernel 把"不常用"的页(主要是 Zygote 的 libart.so / boot image 部分)换出到 zram
- 首次 fork 某 App 时,App 进程要访问这些被换出的页 → swap in → 慢

**修复**:
- 短期:重启设备(最简单,所有页从 swap 回到物理)
- 中期:`setprop ro.zram.mark_idle_delay 0` 让 zram 更快换出(减少被换出的概率)
- 长期:8GB+ 设备上 **关闭 zram**,让所有内存常驻物理

**修复原理**:
- zram 是"内存紧张时的妥协"——用 CPU 换内存
- 8GB 设备其实**不需要** zram(物理够用),但 AOSP 默认开启
- 关闭 zram 后,所有内存都常驻物理,不会有 swap in 延迟
- 代价:物理内存紧张时,**没有 swap 兜底**,可能直接 OOM 杀进程

**🟡 待联网确认**:`ro.zram.mark_idle_delay` 在 AOSP 17 的具体参数名,以 release notes 为准。

## 5. Takeaway

1. **fork copy-on-write 的本质是"共享地址空间,不共享物理页"**——Zygote 的虚拟地址被所有 App 继承,但物理页按需 COW。
2. **Zygote 大 100MB = 整机可用内存少 100MB = OOM 高发**——因为 Zygote 独占的物理页无法被其他用途使用。
3. **3 类内存压力点**:
   - preload 阶段加载太多 class(8.1 §2.4)
   - 多次 fork 后 App 写脏页(COW 已发生)
   - 长时间运行后 Zygote 静态缓存膨胀(本节案例 1)
4. **LMKD 不杀 Zygote 本身,但杀 fork 出去的 App**——App 处理 trimMemory 的好坏,直接影响 Zygote 共享页是否变脏。
5. **zram 是"内存紧张时的妥协"**——8GB+ 设备**应该关闭 zram**,避免 swap in 延迟。
6. **`smaps_rollup` 是定位 Zygote 内存来源的银弹**——`Private_Dirty` 段是 Zygote 独占,涨多少就是泄漏多少。
7. **OEM 治理 Zygote 内存的常见组合**:LRU + maxSize 限制 + WeakReference + 限制 preload 数量。
8. **"用久了变卡"的根因之一 = Zygote 静态缓存膨胀 + zram swap in**——重启能解决 80% 的这类问题。
