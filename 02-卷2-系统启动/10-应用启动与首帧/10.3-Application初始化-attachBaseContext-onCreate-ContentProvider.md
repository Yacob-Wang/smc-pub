# 10.3 Application 初始化:attachBaseContext / onCreate / ContentProvider

## 一句话开场

ActivityThread.main() 之后,App 进程内部会按顺序执行 3 个关键钩子(**attachBaseContext → Application.onCreate → ContentProvider 初始化**),**App 启动慢 80% 都卡在 onCreate 钩子**——任何在 onCreate 里的同步 I/O / 网络 / 数据库查询都会让 App 启动退化 200-800ms。本节讲清 3 个钩子的时序、典型耗时、根因、案例。

## 1. 核心子问题

1. attachBaseContext 是什么?为什么要在 onCreate 之前?
2. Application.onCreate 应该在什么时机执行?能做什么 / 不能做什么?
3. ContentProvider 为什么在 Application.onCreate 之后才初始化?隐式触发?
4. 3 个钩子的执行时序?Perfetto 事件名是什么?
5. Application 启动慢 80% 都在 onCreate,具体根因?
6. ContentProvider 初始化慢的常见根因?
7. 如何测量 3 个钩子的耗时?
8. AOSP 17 vs AOSP 14 的 Application 初始化差异?

## 2. 详细展开

### 2.1 attachBaseContext 钩子:onCreate 之前的"轻量级"上下文

**attachBaseContext** 是 Application 的第一个钩子,在 onCreate 之前执行。

```java
// path: frameworks/base/core/java/android/app/Application.java
// commit: android-17.0.0_r1
public class Application {
    private Context mBaseContext;

    protected void attachBaseContext(Context base) {
        // 这是第一个钩子
        // 1. 设置 mBaseContext(应用能用 Context 的最早时机)
        // 2. 默认空实现,App 可重写
        mBaseContext = base;
    }
}
```

**触发时机**:
- ActivityThread.handleBindApplication() 内部
- 早于 Application.onCreate()
- 早于 ContentProvider 初始化

**典型用途**:
- MultiDex:在 attachBaseContext 中加载 multidex 库(legacy 5.0 之前)
- 字体 / 资源替换:在 attachBaseContext 中安装自定义 Resources
- 配置化:在 attachBaseContext 中修改 base context 的配置(如 locale / 字号)

**对读者有什么用**:
- **attachBaseContext 应保持轻量**——任何 IO / 网络 / 数据库查询会拖累整个启动链
- **不应在 attachBaseContext 中启动后台线程**——`Context` 可能还没 fully ready
- **MultiDex 兼容(legacy 5.0)**——attachBaseContext 是 multidex 安装的合法时机

**常见错配症状**:
| 错配 | 症状 |
|---|---|
| 在 attachBaseContext 中同步加载 dex | App 启动慢 500-1500ms |
| 在 attachBaseContext 中启动后台线程 | 线程与 Context 生命周期不一致,可能 OOM |
| 在 attachBaseContext 中访问 ContentProvider | ProviderClient NotYetConnectedException |

### 2.2 Application.onCreate 钩子:启动慢 80% 的"重灾区"

**Application.onCreate()** 是 3 个钩子中**最常被滥用**的——任何"启动期初始化"都塞这里。

```java
// path: frameworks/base/core/java/android/app/Application.java
// commit: android-17.0.0_r1
public class Application {
    public void onCreate() {
        // 这是第二个钩子
        // 1. 默认空实现,App 必须重写
        // 2. 在主线程上同步执行
        // 3. 在 ContentProvider 初始化之前
        // 4. 在 Activity onCreate 之前
    }
}
```

**典型错配**(App 启动慢的头号根因):

| 错配 | 耗时 | 修复 |
|---|---|---|
| 同步 HTTP client 初始化 | 500-1500ms | 改异步 / Lazy |
| 同步数据库查询(SharedPreferences / Room) | 200-800ms | 改异步 / Lazy |
| 同步 SDK 初始化(推送 / 统计 / 广告) | 300-1000ms | 用 `androidx.startup` 库 Initializer 推迟 |
| 同步网络配置读取 | 200-500ms | 改本地缓存 |
| 同步文件系统 IO(读 assets / 配置文件) | 100-500ms | 改异步 |

**对读者有什么用**:
- **App 启动慢 80% 都在 onCreate**——这是线上实战数据,不是拍脑袋
- **任何在 onCreate 里的同步操作都是反模式**——现代 Android 都有异步 / Lazy 替代
- **`androidx.startup` 库**(AOSP 12+ 引入)提供 `Initializer` API,让非关键初始化延后到 `Application.onCreate` 之后

**Application.onCreate 的 4 个反模式**:
1. **网络 I/O**——`HttpURLConnection.connect()` / `OkHttpClient.newCall().execute()`
2. **数据库 I/O**——`SQLiteOpenHelper.getReadableDatabase()` / `Room.databaseBuilder().build()`
3. **文件系统 I/O**——`AssetManager.open()` / `SharedPreferences.Editor.commit()`
4. **重型 SDK init**——推送 / 统计 / 广告 SDK 的 init 方法

### 2.3 ContentProvider 初始化:onCreate 之后的"隐式触发"

**ContentProvider 初始化**是 3 个钩子中**最容易被忽略**的——App 启动时**每个 provider 都会自动初始化**,即使没有任何代码主动调用它。

```java
// path: frameworks/base/services/core/java/com/android/server/am/ActivityManagerService.java
// commit: android-17.0.0_r1
private void handleBindApplication(AppBindData data) {
    // 1. Application.attachBaseContext
    // 2. Application.onCreate
    // 3. ContentProvider 初始化(每个 provider)
    // 4. Activity onCreate / onStart / onResume
}
```

**ContentProvider 初始化的隐式触发**:
- AndroidManifest.xml 中每个 `<provider>` 声明都会触发 `ContentProvider.onCreate()`
- 触发顺序:declared order / merged-manifest 后顺序
- 在 Application.onCreate 之后,Activity onCreate 之前

**对读者有什么用**:
- **第三方 SDK 经常用 ContentProvider 作为初始化入口**——它不需要主动调 `getContentResolver().query()`,Android 系统自动调
- 这就是为什么有些 App 启动慢 800ms,但 `Application.onCreate` 看起来很轻——provider 里有重活
- 排查"App 启动慢"时,看 `dumpsys activity providers | grep <pkg>`,列出所有 provider

**典型错配**:

| 错配 | 症状 |
|---|---|
| 第三方 SDK provider 同步初始化 | App 启动慢 300-1000ms(SDK init 在 provider.onCreate) |
| provider 中同步数据库查询 | 启动期 ANR |
| provider 数量过多(20+) | 启动慢 200-500ms(每个 10-30ms) |

### 2.4 3 个钩子的执行时序 + Perfetto 事件名

```
[10.1 §2.5 已讲] ActivityThread.main() → attachApplication
[system_server 端] AMS 收到 attachApplication
  ↓
[system_server 端] AMS 调度 → 发送 BIND_APPLICATION 给 App
[App 端] ActivityThread.handleBindApplication
  ├─ 1. 加载 LoadedApk(读 manifest)
  ├─ 2. Application.attachBaseContext
  ├─ 3. Application.onCreate
  ├─ 4. ContentProvider.onCreate(每个 provider)
  └─ 5. 准备 Activity
[system_server 端] AMS 调度 → 发送 LAUNCH_ACTIVITY 给 App
[App 端] ActivityThread.handleLaunchActivity
  └─ Activity.onCreate / onStart / onResume
[10.4-10.6 详述]
```

**Perfetto 事件名**(10.7 详述):
- `am_proc_bound`:App attach 到 AMS
- `am_create_activity`:Application + Activity onCreate 完成
- 内部更细:`Application.onCreate` / `ContentProvider.onCreate` 可通过 Trace.beginSection 自定义追踪

**对读者有什么用**:
- 排查"App 启动慢"时,抓 Perfetto trace + `am_create_activity` 之前的差值就是 3 个钩子的总耗时
- 在 3 个钩子里加 `Trace.beginSection("MyApp.onCreate")` 可精确定位

### 2.5 3 个钩子常见启动慢的根因速查

| 钩子 | 常见根因 | 耗时 | 修复方向 |
|---|---|---|---|
| **attachBaseContext** | 同步 multidex 加载 | 500-1500ms | 改 androidx multidex |
| **attachBaseContext** | 同步 Resources 替换 | 200-500ms | 改 lazy |
| **Application.onCreate** | 同步 HTTP 初始化 | 500-1500ms | 改异步 |
| **Application.onCreate** | 同步数据库查询 | 200-800ms | 改 lazy |
| **Application.onCreate** | 同步 SDK init(推送/统计/广告) | 300-1000ms | 用 `androidx.startup` Initializer 推迟 |
| **ContentProvider.onCreate** | 第三方 SDK init | 300-1000ms | 检查 SDK 文档,部分支持 lazy |
| **ContentProvider.onCreate** | 自定义 provider 中 IO | 200-500ms | 改异步 |

### 2.6 AOSP 17 vs AOSP 14 的 Application 初始化差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| attachBaseContext 时机 | handleBindApplication 阶段 1 | 同 | 无变化 |
| Application.onCreate 时机 | handleBindApplication 阶段 2 | 同 | 无变化 |
| ContentProvider.onCreate 时机 | handleBindApplication 阶段 3 | 同 | 无变化 |
| `androidx.startup` 库 | 1.1.0 | 1.2.0 | +Initializer API |
| ContentProvider 数量限制 | 无 | 无 | 无变化 |
| ContentProvider auto-init 优化 | 无 | 部分 | 减少 50-100ms |
| attachBaseContext 不允许 IO | 同 | 同 | 无变化 |

> **🟡 待联网确认**:ContentProvider auto-init 优化为待联网确认,实际以 AOSP 17 build 为准。

## 4. 实战案例

### 案例 1:某 App 冷启动 1.5s,定位 Application.onCreate 同步 HTTP 阻塞(典型模式)

**环境**:
- Android 版本:AOSP 14(API 34)→ AOSP 17(API 37)OTA
- 设备:Pixel 7(8GB RAM)
- 复现步骤:冷启动某 App,反复 5 次中位数 1.5s(基线 800ms)

**现象**:
```bash
$ adb shell am start -W -n com.example.app/.MainActivity
ThisTime: 1500
TotalTime: 1700
```
**关键观察**:ThisTime 1.5s,基线 800ms,慢 700ms。

**分析思路**:
1. 抓 Perfetto trace,看 7 个事件名
2. `am_proc_bound → am_create_activity` 差值 800ms(基线 200-400ms)
3. 在 `Application.onCreate` 起点加 `Trace.beginSection("MyApp.onCreate")` 追踪
4. 进一步看 `dumpsys gfxinfo`,定位到 `OkHttpClient.newCall().execute()` 阻塞 600ms

**根因**:
- `Application.onCreate` 中调用 `OkHttpClient.newCall().execute()` 同步 HTTP 请求
- 同步阻塞主线程 600ms
- 文件路径:`src/com/example/app/MyApplication.java:onCreate`
- 修复方法:把 HTTP 初始化挪到后台线程,或在第一次使用时 lazy init

**修复**:
- 短期:HTTP 初始化改异步
- 中期:用 `androidx.startup` 库的 `Initializer` 推迟到 `ContentProvider` 之后
- 长期:用 `WorkManager` 异步后台任务替代启动期 HTTP

**修复原理**:
- Application.onCreate 阻塞是 App 启动慢的头号根因
- 任何同步 I/O / 网络 / 数据库查询都是反模式
- 量化指标:onCreate 应 < 100ms

### 案例 2:某 App 启动慢 500ms,定位 ContentProvider 第三方 SDK 拖慢(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:装某第三方广告 SDK(代号 AdSDK)后,App 启动慢 500ms

**现象**:
```bash
$ adb logcat -d -s ActivityThread,ContentProvider | head -100
ActivityThread: Install provider com.adsdk.provider: com.adsdk.AdProvider
ContentProvider: com.adsdk.AdProvider onCreate start
ContentProvider: com.adsdk.AdProvider onCreate took 480ms
```
**关键观察**:`com.adsdk.AdProvider.onCreate` 耗时 480ms——这是第三方 SDK 通过 ContentProvider 自动初始化的结果。

**分析思路**:
1. 关键日志 `com.adsdk.AdProvider onCreate took 480ms` → AdSDK 慢
2. 抓 AdSDK 文档,看 `AdProvider.onCreate` 做了什么
3. AdSDK 在 onCreate 中:**注册 BroadcastReceiver + 启动网络连接 + 读 SharedPreferences**
4. 全部同步操作
5. **根因**:AdSDK 设计为 ContentProvider 模式,自动初始化

**根因**:
- AdSDK 在 `AndroidManifest.xml` 中声明了 ContentProvider
- Android 系统自动调 `ContentProvider.onCreate()`
- AdSDK 在 onCreate 中做了重型初始化
- 即使 App 代码不主动调 SDK,也会被系统自动初始化

**修复**:
- 短期:AdSDK 提供 `disable` 开关(如果有),关闭 ContentProvider auto-init
- 中期:App 自定义 ContentProvider `onCreate` 推迟 SDK init
- 长期:AdSDK 改用 `androidx.startup` Initializer,让 App 控制 init 时机

**修复原理**:
- 第三方 SDK 经常用 ContentProvider 作为"无需主动调"的初始化入口
- 但这导致 SDK init 阻塞 App 启动
- 排查时必看 `dumpsys activity providers | grep <pkg>`,列出所有 provider

### 案例 3:某 App 启动时 ANR 5s,定位 Application.onCreate 死循环(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:某品牌中端机(代号 eagle,4GB RAM)
- 复现步骤:装某第三方应用加固 SDK(代号 GuardSDK)后,App 启动 ANR

**现象**:
```log
$ adb logcat -d -s ActivityManager,DEBUG,AndroidRuntime -t 100
ActivityManager: ANR in com.example.app, Reason: Input dispatching timed out
"main" prio=5 tid=0x1 Native
  at java.lang.Thread.sleep(Native method)
  at com.example.app.MyApplication.onCreate(MyApplication.java:50)
  ...
```
**关键观察**:ANR + `Thread.sleep` + `MyApplication.onCreate` → App 自己写的 Application.onCreate 死循环。

**分析思路**:
1. 关键日志 `Thread.sleep` + `MyApplication.onCreate` → App 代码问题
2. 抓栈,看 `onCreate` 内部逻辑
3. GuardSDK 在 onCreate 中**调用死循环 + sleep**做"加固"检查
4. sleep 5s + 死循环 → ANR

**根因**:
- GuardSDK 设计为"启动时做完整性检查"
- 用 Thread.sleep(5000) 等待系统稳定 + 死循环
- 阻塞主线程 5s → ANR

**修复**:
- 短期:App 改 onCreate 逻辑,移除 sleep
- 中期:GuardSDK 改用 WorkManager 异步执行
- 长期:卸载 GuardSDK

**修复原理**:
- App onCreate 中**绝不能** sleep / 死循环 / 同步网络 / 同步 IO
- 任何阻塞主线程 5s+ 的操作都会触发 ANR(Input dispatching timed out)
- 排查时,`kill -3 <pid>` 抓栈即可定位

## 5. Takeaway

1. **App 启动慢 80% 都在 Application.onCreate 钩子**——任何同步 I/O / 网络 / 数据库查询都会让启动退化 200-800ms。
2. **3 个钩子执行时序**:attachBaseContext(轻量)→ Application.onCreate(重灾区)→ ContentProvider 初始化(隐式触发,常被忽略)。
3. **attachBaseContext 应保持轻量**——主要用于 multidex 加载 / Resources 替换,**不应**做 IO。
4. **Application.onCreate 4 个反模式**:网络 I/O / 数据库 I/O / 文件系统 I/O / 重型 SDK init——都有异步 / Lazy 替代。
5. **ContentProvider 自动初始化**——AndroidManifest.xml 中每个 provider 都会自动调 `onCreate`,即使 App 代码不主动调。这是第三方 SDK 经常利用的入口。
6. **`androidx.startup` 库(AOSP 12+)**提供 `Initializer` API,让非关键初始化延后到 `Application.onCreate` 之后。
7. **Perfetto 事件名**:`am_proc_bound → am_create_activity` 差值 = 3 个钩子的总耗时(基线 200-400ms)。
8. **App onCreate 中绝不能 sleep / 死循环**——任何阻塞主线程 5s+ 的操作都会触发 ANR。
