# 10.1 Launcher 点击 → ActivityThread:Binder 跨进程调用

## 一句话开场

App 冷启动的完整链路是 **7 步**(Launcher 点击 → AMS.startActivity → ActivityTaskManager 任务栈管理 → Zygote fork → ActivityThread.main → Application.onCreate → 第一帧上屏),**任何一步慢都会让 App 启动退化 100-500ms**——本节讲清前 4 步(应用进程被 fork 之前),10.2-10.3 讲 fork 后,10.4-10.6 讲 View 树和 Choreographer,10.7 讲时间测量。

## 1. 核心子问题

1. Launcher 点击 App 图标后,跨进程调用怎么走完到 AMS?
2. AMS.startActivity 与 ActivityTaskManagerService.startActivity 的职责分工?
3. **"Activity" 模式(standard / singleTop / singleTask / singleInstance)**怎么影响启动路径?
4. **Intent Flag**(FLAG_ACTIVITY_NEW_TASK / FLAG_ACTIVITY_CLEAR_TOP 等)怎么影响任务栈?
5. Zygote 怎么被请求 fork?AMS 调用什么方法?
6. 进程 fork 成功后,**子进程的 ActivityThread 入口在哪**?
7. App 启动链路的 **7 个时间点** 各代表什么?怎么读 Perfetto trace?
8. AOSP 17 vs AOSP 14 的 App 启动链路差异?

## 2. 详细展开

### 2.1 7 步主线:从 Launcher 点击到 ActivityThread

App 冷启动的完整链路是 7 步。本节讲前 4 步,其余 3 步分别在 10.2-10.3 详述。

```
[App 启动链路 7 步]
步 1:Launcher 进程点击 App 图标
       → 构造 Intent + 触发 onClickListener
       → 调 Activity.startActivity(Intent)
       ↓
步 2:Launcher 进程 → ActivityManagerService(Binder IPC)
       → ActivityManager.getService().startActivity()
       → 跨进程到 system_server
       ↓
[本节重点]
步 3:AMS.startActivity → ActivityTaskManagerService.startActivity
       → 检查 Intent / 权限 / 任务栈状态
       → 决定 Zygote fork 哪个进程
       ↓
步 4:AMS 请求 Zygote fork
       → Process.start(entryPoint, args)
       → ZygoteProcess.start()
       → ZygoteInit.forkAndSpecialize
       ↓
[10.2 详述]
步 5:fork 后子进程 = ActivityThread.main()
       → Looper.prepare / Looper.loop
       → 等待 AMS 的 attachApplication 请求
       ↓
[10.3 详述]
步 6:ActivityThread.handleLaunchActivity
       → Application.attachBaseContext
       → Application.onCreate
       → Activity.onCreate / onStart / onResume
       ↓
[10.4-10.6 详述]
步 7:Choreographer 触发第一帧
       → View 树 measure / layout / draw
       → 第一帧提交给 SurfaceFlinger
       → 整机 first_frame_drawn
```

**对读者有什么用**:
- 排查"App 启动慢"时,先定位"哪一步慢"——7 步中前 4 步是 Framework 决定,后 3 步是 App 自己写
- 7 步都有 Perfetto 事件名(am_create_task / am_proc_start / am_create_activity 等),可量化

### 2.2 步 1-2:Launcher 进程发起跨进程调用

**Launcher 进程内的起点**是用户在桌面上点击 App 图标——但这只是"用户事件",真正的启动链路从 **Activity.startActivity** 开始。

```java
// path: frameworks/base/core/java/android/app/Activity.java
// commit: android-17.0.0_r1
public class Activity {
    public void startActivity(Intent intent) {
        // 委托给 startActivityForResult
        startActivityForResult(intent, -1);
    }
}
```

**startActivity 流程简图**:

```
[Launcher 进程]
Launcher.onClick → Activity.startActivity(intent)
  ↓
Activity.startActivityForResult(intent, -1)
  ↓
Instrumentation.execStartActivity(...)  ← 准备跨进程
  ↓
ActivityManager.getService().startActivity(...)
  ↓  这是 Binder IPC 入口
  ↓  ActivityManagerProxy(历史名) / IActivityManager.Stub.asInterface
  ↓  通过 binder 驱动发送到 system_server
[system_server 进程]
ActivityManagerService.startActivity(...)
  ↓
ActivityTaskManagerService.startActivity(...)
  ↓
检查 Intent / 权限 / 任务栈
```

**Binder IPC 的关键代码**(`ActivityThread` 在 Application 进程侧):

```java
// path: frameworks/base/core/java/android/app/ActivityThread.java
// commit: android-17.0.0_r1
// 跨进程到 system_server
public static IActivityManager getActivityManager() {
    return IActivityManagerSingleton.get();
}

private static final class IActivityManagerSingleton {
    private static final IActivityManager INSTANCE = IActivityManager.Stub.asInterface(
        Binder.allowBlocking(ServiceManager.getService(Context.ACTIVITY_SERVICE)));
    // ← "activity" 服务,从 ServiceManager 拿到 binder
    // ← IActivityManager.Stub.asInterface 把 binder 包装成 IActivityManager 接口
}
```

**对读者有什么用**:
- 排查"App 启动卡在某步",先看 `IActivityManager` 跨进程调用是不是返回了
- `Binder.allowBlocking` 是 Android 13+ 引入,允许"非 oneway"的 binder 调用,避免 ANR
- `ServiceManager.getService("activity")` 9.4 已讲,本节不重复

### 2.3 步 3:AMS → ActivityTaskManagerService(AOSP 12+ 拆分)

AOSP 12+ 之前,`startActivity` 完全在 AMS 内部。AOSP 12+ 引入 **ActivityTaskManagerService(ATMS)**,把"任务栈管理"从 AMS 拆出来。

**AMS 与 ATMS 的职责分工**(AOSP 17):

| 维度 | AMS | ATMS |
|---|---|---|
| 进程管理 | ✅ 主责 | — |
| Service / Broadcast 管理 | ✅ 主责 | — |
| Provider 管理 | ✅ 主责 | — |
| Activity 任务栈 | 委托给 ATMS | ✅ 主责 |
| Window 管理 | 委托给 WMS | — |
| Intent 解析 / 启动 | 委托给 ATMS | ✅ 主责 |

**关键调用链**:

```java
// path: frameworks/base/services/core/java/com/android/server/am/ActivityManagerService.java
// commit: android-17.0.0_r1
public final int startActivityAsUser(...) {
    return mActivityTaskManager.startActivityAsUser(...);
    // 直接委托给 ATMS,AOSP 12+ 之后是单次跳转
}
```

```java
// path: frameworks/base/services/core/java/com/android/server/wm/ActivityTaskManagerService.java
// commit: android-17.0.0_r1
public final int startActivityAsUser(...) {
    // 1. 校验 caller / permission
    // 2. 解析 Intent(查询 PMS 拿 Activity 信息)
    // 3. 创建或复用 TaskRecord
    // 4. 决定 ProcessRecord(检查进程是否在)
    // 5. 如果进程不在 → 调 Process.start() 请求 Zygote fork
    // 6. 如果进程在 → 调 ActivityThread 端直接进 onCreate
}
```

**对读者有什么用**:
- "AMS 启动慢"90% 实际上是 "ATMS 启动慢"——ATMS 是 AOSP 12+ 的新拆分,debug 时注意栈在 ATMS
- 进程复用 vs 新 fork 的判断在 ATMS 内部,影响启动路径

### 2.4 步 4:ATMS 请求 Zygote fork

ATMS 决定"需要新 fork 进程"时,调 `Process.start()`:

```java
// path: frameworks/base/core/java/android/os/Process.java
// commit: android-17.0.0_r1
public static ProcessStartResult start(...) {
    return ZygoteProcess.start(
        entryPoint /* "android.app.ActivityThread" */,
        processClass /* null */,
        uid, gid, gids,
        runtimeFlags, mountExternal,
        seInfo, niceName, // niceName = 包名,如 "com.example.app"
        ...);
    // → ZygoteProcess 是 Zygote 进程的 Java 侧 wrapper
    // → 通过 socket 通信到 zygote 进程(8.1 已讲)
    // → Zygote 收到后 fork + 处理 fork 参数
}
```

**Zygote fork 应用进程的 7 类参数**(10.2 详述):
- `uid` / `gid` / `gids` — Linux 身份
- `runtimeFlags` — 运行时标志(如 DEBUGGABLE / PROFILEABLE)
- `mountExternal` — 外部存储挂载模式
- `seInfo` — SELinux 标签(如 `platform:app_process`)
- `niceName` — 进程名(默认是包名)
- `instructionSet` — 指令集(arm64 / x86_64)

**对读者有什么用**:
- `Process.start()` 是 Zygote fork 应用的唯一入口
- fork 时的 `seInfo` 错了会触发 SELinux 拒绝(9.4 / 9.6 已讲)
- fork 时的 `niceName` 错了会让 `ps` 看不到应用名

### 2.5 ActivityThread:App 进程的真实入口

**Zygote fork 完成后,子进程会执行 `ActivityThread.main()`**——这是 App 进程的"main 入口",等价于 ZygoteInit.java 对 Zygote 进程的意义。

```java
// path: frameworks/base/core/java/android/app/ActivityThread.java
// commit: android-17.0.0_r1
public static void main(String[] args) {
    // 1. 设置 Process 名字
    android.os.Process.setProcessName("com.example.app");

    // 2. 准备 Looper
    Looper.prepareMainLooper();

    // 3. 创建 ActivityThread 对象
    ActivityThread thread = new ActivityThread();
    thread.attach(false /* non-system process */);

    // 4. 启动 Looper,从此阻塞等待消息
    Looper.loop();

    throw new RuntimeException("Main thread loop unexpectedly exited");
}
```

**ActivityThread.attach() 关键动作**:

```java
// path: frameworks/base/core/java/android/app/ActivityThread.java
// commit: android-17.0.0_r1
private void attach(boolean system) {
    // 非 system 进程走这里
    final IActivityManager mgr = ActivityManager.getService();
    try {
        mgr.attachApplication(mAppThread, ...);
        // ↑ 跨进程告诉 AMS:"我 fork 好了,准备好了,给我发启动任务"
        // ↑ 这是反向 Binder:App 进程 → system_server
    } catch (RemoteException ex) {
        throw ex.rethrowFromSystemServer();
    }
    // ...
}
```

**对读者有什么用**:
- `ActivityThread.main()` 是 App 进程的 main 入口——任何 App 启动失败都从这里开始查
- `mgr.attachApplication()` 是**反向 Binder**——App 进程主动告诉 AMS"我准备好了"
- `Looper.loop()` 抛出 `RuntimeException` 通常意味着 App 进程崩了

### 2.6 App 启动链路的 7 个时间点(Perfetto trace 名)

**App 启动时间量化**,Perfetto trace 用 7 个事件名标记:

| 步 | Perfetto 事件名 | 含义 | 典型耗时(SM8550) |
|---|---|---|---|
| 步 1 | `am_create_task` | 任务栈创建 | 5-20 ms |
| 步 2 | `am_new_intent` | Intent 处理 | 1-5 ms |
| 步 3 | `am_proc_start` | 进程 fork 开始 | 30-60 ms |
| 步 4 | `am_proc_bound` | 进程 attach 到 AMS | 50-150 ms |
| 步 5 | `am_create_activity` | Activity onCreate | 200-800 ms |
| 步 6 | `am_resume_activity` | Activity onResume | 50-200 ms |
| 步 7 | `first_frame_drawn` | 第一帧上屏 | 100-500 ms |
| **App 启动总耗时** | `am_create_task → first_frame_drawn` | 全程 | 800-2000 ms(冷启) |

**关键差值归因**:
- `am_proc_start → am_proc_bound` 差值大 → **Zygote fork 慢**(8.x / 10.2 详述)
- `am_proc_bound → am_create_activity` 差值大 → **Application.onCreate 慢**(10.3 案例 1)
- `am_create_activity → am_resume_activity` 差值大 → **Activity.onCreate 慢**(10.3 案例 2)
- `am_resume_activity → first_frame_drawn` 差值大 → **View 树 / Choreographer 慢**(10.4 / 10.5)

**对读者有什么用**:
- 排查"App 启动慢",先抓 Perfetto boot trace,看 7 个事件名各自的耗时
- `am_proc_bound` 是关键拐点——之前是 Framework 决定,之后是 App 写
- `first_frame_drawn` 是用户感知起点(10.6 详述)

### 2.7 AOSP 17 vs AOSP 14 的 App 启动链路差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| AMS / ATMS 拆分 | ATMS 已存在 | 同 | 无变化 |
| 进程池(USAP) | 默认 4-10 | 默认 4-10 | 无变化 |
| `am_start -W` 输出格式 | 9 字段 | 12 字段 | +3(WaitTime / TotalTime / LaunchState) |
| Activity 启动时间(冷) | 800-2000 ms | 800-2000 ms | 无显著变化 |
| Binder oneway 限制 | 1 / 2 | 1 / 2 | 无变化 |
| 启动任务调度 | FIFO | FIFO + priority | +priority |
| ActivityThread attach 流程 | 8 步 | 7 步(合 1 步) | -1 步优化 |

> **🟡 待联网确认**:ActivityThread attach 步骤数减少为待联网确认,实际以 AOSP 17 build 为准。

## 4. 实战案例

### 案例 1:某 App 冷启动 1.5s,定位 AMS startActivity 跨进程调用阻塞(典型模式)

**环境**:
- Android 版本:AOSP 14(API 34)→ AOSP 17(API 37)OTA
- 设备:Pixel 7(8GB RAM)
- 复现步骤:冷启动某 App,反复 5 次中位数 1.5s(基线 800ms)

**现象**:
```bash
$ adb shell am start -W -n com.example.app/.MainActivity
Starting: Intent { ... }
Status: ok
LaunchState: COLD
Activity: com.example.app/.MainActivity
ThisTime: 1200
TotalTime: 1500
WaitTime: 1500
```
**关键观察**:TotalTime 1.5s,ThisTime 1.2s——ThisTime 占 80%,但基线应该 600-800ms。ThisTime 异常大说明 Application 或 Activity onCreate 慢。

**分析思路**:
1. 抓 Perfetto boot trace,看 7 个事件名各自的耗时
2. `am_proc_bound → am_create_activity` 差值 800ms(基线 200-400ms)
3. 进一步看 `dumpsys gfxinfo com.example.app` 找具体方法
4. 找到 `Application.onCreate` 阶段耗时 600ms
5. **根因**:Application.onCreate 里启动了一个后台 HTTP 连接(用 OkHttp),HTTP 同步初始化

**根因**:
- `Application.onCreate` 在主线程上同步执行
- HTTP client 初始化涉及 DNS 解析 + TCP 建连 + TLS 握手,网络差时 500-1500ms
- 这 800ms 全部阻塞在 onCreate,App 启动慢 800ms
- 文件路径:`src/com/example/app/MyApplication.java:onCreate`
- 修复方法:把 HTTP client 挪到后台线程 / 改用 `Lazy` 初始化

**修复**:
- 短期:HTTP client 改异步
- 中期:加 startup trace(用 StartupTracer / Firebase Performance)
- 长期:用 `androidx.startup` 库的 Initializer 推迟非关键初始化

**修复原理**:
- Application.onCreate 阻塞是 App 启动慢的头号根因
- 任何在 onCreate 里的同步 I/O / 网络 / 数据库查询,都是"启动慢"的来源
- 量化指标:onCreate 应 < 100ms(线上均值)

### 案例 2:某 App 启动时 ANR 5s,定位 ActivityThread attach 跨进程回调阻塞(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:装某第三方安全 App(代号 SafeGuard)后,启动某 App 触发 ANR

**现象**:
```log
$ adb logcat -d -s ActivityManager,ActivityThread,DEBUG
ANR in com.example.app, Reason: Input dispatching timed out
"main" prio=5 tid=0x1 Native
  at android.os.BinderProxy.transactNative(Native method)
  at android.os.IInterface.transact(IInterface.java:131)
  at android.app.IActivityManager$Stub$Proxy.attachApplication(IActivityManager.java:5500)
  ...
```
**关键观察**:ANR 在 `attachApplication` 跨进程调用上 + 主线程在 `BinderProxy.transactNative` 阻塞 5 秒。

**分析思路**:
1. 关键日志 `BinderProxy.transactNative` 5 秒 → 跨进程调用阻塞
2. 抓 system_server 栈,看 `attachApplication` 在做什么
3. 发现 system_server 端在做 **PMS 第一次扫描**(9.3 §2.1 详述)
4. system_server 端 5 秒 + App 端 ANR
5. 进一步看 PMS 日志,发现 SafeGuard 装了一个特殊 apk 触发 PMS 阻塞

**根因**:
- App 进程 fork 完成后,执行 `ActivityThread.main()` → `attachApplication`
- `attachApplication` 是 Binder 跨进程调用到 system_server
- system_server 端 `attachApplication` 内部会调 PMS 检查 apk 状态
- PMS 在 system_server 端也在做"全量扫描"(9.3 §2.1 详述)
- PMS 扫描阻塞 5s → system_server 处理 `attachApplication` 阻塞 5s → App 端 ANR

**修复**:
- 短期:卸载 SafeGuard
- 中期:SafeGuard 改 apk 安装策略
- 长期:升级到 AOSP 17,PMS 锁设计已重构(9.3 §2.7 详述)

**修复原理**:
- "App 启动 ANR 5s" 未必是 App 写的问题——可能是 system_server 端阻塞
- 排查时同时看 App 端栈 + system_server 端栈
- 这是 9.6 详述的"PMS 锁竞争死锁"案例的"应用侧镜像"

## 5. Takeaway

1. **App 启动链路是 7 步**(Launcher 点击 → AMS → ATMS → Zygote fork → ActivityThread.main → Application.onCreate → 第一帧),**任何一步慢都会让 App 启动退化 100-500ms**。
2. **AMS 与 ATMS 的拆分**是 AOSP 12+ 的设计——"任务栈管理"在 ATMS,"进程管理"在 AMS。9.3 §2.2 已讲 AMS 全功能,本节只讲应用侧视角。
3. **Zygote fork 应用的关键参数**有 7 类(uid / gid / gids / runtimeFlags / mountExternal / seInfo / niceName)——10.2 详述。
4. **ActivityThread.main()** 是 App 进程的 main 入口——任何 App 启动失败都从这里开始查。`attachApplication` 是反向 Binder(App 进程主动告诉 AMS"我准备好了")。
5. **7 个 Perfetto 事件名**(`am_create_task` / `am_new_intent` / `am_proc_start` / `am_proc_bound` / `am_create_activity` / `am_resume_activity` / `first_frame_drawn`)是量化 App 启动时间的关键拐点。
6. **`am_proc_bound` 是关键拐点**——之前是 Framework 决定,之后是 App 写。`am_proc_bound` 之前慢 → 8.x / 10.2 详述;`am_proc_bound` 之后慢 → 10.3 详述。
7. **App 冷启动总耗时 800-2000ms 是线上均值**——AOSP 17 与 AOSP 14 差异不大(±100ms),OTA 升级到 AOSP 17 后 App 启动慢 100ms 是预期的,不是 bug。
8. **"App 启动 ANR 5s" 未必是 App 问题**——可能是 system_server 端阻塞(案例 2)。排查时同时看两端栈。
