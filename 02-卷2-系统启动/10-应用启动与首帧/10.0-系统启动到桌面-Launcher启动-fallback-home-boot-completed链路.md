# 10.0 系统启动到桌面:Launcher 启动 + fallback home + boot_completed 链路

## 一句话开场

**卷 2 "上电到桌面"的 14 个关键节点中,卷 2 的 6-10 章只覆盖了 8 个,完全漏了 Launcher 启动机制 / fallback home 触发 / BOOT_COMPLETED 完整链路 / 第三方 SDK 自启 4 个节点**——本节是 10 章的全局观前奏,把这 4 个 gap 一次性补齐,加上 6 个散落节点(AMS 选 Launcher / Launcher fork / fallback 退场 / BOOT_COMPLETED 广播 / 后台 receiver 拉起 / boot_completed 时间点)的细节,让"系统启动慢"调查不再盲区。

1. **AMS 怎么选 Launcher**?`queryIntentActivities` 找 `android.intent.category.HOME` 列表,多个 home app 时怎么排序?
2. **Launcher 进程怎么 fork**?走的是和普通 app 一样的 `Process.start()` 还是特殊路径?
3. **fallback home 什么时候触发**?`AMS.getFallbackHomeIntent()` 在什么条件下走 fallback?
4. **fallback home 怎么被替换**?真正的 Launcher 准备好后,fallback home 怎么退场?
5. **boot_completed 完整链路**?`systemReady()` → `finishBooting()` → 广播 → `boot_completed=1` 的每一步?
6. **ACTION_BOOT_COMPLETED 接收者怎么拉起**?第三方 SDK 自启(典型现象:装新 App 后首次开机慢 10+ 秒)?

### 2.2 gap A:AMS 怎么选 Launcher(queryIntentActivities + HomeIntent 解析)

**AMS systemReady()** 触发后,会启动 home(launcher)。**"选哪个 home app"** 是关键决定:

```java
// path: frameworks/base/services/core/java/com/android/server/am/ActivityManagerService.java
// commit: android-17.0.0_r1
private Intent getHomeIntent() {
    // 1. 构造 home Intent
    Intent intent = new Intent(Intent.ACTION_MAIN);
    intent.addCategory(Intent.CATEGORY_HOME);
    intent.addCategory(Intent.CATEGORY_DEFAULT);
    return intent;
}

private ResolveInfo resolveHomeActivity(Intent homeIntent, int userId) {
    // 2. 找所有 category=home 的 Activity
    List<ResolveInfo> resolves = mPackageManager.queryIntentActivities(
        homeIntent, ..., userId);
    // 3. 排序(优先级 + 默认 + 包名)
    // ...
    return resolves.get(0);  // 第一个
}
```

**Launcher 选择的 3 个判定**:

| 优先级 | 判定 | 来源 |
|---|---|---|
| 1 | `ro.boot.default.home` 属性 | OEM 启动参数 |
| 2 | `ResolveInfo.priority` | manifest `<activity-alias>` priority 属性 |
| 3 | `ResolveInfo.preferredOrder` | manifest `<activity-alias>` preferredOrder |
| 4 | `ResolveInfo.match` 顺序 | queryIntentActivities 返回顺序 |
| 5 | 包名字典序 | 默认 fallback |

**关键代码路径**:

```java
// path: frameworks/base/services/core/java/com/android/server/am/ActivityManagerService.java
// commit: android-17.0.0_r1
private boolean startHomeActivityLocked(int userId, String reason) {
    // 1. 构造 home intent
    Intent homeIntent = getHomeIntent();
    // 2. 解析 home activity
    ResolveInfo homeInfo = resolveHomeActivity(homeIntent, userId);
    if (homeInfo == null) {
        // ⚠️ 找不到 home activity,走 fallback
        homeInfo = resolveHomeFallbackActivity(homeIntent, userId);
    }
    // 3. 启动 home activity
    return startActivityAsUser(...);
}
```

**对读者有什么用**:
- **"找不到 home" → fallback home 触发**——见 §2.3
- **多个 home app 怎么选**——按 priority / preferredOrder / 包名字典序
- **OEM 改 home app**——通过 `ro.boot.default.home` 属性

### 2.3 gap B:Launcher 进程 fork 路径(走和普通 app 一样的 Process.start)

**Launcher 进程的 fork** 走的是**和普通 app 一样的 `Process.start()`**——AMS → ATMS → ZygoteProcess → Zygote fork → ActivityThread.main。

**Launcher fork 的特殊点**:
- `packageName` = `com.android.launcher3`(Pixel 默认) / `com.google.android.apps.nexuslauncher`(旧 Pixel)
- `niceName` = `com.android.launcher3`
- `seInfo` = `platform:app_process`
- `uid` = 10000+(应用专属 UID,不是 system uid)
- `runtimeFlags` = `DEBUGGABLE`(开发时) / 0(发布时)

**Launcher fork 后的初始化**:

```
[10.2 已讲] Process.start() 触发 Zygote fork
  ↓
[10.1 §2.5 已讲] 子进程执行 ActivityThread.main()
  ↓
[10.3 已讲] Application.attachBaseContext + Application.onCreate
  ↓
[10.3 §2.3 已讲] ContentProvider 初始化
  ↓
Activity.onCreate(Launcher.java / Launcher3.java)
  ↓
setContentView(R.layout.launcher)
  ↓
[10.4 已讲] measure / layout / draw View 树
  ↓
[10.5 已讲] Choreographer 触发第一帧
  ↓
[10.6 已讲] first_frame_drawn 时间点
  ↓
Launcher 第一帧上屏 = 桌面 ready
```

**Launcher 启动慢的 3 类根因**:
- **Launcher onCreate 慢**——加载很多资源 / 数据库查询
- **PMS 第一次扫描阻塞 Launcher**——`dumpsys package` 显示 Launcher 还没 ready
- **第三方 home app 抢了 default**——多个 home app 时 AMS 选错

**对读者有什么用**:
- **"Launcher 启动慢"和"App 启动慢"是同一类问题**——`Process.start()` 链
- **PMS 第一次扫描阻塞 Launcher**——9.3 §2.1 详述
- **OEM 改 home app**——必须在 `AndroidManifest.xml` 正确声明 `CATEGORY_HOME`

### 2.4 gap C-1:fallback home 什么时候触发(3 种触发条件)

**`fallback home`** 是 Android 的"应急机制"——当真正的 launcher 还没 ready 时,显示一个**临时**的 launcher 风格界面。

**fallback home 的 3 种触发条件**:

| 触发条件 | 含义 | 常见场景 |
|---|---|---|
| ① 找不到 home activity | `queryIntentActivities` 返回空 | system app 损坏 / OTA 异常 |
| ② Launcher 还没 ready | `PackageManagerService` 没扫描完 Launcher apk | 第一次开机 / OTA 后第一次开机 |
| ③ Launcher 启动失败 | Launcher 进程 crash | Launcher 自启动崩溃 |

**fallback home 的代码路径**:

```java
// path: frameworks/base/services/core/java/com/android/server/am/ActivityManagerService.java
// commit: android-17.0.0_r1
private boolean startHomeActivityLocked(int userId, String reason) {
    Intent homeIntent = getHomeIntent();
    ResolveInfo homeInfo = resolveHomeActivity(homeIntent, userId);
    if (homeInfo == null) {
        // 触发条件 ①:找不到 home activity
        homeInfo = resolveHomeFallbackActivity(homeIntent, userId);
    }
    // ...
    if (homeInfo.activityInfo.applicationInfo.isSystemApp()
        && !isFirstBootOrUpgrade()) {
        // 触发条件 ②:Launcher 还没 ready
        // 走 fallback
    }
    // ...
}
```

**fallback home Activity 是什么**:

```java
// path: frameworks/base/services/core/java/com/android/server/am/FallbackHome.java
// commit: android-17.0.0_r1
public class FallbackHome extends Activity {
    // 1. 显示一个极简 launcher 风格界面
    // 2. 监听 PackageManagerService 的 "packages available" 广播
    // 3. 一旦真正的 home 准备好,finish() 自己
}
```

**对读者有什么用**:
- **"装新 App 后首次开机显示 fallback home 几秒"**——PMS 还没扫完 Launcher apk
- **"OTA 后显示 fallback home 30 秒"**——PMS 第一次扫描慢(9.3 §2.1 详述)
- **`dumpsys activity activities | grep -A2 "FallbackHome"`**——查 fallback home 状态

### 2.5 gap C-2:fallback home 怎么被替换(退场机制)

**fallback home 退场的 3 步**:

```
[fallback home 显示中]
PMS 扫描完所有 apk
  ↓
发出 "android.intent.action.PACKAGES_AVAILABLE" 广播(自定义)
  ↓
FallbackHome 接收广播
  ↓
FallbackHome.finish()
  ↓
触发 "android.intent.action.HOME" 重新启动
  ↓
AMS 重新解析 home activity
  ↓
这次找到真正的 Launcher
  ↓
启动 Launcher
  ↓
fallback home onPause → onStop → onDestroy
  ↓
桌面真正 ready
```

**fallback home 退场的关键代码**:

```java
// path: frameworks/base/services/core/java/com/android/server/am/FallbackHome.java
// commit: android-17.0.0_r1
public class FallbackHome extends Activity {
    @Override
    public void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        // 1. 注册 PACKAGES_AVAILABLE 广播接收者
        IntentFilter filter = new IntentFilter("android.intent.action.PACKAGES_AVAILABLE");
        registerReceiver(mPackageBroadcastReceiver, filter);
    }

    private final BroadcastReceiver mPackageBroadcastReceiver = new BroadcastReceiver() {
        @Override
        public void onReceive(Context context, Intent intent) {
            // 2. 收到广播,退场
            finish();
        }
    };
}
```

**fallback home 不退场的 3 类常见根因**:
- **PMS 扫描卡死**——9.3 §2.1 详述(rollback 校验)
- **PACKAGES_AVAILABLE 广播被禁止**——SELinux 拒绝
- **真正的 Launcher 启动失败**——Process.start 异常

**对读者有什么用**:
- **"装新 App 后开机卡 30 秒显示 fallback home"**——典型 PMS 扫描阻塞
- **查 fallback home 状态**:`adb shell dumpsys activity activities | grep -A2 "FallbackHome"`
- **修复**——9.3 §2.1 详述 rollback 校验 / PMS 锁竞争

### 2.6 gap D-1:boot_completed 完整链路(5 步)

**`boot_completed = 1`** 不是"桌面显示"就立刻触发,而是**AMS 在 AMS.systemReady() 中主动调用 finishBooting()** 才触发。

**boot_completed 完整链路(5 步)**:

```
[9.1 §2.6 已讲] AMS.systemReady(...) 触发
  ↓
[本节 2.5] 启动 home activity(Launcher / fallback)
  ↓
[本节 2.6] Launcher 第一帧上屏(first_frame_drawn)
  ↓
AMS.finishBooting() 触发
  ├─ 1. 设 mBootCompleted = true
  ├─ 2. mSystemReady = true
  ├─ 3. 启动 PersistentDataBlockService / WebViewUpdateService
  ├─ 4. 写 ro.boottime.boot_completed
  ├─ 5. 触发 ACTION_BOOT_COMPLETED 广播
  ↓
所有监听 ACTION_BOOT_COMPLETED 的 receiver 被拉起
  ↓
整机 boot 真正完成
```

**关键代码**:

```java
// path: frameworks/base/services/core/java/com/android/server/am/ActivityManagerService.java
// commit: android-17.0.0_r1
final void finishBooting() {
    // ...
    synchronized (this) {
        mBootCompleted = true;
    }
    // 1. 启动延后服务
    mSystemServiceManager.startBootPhase(SystemService.PHASE_BOOT_COMPLETED);
    // 2. 写 bootstat
    BootTimingLog log = new BootTimingLog("finishBooting", SystemClock.elapsedRealtime());
    // ...
    SystemProperties.set("sys.boot_completed", "1");
    // 3. 触发广播
    final Intent intent = new Intent(Intent.ACTION_BOOT_COMPLETED, null);
    intent.putExtra(Intent.EXTRA_REPLACEMENT_PACKAGE_NAME, "");
    mBroadcastQueue.broadcastIntent(intent, ...);
}
```

**对读者有什么用**:
- **`ro.boottime.boot_completed` 写入** 才是 boot 真正完成的标志
- **不是 first_frame_drawn**——first_frame_drawn 是显示
- **不是 ACTION_BOOT_COMPLETED 接收完**——是触发

### 2.7 gap D-2:ACTION_BOOT_COMPLETED 接收者怎么拉起第三方 SDK

**`ACTION_BOOT_COMPLETED` 广播** 是 Android 启动期的"全系统 broadcast"——所有声明接收这个 action 的应用都会被拉起。

**典型第三方 SDK 自启**:

```xml
<!-- 第三方 SDK 声明接收 BOOT_COMPLETED -->
<!-- file: AndroidManifest.xml -->
<receiver android:name=".BootReceiver" android:exported="true">
    <intent-filter android:priority="1000">
        <action android:name="android.intent.action.BOOT_COMPLETED" />
    </intent-filter>
</receiver>
```

**第三方 SDK 自启的连锁反应**:

```
AMS finishBooting() 触发
  ↓
发送 ACTION_BOOT_COMPLETED 广播
  ↓
BroadcastQueue 处理(按 priority 排序)
  ↓
依次启动每个 receiver 的进程
  ├─ 微信 SDK 启动:拉起 com.tencent.mm 进程
  ├─ 友盟 SDK 启动:拉起 com.umeng 进程
  ├─ 极光推送 SDK 启动:拉起 jpush 进程
  ├─ Bugly SDK 启动:拉起 com.tencent.bugly 进程
  └─ ... 50+ SDK
  ↓
每个 SDK 在 onReceive 中初始化
  ↓
触发整机"装新 App 后首次开机慢 10+ 秒"的现象
```

**典型现象**:
- 装新 App 后首次开机比不装多 5-15 秒
- 100+ 个 SDK 累计 10+ 秒
- **每个 SDK 都要 cold start**——10.6 §2.1 详述

**对读者有什么用**:
- **"装新 App 后首次开机慢 10 秒"**——SDK 自启 90% 的根因
- **OEM 优化方向**——给 SDK 一个"批次启动"框架,避免同时 cold start
- **`adb shell dumpsys package r android.intent.action.BOOT_COMPLETED | wc -l`**——查 SDK receiver 数量

### 2.9 AOSP 17 vs AOSP 14 的差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| fallback home 触发 | 3 种 | 3 种 | 无变化 |
| AMS 选 Launcher 顺序 | priority / preferredOrder | 同 | 无变化 |
| Launcher fork 路径 | Process.start() | 同 | 无变化 |
| `ACTION_BOOT_COMPLETED` 优先级 | priority 字段 | 同 | 无变化 |
| `sys.boot_completed` 写入 | finishBooting | 同 | 无变化 |

## 4. 实战案例

### 案例 1:某设备装新 App 后首次开机慢 10s,定位 ACTION_BOOT_COMPLETED 接收者(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:用户装一个第三方金融 App(代号 FinanceApp)后首次开机,整机 boot 25s(基线 15s)

**现象**:
```bash
$ adb shell getprop ro.boottime.boot_completed
1738234580.000
$ adb shell getprop ro.boottime.first_frame_drawn
1738234575.000
# 差值 5s,但整机 boot 慢 10s
# 进一步看 BOOT_COMPLETED 接收者
$ adb shell dumpsys package r android.intent.action.BOOT_COMPLETED | wc -l
42
```
**关键观察**:`first_frame_drawn → boot_completed` 差值 5s + 42 个 BOOT_COMPLETED 接收者。

**分析思路**:
1. 关键观察:`first_frame_drawn` 正常,但 `boot_completed` 晚 5s
2. 5s 差值 + 42 个 receiver → 怀疑 SDK 自启
3. 抓 Perfetto trace,看 BOOT_COMPLETED 广播后的事件
4. 发现 5s 全部在处理 BOOT_COMPLETED 接收者
5. 看 dumpsys,42 个 receiver 中:
   - 微信 SDK(进程 com.tencent.mm)
   - 友盟 SDK(进程 com.umeng)
   - 极光推送(进程 jpush)
   - 4 个保活 SDK(进程 com.example.keepalive1-4)
6. 每个 SDK onReceive 都要 cold start
7. **根因**:FinanceApp 引入 5+ 第三方 SDK,每个 SDK 都注册 BOOT_COMPLETED,首次开机冷启所有 SDK

**根因**:
- FinanceApp 引入的 5+ SDK 全部声明 BOOT_COMPLETED
- 每个 SDK onReceive 都要 cold start
- 5 SDK × 1s/SDK = 5s(典型)
- 文件路径:FinanceApp 的 `lib/` 目录里的 5+ AAR
- 修复方法:OEM 给 SDK 一个"批次启动"框架,避免同时 cold start

**修复**:
- 短期:FinanceApp 改用 Lazy 启动 SDK
- 中期:OEM 提供 `BatchBootReceiver` 框架
- 长期:升级到 AOSP 17,SDK 自启机制进一步优化

**修复原理**:
- **装新 App 后首次开机慢 10 秒**——SDK 自启 90% 的根因
- **100+ 个 BOOT_COMPLETED receiver**——每个都是 cold start
- 这是卷 2 必须讲清的"系统启动到桌面"的关键节点

### 案例 2:某设备显示 fallback home 30s 不退,定位 PMS 第一次扫描阻塞(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:某品牌中端机(代号 eagle,4GB RAM)
- 复现步骤:用户装一个第三方安全 App(代号 SafeGuard)后首次开机,显示 fallback home 30 秒

**现象**:
- 屏幕显示 fallback home(临时 launcher 风格)
- 30 秒后真正的 Launcher 起来,fallback home 退场
- 整机 boot 35 秒(基线 15 秒)

```bash
$ adb shell dumpsys activity activities | grep -A2 "FallbackHome"
FallbackHome
  Intent: android.intent.action.MAIN
  Process: com.android.settings
  # ↑ FallbackHome 跑在 settings 进程里

$ adb logcat -d -s PackageManagerService | grep -E "scan.*took"
PackageManagerService: Scanning /data/app took 28500ms
```
**关键观察**:`Scanning /data/app` 耗时 28.5 秒(基线 1-2 秒)+ FallbackHome 跑在 settings 进程里。

**分析思路**:
1. 关键观察:PMS 扫描 28.5 秒 + fallback home 30s
2. 9.3 §2.1 详述 PMS 第一次扫描阻塞原因
3. SafeGuard 装了一个特殊 apk(代号 fake-pkg),manifest 损坏 / 签名错误
4. PMS 扫描 fake-pkg 抛异常,卡在扫描循环
5. 触发 fallback home(PMS 还没扫完 Launcher,AMS 找不到 home)
6. PMS 扫描完 → 触发 PACKAGES_AVAILABLE → fallback home 退场

**根因**:
- SafeGuard 的 fake-pkg manifest 损坏
- PMS 扫描抛异常,但 PMS 没有 try-catch
- 整个扫描循环卡 28.5 秒
- 9.3 案例 1 已讲过类似问题(rollback 校验)
- 修复方法:9.3 案例 1 详述

**修复**:
- 短期:卸载 SafeGuard
- 中期:SafeGuard 改 fake-pkg 签名
- 长期:升级到 AOSP 17,PMS 扫描 try-catch 优化

**修复原理**:
- **fallback home 不退**——通常是 PMS 扫描阻塞
- **fallback home 跑在 settings 进程**——不是单独进程
- 这是 10.0 §2.4 / §2.5 详述的"典型现象"

### 案例 3:某设备 boot_completed 慢 5s,定位第三方接收者 ON RECEIVE 阻塞(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:某品牌中端机(代号 fox,4GB RAM)
- 复现步骤:用户装一个第三方音乐 App(代号 MusicApp)后首次开机,boot_completed 慢 5s

**现象**:
```bash
$ adb shell getprop ro.boottime.boot_completed
1738234585.000
$ adb shell getprop ro.boottime.first_frame_drawn
1738234580.000
# 差值 5s

$ adb logcat -d -s ActivityManager,MusicReceiver | head -100
ActivityManager: Sending BOOT_COMPLETED
MusicReceiver: onReceive start
MusicReceiver: Sync network call took 5s  ← 异常!
```
**关键观察**:`first_frame_drawn → boot_completed` 差值 5s + MusicReceiver 同步网络 5s。

**分析思路**:
1. 关键观察:BOOT_COMPLETED 接收者 MusicReceiver 同步网络 5s
2. MusicReceiver.onReceive 同步 HTTP 请求
3. 阻塞 BroadcastQueue
4. **根因**:第三方音乐 App 把 BOOT_COMPLETED 接收者当"启动钩子",同步网络请求阻塞广播

**根因**:
- MusicReceiver.onReceive 中同步 HTTP 请求
- 阻塞 BroadcastQueue 5s
- 文件路径:MusicApp 的 `MusicReceiver.java:onReceive`
- 修复方法:onReceive 只 record,IO 挪到 WorkManager

**修复**:
- 短期:MusicApp 改 onReceive 异步
- 中期:OEM 给 BOOT_COMPLETED 接收者加 timeout
- 长期:升级到 AOSP 17,广播系统进一步优化

**修复原理**:
- **BOOT_COMPLETED 接收者** 是稳定性高危区——任何 onReceive 阻塞会拖累整机
- **OEM 应该给 BOOT_COMPLETED 接收者加 timeout(默认 10s)**——超过就 fail
- 这是 10.0 §2.7 详述的"系统启动盲区"

## 5. Takeaway

1. **卷 2 "上电到桌面"有 14 个关键节点,卷 2 的 6-10 章只覆盖 8 个,4 个 gap 在本节一次性补齐**——AMS 选 Launcher / Launcher fork / fallback home 触发与退场 / BOOT_COMPLETED 完整链路。
2. **AMS 选 Launcher** 用 `queryIntentActivities` + priority / preferredOrder / 包名字典序 5 个判定——多 home app 时易出错。
3. **Launcher 进程 fork 走的是和普通 app 一样的 `Process.start()`**——不是特殊路径;启动慢的 3 类根因:Launcher onCreate / PMS 扫描阻塞 / 多个 home app。
4. **fallback home 的 3 种触发条件**:① 找不到 home activity ② Launcher 还没 ready ③ Launcher 启动失败——典型现象"装新 App 后显示 fallback home 几秒"。
5. **fallback home 退场靠 `PACKAGES_AVAILABLE` 广播**——PMS 扫描完后通知 fallback home 退场。**fallback home 不退 = PMS 扫描阻塞**。
6. **boot_completed 完整链路 5 步**:systemReady → finishBooting → mBootCompleted=true → 写 ro.boottime.boot_completed → 触发 ACTION_BOOT_COMPLETED 广播。
7. **第三方 SDK 自启是"装新 App 后首次开机慢 10+ 秒"的根因**——100+ 个 BOOT_COMPLETED 接收者每个都 cold start。
8. **"装新 App 后首次开机慢"是 10.0 §2.7 的典型现象**——OEM 应该给 SDK 一个"批次启动"框架,避免同时 cold start。
