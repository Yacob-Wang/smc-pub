# 11.5 开机期稳定性:黑屏 / boot loop / 开机 ANR

## 一句话开场

开机期稳定性是 Android 系统中**判错代价最高**的子系统——用户在按下电源键后,如果遇到黑屏、boot loop 或开机 ANR,没有任何 UI 入口可以"绕过"这个问题,只能等待或强制重启;而运行期闪退通常可以靠重启应用、清理缓存、卸载重装解决。本节讲清 3 大类开机期故障的检测窗口、判定阈值、根因模式与止血手段。

## 1. 核心子问题

本节回答以下 8 个问题:

1. **黑屏**怎么判定?Boot animation 卡住 vs SurfaceFlinger 没起来 vs ActivityManager 没 systemReady,三者黑屏的根因完全不同
2. 黑屏**超时阈值**是多少?AOSP 默认 30s (boot animation timeout) / 60s (SurfaceFlinger first frame) / 厂商 override 10s/20s 的来源
3. **boot loop** 怎么识别?init crash 计数器 `ro.boot.bootloader` 状态机的 `boot_attempt` 累计、SystemServer 重启计数器的阈值
4. boot loop 与"开机慢"在 metrics 上有何**本质区别**?boot loop 是**重启次数 ≥ N** 的事件,开机慢是**单次开机时间偏长**的指标
5. **开机 ANR** 与运行期 ANR 有什么不同?运行期 ANR 是 InputDispatcher 5s / Broadcast 10s,开机 ANR 是 SystemServer `systemReady` 卡死、PMS 扫描 5 分钟未结束、ActivityManager `attachApplication` 阻塞
6. **critical window** 是什么?从 `boot_progress_start` 到 `boot_completed` 这段时间,任何 service crash 都会触发 restart,而 restart 又会回到这条 critical path
7. 开机期**止血手段**有哪些?快速降级(关闭 feature flag)、旁路服务(用 placeholder 替代)、adb 抢救(进入 recovery / fastbootd)
8. **dropbox** 与 **tombstone** 在开机期怎么用?两者都能保存 crash 现场,但 dropbox 是周期性持久化、tombstone 是 native crash 专用

## 2. 详细展开

### 2.1 黑屏的 3 类根因

开机黑屏不是单一故障,而是**多个子系统任一卡住**都会表现出的同一现象。从 SurfaceFlinger 视角往下看,黑屏原因有 3 类:

```
开机黑屏 3 类根因(按 OS 栈从上到下)
┌──────────────────────────────────────────┐
│ 第 1 类:Boot Animation 卡住              │
│   触发:bootanimation.zip 内的 desc.txt   │
│        解析失败 / 帧动画单帧 > 5s         │
│   检测路径:SurfaceFlinger 进程 + bootanim │
│   表现:屏幕显示 boot logo 但无动画,30s+  │
│   黑屏后是否亮屏:否                        │
├──────────────────────────────────────────┤
│ 第 2 类:SurfaceFlinger 没起来              │
│   触发:SurfaceFlinger 启动前卡 init       │
│        阶段(驱动 init 或 boot HAL 卡死)   │
│   检测路径:HIDL / AIDL HAL init + SF 进程 │
│   表现:完全黑屏,无 logo,无动画            │
│   黑屏后是否亮屏:否                        │
├──────────────────────────────────────────┤
│ 第 3 类:ActivityManager 没 systemReady    │
│   触发:AMS.systemReady 阻塞(等 PMS 扫     │
│        描 / 等 system_server 内部 service) │
│   检测路径:ActivityManagerService logcat  │
│   表现:boot logo + 动画正常,但停在 boot   │
│        animation 完成后不再显示 launcher  │
│   黑屏后是否亮屏:启动期间黑屏              │
└──────────────────────────────────────────┘
```

| 类别 | 根因层 | 检测信号 | 典型耗时 | 修复方向 |
|------|--------|----------|----------|----------|
| Boot Animation 卡住 | framework | `SurfaceFlinger: Boot animation finished` 缺失 | 5-30s | 检查 bootanim.zip + bootanim 进程状态 |
| SurfaceFlinger 没起 | HAL / kernel | `SurfaceFlinger` 进程不存在 / 驱动 init 卡 | 5-60s | 检查 display HAL + GPU 驱动 |
| AMS 没 systemReady | framework | `ActivityManager: System now ready` 缺失 | 10-180s | 看 systemReady 卡哪一行 |
| PowerManager 黑屏 | framework | `PowerManager: Waking up` 缺失 | 10-30s | 检查 wake lock / sensor 服务 |
| Keyguard 锁屏异常 | framework | 显示 launcher 但立刻被 keyguard 覆盖 | <5s | 检查 KeyguardService |

### 2.2 boot loop 的判定与检测

boot loop 与"开机慢"在 metrics 上有**本质区别**——前者是**事件**(`boot_attempt` ≥ N 失败后重置),后者是**指标**(单次 boottime 偏长)。Android 用以下机制检测 boot loop:

```
boot loop 检测机制
┌────────────────────────────────────────┐
│ init 层                                 │
│   - restart_service 默认 4 次后停重启   │
│   - exec_start() 失败:重启进程上限 5 次  │
│   - 计数器:svc.name.restart_count       │
├────────────────────────────────────────┤
│ SystemServer 层                         │
│   - SystemServer 进程内 RuntimeInit     │
│     抛未捕获异常 → SystemServer 整体崩  │
│   - CrashRestartCountLimit 默认 4 次   │
│   - 超过后进入 "Boot looped" 状态       │
├────────────────────────────────────────┤
│ Watchdog 层                             │
│   - 监控 SystemServer 主线程 / IO /     │
│     Display 线程 / UI 线程 4 个          │
│   - 阻塞 60s (DEFAULT_TIMEOUT) 即        │
│     dump stack + SystemServer crash      │
│   - crash 4 次 → 重启进入 recovery 模式  │
└────────────────────────────────────────┘
```

| 层级 | 计数器 | 默认阈值 | 超限行为 | 检测方式 |
|------|--------|----------|----------|----------|
| init service | `svc.<name>.restart_count` | 4 | 停重启 + 写 dropbox | `adb logcat -b events` |
| SystemServer | `sys.boot.loop` | 4 | 触发 reboot to recovery | `getprop sys.boot.loop` |
| Zygote | zygote crash 计数 | 1 (致命) | 触发 reboot | `logcat -b crash` |
| Watchdog | SystemServer crash | 4 | reboot + 进入 recovery | `dropbox --print` |

### 2.3 开机 ANR 的判定与根因

开机 ANR 不是"InputDispatcher 5s 触发"那种运行期 ANR,而是**关键路径卡死超过预期阈值**的事件。常见根因:

```
开机 ANR 常见 6 类根因(按发生概率)
┌────────────────────────────────────────┐
│ 1. PMS 扫描阻塞 (40% 案例)              │
│    场景:开机第一次 dex2oat / ART 编译   │
│    表现:从 init 到 boot_completed 卡在  │
│         PMS 阶段,可能 5-10 分钟          │
│    修复:incremental / Cloud Profile      │
├────────────────────────────────────────┤
│ 2. ServiceManager 卡死 (15% 案例)       │
│    场景:binder 驱动 / ServiceManager     │
│         binder_call 阻塞                 │
│    修复:检查 binder 驱动 + SM 进程状态   │
├────────────────────────────────────────┤
│ 3. 系统服务 Service 死锁 (15% 案例)     │
│    场景:ActivityManager / WindowManager │
│         / InputManager 跨服务同步死锁   │
│    修复:看 AMS / WMS / IMS log 同步点   │
├────────────────────────────────────────┤
│ 4. 关键 IO 操作阻塞 (10% 案例)          │
│    场景:Provider 加载 / ContentProvider │
│         主线程 onCreate 阻塞             │
│    修复:AsyncProvider / 延迟注册         │
├────────────────────────────────────────┤
│ 5. 启动器 Activity 加载慢 (10% 案例)    │
│    场景:Launcher 第一次启动 / fallback   │
│         home 加载 / wallpaper load      │
│    修复:预编译 + 资源预加载              │
├────────────────────────────────────────┤
│ 6. HAL / 驱动 init 卡 (10% 案例)        │
│    场景:GPU / Display / Sensor HAL      │
│         init 阻塞或超时                  │
│    修复:看 vendor init.rc + 驱动 log     │
└────────────────────────────────────────┘
```

### 2.4 critical window 与重启风险

从 `boot_progress_start` 到 `boot_completed` 这段时间被称为 **critical window**。在此期间:

- **任何 service crash** 都会触发 init 层的 `restart_service` 机制
- **每次 restart** 都会消耗额外时间(冷启动一次 service 500ms-2s)
- **restart 计数累积** → 触发 boot loop 检测 → 进入 recovery
- 用户视角:**开机过程中看到 logo 反复闪动 / 出现多次震动 / 多次 zygote 重启**

| 阶段 | critical window 入口 | critical window 出口 | 风险等级 |
|------|----------------------|----------------------|----------|
| Pre-SystemServer | `boot_progress_start` | `boot_progress_pms_start` | 高 |
| PMS 启动 | `boot_progress_pms_start` | `boot_progress_ams_ready` | 极高 |
| AMS + WMS | `boot_progress_ams_ready` | `boot_progress_enable_screen` | 中 |
| Launcher 启动 | `boot_progress_enable_screen` | `boot_completed` | 低 |
| 启动后 | `boot_completed` | 无 | 极低 |

### 2.5 开机期止血与降级

当开机期故障发生时,**止血优先级** 远高于修复,因为每次重启都消耗时间 + 触发 boot loop:

| 止血手段 | 适用场景 | 操作方式 | 风险 |
|----------|----------|----------|------|
| Feature flag 关闭 | 某 feature 引发卡死 | `setprop persist.sys.<feature>.disabled 1` | 低 |
| 服务旁路 | 某 service 必崩 | 注释 init.rc 启动行 + 改用 placeholder | 中 |
| 强制进入 recovery | boot loop 触发 | `adb reboot recovery` | 高(用户数据可读) |
| 强制进入 fastbootd | 系统崩溃 | `adb reboot fastboot` | 高(需解锁) |
| Watchdog 临时禁用 | Watchdog 误判 | `setprop dalvik.vm.dexopt-flags v=n` | 中 |
| 跳过 PMS 校验 | PMS 扫描卡 | `setprop pm.dexopt.abort-on-failure false` | 中 |

## 3. 关键产出(可执行 SOP)

**开机黑屏定位 SOP(5 步)**:
```bash
# 第 1 步:看是否有 SurfaceFlinger 进程
adb shell ps -A | grep surfaceflinger
# 有 → 第 2 步;无 → HAL/驱动问题(2.1 第 2 类)

# 第 2 步:看 boot animation 是否有 finished 标记
adb logcat -d -b events | grep -E 'bootanim|boot_animation'
# 有 finished → 第 3 步;无 → boot animation 卡住(2.1 第 1 类)

# 第 3 步:看 ActivityManager systemReady
adb logcat -d -s ActivityManager:I | grep -E 'System (now|boot) ready'
# 有 systemReady → 第 4 步;无 → AMS 卡(2.1 第 3 类)

# 第 4 步:看启动器 Activity 是否成功显示
adb shell dumpsys activity activities | grep -E 'mResumedActivity|mFocusedApp'
# 有 launcher → keyguard / 锁屏问题;无 → SystemServer 内部 service 卡

# 第 5 步:用 Perfetto 抓开机 trace
adb shell perfetto --time 10s --out /data/trace.pb
# 重点看 ams_ready / wms_ready / boot_completed 三个时间戳
```

**boot loop 定位 SOP(4 步)**:
```bash
# 第 1 步:看 init 层的 service 重启次数
adb logcat -b events | grep -E 'service.*restart'
# 出现 svc.<name> restart count >= 4 → 触发 init 层 stop

# 第 2 步:看 SystemServer 是否在重启
adb logcat -b events | grep -E 'sys.boot.loop'
# getprop sys.boot.loop 值为 1 → 已进入 boot loop 状态

# 第 3 步:拉 dropbox 看 crash 现场
adb shell dumpsys dropbox --print | grep -A 30 'system_server_crash'
# 重点看 stack trace 顶部 + 引发 crash 的 service name

# 第 4 步:看 crash 是发生在哪个阶段
# 根据 timestamp + boot_progress_xxx 标记
adb logcat -d -b events | grep boot_progress | tail -20
```

## 4. 实战案例

### 案例 1:某设备开机黑屏 30s 不显示 launcher

**背景**:
- 设备:某 SoC 平台 8GB RAM,出厂 6.0.0,升级到 AOSP 17
- 现象:用户从 5% 电量充电到 50%,按下电源键,boot animation 正常,30s 后仍未显示 launcher
- 现场数据:`boot_progress_enable_screen` 时间戳缺失,`boot_completed` 时间戳延迟

**调查过程**:
1. 抓 logcat,看到 `SurfaceFlinger: Boot animation finished` 在 8.2s 出现
2. 但 `ActivityManager: System now ready` 始终未出现
3. 拉 dropbox,看到 system_server 正常运行,AMS 在等 PMS 的 `PACKAGE_SCANNED` 回调
4. 看 `boot_progress_pms_start` → `boot_progress_ams_ready` 时间差:**47s**
5. 看 PMS log,`dex2oat` 编译阶段 `com.android.systemui` 跑了 38s

**根因**:
- 该设备第一次开机时,**Cloud Profile 还没下载**,所有应用都走 `dex2oat` 全量编译
- `com.android.systemui` 是个大 dex,38s 编译时间拖垮 PMS
- 同时 boot animation 已经结束,但 AMS 等不到 PMS ready,所以显示"动画后黑屏"

**修复**:
- 走 `dexopt-incremental` 增量编译(参考 [8.4 §2.3 增量编译](8-Zygote 与 ART 启动/8.4-启动类加载优化-deferred-class-load.md))
- 启用 `pm.dexopt.bg-dexopt` 让后台线程跑非关键应用
- **总节省:开机时间从 38s → 12s(节省 26s)**

### 案例 2:某设备开机 ANR,SystemServer 主线程死锁

**背景**:
- 设备:某 OEM 6GB RAM 设备,出厂 14
- 现象:用户报开机 3 分钟后自动重启,重启后 5 分钟又重启
- 现场数据:`sys.boot.loop` 值为 1,system_server_crash 在 dropbox 出现 4 次

**调查过程**:
1. 拉 dropbox,看到 system_server_crash 4 次,每次都是 Watchdog 触发
2. Watchdog log 显示主线程 blocked,栈顶在 `ActivityManagerService.attachApplication`
3. 看 `ActivityManagerService` log,发现 `attachApplication` 在等 `WindowManagerService` 的回调
4. `WindowManagerService` log 显示 WMS 在等 `InputManagerService` 的回调
5. `InputManagerService` 在等一个 `InputReader` 线程的事件,但该线程 stuck 在 `epoll_wait`

**根因**:
- Input 设备的 `epoll` 句柄被某个 native service 错误地 `close` 掉
- `InputReader` 线程卡在 `epoll_wait` 永远不返回
- WMS 等 IMS 回调 → AMS 等 WMS 回调 → 主线程死锁
- Watchdog 60s 后强制 crash SystemServer,触发 boot loop

**修复**:
- 给 InputReader 线程加 timeout,避免无限等待
- 给 service 间回调加超时(参考 11.3 §3)
- 总节省:开机稳定性从"3 分钟重启"变成"正常开机"

## 5. Takeaway

1. **开机期故障 P0 优先级**——用户在按下电源键后无 UI 入口绕过,等待/强制重启是唯一选择,比运行期闪退严重得多
2. **黑屏 3 类根因,检测方式完全不同**——boot animation 卡 / SurfaceFlinger 没起 / AMS 没 systemReady,三者检测 logcat 关键字不同,定位 SOP 必须分支
3. **boot loop 是"事件"不是"指标"**——`boot_attempt` 计数超阈值进入 recovery,而不是简单的开机慢;识别用 `sys.boot.loop` 属性
4. **critical window 概念**——`boot_progress_start` 到 `boot_completed` 期间任何 service crash 都会触发 restart,restart 消耗 500ms-2s,反复 restart 触发 boot loop
5. **开机 ANR 与运行期 ANR 完全不同**——前者是 critical window 内的 service 卡死,后者是 InputDispatcher 5s / Broadcast 10s 触发;修复 SOP 不通用
6. **止血优先于修复**——boot loop 期间不要急着改代码,先 `setprop` 关闭 feature flag / 注释 init.rc 启动行,止血后再排查根因
7. **dropbox 是开机期核心调试入口**——比 logcat 持久化更好,因为开机 crash 经常发生在 logcat buffer 滚出去之前
8. **Watchdog 60s 是 AOSP 默认值,常被 OEM override**——10s/20s/30s 在不同 OEM 都见过,定位前先确认设备实际阈值
9. **6 类开机 ANR 根因的概率分布**——PMS 扫描 40% / ServiceManager 15% / service 死锁 15% / IO 阻塞 10% / launcher 慢 10% / HAL 卡 10%;先看 PMS
10. **HAL/驱动卡死最难排查**——往往没有 framework log,只有 kernel log + 厂商私有 log,需要联合 BSP 团队
