# 11.3 开机慢的定位方法:服务依赖链 / 串行阻塞 / IO 争抢

## 一句话开场

**开机慢有 3 类根因模式**:① **服务依赖链**(50+ 服务的硬依赖图,关键路径 = 入度高的服务)② **串行阻塞**(一个服务卡住,所有下游服务都等)③ **IO 争抢**(多个服务同时读 /data 慢)。**找关键路径比找最慢服务更重要**——一个被 10 个服务依赖的 2s 服务,比一个独立的 5s 服务影响大 5 倍。

## 1. 核心子问题

1. **服务依赖图** 怎么画?SystemServer.run 5 大步里哪些服务是关键路径?
2. **入度高的服务**(被很多服务依赖)为什么是优化重点?
3. **串行阻塞** 的 3 种模式?
4. **IO 争抢** 的 3 种类型(读 / 写 / 共享资源)?
5. **资源竞争**(CPU / Memory / IO)的优先级怎么排?
6. **找关键路径** 的方法论?不是找"最慢的服务"而是找"最被依赖的服务"?
7. **3 类根因模式** 怎么选调查工具?
8. AOSP 17 vs AOSP 14 的差异?

## 2. 详细展开

### 2.1 服务依赖图:SystemServer.run 5 大步的硬依赖

**SystemServer 启动 50+ 服务时,服务之间有硬依赖**——A 必须等 B ready 才能启动。

**SystemServer.run 5 大步的关键依赖链**:

```
[SystemServer 启动依赖图]
startBootstrapServices (优先级 1)
  ├─ Installer → 必须先起(其他服务依赖)
  ├─ AMS (lightInit) → 必须先起
  ├─ PowerManagerService → AMS 依赖
  ├─ DisplayManagerService → PowerMS 依赖
  └─ ActivityTaskManager → AMS 依赖
  ↓
startCoreServices (优先级 2)
  ├─ PackageManagerService → 必须先起(50+ 服务依赖)
  ├─ BatteryService → PowerMS 依赖
  └─ UsageStatsService → ActivityManager 依赖
  ↓
startOtherServices (优先级 3,内部串行)
  ├─ WindowManagerService → AMS 依赖
  ├─ InputManagerService → WMS 依赖
  ├─ NotificationManagerService → AMS / WMS 依赖
  └─ JobSchedulerService → AMS 依赖
  ↓
[依赖图 JSON 实际输出]
$ adb shell dumpsys activity services | head -100
# (输出:服务依赖图,标注每个服务的入度)
```

**关键路径 = 入度高的服务**:

| 服务 | 入度(被依赖数) | 启动耗时 | 关键路径权重 |
|---|---|---|---|
| ActivityManagerService | 30+ | 300-800ms | **极高** |
| PackageManagerService | 20+ | 800-1500ms | **极高** |
| PowerManagerService | 10+ | 100-200ms | **高** |
| WindowManagerService | 15+ | 500-1200ms | **极高** |
| InputManagerService | 5+ | 100-300ms | 中 |
| DisplayManagerService | 5+ | 50-150ms | 中 |
| NotificationManagerService | 5+ | 100-300ms | 中 |
| JobSchedulerService | 3+ | 50-150ms | 低 |

**关键洞察**:
- **AMS / PMS / WMS 三个服务的入度都 > 15**——是"关键路径"
- **PMS 慢 1s = 整个 SystemServer 慢 1s**——因为 20+ 服务等 PMS ready
- **优化重点** = 优化入度高的服务(AMS / PMS / WMS)而不是最慢的独立服务

**对读者有什么用**:
- **"找关键路径" = 找入度高的服务**——而不是"找最慢的服务"
- **优化 PMS 比优化 WMS 价值大**——PMS 入度更高
- **WMS 慢 1s 不如 PMS 慢 1s 影响大**——因为依赖链不同

### 2.2 模式 1:串行阻塞(一个服务卡住,所有下游等)

**串行阻塞** 是 SystemServer 启动期最常见的根因——一个服务在 ready 阶段卡住,所有等它的服务都等。

**3 种串行阻塞模式**:

```
模式 1a: AMS 锁竞争
[Init 启动期]
50+ 服务同时调 AMS 锁
  ↓
AMS 锁被某个服务长持
  ↓
其他 49 个服务等锁
  ↓
所有服务都慢 = 整机慢

模式 1b: PMS 第一次扫描阻塞
[SystemServer 启动期]
startCoreServices 触发 PMS 完整初始化
  ↓
PMS.scanDirTracedLI 扫描 /data/app 5s
  ↓
20+ 服务等 PMS ready
  ↓
所有服务都慢 = 整机慢

模式 1c: WMS policy 加载阻塞
[SystemServer 启动期]
startOtherServices 触发 WMS 初始化
  ↓
WMS 加载 framework-res.apk 12s
  ↓
15+ 服务等 WMS ready
  ↓
所有服务都慢 = 整机慢
```

**串行阻塞的 3 个典型症状**:

| 症状 | 表现 | 调查方向 |
|---|---|---|
| SystemServer.run 总时长 > 6s | 多服务都等 | 看 Perfetto 哪个函数在持锁 |
| 多个 ro.boottime.* 同步晚 | 多个服务一起慢 | 找上游 1 个慢服务 |
| `kill -3 system_server` 看到主线程 block | 栈停在某个锁 | 查持锁服务 |

**对读者有什么用**:
- **"SystemServer 慢" 90% 是串行阻塞**——3 种模式 9.3 / 10.0 都讲过
- **PMS 锁竞争**是案例 1 的隐藏根因
- **优化串行阻塞 = 把同步改成异步**

### 2.3 模式 2:服务依赖链(50+ 服务的硬依赖图)

**服务依赖链** 是 SystemServer 启动期的"调度图"——A 等 B,B 等 C,C 等 D...

**关键路径 vs 非关键路径**:

```
[依赖图]
A ← B ← C ← D ← E
         ↑
        (关键路径: D 是关键)

F ← G
   ↑
  (非关键: G 慢 1s 不影响 A)
```

**例子**:

```
[关键路径 1: PMS 路径]
PMS.fullInit (5s)
  ↓ 等
ActivityManagerService 继续
  ↓ 等
WindowManagerService 继续
  ↓ 等
BootReceiver 继续
  ↓ 等
InputManagerService 继续
  ↓ 等
...

[非关键路径 1: UsageStatsService]
UsageStatsService (300ms)
  ↓ 等
WebViewUpdateService
  ↓ 等
(无其他依赖)
```

**关键路径 vs 非关键路径的优化价值**:

| 路径 | 耗时 | 优化后节省 |
|---|---|---|
| 关键路径(PMS 慢 1s) | 1s | **整机节省 1s** |
| 非关键路径(UsageStats 慢 1s) | 1s | **整机节省 0s**(没人等它) |

**对读者有什么用**:
- **找关键路径 = 找"被最多服务依赖"的服务**——而不是"最慢的服务"
- **优化 PMS / AMS / WMS 价值最大**——入度高
- **优化 UsageStats / WebViewUpdate 价值小**——入度低

### 2.4 模式 3:IO 争抢(多个服务同时读 /data 慢)

**IO 争抢** 是开机期"多阶段都稍长"的根因——多个服务同时读 /data,/data 的 IO 性能被分摊,每个服务都慢。

**3 种 IO 争抢类型**:

| 类型 | 表现 | 典型场景 |
|---|---|---|
| **读 /data** | 多个服务同时读 apk / 数据库 / SharedPreferences | PMS 扫描 + 应用 onCreate 同时读 |
| **写 /data** | 多个服务同时写文件 | 多个 SDK 自启写相同文件 |
| **共享资源** | 多个服务等同一个锁(10.x / PMS 锁) | AMS 锁竞争 / PMS 锁竞争 |

**IO 争抢的 3 个典型症状**:

| 症状 | 表现 | 调查方向 |
|---|---|---|
| 多阶段都稍长 1s | iowait 高 4s | 看 Perfetto IO trace |
| 4GB + eMMC 设备 | 大量包读取慢 5s | 检查存储性能 |
| 锁竞争(AMS / PMS) | 50+ 服务等 | 看 logcat 持锁日志 |

**对读者有什么用**:
- **"多阶段都稍长" = IO 争抢**——11.1 案例 2 详述
- **修复**= 减少读 / 写 / 共享资源竞争
- **4GB + eMMC + 大量包 = 经典 IO 性能问题**

### 2.5 资源竞争的优先级

**3 类资源竞争有优先级**:

| 资源 | 优先级 | 调查方向 | 修复 |
|---|---|---|---|
| **CPU 争抢** | 高 | `top -m 5` / Perfetto CPU | 减少 CPU 密集操作 |
| **Memory 争抢** | 高 | `dumpsys meminfo` | 减内存 / 用 ZRAM |
| **IO 争抢** | 中 | `dumpsys diskstats` / Perfetto IO | 减少 IO / 换 UFS |
| **Binder 锁争抢** | 高 | `dumpsys binder` | 减 binder 调用 / 异步化 |

**调查顺序**:
1. **先看 bootstat 差值** → 找"最慢的 1 阶段"
2. **Perfetto 看 IO 等待** → 是不是 IO 争抢
3. **dumpsys meminfo** → 是不是内存争抢
4. **`top -m 5` + `dumpsys cpuinfo`** → 是不是 CPU 争抢
5. **`dumpsys binder`** → 是不是 Binder 锁争抢

**对读者有什么用**:
- **调查顺序:bootstat → Perfetto → meminfo → cpu → binder**——一站式
- **先看 IO 是最快的**——90% 的"多阶段都慢"是 IO

### 2.6 找关键路径的方法论

**方法论 3 步**:

```
[找关键路径]
步骤 1: 画服务依赖图
  - 列出 SystemServer.run 5 大步的 50+ 服务
  - 标注每个服务的"被依赖数"(入度)
  ↓
步骤 2: 找入度 > 10 的服务
  - AMS / PMS / WMS / PowerMS(关键路径)
  - 这些是优化的"高价值"目标
  ↓
步骤 3: 找串行阻塞点
  - 抓 Perfetto 找"卡住的持锁服务"
  - 优化"被 10+ 服务等"的 1 个 2s 服务,比优化 1 个独立 5s 服务价值大
```

**3 类服务优化策略**:

| 服务类型 | 优化策略 |
|---|---|
| **入度高 + 启动慢**(PMS) | **必须优化**——整机都等它 |
| **入度高 + 启动快**(AMS) | 监控 + 早期发现退化 |
| **入度低 + 启动慢**(UsageStats) | **不优化**——节省的价值小 |

**对读者有什么用**:
- **"找关键路径" = 找"被 10+ 服务依赖"的服务**——而不是"最慢的服务"
- **优化 1 个 2s PMS = 整机省 2s**——10.0 案例 1 详述
- **优化 1 个 5s 独立服务 = 整机省 0s**——浪费

### 2.7 3 类根因模式的调查工具

| 模式 | 调查工具 | 关键命令 |
|---|---|---|
| **服务依赖链** | dumpsys + Perfetto | `adb shell dumpsys activity services` + Perfetto 服务依赖视图 |
| **串行阻塞** | Perfetto + logcat | `adb logcat -d -s SystemServer` 找持锁 |
| **IO 争抢** | Perfetto + iostat | `adb shell iostat` + Perfetto IO trace |

**对读者有什么用**:
- **dumpsys 看依赖图**——5 秒定位入度
- **Perfetto 看持锁**——10 秒定位串行阻塞
- **Perfetto + iostat 看 IO**——5 秒定位 IO 争抢

### 2.8 AOSP 17 vs AOSP 14 的差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| 服务依赖图 | JSON 基础 | JSON + 可视化 | +可视化 |
| 锁优化 | 部分 | 全部 | +优化 |
| IO 调度器 | mq-deadline | bfq | 切换 |
| Binder 异步化 | 部分 | 全部 | 优化 |
| AMS 锁 | 单一 | 分级锁 | 优化 |

## 4. 实战案例

### 案例 1:某设备 SystemServer 慢 5s,定位 PMS 串行阻塞(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:用户装某第三方 App(代号 TestApp)后,首次开机 25s

**现象**:
```bash
$ adb shell getprop | grep boottime
[ro.boottime.pms]: [1738234574.000]    ← 4.8s
[ro.boottime.ams_ready]: [1738234574.500]  ← 0.5s(ams 自身快)
[ro.boottime.wms]: [1738234575.000]  ← 0.5s(wms 自身快)
[ro.boottime.ims]: [1738234575.500]
[ro.boottime.boot_completed]: [1738234580.000]  ← 整机 12.1s
```

**根因**:
- PMS 第一次扫描 4.8s
- 20+ 服务等 PMS ready
- ams_ready 0.5s(ams 自身 OK,但必须等 PMS)
- **串行阻塞**:PMS 慢 4.8s,所有下游都等

**修复**:
- 短期:把 rollback 校验挪到 PMS 其他阶段
- 中期:TestApp 改 apk 签名
- 长期:升级 AOSP 17,PMS 锁设计已重构

**修复原理**:
- **PMS 入度高 = 关键路径**——优化 PMS 价值大
- **优化 1 个 2s PMS = 整机省 2s**——这就是关键路径价值

### 案例 2:某设备开机多阶段慢,定位 IO 争抢(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:某品牌中端机(代号 eagle,4GB RAM, eMMC 5.1)
- 复现步骤:用户装 450 个 App 后,首次开机 28s

**现象**:
```bash
# 多阶段都稍长(1-2s):
init → zygote: 1.1s (基线 0.5s, 稍长)
zygote → system_server: 1.5s (基线 1s, 稍长)
system_server → pms: 2.5s (基线 1s, 稍长)
pms → ams_ready: 1.0s (基线 0.5s, 稍长)
ams_ready → first_frame_drawn: 4.0s (基线 2-3s, 稍长)
first_frame_drawn → boot_completed: 4.0s (基线 1-3s, 稍长)
# 总耗时:14.1s vs 基线 18s(实际多阶段都慢)
```

**根因**:
- 4GB + eMMC 5.1 + 450 个包
- 多阶段都稍长 = IO 争抢
- iowait 4s 主导

**修复**:
- 短期:eMMC → UFS 3.1
- 中期:减少包数
- 长期:优化 IO 调度器

**修复原理**:
- **"多阶段都稍长" = IO 争抢**——11.1 案例 2 详述
- **优化 1 阶段没用**——必须优化 IO 整体

## 5. Takeaway

1. **开机慢有 3 类根因模式**:服务依赖链 / 串行阻塞 / IO 争抢——不能用同一个 SOP 修。
2. **服务依赖图的关键路径 = 入度高的服务**——AMS / PMS / WMS 入度 > 15,优化价值最大。
3. **串行阻塞的 3 种模式**:AMS 锁竞争 / PMS 第一次扫描 / WMS policy 加载——任一阻塞 5s = 整机慢 5s。
4. **IO 争抢的 3 种类型**:读 /data / 写 /data / 共享资源——多阶段都稍长就是 IO 争抢。
5. **资源竞争优先级**:Binder 锁 > Memory > CPU > IO——但**实际调查 IO 最快**(90% 的"多阶段都慢"是 IO)。
6. **"找关键路径"比"找最慢服务"更重要**——优化入度高的服务价值是独立的 N 倍。
7. **3 类服务优化策略**:入度高 + 慢 = 必须优化 / 入度高 + 快 = 监控 / 入度低 + 慢 = 不优化(浪费)。
8. **AOSP 17 vs AOSP 14 的差异**:服务依赖图可视化 / 锁优化 / IO 调度器切换 / Binder 异步化。
