# 11.4 开机优化手段:并行化 / 延迟启动 / 预编译 / 镜像优化

## 一句话开场

**5 类开机优化手段**(并行化 / 延迟启动 / 预编译 / 镜像优化 / 服务依赖优化)针对 11.3 的 3 类根因模式——**优化价值评估**是关键:优化 PMS 1s = 整机省 1s(入度高),优化 UsageStats 1s = 整机省 0s(入度低)。本章 5 类优化讲清"什么场景用什么优化 + 投入产出比"。

## 1. 核心子问题

1. **并行化** 怎么用?init.rc action 并行启动有什么限制?
2. **延迟启动** 怎么实现?哪些服务可以延后?
3. **预编译**(dex2oat) 怎么减少启动期 dex2oat?
4. **镜像优化**(EROFS / squashfs) 怎么减少读 IO?
5. **服务依赖优化** 怎么减少"入度高服务"的启动耗时?
6. **5 类优化手段的成本排序** 怎么算?
7. **优化 PMS 1s = 整机省 1s** 的量化机制?
8. AOSP 17 vs AOSP 14 的差异?

## 2. 详细展开

### 2.1 优化 1:并行化(init.rc action 并行 + SystemServer 服务并行)

**并行化** 是最直接的优化——把串行改成并行。

**init.rc action 并行启动**:

```
# path: init.rc
# AOSP 11+ 支持并行 action
on early-init
  start ueventd          ← 并行 1
  start watchdogd         ← 并行 2
  start vold              ← 并行 3
```

**SystemServer 服务并行启动**:

```java
// path: frameworks/base/services/java/com/android/server/SystemServer.java
// commit: android-17.0.0_r1
private void startOtherServices() {
    // 1. 串行启动关键路径服务(PMS / WMS / AMS)
    mActivityManagerService.systemReady(...);
    
    // 2. 并行启动非关键路径服务
    mSystemServiceManager.startService(NotificationManagerService.class);
    mSystemServiceManager.startService(VibratorService.class);
    mSystemServiceManager.startService(StorageManagerService.class);
    // 上述 3 个并行启动,优化 200-500ms
}
```

**并行化的 3 种类型**:

| 类型 | 适用场景 | 典型优化 |
|---|---|---|
| **init.rc action 并行** | init 阶段 | early-init 多个 action 并行 |
| **SystemServer 服务并行** | SystemServer 启动 | startOtherServices 内部并行 |
| **第三方 SDK 自启并行** | Launcher + boot_completed 阶段 | 10.0 §2.7 详述的"批次启动" |

**对读者有什么用**:
- **并行化是最直接的优化**——把串行改成并行,简单有效
- **但并行有依赖约束**——AMS / PMS 慢,其他服务都等
- **优化的关键路径服务比并行更多服务价值大**

### 2.2 优化 2:延迟启动(把非关键服务挪到 boot_completed 后)

**延迟启动** 是把"现在不用的服务"延后到 boot_completed 之后。

**3 类延迟启动策略**:

| 策略 | 适用 | 典型 |
|---|---|---|
| **`defer-start`** | init 阶段 | `service xxx /system/bin/xxx class main` 加 `disabled` |
| **`PHASE_BOOT_COMPLETED`** | SystemServer 阶段 | SystemService.onBootPhase(PHASE_BOOT_COMPLETED) |
| **`WorkManager`** | Launcher 阶段 | boot_completed 后异步任务 |

**典型延后服务**:

| 服务 | 延后策略 | 节省耗时 |
|---|---|---|
| `BackupManagerService` | 延后到 boot_completed + 5s | 200-500ms |
| `WebViewUpdateService` | 延后到 boot_completed + 10s | 300-500ms |
| `BugreportManagerService` | 延后到 boot_completed + 30s | 100-200ms |
| `VibratorService` | 延后到 boot_completed | 50-100ms |
| `StorageManagerService` | 延后到 boot_completed | 100-300ms |
| 第三方 SDK 自启 | 延后到 boot_completed + 5s | 500-2000ms(10.0 §2.7) |

**对读者有什么用**:
- **延迟启动 = 关键路径优化**——把非关键服务从 SystemServer 启动期挪走
- **但延迟启动有上限**——用户期待某些服务立即可用(如 SMS)
- **第三方 SDK 自启延后** 是装新 App 后首次开机慢的最优优化

### 2.3 优化 3:预编译(dex2oat / Cloud Profile / AOT 缓存)

**预编译** 是把"运行时编译"挪到"安装时/空闲时"——减少启动期 dex2oat 阻塞。

**3 类预编译策略**:

| 策略 | 适用 | 节省 |
|---|---|---|
| **`pm.dexopt.install=verify`** | 应用安装时 | 减少启动期 dex2oat 1-3s |
| **`pm.dexopt.bg-dexopt-scheduling-threshold`** | 空闲时 | 减少首次启动 dex2oat 0.5-2s |
| **Cloud Profile** | 启动预优化 | 减少首次启动 1-2s(8.3 详述) |

**8.3 已讲**:
- 预编译触发链:installd → dex2oat → 写 ART profile
- Cloud Profile:从 Google Play 下载 + 写本地 profile
- lazy preload:把不常用 class 延后(8.4 详述)

**对读者有什么用**:
- **预编译是"减少启动期 dex2oat"的核心**——8.3 已详述
- **装新 App 后首次开机慢**——主要因为 dex2oat 第一次
- **Cloud Profile** 是 Google 推动的优化——AOSP 17 加强

### 2.4 优化 4:镜像优化(EROFS / squashfs / 增量更新)

**镜像优化** 是从存储层减少读 IO——开机期大量读 /system 慢,优化镜像格式。

**4 类镜像优化**:

| 优化 | 适用 | 节省 |
|---|---|---|
| **EROFS**(Enhanced Read-Only File System) | /system 分区 | 减少读 IO 20-30% |
| **squashfs**(替代 ext4) | /system 分区 | 减少读 IO 10-20% |
| **dm-verity** | /system 完整性 | 减少读 IO 5-10% |
| **快照增量更新**(Snapshots) | OTA 升级 | 减少 IO 50%+ |

**EROFS 详解**(AOSP 13+):

```
EROFS 是华为贡献的 read-only 文件系统
  - 比 ext4 快 20-30%
  - 支持压缩(zstd / lz4)
  - 支持 in-place decompression
  - AOSP 13+ 默认启用
  - 写仍然用 ext4(只读不写)
```

**对读者有什么用**:
- **EROFS 是 AOSP 13+ 默认**——不需要 OEM 改
- **4GB + eMMC + 大量包 = 镜像优化价值大**——11.1 案例 2 详述
- **OTA 增量更新**——降低 30s OTA → 5s OTA

### 2.5 优化 5:服务依赖优化(入度高的服务重点优化)

**服务依赖优化** 是按 11.3 §2.6 找关键路径方法论,优化入度高的服务。

**3 类服务依赖优化**:

| 优化 | 适用 | 价值 |
|---|---|---|
| **PMS 第一次扫描优化** | PMS 慢 5s | 整机省 5s(9.3 §2.1) |
| **WMS policy 资源优化** | WMS 慢 2s | 整机省 2s(9.2 §2.4) |
| **AMS 锁竞争优化** | AMS 卡 | 50+ 服务都等 |

**PMS 第一次扫描的 5 类优化**:

| 优化 | 节省 |
|---|---|
| **关闭 rollback 校验** | 1-3s |
| **incremental OTA** | 1-2s |
| **减少 preload classes** | 0.5-1s |
| **DEX opt 缓存** | 0.5-1s |
| **lazy-preloaded-classes** | 0.5-1s |

**对读者有什么用**:
- **PMS 优化价值最大**——入度高(20+)
- **WMS 优化次之**——入度高(15+)
- **优化 1 个 PMS 1s = 整机省 1s**——这是关键路径优化价值

### 2.6 5 类优化手段的成本排序

**5 类优化的"投入 vs 价值"排序**:

| 优化 | 投入 | 价值(整机节省) | 投入产出比 |
|---|---|---|---|
| **延迟启动第三方 SDK** | 低(改 manifest) | 高(500-2000ms) | **极高** |
| **EROFS 镜像** | 中(内核) | 高(200-500ms) | 中 |
| **并行化** | 中(改 init.rc) | 中(200-500ms) | 中 |
| **预编译(dex2oat)** | 中(改系统) | 中(300-500ms) | 中 |
| **服务依赖优化(PMS)** | 高(改 framework) | 高(1-3s) | 中(改 framework 风险大) |

**优化优先级**:
1. **延迟启动第三方 SDK**——最便宜,价值最高(10.0 §2.7)
2. **EROFS 镜像**——AOSP 13+ 默认,OEM 只需验证
3. **并行化**——改 init.rc + SystemServer,中等投入
4. **预编译**——改 system,中等投入
5. **服务依赖优化**——改 framework,高风险高价值

**对读者有什么用**:
- **优化先做"投入产出比"高的**——延后 SDK 自启最划算
- **OEM 应该把 EROFS 验证通过**——这是免费的优化
- **服务依赖优化是高风险**——改 framework 出错可能整机挂

### 2.7 AOSP 17 vs AOSP 14 的差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| EROFS 优化 | 稳定 | 稳定 + 增强 | +zstd 压缩 |
| 第三方 SDK 自启 | OEM 自定义 | OEM 批次启动框架 | +feature |
| PMS 第一次扫描 | rollback 校验 | rollback 校验可关闭 | +优化 |
| init.rc 并行 | 部分支持 | 全部支持 | +10% 优化 |
| Cloud Profile | 稳定 | 稳定 + 增强 | +feature |
| 服务依赖 | 50+ 服务 | 60+ 服务 | +10 服务,更多依赖 |

> **🟡 待联网确认**:init.rc 并行启动的 AOSP 17 实际语法,以 AOSP 17 build 为准。

## 4. 实战案例

### 案例 1:某设备装新 App 后首次开机慢 10s,定位第三方 SDK 自启,延后 SDK 节省 5s(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:装新 App 后首次开机 25s(基线 18s)

**优化前**:
```bash
$ adb shell getprop | grep boottime
[ro.boottime.boot_completed]: [1738234585.000]  ← 整机 17.1s
# 差值:
# first_frame_drawn → boot_completed = 5s
# (第三方 SDK 自启)
```

**优化方案**:延后 5 个 SDK 到 boot_completed + 10s

```java
// 修 SDK 的 AndroidManifest.xml
// 改之前:
<receiver android:name=".BootReceiver" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.BOOT_COMPLETED" />
    </intent-filter>
</receiver>

// 改之后:
<receiver android:name=".BootReceiver" android:exported="false">
    <!-- 改用 WorkManager 延后启动 -->
</receiver>

// 在 Application.onCreate 中:
WorkManager.getInstance(this).enqueueUniqueWork(
    "delayed_init",
    ExistingWorkPolicy.REPLACE,
    OneTimeWorkRequestBuilder<DelayedInitWorker>()
        .setInitialDelay(10, TimeUnit.SECONDS)
        .build()
);
```

**优化后**:
```bash
$ adb shell getprop | grep boottime
[ro.boottime.boot_completed]: [1738234580.000]  ← 整机 12.1s
# 节省 5s
```

**根因**:
- 5 SDK 在 BOOT_COMPLETED 自启
- 每个 SDK 冷启 1s × 5 = 5s
- 延后到 boot_completed + 10s(用户不感知)

**修复原理**:
- **延后启动第三方 SDK** 是"投入产出比"最高的优化
- **节省 5s,投入是改 SDK 几个文件**
- 这是 10.0 §2.7 详述的"典型现象"

### 案例 2:某设备开机慢 5s,定位 PMS rollback 校验,优化 PMS 节省 3s(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 eagle,4GB RAM)
- 复现步骤:用户装 380 个 App 后,首次开机 25s(基线 18s)

**优化前**:
```bash
$ adb shell getprop | grep boottime
[ro.boottime.pms]: [1738234574.000]    ← 4.8s 异常
[ro.boottime.boot_completed]: [1738234580.000]  ← 整机 12.1s
```

**优化方案**:
- 把 PMS rollback 校验挪到 PMS 其他阶段
- 9.3 §2.1 详述

```java
// path: frameworks/base/services/core/java/com/android/server/pm/PackageManagerService.java
// commit: android-17.0.0_r1
// 改之前:
private void scanDirTracedLI(File scanDir, ...) {
    // ... 扫描时同步做 rollback 校验
    // 360+ apk × 10ms = 3.6s
}

// 改之后:
private void scanDirTracedLI(File scanDir, ...) {
    // 扫描时只做轻量校验
    // 完整 rollback 校验延后到 postBoot 阶段
    mPostBootRollbackChecks.add(apk);
}
```

**优化后**:
```bash
$ adb shell getprop | grep boottime
[ro.boottime.pms]: [1738234571.000]    ← 1.8s
[ro.boottime.boot_completed]: [1738234577.000]  ← 整机 9.1s
# 节省 3s
```

**根因**:
- PMS 第一次扫描 4.8s
- rollback 校验占 3s
- 20+ 服务等 PMS,整机都慢
- **PMS 是关键路径**——优化 3s = 整机省 3s

**修复原理**:
- **优化 PMS 1s = 整机省 1s**——这是关键路径优化价值
- **入度 20+ 的服务值得高风险优化**——framework 修改
- 修复必须做完整测试(framework 改错可能整机挂)

## 5. Takeaway

1. **5 类优化手段**(并行化 / 延迟启动 / 预编译 / 镜像优化 / 服务依赖优化)针对 11.3 3 类根因模式。
2. **优化优先级**:延后第三方 SDK > EROFS > 并行化 > 预编译 > 服务依赖优化——按"投入产出比"排。
3. **延后启动第三方 SDK** 是"投入产出比"最高的优化——节省 500-2000ms,投入是改 SDK 几个文件。
4. **优化 PMS 1s = 整机省 1s**——PMS 入度高(20+),是"关键路径"。
5. **优化 1 个 2s PMS 比优化 1 个 5s 独立服务价值大 5 倍**——这是 11.3 §2.6 找关键路径的核心。
6. **EROFS 是 AOSP 13+ 默认**——OEM 只需验证,免费的优化。
7. **服务依赖优化是高风险**——改 framework 出错可能整机挂,必须完整测试。
8. **AOSP 17 vs AOSP 14 差异**:EROFS 增强 / OEM 批次启动框架 / init.rc 全部并行 / 60+ 服务(更多依赖)。
