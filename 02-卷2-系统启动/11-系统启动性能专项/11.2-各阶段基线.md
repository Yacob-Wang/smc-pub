# 11.2 各阶段基线:Bootloader / Kernel / init / Zygote / SystemServer / Launcher

## 一句话开场

**5 个阶段各自有标准基线和异常阈值**——Bootloader 1-3s / Kernel 1-3s / Init 1-3s / Zygote+SystemServer 2-4s / Launcher+boot_completed 2-5s,总耗时 7-18s 是健康。本节逐一展开每个阶段的标准耗时/异常阈值/典型根因/相关章节,让读者"看到差值"就能定位章节。

## 1. 核心子问题

1. Bootloader 阶段标准基线是多少?AVB 校验为什么慢?
2. Kernel 阶段标准基线是多少?内核 initcall 慢的根因?
3. Init 阶段标准基线是多少?init.rc action 卡死的根因?
4. Zygote 阶段标准基线是多少?preload 慢的根因?
5. SystemServer 阶段标准基线是多少?50+ 服务慢的根因?
6. Launcher 阶段标准基线是多少?第三方 SDK 自启慢的根因?
7. 5 阶段联动:总耗时 = 串行慢叠加?
8. 异常阈值怎么定?比基线慢多少算"需要调查"?

## 2. 详细展开

### 2.1 阶段 1:Bootloader(1-3s 标准基线)

**Bootloader 阶段**是上电到 kernel 入口的过渡,标准基线 1-3s。

| 子阶段 | 标准耗时 | 异常阈值 | 典型根因 |
|---|---|---|---|
| PBL(Boot ROM) | 100-300ms | > 500ms | 硬件故障(极少) |
| XBL(Secondary Bootloader) | 200-500ms | > 1s | AVB 校验失败 / 锁状态异常 |
| ABL(Apps Bootloader,基于 edk2) | 300-800ms | > 2s | AVB 校验 / logo 渲染慢 |
| Kernel Load(zImage 加载) | 100-300ms | > 500ms | 存储慢(eMMC 5.1 / UFS 2.1) |
| DT 解析 | 50-150ms | > 300ms | DT 复杂 / overlay 慢 |
| **总计** | **1-3s** | **> 5s** | — |

**典型根因细化**:

| 根因 | 症状 | 修复 |
|---|---|---|
| AVB 校验失败 | Bootloader 慢 5s,log 报 `avb_slot_verify` | OEM 检查 vbmeta 链 |
| OEM logo 渲染 | Bootloader 慢 2s,但 AVB OK | 减小 logo 分辨率 |
| eMMC 5.1 慢 | Bootloader 慢 3s,log 报 `mmcqd_timeout` | 换 UFS 3.1 |
| DT overlay 复杂 | DT 解析慢 1s | 合并 DT overlay |

**对读者有什么用**:
- **`ro.boottime.init` 晚** → Bootloader 慢
- **Bootloader > 5s** → 严重 AVB / 存储问题
- **看 last_kmsg**:6.x 已讲,定位 AVB 错误

### 2.2 阶段 2:Kernel(1-3s 标准基线)

**Kernel 阶段**是从 head.S 到 `/init` 启动,标准基线 1-3s。

| 子阶段 | 标准耗时 | 异常阈值 | 典型根因 |
|---|---|---|---|
| head.S(汇编) | 50-150ms | > 300ms | 启动参数多(quiet log) |
| start_kernel | 100-300ms | > 500ms | 内核线程多 |
| SMP bringup(多核) | 200-500ms | > 1s | CPU 数量多(8 核+) |
| initcall(驱动初始化) | 500-1500ms | > 3s | 驱动多 / 慢驱动 |
| ACPI 初始化 | 100-300ms | > 500ms | ACPI 表复杂 |
| `/init` 启动 | 50-100ms | > 200ms | init 自身慢 |
| **总计** | **1-3s** | **> 5s** | — |

**典型根因细化**:

| 根因 | 症状 | 修复 |
|---|---|---|
| 内核 initcall 慢 | Kernel 慢 3s,log 报 `initcall xxx returned 0` | 减驱动 / 延后初始化 |
| CPU 数量多(8 核+) | SMP bringup 慢 1s | 减少 CPU 数量 |
| ACPI 表复杂 | ACPI 慢 1s,log 报 `ACPI: xxx` | 简化 ACPI 表 |
| 慢文件系统挂载 | Kernel → Init 切换慢 1s | 检查 fstab |

**对读者有什么用**:
- **`ro.boottime.init` 晚** → Kernel 慢
- **Kernel > 5s** → 内核 initcall 严重问题
- **看 dmesg + last_kmsg**:6.x 已讲,定位 initcall 慢

### 2.3 阶段 3:Init(1-3s 标准基线)

**Init 阶段**是 init 进程从 main 到关键 action 跑完,标准基线 1-3s。

| 子阶段 | 标准耗时 | 异常阈值 | 典型根因 |
|---|---|---|---|
| init main | 100-300ms | > 500ms | init 自身初始化 |
| LoadBootScripts(解析 init.rc) | 50-150ms | > 300ms | init.rc 复杂 / import 多 |
| early-init action | 50-200ms | > 500ms | ueventd 启动慢 |
| init action | 200-500ms | > 1s | 服务启动慢 |
| post-fs action(mount) | 200-500ms | > 1s | fstab 复杂 / mount 慢 |
| post-fs-data(action + 准备 /data) | 200-500ms | > 1s | /data mount 慢 |
| late-start action(启动 zygote) | 100-300ms | > 500ms | zygote 启动慢 |
| **总计** | **1-3s** | **> 5s** | — |

**典型根因细化**:

| 根因 | 症状 | 修复 |
|---|---|---|
| init.rc action 卡死 | Init 慢 3s,log 报 `wait for property` | 检查 init.rc 死等 |
| odsign 等待 | Init 慢 2s,log 报 `wait for odsign.verification.done` | 7.3 详述 |
| fstab 复杂 | mount 慢 1s,log 报 `mount /system` | 简化 fstab |
| /data mount 慢 | post-fs-data 慢 1s | 检查 f2fs 状态 |

**对读者有什么用**:
- **`ro.boottime.zygote - ro.boottime.init` 差值大** → Init 慢
- **Init > 5s** → init.rc action 死等问题
- **看 init.log + last_kmsg**:7.x 已讲,定位 action 卡死

### 2.4 阶段 4:Zygote + SystemServer(2-4s 标准基线)

**Zygote + SystemServer 阶段**是从 app_process 到 50+ 服务 ready,标准基线 2-4s。

| 子阶段 | 标准耗时 | 异常阈值 | 典型根因 |
|---|---|---|---|
| Zygote preload | 800-1500ms | > 3s | preload class 多 / ImageSpace 慢 |
| Zygote fork system_server | 30-60ms | > 200ms | USAP 池未命中 |
| SystemServer.run 5 大步 | 1500-3000ms | > 5s | 服务启动慢(见 9.3) |
| ├─ startBootstrapServices | 200-500ms | > 1s | AMS.lightInit / PowerMS 慢 |
| ├─ startCoreServices | 500-1500ms | > 3s | **PMS 第一次扫描阻塞** |
| └─ startOtherServices | 1500-3500ms | > 5s | WMS / IMS 慢 |
| PMS 第一次扫描(/data/app) | 800-1500ms | > 3s | **rollback 校验慢**(9.3 §2.1) |
| **总计** | **2-4s** | **> 6s** | — |

**典型根因细化**:

| 根因 | 症状 | 修复 |
|---|---|---|
| Zygote preload 慢 | Zygote 阶段慢 2s | 减 preload class / 改 lazy |
| PMS rollback 校验 | Core 阶段慢 3s,log 报 `Scanning /data/app took` | 改扫描策略(9.3 §2.1) |
| WMS policy 加载 | Other 阶段慢 2s,log 报 `Window manager policy loaded` | 9.2 案例 1 |
| AMS service 注册慢 | Other 阶段慢 1s | 9.3 §2.6 |
| USAP 池未命中 | App 启动慢 | 10.2 案例 1 |

**对读者有什么用**:
- **`ro.boottime.ams_ready - ro.boottime.init` 差值大** → Zygote + SystemServer 慢
- **SystemServer > 6s** → 服务启动严重问题
- **看 Perfetto + logcat**:8.x / 9.x 已讲,定位具体服务慢

### 2.5 阶段 5:Launcher + boot_completed(2-5s 标准基线)

**Launcher + boot_completed 阶段**是从 Launcher fork 到第三方 SDK 自启完,标准基线 2-5s。

| 子阶段 | 标准耗时 | 异常阈值 | 典型根因 |
|---|---|---|---|
| Launcher fork + onCreate | 500-1500ms | > 3s | Launcher 自身慢 |
| ├─ AMS 选 Launcher | 5-20ms | > 50ms | 多 home app 选错(10.0 §2.2) |
| ├─ Launcher fork | 30-60ms | > 200ms | USAP 池未命中 |
| ├─ Launcher Application.onCreate | 100-300ms | > 1s | Launcher 同步 IO |
| └─ Launcher Activity onCreate | 200-500ms | > 1s | Launcher 布局复杂 |
| Launcher 第一帧 | 200-500ms | > 1s | Choreographer 等待 VSYNC |
| finishBooting + boot_completed | 100-300ms | > 1s | AMS 内部 finishBooting 慢 |
| 第三方 SDK 自启 | 500-2000ms | > 5s | 100+ BOOT_COMPLETED receiver(10.0 §2.7) |
| **总计** | **2-5s** | **> 8s** | — |

**典型根因细化**:

| 根因 | 症状 | 修复 |
|---|---|---|
| 多个 home app | AMS 选错 Launcher | 改 priority / preferredOrder(10.0 §2.2) |
| fallback home 不退 | 显示 fallback 30s | 修 PMS 扫描(10.0 §2.4) |
| Launcher 同步 IO | Launcher 慢 1s | 改 lazy |
| PMS 扫描阻塞 Launcher | Launcher 慢 2s | 9.3 §2.1 优化 |
| 100+ SDK 自启 | boot_completed 慢 5s | OEM 批次启动优化(10.0 §2.7) |
| BOOT_COMPLETED 同步 IO | boot_completed 慢 5s | 修第三方 SDK(10.0 案例 3) |

**对读者有什么用**:
- **`ro.boottime.boot_completed - ro.boottime.first_frame_drawn` 差值大** → 第三方 SDK 自启
- **Launcher > 8s** → 多 root 原因叠加
- **看 dumpsys + Perfetto**:10.0 已讲

### 2.6 5 阶段联动:总耗时 = 串行慢叠加

**5 阶段不是独立的**——1 阶段慢会拖累下个阶段,有时总耗时 = 串行慢叠加:

```
[5 阶段 串行]
Bootloader (3s) → Kernel (3s) → Init (3s) → Zygote+SystemServer (4s) → Launcher+boot_completed (5s)
   ↓              ↓              ↓                ↓                                ↓
 最坏 18s        最坏 18s       最坏 18s         最坏 18s                          最坏 18s
                                                                          总耗时 = 18s
```

**总耗时 = 5 阶段耗时累加**(基线累加) + 阶段间联动(资源竞争 / 共享 IO)

**常见叠加场景**:
- Bootloader 3s + Kernel 3s + Init 3s + Zygote+SystemServer 4s + Launcher+boot_completed 5s = **总 18s(基线)**
- 异常叠加:Bootloader 5s + Kernel 5s + Init 5s + SystemServer 6s + Launcher 8s = **总 29s(异常)**
- 资源竞争:Kernel IO 慢 → Init mount 慢 → Zygote preload 慢 → SystemServer 服务慢 → Launcher 慢(**总 25s 但每阶段都稍长**)

**对读者有什么用**:
- **"开机慢 5 秒"通常不是 1 阶段慢 5s**——可能是 5 阶段各慢 1s 叠加
- **找"最慢的 1 阶段"是错误思路**——找"叠加最严重"的组合
- **10.0 案例 2 详述 IO 争抢**——4GB + eMMC + 450 包

### 2.7 异常阈值与调查 SOP

**5 阶段各自的异常阈值**(以基线 50% 慢为门槛):

| 阶段 | 标准基线 | 异常阈值(> 50% 慢) | 调查 SOP |
|---|---|---|---|
| Bootloader | 1-3s | > 4.5s | 6.x + last_kmsg |
| Kernel | 1-3s | > 4.5s | 6.x + dmesg |
| Init | 1-3s | > 4.5s | 7.x + init.log |
| Zygote + SystemServer | 2-4s | > 6s | 8.x / 9.x + Perfetto |
| Launcher + boot_completed | 2-5s | > 7.5s | 10.0 + dumpsys |
| **总耗时** | **7-18s** | **> 27s** | 11.x 多阶段叠加 |

**调查 SOP**:

```
"开机慢 X 秒"用户报告
  ↓
[1] adb shell getprop | grep boottime  ← 5 秒(11.1)
  - 算 5 阶段差值
  - 找"最慢的 1 阶段"
  ↓
[2] 该阶段 > 异常阈值?
  ├─ Bootloader 慢 → 6.x
  ├─ Kernel 慢 → 6.x
  ├─ Init 慢 → 7.x
  ├─ Zygote+SystemServer 慢 → 8.x / 9.x
  ├─ Launcher+boot_completed 慢 → 10.0
  └─ 多阶段叠加慢 → 11.3 §
  ↓
[3] 查具体章节 + 跑对应 SOP
```

## 4. 实战案例

### 案例 1:某设备 Kernel 慢 3s,定位 initcall 慢(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:首次开机 22s(基线 18s)

**现象**:
```bash
$ adb shell getprop | grep boottime
[ro.boottime.init]: [1738234567.890]
# init 时间正常,但 Kernel 阶段(从 power on 到 init)慢 4s
$ adb pull /sys/fs/pstore/console-ramoops | grep -E "initcall"
[    0.005000] initcall xxx returned 0 (used 50ms)
[    0.500000] initcall yyy returned 0 (used 200ms)  ← 慢
[    1.500000] initcall zzz returned 0 (used 800ms)  ← 异常慢!
[    2.800000] initcall aaa returned 0 (used 100ms)
[    3.500000] Run /sbin/init as init process
# 5 个 initcall 累计 1.3s,但 zzz 占 800ms
```

**根因**:
- OEM 加的某个内核驱动 initcall 耗时 800ms
- 5 个 initcall 累计 1.3s,这是 Kernel 慢的主因
- 修复:把 zzz 驱动改为 late_initcall(延后初始化)

**修复**:
- 短期:把慢的 initcall 改为 late_initcall
- 中期:把 zzz 驱动移到 modprobe(按需加载)
- 长期:减少 initcall 数量

### 案例 2:某设备 SystemServer 慢 5s,定位 PMS rollback 校验(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 eagle,4GB RAM)
- 复现步骤:用户装某第三方 App(代号 TestApp)后,首次开机 28s

**现象**:
```bash
$ adb shell getprop | grep boottime
[ro.boottime.init]: [1738234567.890]
[ro.boottime.zygote]: [1738234568.500]
[ro.boottime.system_server]: [1738234569.200]
[ro.boottime.pms]: [1738234574.000]    ← 4.8s(基线 1-2s)
[ro.boottime.ams_ready]: [1738234575.000]
[ro.boottime.boot_completed]: [1738234580.000]  ← 整机 12.1s

# 差值:system_server → pms = 4.8s
```

**根因**:
- PMS 第一次扫描 4.8s
- TestApp 引入 rollback 校验慢(9.3 §2.1 详述)
- 修复:挪走 rollback 校验

**修复**:
- 短期:把 rollback 校验挪到 PMS 其他阶段
- 中期:TestApp 改 apk 签名
- 长期:升级 AOSP 17,PMS 锁设计已重构

## 5. Takeaway

1. **5 阶段各自有标准基线和异常阈值**——Bootloader 1-3s / Kernel 1-3s / Init 1-3s / Zygote+SystemServer 2-4s / Launcher+boot_completed 2-5s。
2. **总耗时 7-18s 是健康**——> 27s 是"用户能感知的慢"。
3. **每个阶段慢的根因不一样**——Bootloader 慢是 AVB / Kernel 慢是 initcall / Init 慢是 action 卡死 / SystemServer 慢是 PMS / Launcher 慢是 SDK 自启。
4. **异常阈值 = 基线 × 1.5**(50% 慢是门槛)——给具体调查触发条件。
5. **5 阶段不是独立的**——1 阶段慢会拖累下个阶段,总耗时 = 串行慢叠加 + 资源竞争(IO / CPU / Memory)。
6. **"开机慢 X 秒"通常不是 1 阶段慢 X 秒**——可能是 5 阶段各慢 1s 叠加(11.0 案例 2 IO 争抢 iowait 4s)。
7. **Kernel 慢通常看 initcall**——last_kmsg 找 `initcall xxx returned 0`,找耗时 > 200ms 的 initcall。
8. **SystemServer 慢通常看 PMS**——`ro.boottime.pms` 是 Core 阶段绝对瓶颈(9.3 §2.1 详述)。
