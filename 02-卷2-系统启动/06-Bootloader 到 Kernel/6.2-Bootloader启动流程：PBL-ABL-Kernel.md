# 6.2 Bootloader 启动流程：PBL → ABL → Kernel

## 一句话开场

**Android 设备从按电源键到桌面，总共经历 4 段 7 阶段**——每段耗时、失败现象、调查工具都不同。理解这个时序是 boot loop 调查的"时间线基础"。

按 AOSP 17 + Pixel 8 SM8550 的实测基线：

```
上电 → PBL(50ms) → XBL(300ms) → ABL(200ms) → Kernel start_kernel(100ms) → init/main.c(2s) → 桌面
总耗时：2-4s（冷启动）/ 1-2s（温启动）
```

任何一段的"卡"都会表现为不同的用户感知——这就是 boot loop 调查**第一手观察**的判定依据。

## 1. PBL（Primary Boot Loader）：SoC 里的"硬连线"

### 1.1 PBL 的固化位置与不可升级性

PBL 是 **SoC 出厂时硬连线在 ROM 里的启动代码**——

- **存储介质**：Mask ROM / OTP（One-Time Programmable）
- **不可升级性**：物理上不可写（OTP）/ 物理上无法定位（Mask ROM 集成在 SoC 硅片里）
- **失效概率**：正常情况下 0%（设计时 burned-in），但有"早期良率"风险（OTP 烧录失败）

### 1.2 PBL 的 4 个最小职责

```c
// 简化版 PBL 流程（Qualcomm 实现，参考 boot_images）
void pbl_main(void) {
    // 1. 硬件自检（Power-on self-test）
    pmic_init();           // PMIC 上电时序
    sram_init();           // SRAM 自检
    
    // 2. 选择启动源（boot from）
    detect_boot_source();  // eMMC / UFS / SD
    
    // 3. 加载下一阶段镜像
    load_xbl();            // 从 boot 分区加载 XBL
    
    // 4. 校验 + 跳转
    verify_and_jump();     // 校验 + 跳到 XBL 入口
}
```

PBL 阶段**没有日志输出**（无 console 协议），调查依赖外部工具：
- **示波器**测量 PMIC 复位时序
- **JTAG** 在线抓取 SRAM 状态
- **工厂良率数据**（生产测试阶段的 PBL 失败率）

### 1.3 PBL 失败现象

| 现象 | 概率 | 调查路径 |
|---|---|---|
| 设备完全无反应（按电源键无任何 LED） | 30% | 硬件（PMIC、电池、SoC） |
| 卡"Qualcomm / MediaTek" 第一屏 logo 长时间不动 | 50% | 工厂检测（大概率 XBL 阶段） |
| 自动重启循环（PBL → XBL → 失败 → 重启） | 15% | eMMC/UFS 硬件故障 |
| 设备发烫 | 5% | 工厂级返修 |

## 2. XBL（eXtensible Boot Loader）：从 PBL 到 ABL 的"过桥"

### 2.1 XBL 的多阶段加载

高通平台的 XBL 不是单一镜像，而是一个**多阶段加载链**——

```
PBL (50ms)
  ↓
XBL Loader (300ms)        ← PBL 加载的最小引导
  ↓
XBL Config (XBL_CFG, 200ms) ← 加载 SoC 配置
  ↓
XBL Ramdump (备用, 0ms)   ← 仅在 ramdump 模式下加载
  ↓
ABL (Android Bootloader, 200ms)  ← 真正的 AOSP 启动入口
```

**为什么分这么多阶段？**
- **加载体积限制**：PBL 只能加载 256KB 镜像
- **SoC 差异**：不同 SoC 子型号（SM8550 vs SM8550+）有不同 XBL 配置
- **故障隔离**：ramdump 模式（设备卡死时抓现场）独立

### 2.2 XBL 阶段的日志抓取

XBL 阶段**没有 dmesg**，但有：
- **Sahara 协议**：Qualcomm 私有协议，通过 9008 / EDL 端口抓取
- **PBL Log**：通过 JTAG 抓取 SRAM 中的日志 buffer
- **Fastboot 阶段日志**：ABL 加载后才能看

**实操命令**：
```bash
# 通过 EDL 模式（Emergency Download）抓取 XBL log
edl.py --loader prog_firehose_ddr.elf --memory=ramdump --output=ramdump.bin
# ramdump.bin 解析后包含 XBL 阶段日志
```

## 3. ABL（Android Bootloader）：用户感知的"第一屏"

### 3.1 ABL 的核心职责

ABL 是用户能直接感知的"第一屏"——

- **引导动画**：显示 OEM logo（Pixel "G" / 三星"SAMSUNG" / 小米"mi"）
- **AVB 校验**：校验 boot.img / system.img / vendor.img 的签名
- **DTB 加载**：从 `dtbo` 分区读取设备树 overlay
- **cmdline 组装**：从 Bootloader 配置拼装 Linux kernel cmdline
- **跳转 Kernel**：调用 ARM64 启动协议移交控制权

### 3.2 ABL 的 5 大处理阶段

```c
// ABL 简化流程（基于 edk2 + QcomModulePkg）
void abl_main(void) {
    // 阶段 1: UEFI 协议初始化
    init_uefi_protocols();      // Block I/O, Simple FS, Global Variable
    
    // 阶段 2: AVB 校验
    avb_verify_boot_image();    // 校验 boot.img 签名
    avb_verify_system_image();  // 校验 system.img 签名
    
    // 阶段 3: DTB 组装
    load_main_dtb();            // 主 DTB（boot 分区）
    load_dtbo_overlay();        // 设备树 overlay（dtbo 分区）
    fdt_overlay_apply();        // 合并 DTB
    
    // 阶段 4: cmdline 组装
    build_cmdline();            // 从 ABL 配置 + 用户设置拼装 cmdline
    
    // 阶段 5: 跳转 Kernel
    jump_to_kernel(             // ARM64 启动协议
        fdt_addr,               // x0 = DTB 地址
        0,                      // x1 = 机器号（设备树模式下为 0）
        0,                      // x2 = atags（设备树模式下为 0）
        0                       // x3 = 0
    );
}
```

### 3.3 ABL 阶段的失败现象

| 失败位置 | 现象 | 调查工具 |
|---|---|---|
| UEFI 协议 init | 卡 logo（不进入下一阶段） | serial + aboot log |
| AVB boot.img 校验 | 开机动画卡 + "Orange State" | fastboot getvar current-slot |
| AVB system.img 校验 | 卡第二屏 | veritymode + last_kmsg |
| DTB overlay 失败 | 启动到 Kernel early → panic | dmesg + pstore |
| cmdline 组装失败 | 启动后 init 行为异常 | cat /proc/cmdline |
| jump_to_kernel 失败 | 卡 logo 最后阶段 | 串口 + ramoops |

## 4. ARM64 启动协议：ABL → Kernel 的交接

### 4.1 4 个寄存器的约定

ARM64 启动协议定义了 **x0-x3 寄存器**的语义：

| 寄存器 | 含义 | ABL 设置示例 |
|---|---|---|
| `x0` | DTB 物理地址 | `0x0a000000`（对齐到 2MB） |
| `x1` | 机器号 | `0`（设备树模式下忽略） |
| `x2` | atags 指针 | `0`（设备树模式下忽略） |
| `x3` | 保留 | `0` |

Kernel 端（`arch/arm64/kernel/head.S`）的接收逻辑：

```asm
// head.S · Linux 6.18
    bl  __primary_switched     // x0=FDT addr 传入
    ...
__primary_switched:
    // 1. 设置栈
    msr sp_el0, x0             // 临时栈
    // 2. 解析 DTB
    ldr x4, =__fdt_pointer
    str x0, [x4]               // 保存 DTB 地址到全局
    // 3. 跳到 start_kernel
    b   start_kernel
```

### 4.2 设备树地址对齐要求

`x0`（DTB 地址）必须满足 **2MB 对齐**（`0x200000`）——不满足会导致 `__create_page_tables` 失败。

ABL 端的对齐处理：
```c
// ABL · fdt_loader.c
uint64_t fdt_align_2mb(uint64_t addr) {
    return (addr + 0x1fffff) & ~0x1fffffULL;
}
```

## 5. 启动 Log 抓取全路径

### 5.1 5 段启动 log 各自的存放位置

| 段 | 日志内容 | 抓取方式 | 存放位置 |
|---|---|---|---|
| PBL | 极简（无 console） | JTAG / 工厂测试 | 工厂良率数据库 |
| XBL | Sahara 协议 | EDL 模式 + edl.py | ramdump.bin |
| ABL | 启动动画 + AVB | serial console | dmesg 之前 |
| Kernel early | head.S + start_kernel | dmesg | kernel ring buffer |
| Kernel late | init/main.c + initcalls | dmesg + logcat | /proc/kmsg |

### 5.2 启动期完整 log 抓取脚本（生产 SOP）

```bash
#!/bin/bash
# 启动期 boot log 抓取脚本（adb root 模式）
set -e

OUT=boot_$(date +%Y%m%d_%H%M%S)
mkdir -p $OUT

# 1. last_kmsg（上次启动的最后 kernel log）
adb shell su -c 'cat /proc/last_kmsg' > $OUT/last_kmsg.txt 2>/dev/null || \
adb shell cat /proc/last_kmsg > $OUT/last_kmsg.txt 2>/dev/null

# 2. pstore（persistent storage，启动 panic 时的 log）
adb shell su -c 'ls /sys/fs/pstore/' > $OUT/pstore_list.txt 2>/dev/null

# 3. dropbox 系统日志（启动异常）
adb shell dumpsys dropbox --print > $OUT/dropbox.txt 2>/dev/null

# 4. bootstat（启动耗时统计）
adb shell dumpsys bootstat > $OUT/bootstat.txt 2>/dev/null

# 5. 启动进度
adb shell dumpsys activity processes > $OUT/processes.txt 2>/dev/null

echo "Boot log saved to $OUT/"
ls -la $OUT/
```

### 5.3 关键 tracepoint 标记

启动过程中关键 tracepoint（用于 Perfetto / systrace 抓取）：

| Tracepoint | 触发位置 | 用途 |
|---|---|---|
| `pbl_start` | PBL 入口 | PBL 阶段耗时基线 |
| `xbl_load_complete` | XBL 加载完成 | XBL 阶段耗时 |
| `abl_avb_verify_start` | AVB 校验开始 | AVB 阶段耗时 |
| `abl_jump_kernel` | ABL 跳转 Kernel | ABL 总耗时 |
| `kernel_start_kernel` | start_kernel 入口 | Kernel 阶段开始 |
| `kernel_initcall_done` | 所有 initcall 完成 | Kernel 总耗时 |

## 6. 启动时序速查表（按 AOSP 17 + SM8550 实测）

| 阶段 | 子环节 | 耗时基线 | 🔴 高风险 | 调查命令 |
|---|---|---|---|---|
| 1 | 上电 | 100ms | - | 硬件示波器 |
| 2 | PBL | 50ms | - | JTAG |
| 3 | XBL Loader | 300ms | OEM 启动失败 | EDL ramdump |
| 4 | XBL Config | 200ms | - | EDL ramdump |
| 5 | ABL UEFI init | 50ms | - | serial log |
| 6 | ABL AVB 校验 | 200ms | OEM 改 boot | serial + dmesg |
| 7 | ABL DTB 加载 | 50ms | OEM 改 dtbo | serial + pstore |
| 8 | ABL cmdline 组装 | 10ms | OEM 私参 | /proc/cmdline |
| 9 | Kernel head.S | 20ms | - | dmesg |
| 10 | start_kernel | 100ms | OEM 改 init | dmesg |
| 11 | setup_arch | 200ms | cmdline 错 | dmesg |
| 12 | mm_init | 300ms | 内存探测失败 | dmesg + pstore |
| 13 | do_basic_setup | 800ms | **🔴 驱动 initcall 失败** | dmesg + ftrace |
| 14 | do_initcalls | 200ms | OEM 自定义 init | initcall_debug |
| 15 | rest_init | 50ms | - | dmesg |
| 16 | init 进程启动 | 500ms | init.rc 错 | logcat |

**总耗时：~3.1 秒**（AOSP 17 + SM8550 默认配置）

## 7. 实战案例：Pixel 7 卡开机 logo 调查

### 7.1 现场

用户报：Pixel 7 按电源键后卡在 "G" logo 不动，**20 秒后自动重启**。

### 7.2 调查步骤

```bash
# 1. 确认进入哪个阶段
adb shell dmesg | head -50
# 看到 "Booting Linux on physical CPU 0x0" → 已进入 Kernel
# 看到 "Run /init as init process" → 已到 init 阶段
# 看到 "PM: Resume from suspend" → 卡在 PBL/XBL/ABL

# 2. 抓 last_kmsg
adb shell cat /proc/last_kmsg > last_kmsg.txt
# 看到 "Bootloop: reboot reason: bootloader" → 卡 XBL/ABL 阶段
# 看到 "Failed to mount /system" → 卡在 init 阶段
```

### 7.3 根因定位

last_kmsg 显示：
```
[    2.123456] avb_slot_verify: Slot _a is invalid
[    2.123478] avb_slot_verify: Slot _b is invalid
[    2.123500] AVB verification failed
[    2.123521] reboot: Restarting system
```

**根因**：A/B 分区都校验失败，ABL 启动 abort → 重启。

### 7.4 修复路径

```bash
# 1. 进 fastboot 模式
adb reboot bootloader

# 2. 手动切槽位
fastboot --set-active=a
fastboot --set-active=b

# 3. 重新刷 system
fastboot flash system system.img

# 4. 验证
fastboot boot boot.img
```

## 8. Takeaway

- **4 段 7 阶段**：PBL → XBL → ABL → Kernel，每段失败现象不同
- **x0-x3 寄存器协议**：x0=DTB 地址（2MB 对齐），x1=机器号，x2=atags，x3=0
- **5 段 log 抓取路径**：JTAG（PBL）→ EDL（XBL）→ serial（ABL）→ dmesg（Kernel）
- **Pixel 8 SM8550 总耗时 ~3.1s**：OEM 启动失败的"高风险段"是阶段 13 do_basic_setup
- **AVB 校验失败 → 反复重启**：用 fastboot 切槽位 + 重刷 system
- **initcall_debug 开关**：`CONFIG_INITCALL_DEBUG=y` 启动时打印每个 initcall 耗时
