# 6.4 早期初始化：setup_arch / sched_init / page_alloc

## 一句话开场

**Kernel 早期初始化的 3 大函数，决定了"硬件探测成功/失败""内存可用/不可用""进程能否 fork"**——任何一个失败都会导致 Kernel 早期 panic。

按 AOSP 17 + Linux 6.18 + ARM64 架构，3 大函数耗时基线：

| 函数 | 耗时 | 失败现象 | 🔴 风险 |
|---|---|---|---|
| `setup_arch` | 200ms | "卡 Boot" 不进入下一步 | ★★★ |
| `sched_init` | 5ms | 调度器 hang | ★ |
| `page_alloc_init` | 100ms | "Bad page state" panic | ★★★ |

## 1. setup_arch：架构 + cmdline + DTB + 内存探测

### 1.1 setup_arch 的 30 个关键调用（ARM64）

```c
// arch/arm64/kernel/setup.c
void __init setup_arch(char **cmdline_p)
{
    // ===== 阶段 1: 早期内存管理（~50ms）=====
    init_mem_migration();                  // 内存迁移特性
    memblock_init();                       // memblock 初始化
    
    // ===== 阶段 2: CPU 能力探测（~10ms）=====
    smp_init_cpus();                       // SMP CPU 数
    cpu_read_boot_cpu_ops();               // CPU ops
    setup_processor();                     // CPU 类型
    cpu_feature_matches_arm64();           // CPU feature
    
    // ===== 阶段 3: early 阶段参数解析（~5ms）=====
    parse_early_param();                   // early cmdline 解析
    //  ├ early_mem
    //  ├ earlyprintk
    //  └ earlycon
    
    // ===== 阶段 4: 设备树解析（~30ms）=====
    setup_machine_fdt();                   // DTB 机器匹配
    //  ├ of_flat_dt_match_machine()        // 设备树 machine_desc 匹配
    //  ├ of_scan_flat_dt()                 // 扫描 DTB
    //  └ unflatten_device_tree()           // DTB 展开为 device_node 树
    
    // ===== 阶段 5: 内存布局（~50ms）=====
    arm64_memblock_init();                 // memblock 内存初始化
    //  ├ memblock_add()
    //  ├ memblock_reserve()
    //  └ early_init_fdt_scan_reserved_mem()
    
    // ===== 阶段 6: 页表（~30ms）=====
    paging_init();                         // 建立完整页表
    //  ├ map_kernel()
    //  ├ map_mem()
    //  └ create_mapping_noalloc()
    
    // ===== 阶段 7: 平台特定（~30ms）=====
    init_mmio();                           // MMIO 探测
    request_standard_resources();          // 资源探测
    cpu_uninstall_idmap();                 // 卸载 idmap
    
    // ===== 阶段 8: cmdline 解析（~5ms）=====
    parse_cmdline();                       // 解析 cmdline
    //  ├ command_line = boot_command_line
    //  └ strlcpy(cmdline, boot_command_line, COMMAND_LINE_SIZE)
    
    // ===== 阶段 9: 平台设备（~10ms）=====
    of_platform_populate();                // 平台设备树展开
    
    // ===== 阶段 10: 中断与 CPU（~10ms）=====
    init_cpu_topology();                   // CPU 拓扑
    smp_prepare_cpus();                    // SMP 准备
    setup_per_cpu_areas();                 // per-CPU 区域
    
    // ===== 阶段 11: ARCH 资源（~5ms）=====
    reserve_bios_regions();                // BIOS 区域保留
    early_trap_init();                     // 早期异常处理
}
```

### 1.2 30 个函数的"高风险 5 个"

| # | 函数 | 失败原因 | 失败现象 |
|---|---|---|---|
| 1 | `parse_early_param` | cmdline malformed | 卡"setup_arch: command line" |
| 2 | `setup_machine_fdt` | DTB 损坏 / machine_desc 不匹配 | 卡"setup_arch" → reboot |
| 3 | `arm64_memblock_init` | 内存探测失败（memblock_add 失败） | "Bad page state" panic |
| 4 | `paging_init` | 页表建立失败 | 启动期 Kernel panic |
| 5 | `of_platform_populate` | 设备树节点指向不存在的设备 | "of: populate failed" warn |

## 2. sched_init：调度器 + idle 进程创建

### 2.1 sched_init 的 5 步

```c
// kernel/sched/core.c
void __init sched_init(void)
{
    // 1. 初始化 waitqueue
    init_waitqueues();
    
    // 2. 初始化每个 CPU 的 runqueue
    for_each_possible_cpu(cpu) {
        struct rq *rq = &per_cpu(runqueues, cpu);
        rq->cpu = cpu;
        rq->idle = NULL;  // 还没创建 idle
        raw_spin_lock_init(&rq->lock);
        rq->nr_running = 0;
    }
    
    // 3. 注册公平调度类（CFS）
    for_each_class(class) {
        if (class->init)
            class->init(&init_task);  // 0 号进程绑定调度类
    }
    
    // 4. 创建 idle 进程（0 号进程）
    for_each_possible_cpu(cpu) {
        struct task_struct *idle = &init_task;  // 0 号进程
        // 设置 idle 进程的 rq
        set_task_rq(idle, cpu);
        init_idle(idle, cpu);  // 关键
    }
    
    // 5. 设置初始调度实体
    set_load_weight(&init_task, NICE_0_LOAD);
}
```

### 2.2 0 号进程（init_task）的关键性

`init_task` 是 Kernel 启动的**第 0 个进程**（PID 0），也是后续所有进程的祖先：

```c
// init/init_task.c
struct task_struct init_task = {
    .pid = 0,
    .comm = "swapper/0",          // 0 号进程名
    .state = TASK_RUNNING,         // 一直 running
    .flags = PF_KTHREAD,
    .cpus_ptr = &init_task_cpu,    // 0 号 CPU
    .sched_class = &idle_sched_class,  // idle 调度类
    .prio = MAX_PRIO,              // 最低优先级
    .static_prio = MAX_PRIO,
    .mm = &init_mm,                // 0 号进程的内存描述符
    .files = &init_files,          // 0 号进程的文件描述符
};
```

**关键点**：
- 0 号进程**不会退出**（永远 idle 状态）
- 所有进程（init / kthreadd / user process）都是 0 号进程的**子进程或子孙**
- `init_task` 的失败会导致整个 Kernel 调度器 hang

## 3. page_alloc_init：内存分配器

### 3.1 page_alloc_init 的 5 步

```c
// mm/page_alloc.c
void __init page_alloc_init(void)
{
    // 1. 初始化 zone
    build_all_zonelists(NULL);          // 建立所有 zone 列表
    //  ├ NODE_DATA(nid)->node_zonelists[ZONE_TYPE] = ...
    //  └ for each zone: setup its per-CPU pageset
    
    // 2. 初始化 per-CPU pageset
    for_each_possible_cpu(cpu) {
        struct per_cpu_pageset *p = &per_cpu(boot_pageset, cpu);
        setup_pageset(p, 0);
    }
    
    // 3. 初始化 vmstat
    init_mm_internals();
    
    // 4. 启动 page allocator 工作线程
    kswapd_run();                       // 启动内存回收线程
    
    // 5. 启用 page allocation
    page_allocator_ready = 1;           // 标记 page_allocator 就绪
}
```

### 3.2 5 个常见 page_alloc 失败场景

| # | 场景 | 现象 | 调查 |
|---|---|---|---|
| 1 | 内存节点探测失败 | "No zones found" panic | dmesg + memblock info |
| 2 | zone 大小为 0 | "Empty zone" panic | dmesg + cat /proc/zoneinfo |
| 3 | per-CPU pageset 失败 | "Per-CPU pageset init failed" | dmesg + maxcpus |
| 4 | kswapd 启动失败 | "kswapd: not started" | dmesg + ps |
| 5 | 高阶 page 分配失败 | "page allocation failure" | dmesg + cat /proc/buddyinfo |

## 4. memblock 早期内存管理

### 4.1 memblock vs page_alloc

Kernel 早期用 **memblock**（boot-time memory allocator），后期用 **page_alloc**（runtime page allocator）：

| 维度 | memblock | page_alloc |
|---|---|---|
| 启动阶段 | head.S → setup_arch | page_alloc_init 后 |
| 分配粒度 | 字节（任意大小） | 4KB page |
| 内存管理 | 简单链表 | buddy system + LRU |
| 性能 | 快 | 相对慢 |
| 用途 | 早期页表、DTB、内核镜像 | runtime 内存分配 |

### 4.2 memblock 的 3 个核心操作

```c
// mm/memblock.c
// 1. 登记内存区域
memblock_add(base, size);              // 如 memblock_add(0x40000000, 0x80000000);

// 2. 预留内存区域（不可分配）
memblock_reserve(base, size);           // 如 memblock_reserve(__pa(_text), _end - _text);

// 3. 分配内存
memblock_alloc(size, align);            // 分配 size 字节，对齐到 align
// 例：memblock_alloc(PAGE_SIZE * 16, PAGE_SIZE)  // 分配 16 个 page，4KB 对齐
```

### 4.3 memblock 转 page_alloc 的 3 步交接

```c
// 1. memblock 冻结
memblock_free_all();                   // 释放所有已分配但未用的内存
memblock = false;                       // 标记 memblock 阶段结束

// 2. page_alloc 接管
init_unavailable_mem();                // 标记不可用内存
free_low_memory_regions();             // 释放低端内存到 page_alloc

// 3. slab 分配器
kmem_cache_init();                     // 初始化 slab
```

## 5. 启动期 page fault 处理

### 5.1 Kernel 启动期的 3 类 page fault

| 类型 | 触发位置 | 处理 |
|---|---|---|
| 1. 已知地址 | head.S / setup_arch 的页表 | 正常处理 |
| 2. 未知地址 | 调试 printk 越界 | Kernel oops |
| 3. 物理地址未映射 | 设备树扫描 | 重新建立映射 |

### 5.2 early_pgtable 的 4 步建立

```asm
// arch/arm64/kernel/head.S
__create_page_tables:
    // 1. 清空页表
    adrp    x0, idmap_pg_dir
    mov     x1, #ZERO
    mov     x2, #PAGE_SIZE
    bl      __pi_memset
    
    // 2. identity map kernel
    adrp    x1, _text
    mov     x2, #IDMAP_SIZE
    bl      create_idmap
    
    // 3. fixup
    adrp    x0, idmap_pg_dir
    ldr     x1, [x0, #IDMAP_OFFSET]
    ...
    
    // 4. 跳到 __primary_switched
    b       __primary_switched
```


## 7. Takeaway

- **3 大函数**：setup_arch（200ms · 架构 + DTB） / sched_init（5ms · 调度） / page_alloc_init（100ms · 页分配）
- **memblock 是过渡方案**：head.S → page_alloc_init 之前都用 memblock，page_alloc_init 后切到 page_alloc
- **0 号进程 init_task**：永远 idle，是所有进程的祖先
- **🔴 高风险**：setup_arch 的 cmdline 解析 + DTB 匹配、page_alloc_init 的 zone 初始化
- **5 个 debug 开关**：initcall_debug + printk.time + earlyprintk + CONFIG_DEBUG_PAGEALLOC + panic=N
