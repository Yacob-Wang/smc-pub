# 6.1 Bootloader 类型：LK / ABL / U-Boot

## 一句话开场

**Bootloader 决定 Android 设备从硬件上电到 Kernel 接管控制权的整个启动链路**——它是 boot loop 调查的"第一公里"，所有"卡第一屏""开机黑屏""无法进入恢复模式"问题都得从这里开始查。

Android 设备里跑的 Bootloader 体系，按历史演进和市场分布主要有三种：

- **LK（Little Kernel）**：高通 2010-2016 年主力
- **ABL（Android Bootloader）**：基于 UEFI edk2，**AOSP 17 默认**，Pixel / 三星 / OPPO / vivo 主流
- **U-Boot**：MTK / 三星 Exynos / 瑞芯微 / 全志等嵌入式主导

这三种不是简单的"前后替代"关系——它们在今天的 Android 设备里**同时存在**，不同阶段承担不同角色。

## 1. LK（Little Kernel）：小而美的 ARM-first Bootloader

LK 是 2008 年由 Travis Geiselbrecht 开源的极简内核，专为嵌入式 Bootloader 场景设计。高通在 2010 年代将其深度定制为手机平台主力 Bootloader（搭配 PBL 1+1 启动）。

### LK 的 5 个关键特性

1. **极小体积**：~200 KB 二进制（对比 ABL 1.5MB+），适合固化在 eMMC 引导区
2. **单线程 + 事件循环**：没有真正的多线程，靠 `event_t` 异步回调
3. **ARM-first**：x86 移植不完整，主要服务 ARM 嵌入式
4. **QCom 深度定制**：集成 `app/` 子系统（fastboot、aboot、recovery 模式）
5. **强耦合 QCom 硬件抽象**：OEM 修改需要 vendor 分支

### LK 的代码组织

```
bootable/bootloader/lk/
├── arch/        # ARM / x86 平台相关
├── include/     # LK 头文件
├── kernel/      # 线程/调度/中断
├── platform/    # 平台相关 (msm8953, sm8550 等)
├── app/         # 应用层 (aboot, fastboot, recovery)
├── dev/         # 设备驱动 (mmc, display, watchdog)
├── lib/         # 标准库 (printf, ctype, libc)
├── target/      # 目标板配置
└── tools/       # mkheader, scripts 等
```

AOSP 17 里 LK 仍然保留在 `bootable/bootloader/lk/`，但**不再是默认 Bootloader**——只作为"非 ABL 平台"（如部分 MTK）的回退方案。

## 2. ABL（Android Bootloader）：AOSP 17 的事实标准

ABL 是 Google 2018 年基于 **UEFI edk2** 实现的标准化 Bootloader，目标是为所有 Android 设备提供统一的启动接口。**AOSP 17（2025）将 ABL 设为默认**——Pixel 7/8、三星 Galaxy S24/S25、OPPO Find X8、vivo X100 等主流机型都用 ABL。

### ABL 的 5 大组件

1. **UEFI 协议栈**：基于 edk2，提供标准化的启动服务（Block I/O / Simple File System / Global Variable）
2. **ABL 命令处理**：解析 fastboot / recovery / bootonce 等指令
3. **AVB 校验**：Android Verified Boot 2.0——校验 vbmeta、boot、system、vendor 分区签名
4. **设备树加载**：从 `boot` 或 `dtbo` 分区读取 DTB，覆盖主 DTB
5. **Linux 启动协议**：通过 ARM64 启动协议（x0/x1/x2/x3 寄存器约定）移交控制权

### ABL 在 AOSP 17 的位置

```
bootable/bootloader/edk2/
├── QcomModulePkg/    # 高通模块化协议
├── ArmPkg/           # ARM 通用
├── OemActivationPkg/ # OEM 定制
├── AppPkg/           # UEFI Shell
├── edksetup.sh       # edk2 环境配置
└── README.md         # AOSP 17 完整 ABL 文档
```

ABL 的优势在于**标准化**——Google 维护的 edk2 兼容层 + AOSP 适配层，OEM 只需修改"自己 SoC 的协议实现"，其他全部复用上游。

## 3. U-Boot：嵌入式市场的事实标准

U-Boot（Das U-Boot）1999 年由 Wolfgang Denk 开源，是嵌入式 Linux 设备的"老牌"Bootloader。在 Android 设备里，U-Boot 主要服务于：

- **MTK（联发科）**：天玑 9200/9300 等中高端平台
- **三星 Exynos**：Galaxy S22 及之前部分机型
- **瑞芯微 / 全志 / 晶晨（Amlogic）**：Android 盒子、车机、电视棒

### U-Boot 的 5 个 Android 场景特性

1. **GPL-2.0**：必须开源，OEM 改不了不公开
2. **多平台**：ARM / x86 / RISC-V / PowerPC 都支持
3. **设备树（DTB）原生支持**：Bootloader → Kernel 的设备树传递是天然设计
4. **fastboot 协议适配**：通过 `fastboot` 命令支持
5. **SPL / TPL 多阶段加载**：System Programmer + Trusted Firmware 双层

### MTK 平台的特殊链路

MTK 设备的 Bootloader 链路比较独特：
- **PBL**（固化） → **BootROM** → **Preloader** → **LK / U-Boot** → **Kernel**

其中 Preloader 是 MTK 私有，启动时间 ~50-200ms，在 AOSP / 内核 logcat 之前执行——boot loop 调查时**容易漏掉这一段**。

## 4. 同一颗 SoC 上的 Bootloader 角色分工

不管是 Pixel / 小米 / OPPO，**同一颗 SoC 上有多个 Bootloader 角色分工**——理解这一点对 boot loop 调查至关重要。

以 Qualcomm SM8550（Pixel 8）为例，启动链上其实是 4 段：

| 阶段 | 名称 | 位置 | 角色 | 失败现象 |
|---|---|---|---|---|
| 1 | **PBL**（Primary Boot Loader） | SoC ROM 固化 | 引导最小 XBL | 设备无任何反应（砖） |
| 2 | **XBL**（eXtensible Boot Loader） | 引导分区 | 加载 + 校验 ABL | 卡在"Qualcomm"logo |
| 3 | **ABL** | 引导分区 | 加载 + 校验 Kernel | 卡开机动画第一屏 |
| 4 | **Kernel** | boot 分区 | 接管控制权 | 卡白屏 / 反复重启 |

**关键点**：每个阶段的失败现象都不同，调查工具也不同：
- PBL 失败 → JTAG / 工厂返修
- XBL 失败 → 9008 模式强刷
- ABL 失败 → fastboot / EDL 模式
- Kernel 失败 → last_kmsg / dmesg

## 5. 三大 Bootloader 横向对比

| 维度 | LK | ABL | U-Boot |
|---|---|---|---|
| **代码库** | `bootable/bootloader/lk` | `bootable/bootloader/edk2` | `u-boot` (u-boot 仓库) |
| **体积** | ~200KB | ~1.5MB+ | ~500KB |
| **标准** | 私有过渡 | UEFI edk2 | GPL-2.0 |
| **AVB 集成** | 需手写 | edk2 原生 | 需手写 |
| **DTB 传递** | 平台代码 | 协议 | 原生 |
| **OEM 改动量** | 大量平台代码 | 协议适配即可 | 板级配置 |
| **维护方** | 高通历史 | Google + 高通 | DENX + 社区 |
| **AOSP 17 默认** | ❌ | ✅ | ❌ |
| **boot loop 调查工具** | serial + aboot log | serial + dmesg + pstore | serial + uboot log |

## 6. 主流机型 Bootloader 矩阵

| 厂商 | 主力 SoC | Bootloader 体系 | 备注 |
|---|---|---|---|
| **Pixel 7/8** | Tensor G2/G3 (Samsung 4nm) | PBL → ABL (edk2) | AOSP 17 默认 |
| **三星 Galaxy S24/S25** | Snapdragon 8 Gen 3 | PBL → XBL → ABL | 锁定 bootloader |
| **小米 14** | Snapdragon 8 Gen 3 | PBL → ABL | 解锁需社区 |
| **OPPO Find X8** | Dimensity 9400 | Preloader → U-Boot → Kernel | MTK 链路 |
| **vivo X100** | Dimensity 9300 | Preloader → U-Boot | MTK 链路 |
| **华为 Mate 60** | 麒麟 9000S | PBL → ABL (edk2 私有 fork) | 自研 |
| **一加 12** | Snapdragon 8 Gen 3 | PBL → ABL | 社区活跃 |

## 7. 稳定性焦点

### 7.1 启动失败时的 fallback 链

```
正常启动: PBL → ABL → Kernel
↓
ABL 校验失败 → fastboot mode (user 可见) / EDL mode (工程)
↓
Kernel panic → 引导回 ABL → 显示 boot failure menu
↓
5 次 / 5min boot loop → 工厂重置
```

### 7.2 AVB 校验失败 → boot loop 的根因

- **OEM 修改 boot.img**：校验失败 → 卡开机动画
- **dtbo 不匹配**：kernel 启动后立即 panic
- **vbmeta 被破坏**：进入"Orange State"（屏幕底部出现"unlocked"警告）
- **user 版本 vs userdebug 版本**：交叉刷入会触发 verified boot fail

### 7.3 Bootloader 升级失败 → 变砖的恢复路径

- **PBL 阶段变砖**：唯一恢复路径是 JTAG（工厂级）
- **XBL 阶段变砖**：9008 / Sahara 协议强刷
- **ABL 阶段变砖**：fastboot / EDL 模式救回
- **应用层变砖**（Kernel 之后）：recovery 模式救回

## 8. Takeaway

- **3 大 Bootloader 体系**：LK（QCom 历史）/ ABL（edk2，AOSP 17 默认）/ U-Boot（MTK + 嵌入式）
- **同一颗 SoC 上有多段 Bootloader**：PBL → XBL/SBL → ABL → Kernel，每段失败现象不同
- **boot loop 调查必须先定位失败段**：PBL（砖）/ XBL（卡 logo）/ ABL（卡动画）/ Kernel（卡白屏）
- **AVB 校验失败是常见根因**：OEM 修改 boot.img / dtbo 不匹配 / vbmeta 破坏
- **Pixel 7/8、三星、OPPO、vivo 都已切 ABL**；MTK 系仍以 U-Boot 为主
