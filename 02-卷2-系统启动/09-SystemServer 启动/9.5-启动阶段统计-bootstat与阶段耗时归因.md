# 9.5 启动阶段统计:bootstat 与阶段耗时归因

## 一句话开场

bootstat 是 Android 的"启动埋点系统"——把启动期所有关键时间点(`ro.boottime.init` / `ro.boottime.zygote` / `ro.boottime.system_server` / `ro.boottime.ams_ready` / `ro.boottime.boot_completed`)落盘到 `/data/bootstat/` 目录,让线上"系统启动慢"可以归因到具体服务。**bootstat 慢 1 段 = 整机慢 1 段**,但 bootstat 误读会误导整个调查方向。

## 1. 核心子问题

1. bootstat 是什么?它怎么埋点?落盘到哪个文件?
2. `ro.boottime.*` 属性有哪些?每个属性的具体含义?
3. bootstat 怎么读?`dumpsys bootstat` 输出怎么看?
4. 怎么把"系统启动慢 5 秒"归因到具体服务?
5. bootstat 与 Perfetto boot trace 的关系?两者怎么配合?
6. bootstat 误读的常见坑?什么会让归因错?
7. AOSP 17 vs AOSP 14 的 bootstat 差异?

## 2. 详细展开

### 2.1 bootstat 是什么 + 怎么落盘

**bootstat 是一个 native 进程 + Java API 的混合系统**:
- **native 端**:`system/core/bootstat/bootstat.cpp` 提供 C++ API `record_boot_event()` + `get_boot_events()`
- **Java 端**:`frameworks/base/services/core/java/com/android/server/SystemBootProgress.kt` 包装 native API
- **落盘位置**:`/data/bootstat/last_boot.txt`(每次启动重写)

**bootstat 的核心数据结构**:
```
{
  "ro.boottime.init": 1738234567.890,
  "ro.boottime.zygote": 1738234568.500,
  "ro.boottime.system_server": 1738234569.200,
  "ro.boottime.ams_ready": 1738234573.500,
  "ro.boottime.first_frame_drawn": 1738234576.000,
  "ro.boottime.boot_completed": 1738234578.000,
  "ro.boottime.pms": 1738234571.000,           // PMS 第一次扫描完成
  "ro.boottime.wms": 1738234574.500,           // WMS 启动完成
  "ro.boottime.ims": 1738234575.000,           // IMS 启动完成
  "ro.boottime.zygote64": 1738234568.500,      // 64-bit zygote
  "ro.boottime.servicemanager": 1738234567.700  // servicemanager
}
```

**关键时间点的写入者**:

| 时间点 | 写入者 | 时机 |
|---|---|---|
| `ro.boottime.init` | init 进程 | init 启动时 |
| `ro.boottime.servicemanager` | init 进程 | servicemanager 启动时 |
| `ro.boottime.zygote` / `ro.boottime.zygote64` | init 进程 | zygote 启动时 |
| `ro.boottime.system_server` | SystemServer.run() 入口 | SystemServer 启动时 |
| `ro.boottime.pms` | PackageManagerService.fullInit() 末尾 | PMS 完整初始化完成 |
| `ro.boottime.ams_ready` | ActivityManagerService.systemReady() 触发 | AMS 全功能 |
| `ro.boottime.wms` | WindowManagerService init 末尾 | WMS 启动完成 |
| `ro.boottime.ims` | InputManagerService init 末尾 | IMS 启动完成 |
| `ro.boottime.first_frame_drawn` | WindowManager 显示第一帧 | 第一帧上屏 |
| `ro.boottime.boot_completed` | ActivityManagerService 触发 | 整机 boot 完成 |

> **🟡 待联网确认**:AOSP 17 实际写入点需对照 cs.android.com 实际代码。

### 2.2 关键时间点的归因意义

**9.1 §2.6 列过的关键时间点,本节解释它们在线上归因的用法**:

| 时间点 | 归因方向 | 异常典型原因 |
|---|---|---|
| `ro.boottime.init` | 整机启动起点 | init 启动慢 → 整机问题,转 11 章 |
| `ro.boottime.zygote` | Zygote 启动时机 | Zygote 启动慢(8.x 已讲) |
| `ro.boottime.system_server` | SystemServer fork 时机 | 8.1 §2.6 详述 |
| `ro.boottime.pms` | PMS 全功能时机 | PMS 第一次扫描阻塞(9.1 案例 1) |
| `ro.boottime.ams_ready` | AMS 全功能时机 | AMS 启动期阻塞(9.3 §2.6) |
| `ro.boottime.wms` | WMS 启动完成 | WMS 加载 policy 资源慢(9.2 案例 1) |
| `ro.boottime.ims` | IMS 启动完成 | IMS native 死锁(9.3 案例 2) |
| `ro.boottime.first_frame_drawn` | 第一帧上屏 | WMS 启动阻塞 / Launcher 启动慢 |
| `ro.boottime.boot_completed` | 整机 boot 完成 | Other 阶段服务启动慢 / 第三方 App 启动慢 |

**关键差值**:
- `ro.boottime.boot_completed - ro.boottime.init` = 整机 boot 总耗时
- `ro.boottime.ams_ready - ro.boottime.system_server` = SystemServer.run() 总耗时(9.1 已用)
- `ro.boottime.pms - ro.boottime.system_server` = SystemServer.run() 走到 PMS 全功能
- `ro.boottime.first_frame_drawn - ro.boottime.ams_ready` = AMS 全功能到第一帧上屏

### 2.3 bootstat 怎么读

**最常用命令**:

```bash
# 1. dumpsys bootstat
adb shell dumpsys bootstat
# 输出类似:
# Boot event stats:
# 1738234567.890 init
# 1738234567.700 servicemanager
# 1738234568.500 zygote
# 1738234569.200 system_server
# 1738234571.000 pms
# 1738234573.500 ams_ready
# 1738234574.500 wms
# 1738234575.000 ims
# 1738234576.000 first_frame_drawn
# 1738234578.000 boot_completed

# 2. 单独查某个时间点
adb shell getprop ro.boottime.ams_ready

# 3. 看上次启动的 bootstat 文件
adb shell cat /data/bootstat/last_boot.txt

# 4. 算差值(在 host 端用 awk 算)
adb shell dumpsys bootstat | grep -E "ams_ready|system_server|init" | awk '...'
```

**dumpsys bootstat 输出解读**:
- 时间戳是 Unix epoch(秒)
- 顺序按时间点
- 关键差值(两个时间点相减)代表那段耗时的近似

### 2.4 阶段耗时归因实战:从"系统启动慢 5 秒"到具体服务

**实战场景**:用户报告"手机开机慢 5 秒",怎么定位到具体服务?

**步骤 1:看整机 boot 总耗时**
```bash
$ adb shell dumpsys bootstat | tail -5
# 1738234567.890 init
# 1738234578.000 boot_completed
# 差值:10.1 秒(假设基线 8 秒,慢 2 秒)
```

**步骤 2:看每个关键时间点的差值**
```bash
$ adb shell getprop ro.boottime.init
1738234567.890
$ adb shell getprop ro.boottime.zygote
1738234568.500
$ adb shell getprop ro.boottime.system_server
1738234569.200
$ adb shell getprop ro.boottime.pms
1738234571.000    ← PMS 全功能时
$ adb shell getprop ro.boottime.ams_ready
1738234573.500    ← AMS 全功能时
$ adb shell getprop ro.boottime.boot_completed
1738234578.000

# 差值(秒):
# init → zygote: 0.61 s(基线 0.5 s,正常)
# zygote → system_server: 0.70 s(基线 0.5 s,正常)
# system_server → pms: 1.80 s(基线 1.0 s,慢 0.8 s) ← 异常!
# pms → ams_ready: 2.50 s(基线 2.0 s,慢 0.5 s) ← 异常!
# ams_ready → boot_completed: 4.50 s(基线 3.0 s,慢 1.5 s) ← 异常!
```

**步骤 3:定位"system_server → pms"慢 0.8 秒**
- 这段时间是 SystemServer.run() 走到 PMS 完整初始化
- 包括 Bootstrap 阶段(200-500ms)+ Core 阶段(500-1500ms)
- **慢在 Core 阶段** = 慢在 PMS 第一次扫描
- 进一步看 PMS 日志确认

**步骤 4:定位"ams_ready → boot_completed"慢 1.5 秒**
- 这段时间是 AMS 全功能到整机 boot 完成
- 包括 WMS 启动 / IMS 启动 / launcher 启动 / 第三方 receiver 启动
- **慢在 WMS / launcher / 第三方 receiver**
- 进一步看 WMS 日志 + launcher 日志

**结论**:本次"慢 2 秒"= PMS 第一次扫描慢 0.8s + Other 阶段慢 1.2s。修复方向:① 减少 /data/app apk 数量 ② 压缩 framework-res 资源。

### 2.5 bootstat 与 Perfetto boot trace 的关系

**bootstat vs Perfetto**:

| 维度 | bootstat | Perfetto boot trace |
|---|---|---|
| **粒度** | 粗(10+ 个时间点) | 细(每条 binder / 每个 CPU 调度) |
| **存储成本** | 极低(几百字节) | 高(几 MB-几十 MB) |
| **可读性** | 文本,易读 | 二进制,需要 Perfetto UI 解读 |
| **适用场景** | 线上远端 / 量产数据 | lab 深度调查 / 单设备 |
| **数据源** | system_property | atrace + ftrace + binder |

**典型使用**:
- **bootstat 用于线上归因**——用户报告"手机慢"时,adb 一行命令拿数据
- **Perfetto 用于 lab 复现**——研发拿真机抓 trace,定位到具体方法调用

**两者配合**:
- 线上用 bootstat 定位"慢在哪一段"
- 拿到差值后,告诉研发"system_server → pms 慢 0.8s"
- 研发用 Perfetto 抓 trace,定位到具体方法(如 `scanDirTracedLI` 卡 0.8s)
- 研发改源码或配置后,bootstat 验证修复效果

### 2.6 bootstat 误读常见坑

**实战 4 个常见 bootstat 误读**——

**坑 1:把 `ro.boottime.*` 当 Unix 时间戳直接做差**
- `ro.boottime.init` 是 Unix epoch(秒),不是单调时间
- 如果设备时区 / NTP 校时,**boottime.* 的相对差值仍然有效**
- **绝对值不可靠**(校时后会被覆盖)

**坑 2:bootstat 数据被覆盖就丢**
- `ro.boottime.*` 是单值属性,新启动会覆盖旧值
- 反复崩的设备,只能看到**最后一次**启动的数据
- 想要历史数据,看 `/data/bootstat/last_boot.txt`

**坑 3:`ro.boottime.pms` 等中间时间点不是所有设备都有**
- AOSP 17 在 SystemServer.run() 里写入,但 OEM 可能**没有**正确写入
- 如果 `getprop ro.boottime.pms` 返回空,说明设备没埋这个点
- 解决:看 logcat 里 SystemServer 的 Phase 日志

**坑 4:`ro.boottime.ams_ready` 和 `ro.boottime.first_frame_drawn` 的差值不一定是 WMS 启动耗时**
- `ams_ready` 是 AMS 全功能,`first_frame_drawn` 是第一帧上屏
- 中间还有 launcher 启动、PowerMS 启动、NotificationService 等
- **所以这个差值是"Other 阶段末尾"耗时,不是 WMS 启动耗时**
- 准确 WMS 启动耗时看 `ro.boottime.wms`

### 2.7 AOSP 17 vs AOSP 14 的 bootstat 差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| 时间点数量 | 8-10 | 12-15 | +4-5 |
| 落盘文件 | `last_boot.txt` | `last_boot.txt` + `last_boot_proto.pb` | + proto 格式 |
| 读取 API | dumpsys bootstat | dumpsys bootstat + proto | + proto |
| 写入点 | SystemServer.run() | SystemServer.run() + SystemBootProgress.kt | + Kotlin 化 |
| 启动统计 | 启动期时间 | 启动期 + 启动后 1 分钟内关键事件 | + 启动后事件 |

### 3.3 bootstat 误读规避

| 误读类型 | 正确做法 |
|---|---|
| 用 `ro.boottime.*` 绝对值做时间戳 | 只用**差值**,不用绝对值 |
| bootstat 数据被覆盖 | 看 `/data/bootstat/last_boot.txt` 取历史 |
| 某个时间点没数据 | 用 logcat 里 SystemServer 的 Phase 日志补全 |
| `ams_ready → first_frame_drawn` 误认为是 WMS 启动耗时 | 看 `ro.boottime.wms`,那个才是 WMS 启动时间 |

## 4. 实战案例

### 案例 1:某设备"系统启动慢 5 秒",bootstat 归因到 PMS 第一次扫描阻塞(典型模式)

**环境**:
- Android 版本:AOSP 14(API 34)→ AOSP 17(API 37)OTA
- 设备:Pixel 7(8GB RAM)
- 复现步骤:OTA 升级后第一次开机,boot_completed 25 秒(基线 12 秒)

**现象**:
```bash
$ for prop in init zygote system_server pms ams_ready wms boot_completed; do
    echo "$prop: $(adb shell getprop ro.boottime.$prop)"
done
init: 1738234567.890
zygote: 1738234568.500
system_server: 1738234569.200
pms: 1738234573.000    ← 4.6s 后 PMS 全功能
ams_ready: 1738234573.500
wms: 1738234576.000
boot_completed: 1738234585.000    ← 整机 17.1s
```

**关键观察**:`system_server → pms` 差值 3.8s,远超基线 1.0s。

**分析思路**:
1. 关键差值 `system_server → pms = 3.8s` → 慢在 Core 阶段 PMS 第一次扫描
2. `pms → ams_ready = 0.5s` → AMS 启动正常
3. `ams_ready → wms = 2.5s` → WMS 启动略慢(基线 1.0s)
4. `wms → boot_completed = 9.0s` → Other 阶段末尾慢(第三方 receiver / launcher)
5. **主要瓶颈**:Core 阶段 PMS 第一次扫描(3.8s),次要:Other 阶段末尾(9.0s,比基线慢 6s)

**根因**:同 9.1 案例 1——PMS 第一次扫描 /data/app 时,AOSP 17 加了 rollback 校验,360+ apk × 10ms = 3.6s。

**修复**:同 9.1 案例 1。把 rollback 校验挪到 PMS 其他阶段。

**修复原理**:bootstat 归因让"慢 5 秒"具体到"Core 阶段 PMS 扫描慢 3.8s",研发改源码时直接定位到 `PackageManagerService.scanDirTracedLI()`。

### 案例 2:某设备 bootstat 误读"ams_ready → first_frame_drawn 慢 3 秒"误判为 WMS 慢(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:用户装了一个新 launcher App(代号 NewLauncher)后,开机"慢 3 秒"

**现象**:
```bash
$ for prop in ams_ready first_frame_drawn; do
    echo "$prop: $(adb shell getprop ro.boottime.$prop)"
done
ams_ready: 1738234573.500
first_frame_drawn: 1738234576.500    ← 差值 3.0s
```

**关键观察**:`ams_ready → first_frame_drawn = 3.0s`,基线 1.0s,慢 2.0s。

**分析思路**:
1. 研发初步判断"WMS 启动慢",查 WMS 日志
2. WMS 日志显示"Window manager policy loaded" 1.0s,**WMS 启动正常**
3. 进一步看 first_frame_drawn 触发原因:launcher 启动慢
4. 抓 launcher 日志,发现 NewLauncher 的 onCreate 跑了 2.0s
5. 真相:不是 WMS 慢,是 launcher 慢

**根因**:
- NewLauncher 的 Application.onCreate 拉了一个 HTTP 请求,4G 网络差
- 2.0s 都在等 HTTP 响应
- AMS 在 systemReady() 之后启动 launcher,launcher onCreate 慢导致 first_frame_drawn 慢
- **WMS 完全正常**

**修复**:
- 短期:让 NewLauncher 把 HTTP 请求挪到后台线程
- 中期:OEM 给 launcher 设置白名单,只允许 AOSP launcher
- 长期:升级到 AOSP 17,launcher 启动策略优化

**修复原理**:
- 误读 `ams_ready → first_frame_drawn` 当作 WMS 启动耗时
- 真实:这是"AMS 全功能到第一帧上屏"耗时,包含 WMS 启动 + launcher 启动 + 第三方 receiver 启动
- 正确做法:看 `ro.boottime.wms`,那个才是 WMS 启动时间

## 5. Takeaway

1. **bootstat 是 Android 的"启动埋点系统"**——把启动期所有关键时间点落盘到 `/data/bootstat/last_boot.txt`。**bootstat 慢 1 段 = 整机慢 1 段**。
2. **10+ 个 ro.boottime.* 时间点**:init / servicemanager / zygote / system_server / pms / ams_ready / wms / ims / first_frame_drawn / boot_completed,每个时间点对应一个明确事件。
3. **差值归因法**:从"系统启动慢 5 秒"到具体服务,通过多个时间点差值层层定位——system_server → pms 慢 = PMS 第一次扫描慢;ams_ready → wms 慢 = WMS 启动慢;wms → boot_completed 慢 = Other 阶段末尾慢。
4. **bootstat 与 Perfetto 的分工**:bootstat 用于线上远端归因(粗粒度),Perfetto 用于 lab 深度调查(细粒度)。两者配合,先 bootstat 定位段,再 Perfetto 定位方法。
5. **bootstat 误读 4 个常见坑**:绝对值当时间戳 / 单值被覆盖 / 某时间点没数据 / `ams_ready → first_frame_drawn` 误判为 WMS 启动耗时。
6. **AOSP 17 vs AOSP 14 的 bootstat 差异**:时间点 8-10 → 12-15 + 落盘格式加 proto + Kotlin 化 + 启动后事件追踪。
7. **本节是 9.1-9.4 的"读法层"**——9.1-9.4 是"埋点层",本节是"读法层";9.6 是"调查层"——三层配合完成 SystemServer 启动的完整可观测性。
8. **实战经验**:bootstat 一次"慢 5 秒"通常对应 2-3 个慢段(PMS + Other 阶段),不要期待只有 1 个根因。

## 附录 D:工程基线表(可调参数)

| 参数 | 典型默认 | 选用准则 | 踩坑提醒 |
