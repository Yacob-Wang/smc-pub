# 9.4 ServiceManager 与 Binder 域

## 一句话开场

ServiceManager 是 Android 的"服务注册中心"——50+ 系统服务启动时通过它注册,跨进程客户端通过它查找。它的地位相当于"全局的 DNS",但比 DNS 更重要:**ServiceManager 慢 = 50+ 服务都慢;ServiceManager 找不到服务 = 50+ 服务都找不到**。AOSP 17 的 4 类 Binder 域(SYSTEM / vendor / isolated / contextHub)进一步隔离了服务的可见性。

## 1. 核心子问题

1. ServiceManager 是什么?它怎么启动?为什么它在 init 阶段就被拉起?
2. 50+ 系统服务怎么注册到 ServiceManager?注册流程是什么?
3. 跨进程客户端怎么通过 ServiceManager 找到服务?查找路径?
4. AOSP 17 的 4 类 Binder 域怎么隔离?什么服务在哪个域?
5. ServiceManager 启动期失败会怎样?整机怎么反应?
6. "Service not found" 错误在 SystemServer 启动期常见根因?
7. AOSP 17 vs AOSP 14 的 ServiceManager 差异?

## 2. 详细展开

### 2.1 ServiceManager 是什么 + 怎么启动

**ServiceManager 是一个独立的 native 进程**——它在 init 阶段就被拉起(早于 zygote,早于 system_server):

```
[init 阶段]
init 解析 init.rc
  ↓
发现 service servicemanager /system/bin/servicemanager
  ↓
启动 servicemanager 进程
  PID 在 init 之后,zygote 之前
  ↓
servicemanager 进程打开 binder 设备
  ↓
servicemanager 进程成为 binder 域的"上下文管理器"(context manager)
  ↓
等待其他进程通过 binder 注册服务
  ↓
[zygote 启动]
[system_server 启动]
  ↓
[50+ 服务启动]
每个服务的 publishBinderService(name, binder)
  ↓
binder 请求路由到 servicemanager
  ↓
servicemanager 把 name → binder handle 存入哈希表
```

**ServiceManager 的源码位置**:
- AOSP 14+:`frameworks/base/native/cmds/servicemanager/binder/service_manager.cpp`(已 binder 化)
- AOSP 13 及之前:`frameworks/base/native/cmds/servicemanager/service_manager.c`

> **🟡 待联网确认**:AOSP 17 实际用哪个文件,需对照 cs.android.com 实际代码。

**ServiceManager 的核心数据结构**:
- 一个 `std::unordered_map<std::string, BinderHandle>` 哈希表
- key = 服务名(如 "activity" / "package" / "window")
- value = BinderHandle(指向该服务的 binder 引用)
- 增/查/删都是 O(1) 平均复杂度

### 2.2 50+ 系统服务怎么注册到 ServiceManager

**SystemServer.run() 启动每个服务时,通过 `publishBinderService(name, binder)` 注册**:

```java
// path: frameworks/base/services/core/java/com/android/server/SystemService.java
// commit: android-17.0.0_r1
protected final void publishBinderService(String name, IBinder binder) {
    // 实际调用 ServiceManager.addService()
    ServiceManager.addService(name, binder, allowIsolated, dumpPriority);
}

// 实际 addService:
// path: frameworks/base/core/java/android/os/ServiceManager.java
public static void addService(String name, IBinder service) {
    // 通过 binder IPC 路由到 servicemanager 进程
    // 内部:Parcel.writeString(name) + Parcel.writeStrongBinder(service)
    // servicemanager 接收后存入哈希表
}
```

**典型服务的注册名**:

| 服务 | 注册名 | Binder 域 |
|---|---|---|
| ActivityManagerService | "activity" | SYSTEM |
| PackageManagerService | "package" / "package_native" | SYSTEM |
| WindowManagerService | "window" | SYSTEM |
| InputManagerService | "input" | SYSTEM |
| PowerManagerService | "power" | SYSTEM |
| DisplayManagerService | "display" | SYSTEM |
| NotificationManagerService | "notification" | SYSTEM |
| AlarmManagerService | "alarm" | SYSTEM |
| JobSchedulerService | "jobscheduler" | SYSTEM |
| ConnectivityService | "connectivity" | SYSTEM |
| ActivityTaskManagerService | "activity_task" | SYSTEM |
| ... | (50+ 个) | |

**关键洞察**:
- 服务**注册名是全局唯一**的——任何两个服务不能用相同名字,否则后注册的覆盖先注册的
- 9.6 案例 1 会讲"服务被覆盖导致 50+ 服务错乱"的灾难

### 2.3 跨进程客户端怎么通过 ServiceManager 找到服务

**任何进程想用"ActivityManager 服务"的标准流程**:

```java
// path: 任意应用层代码
// commit: android-17.0.0_r1

// 1. 通过 ServiceManager 查 AMS 的 binder handle
IBinder binder = ServiceManager.getService("activity");
// 2. 把 binder handle 包装成 IActivityManager 接口
IActivityManager am = IActivityManager.Stub.asInterface(binder);
// 3. 调用 AMS 的方法(通过 binder IPC)
am.startActivity(...);
```

**查找路径的时延分布**(线上均值,SM8550 平台):

| 步骤 | 耗时 | 说明 |
|---|---|---|
| 1. ServiceManager.getService("activity") | 1-5 ms | 第一次查会拉 binder handle 进缓存 |
| 2. asInterface 包装 | < 1 ms | 纯 Java 侧 |
| 3. 第一次调用 IPC | 5-20 ms | 跨进程 binder 调用,首次要建立连接 |
| 4. 后续调用 IPC | 0.5-2 ms | 已建立连接,binder 调用快速 |
| **第一次"get + call"** | **7-26 ms** | 第一次访问的固定成本 |
| **后续每次"call"** | **0.5-2 ms** | 已缓存 binder handle |

**关键洞察**:
- "getService" 第一次慢(7-26 ms),后续调用快(0.5-2 ms)
- 9.5 详述 bootstat 怎么埋点
- 9.6 详述"Service not found" 错误

### 2.4 AOSP 17 的 4 类 Binder 域

**AOSP 17 的服务有 4 类 Binder 域**(根据启动位置和 SELinux 标签):

| 域 | 启动位置 | 服务的 SELinux 标签 | 典型服务 |
|---|---|---|---|
| **SYSTEM** | SystemServer | `u:r:system_server:s0` | 50+ 系统服务(AMS/PMS/WMS/IMS/...) |
| **VENDOR** | vendor init | `u:r:vendor_init:s0` | 厂商 GKI 扩展服务(摄像头 HAL / 音频 HAL) |
| **ISOLATED** | 独立子进程 | `u:r:isolated_app:s0` | 隔离域服务(Android 11+ 默认 1 个 isolated 进程) |
| **CONTEXTHUB** | ContextHub 进程 | `u:r:context_hub:s0` | sensor hub 类服务 |

**域隔离的稳定性意义**:
- **SYSTEM 域** 的服务**不能**被 VENDOR 域的进程直接调用
- **VENDOR 域** 的服务**不能**被 SYSTEM 域直接调用
- **ISOLATED 域** 只能跑 SELinux 允许的少数服务
- **CONTEXTHUB 域** 是 sensor hub 专用,其他域不能访问

**域隔离的实现机制**:
- SELinux:每个域有自己的 SELinux 上下文,跨域访问需要 sepolicy 显式 allow 规则
- Binder 节点:每个域的 binder 节点在 servicemanager 内部隔离(不同域的服务用不同前缀)
- 9.6 案例会讲"跨域访问被 SELinux 拒绝"导致的失败

### 2.5 ServiceManager 启动期失败会怎样

**ServiceManager 启动失败 = 整机立即重启**(因为它是 init 拉起的 critical 进程):

```
[init 阶段]
init 启动 servicemanager
  ↓
servicemanager 立即退出 / 启动失败
  ↓
init 检测到子进程退出
  ↓
触发 critical window(默认 4 次反复失败)
  ↓
整机进入 recovery 模式
```

**为什么 ServiceManager 是 critical 进程**:
- 它是 50+ 系统服务注册的目标
- servicemanager 没起 → AMS / PMS / WMS 全部无法注册
- servicemanager 没起 → 整机不响应

**init.rc 中 servicemanager service 的声明**(典型):
```
service servicemanager /system/bin/servicemanager
    class core
    critical
    onrestart restart zygote
    onrestart restart media
    onrestart restart netd
    ...
```

**关键点**:
- `class core` 表示它是 core class,在 init early 阶段启动
- `critical` 表示它崩了整机要重启
- `onrestart` 链重启 zygote / media / netd(它们都依赖 servicemanager)

### 2.6 "Service not found" 错误在 SystemServer 启动期常见根因

**SystemServer 启动时,经常会报"Service not found"**——这通常意味着某个服务在它被注册前就被调用了。常见根因:

| 根因 | 触发条件 | 修复方向 |
|---|---|---|
| 服务没注册就调用 | 启动顺序错(服务 A 等服务 B,B 还没起) | 调整启动顺序 |
| 跨 Binder 域访问 | SYSTEM 域访问 VENDOR 域服务,被 SELinux 拒绝 | 加 sepolicy allow 规则 |
| 服务名拼写错 | OEM 改了服务名但调用方没改 | 统一服务名 |
| 服务注册时崩溃 | 服务的 onStart() 抛异常,服务被丢弃 | 查 DropBox / tombstones |
| ServiceManager 慢 | servicemanager 进程卡,所有服务注册排队 | 查 servicemanager 进程状态 |

**9.6 案例 4** 会讲"第三方 sepolicy 拒绝 SYSTEM 域访问 vendor 域服务"导致的 SystemServer 反复 crash。

### 2.7 AOSP 17 vs AOSP 14 的 ServiceManager 差异

| 维度 | AOSP 14 (API 34) | AOSP 17 (API 37) | 变化 |
|---|---|---|---|
| ServiceManager 源码 | `service_manager.c` | `binder/service_manager.cpp` | C → C++,binder 化 |
| Binder 域 | 3 类(SYSTEM / vendor / contextHub) | 4 类(+ isolated) | +1 域 |
| 服务数量 | 50-60 | 60-80 | +10-20 |
| 启动时间 | 30-80 ms | 50-120 ms | +20-40 ms(更多服务) |
| 内存占用 | 5-10 MB | 8-15 MB | +3-5 MB |
| 跨域访问限制 | 严格 | 更严格 | SELinux 规则更严 |

## 4. 实战案例

### 案例 1:某 App 装后第一次启动,SystemServer 启动期报"PackageManagerService not found"(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:用户装了某第三方安全 App(代号 SecureGuard)后重启,SystemServer 启动期反复报"PackageManagerService not found"

**现象**:
```log
$ adb logcat -d -b system -s SystemServer,ActivityManagerService | head -100
SystemServer: Phase 100: Core
ActivityManagerService: Service not found: package
ActivityManagerService: Service not found: package
ActivityManagerService: java.lang.IllegalStateException: Service not found: package
  at android.os.ServiceManager.getService(ServiceManager.java:85)
  at com.android.server.am.ActivityManagerService.getPackageManager(ActivityManagerService.java:3000)
  ...
```

**分析思路**:
1. 关键日志 `Service not found: package` → PMS 没注册
2. 抓 servicemanager 栈,发现 servicemanager 进程**没收到 PMS 注册请求**
3. 检查 PMS 日志,发现 PMS.lightInit() 抛了异常
4. 查异常原因:`PackageManagerException: Cannot load package info`
5. 进一步看 PMS 构造,发现 SecureGuard 装了一个特殊的 apk,导致 PMS 启动时扫描这个 apk 失败

**根因**:
- SecureGuard 装了一个特殊的 apk(代号 fake-pkg)
- fake-pkg 的 manifest 损坏 / 签名错误
- PMS 启动期扫描 /data/app 时,扫描到 fake-pkg 抛异常
- 异常导致 PMS.lightInit() 失败
- PMS 没起来 → AMS 启动期 getPackageManager() 报 Service not found
- 整机 boot 失败

**修复**:
- 短期:卸载 SecureGuard
- 中期:SecureGuard 改 fake-pkg 的 manifest / 签名
- 长期:OEM 给 PMS 加 try-catch,扫描失败时降级

**修复原理**:
- "Service not found" 错误**几乎都源于启动顺序错**——服务 A 等服务 B,B 还没起
- 但本案例是"服务 B 的初始化失败,根本没注册"
- 线上治理:遇到 "Service not found" 错误,优先看 servicemanager 注册日志,确认服务**是否真的没注册**

### 案例 2:某设备第三方 sepolicy 拒绝 SYSTEM 域访问 vendor 域服务(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:Pixel 7(8GB RAM)
- 复现步骤:用户装了某第三方 camera App(代号 ProCam)后重启,SystemServer 启动期报"camera_service not found"

**现象**:
```log
$ adb logcat -d -b system -s SystemServer,camera | head -100
SystemServer: Phase 500: Other
SystemServer: Starting CameraService
CameraService: Service registration failed
CameraService: java.lang.SecurityException: SELinux denial
  ...
audit: type=1400 audit(...): avc: denied { find } for comm="system_server"
    name="ProCamService" scontext=u:r:system_server:s0
    tcontext=u:r:vendor_init:s0 tclass=binder
```

**关键观察**:`avc: denied { find }` + scontext=system_server + tcontext=vendor_init + tclass=binder → SELinux 拒绝跨域访问。

**分析思路**:
1. 关键日志 `avc: denied` + 跨域标签 → SELinux 拒绝
2. 查 ProCam sepolicy 模块,发现 ProCam 加了"vendor 域服务"的 sepolicy 规则
3. 这条规则**没有**给 system_server 域 allow 权限
4. system_server 启动 CameraService 时需要访问 ProCamService,被 SELinux 拒绝
5. CameraService 启动失败 → 整机不响应

**根因**:
- ProCam 是个 vendor 域服务,它的 sepolicy 模块只允许 vendor 域访问
- 实际需要 system_server(CameraService)也能访问,否则 CameraService 不能注册到 ServiceManager
- ProCam 没考虑到这点,sepolicy allow 规则写漏了

**修复**:
- 短期:卸载 ProCam
- 中期:ProCam 改 sepolicy 规则,加 system_server 域的 allow
- 长期:OEM 给 sepolicy 加"默认 allow" 规则,降低误配

**修复原理**:
- 跨 Binder 域访问是稳定性最常见的"隐形问题"之一
- 任何 vendor 域服务想被 system_server 调用,sepolicy 必须显式 allow
- 调试方法:`adb shell setenforce 0` 临时关闭 SELinux,验证是否是 SELinux 问题

## 5. Takeaway

1. **ServiceManager 是 Android 的"服务注册中心"**——50+ 系统服务都注册到它,跨进程客户端都通过它查找。**它慢 = 50+ 服务都慢,它找不到服务 = 50+ 服务都找不到**。
2. **ServiceManager 是 init 拉起的 critical 进程**——在 init 阶段、zygote 之前被拉起;它崩了整机立即重启。
3. **AOSP 17 的 4 类 Binder 域**(SYSTEM / vendor / isolated / contextHub)隔离了服务的可见性,跨域访问需要 sepolicy 显式 allow。
4. **服务注册是 O(1) 哈希表**——但跨进程 binder IPC 的第一次调用慢(7-26 ms),后续调用快(0.5-2 ms)。
5. **"Service not found" 错误的 5 类根因**:启动顺序错 / 跨 Binder 域拒绝 / 服务名拼写错 / 服务注册时崩溃 / ServiceManager 慢。
6. **AOSP 17 vs AOSP 14 的 ServiceManager 差异**:源码 C → C++(binder 化)+ Binder 域 3 → 4(+ isolated)+ 服务数 50-60 → 60-80。
7. **调试 "Service not found" 的标准步骤**:抓 servicemanager 栈 / 看服务注册日志 / 看 SELinux 拒绝 / 看崩溃日志 / 看 servicemanager 启动时间。
8. **vendor 域服务被 system_server 调用是常见稳定性问题**——任何 vendor 域服务都必须在 sepolicy 中显式 allow system_server 访问。
