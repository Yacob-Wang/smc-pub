# 9.6 SystemServer 启动慢/死锁/crash 调查

## 一句话开场

**SystemServer 启动慢的 5 类根因**(PMS 扫描阻塞 / WMS 加载 policy 慢 / Other 阶段服务阻塞 / 第三方 sepolicy 拒绝 / 启动期 OOM)、**死锁的 3 类根因**(PMS 锁竞争 / IMS native 死锁 / 第三方服务持有锁)、**crash 的 4 类根因**(SELinux 拒绝 / 启动期 OOM / native crash / 反复崩触发 critical window),用 `kill -3` + `debuggerd` + bootstat + DropBoxManager 四个工具**30 秒内**能定位。整机调查的完整 SOP 留给第 11 章,本节只讲 SystemServer 内部视角。

## 1. 核心子问题

1. SystemServer 启动慢的 5 类代码点分别在哪?怎么区分?
2. SystemServer 死锁的 3 类根因分别有什么 logcat 关键词?
3. SystemServer crash 的 4 类根因分别有什么触发条件?
4. Watchdog + DropBoxManager + tombstones + last_kmsg 四个抓栈工具怎么配合?
5. `ro.boottime.*` + `init.svc.system_server` + DropBox 文件三类来源怎么用?
6. SystemServer 反复崩的 critical window 怎么联动 init?
7. SystemServer 死锁后,如何拿到堆栈(rotten tombstone 是什么)?
8. 9.6 与 11 章分工:9.6 只管"已知是 SystemServer 问题",11 章管"整机启动慢"。

## 2. 详细展开

### 2.1 SystemServer 启动慢的 5 类根因

SystemServer 启动慢,根据 9.1-9.5 已讲过的机制,可以归为 5 类根因:

```
SystemServer 启动慢
  ↓
[1] PMS 第一次扫描阻塞(Core 阶段)     ← 9.1 案例 1 / 9.2 案例 2
  特征:ro.boottime.pms 晚 1+ 秒
  logcat:PackageManagerService: Scanning /data/app took <N>ms
  ↓
[2] WMS 加载 policy 资源阻塞(Other 阶段) ← 9.2 案例 1
  特征:ro.boottime.wms 晚 2+ 秒
  logcat:WindowManagerService: Window manager policy loaded
  ↓
[3] Other 阶段 30+ 服务阻塞              ← 9.2 §2.7
  特征:ro.boottime.boot_completed - ro.boottime.wms 差值大
  logcat:多个 SystemServer.* 服务启动日志
  ↓
[4] 第三方 sepolicy 拒绝服务启动          ← 9.1 案例 2 / 9.4 案例 2
  特征:反复崩触发 zygote-fatal / system_server-fatal
  logcat:avc: denied { ... } scontext=u:r:system_server:s0
  ↓
[5] SystemServer 启动期 OOM(4GB 设备)   ← 9.1 §2.8
  特征:反复崩 + Java heap OOM
  logcat:java.lang.OutOfMemoryError: Java heap space
```

**5 类根因在 SystemServer.run() 的发生位置**:

| 根因类别 | 发生在 | 单次启动慢的耗时 | 反复启动慢的耗时 |
|---|---|---|---|
| **① PMS 扫描阻塞** | startCoreServices() 内 PMS.fullInit() | +1-5s | 持续 +1-5s |
| **② WMS 加载 policy 慢** | startOtherServices() 内 WMS 初始化 | +1-15s | 持续 +1-15s |
| **③ Other 阶段服务阻塞** | startOtherServices() 内 30+ 服务 | +1-5s | 持续 +1-5s |
| **④ 第三方 sepolicy 拒绝** | 任意阶段(被拒绝时) | 立即崩 | 反复崩,触发 critical window |
| **⑤ 启动期 OOM** | 任意阶段(内存不足时) | 立即崩 | 反复崩 |

### 2.2 SystemServer 死锁的 3 类根因

SystemServer 死锁比启动慢更严重——主线程卡住,Watchdog 30 秒后杀进程。

**3 类死锁的代码点**:

| 死锁类别 | 发生在 | 单次死锁的耗时 | 反复死锁的耗时 |
|---|---|---|---|
| **① PMS 锁竞争死锁** | performBootDexOpt / scanDirTracedLI 持锁 | 30s+(Watchdog 超时) | 30s+ |
| **② IMS native 死锁** | InputReader / InputDispatcher 互持锁 | 30s+ | 30s+ |
| **③ 第三方服务持锁** | 第三方 SystemService 子类持锁不释放 | 30s+ | 30s+ |

**9.3 案例 1(PMS performBootDexOpt 锁竞争)已讲过详细案例**——PMS 内部 mPackagesLock 在多个路径下被持锁,异步 dex2oat 持锁后 scanDirTracedLI 等待同一把锁。

**9.3 案例 2(IMS native 死锁)已讲过详细案例**——InputReader 持 mPolicyLock 等 InputDispatcher 的 mLock,InputDispatcher 反之,典型 AB-BA 死锁。

**第三方服务持锁的常见模式**:
- 第三方 app 装了 SystemService 子类,在 systemReady() 阶段持锁
- 锁一直不释放,导致后续服务等待
- 30s 后 Watchdog 抓栈

### 2.3 SystemServer crash 的 4 类根因

SystemServer crash 比死锁更直接——主线程抛异常 / 致命错误,直接 kill 进程。

**4 类 crash 的触发条件**:

| crash 类别 | 触发条件 | logcat 关键词 |
|---|---|---|
| **① SELinux 拒绝** | 第三方 sepolicy 误配 | `avc: denied { ... }` |
| **② 启动期 OOM** | Java heap / Native heap 不够 | `OutOfMemoryError` |
| **③ native crash** | JNI / HAL 抛 SIGSEGV | `signal 11 (SIGSEGV)` |
| **④ 反复崩触发 critical window** | 5 分钟内 4 次崩 | `init: too many crashes` |

**9.1 案例 2 已讲过"SELinux 拒绝导致反复崩"**——某第三方安全 App 误配 sepolicy,导致 system_server 启动期访问 dex2oat 被拒绝,反复崩。

**9.4 案例 2 已讲过"跨 Binder 域 SELinux 拒绝"**——ProCam 服务的 sepolicy 没 allow system_server 访问,CameraService 启动失败,反复崩。

**启动期 OOM 的常见根因**:
- 第三方 app 装了太多,导致 /data/app apk 数量多(影响 PMS 扫描,但不直接 OOM)
- framework-res 资源过多(影响 WMS 加载,可能 OOM)
- 4GB 设备同时启动 50+ 服务,Java heap 总占用超 1.5GB 触发 OOM

### 2.4 抓栈四件套:Watchdog + DropBoxManager + tombstones + last_kmsg

**SystemServer 启动期出问题时,有 4 个工具可以抓栈**:

**(1) Watchdog(主动杀进程 + 抓栈)**:

```java
// path: frameworks/base/services/core/java/com/android/server/Watchdog.java
// commit: android-17.0.0_r1
// Watchdog 内部:
// 1. 每 30 秒发心跳给 30+ 监测服务
// 2. 监测服务 30 秒不回复,判定卡死
// 3. 抓所有线程栈(Java + native)
// 4. 写 DropBoxManager
// 5. 杀 system_server
```

**(2) DropBoxManager(异常日志落盘)**:

```bash
# 1. 看 SystemServer 异常的落盘
adb shell ls -la /data/system/dropbox/system/ | head -30
# 期望文件名:
# @data_app_crash@<ts>.system_server.txt
# @data_app_anr@<ts>.system_server.txt
# system_server_native_crash@<ts>.txt

# 2. 读某个落盘文件
adb shell cat /data/system/dropbox/system/@data_app_anr@<ts>.system_server.txt

# 3. dumpsys dropbox
adb shell dumpsys dropbox --print
```

**(3) tombstones(native 侧崩溃落盘)**:

```bash
# 1. 看 tombstones 目录
adb shell ls -la /data/tombstones/

# 2. 读某个 tombstone
adb shell cat /data/tombstones/tombstone_XX

# 3. rotten tombstone(空 tombstones 文件夹)
# 原因:system_server 启动期崩,tombstoned 还没完全初始化
# 解决:从 last_kmsg / pstore 取
```

**(4) last_kmsg / pstore(内核 + 早期 init 日志)**:

```bash
# 1. 取 last_kmsg(内核侧 + 早期 init 侧)
adb pull /sys/fs/pstore/console-ramoops

# 2. 取 init 早期的 logcat
adb logcat -d -b all -t 1000 | head -200
```

### 2.5 SystemServer 反复崩的 critical window

**SystemServer 是 init 的 critical 进程**——它反复崩,init 触发 `system_server-fatal` 目标:

```
[init 阶段]
init.rc 中 system_server 是 critical class
  ↓
[SystemServer 启动失败 1 次]
init 检测到子进程退出
  ↓
[critical window 内 4 次]
init 统计崩溃次数
  ↓
[触发 system_server-fatal 目标]
init 跳转到 recovery 模式
  ↓
[用户看到]
屏幕提示"系统已崩溃,请恢复出厂设置"
```

**关键时间窗口**:
- 默认 5 分钟内 4 次崩 → 触发 critical 目标
- 改小 → 更激进,会让偶发崩被误判
- 改大 → 更宽松,可能漏掉真问题

**对应 init.rc 声明**(典型):
```
service system_server /system/bin/app_process64 -Xzygote /system/bin --zygote --system-server
    class core
    critical
    onrestart restart zygote
    onrestart restart media
    onrestart restart netd
    ...
```

### 2.6 SystemServer 启动期调查的 30 秒 SOP

**实战 30 秒定位 SystemServer 内部问题**:

```bash
# 步骤 1:抓 SystemServer 栈(SIGQUIT,5 秒)
SS_PID=$(adb shell ps -A | grep system_server | head -1 | awk '{print $2}')
adb shell kill -3 $SS_PID
adb logcat -d -b main -s DEBUG -t 50

# 步骤 2:看 DropBoxManager 落盘(5 秒)
adb shell ls -la /data/system/dropbox/system/ | head -20
# 期望:看到 @data_app_crash@<ts>.system_server.txt 或 @data_app_anr@<ts>.system_server.txt

# 步骤 3:看 tombstones(3 秒)
adb shell ls -la /data/tombstones/ | head -10
# 期望:看到 tombstone_XX 文件

# 步骤 4:看 last_kmsg(5 秒,仅在 tombstones 为空时)
adb pull /sys/fs/pstore/console-ramoops 2>/dev/null

# 步骤 5:看 bootstat 归因(5 秒)
adb shell dumpsys bootstat | tail -10
# 期望:看到 system_server / pms / ams_ready / wms / boot_completed 几个时间点

# 步骤 6:看 ro.boottime.*(3 秒)
for prop in system_server pms ams_ready wms boot_completed; do
    echo "$prop: $(adb shell getprop ro.boottime.$prop)"
done
# 期望:从差值识别哪段慢
```

## 4. 实战案例

### 案例 1:某设备 boot_completed 晚 6 秒,bootstat 归因到 Other 阶段某服务阻塞(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 wolf,6GB RAM)
- 复现步骤:用户装了一个新输入法(代号 QuickInput)后,boot_completed 14 秒(基线 8 秒)

**现象**:
```bash
$ for prop in system_server pms ams_ready wms boot_completed; do
    echo "$prop: $(adb shell getprop ro.boottime.$prop)"
done
system_server: 1738234569.200
pms: 1738234571.000    ← +1.8s(基线 1.0s,慢 0.8s)
ams_ready: 1738234573.500
wms: 1738234574.500
boot_completed: 1738234580.000    ← +5.5s(基线 3.0s,慢 2.5s)
```

**关键观察**:
- `wms → boot_completed` 差值 5.5s,远超基线 3.0s
- 这段时间是 WMS 启动完成后,IMS / launcher / 第三方 receiver 启动
- 慢 2.5s,怀疑是 Other 阶段某服务阻塞

**分析思路**:
1. 抓 SystemServer SIGQUIT
2. 看主线程在哪个方法
3. 发现主线程在 `InputMethodManagerService.onBootPhase(PHASE_BOOT_COMPLETED)` 卡 2.5s
4. 进一步看 InputMethodManagerService 日志,发现 QuickInput 触发 IME 切换
5. IME 切换是阻塞操作,等到 QuickInput 初始化完成才返回

**根因**:
- QuickInput 是个新装的 IME(输入法)
- SystemServer 启动期,其他服务监听 PHASE_BOOT_COMPLETED 事件
- InputMethodManagerService 监听 PHASE_BOOT_COMPLETED 时,会触发 IME 列表更新
- QuickInput 初始化慢,IME 列表更新等它 → InputMethodManagerService 卡 2.5s
- 这段时间阻塞 SystemServer 主线程

**修复**:
- 短期:QuickInput 优化初始化时间
- 中期:InputMethodManagerService 改异步,不阻塞主线程
- 长期:OEM 在 init 阶段禁用第三方 IME,等 boot_completed 后再启用

**修复原理**:
- PHASE_BOOT_COMPLETED 监听者是**同步**执行的,任何一个慢都阻塞 SystemServer 主线程
- 这是 AOSP 的设计局限,AOSP 17+ 计划异步化但还没完全落地
- 线上治理:遇到 `wms → boot_completed` 差值大,**优先看 PHASE_BOOT_COMPLETED 监听者**

### 案例 2:某设备 SystemServer 反复崩 4 次,last_kmsg 找到 sepolicy 误配(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:某品牌中端机(代号 eagle,4GB RAM)
- 复现步骤:用户装了一个新安全 App(代号 SafeGuard)后,反复崩到 recovery

**现象**:
- /data/tombstones/ 空 → rotten tombstone
- 反复崩 4 次后停在 recovery 模式
- 屏幕提示"系统已崩溃,请恢复出厂设置"

**分析思路**:
1. 4 次崩 → critical window 触发 system_server-fatal
2. tombstone 是空的 → 必须从 last_kmsg 取
3. `adb pull /sys/fs/pstore/console-ramoops` 拿到 last_kmsg
4. 关键片段:
   ```
   init: service 'system_server' (pid 1234) killed by signal 9
   init: critical: too many crashes in 5 minutes, rebooting
   ...
   last_kmsg:
   type=1400 audit(1738234567.890:123): avc: denied { read } for
   scontext=u:r:system_server:s0 tcontext=u:r:untrusted_app:s0 tclass=file
   ...
   system_server: E SELinux : Failed to read /data/app/com.safeguard/oat/arm64/dex2oat
   ```
5. 关键信号 `avc: denied` + scontext=system_server + tcontext=untrusted_app → **sepolicy 误配**

**根因**:
- SafeGuard 在它的 sepolicy 模块里加了一条规则:限制 system_server 访问 /data/app/com.safeguard
- 这条规则被 SafeGuard 安装时写入 /data/security/sandbox
- 加载到 SELinux 策略后,system_server 启动期执行 `performBootDexOpt` 时需要读这个目录,被这条规则拒绝
- SELinux 拒绝 → 抛异常 → SystemServer 死循环
- 5 分钟内死 3 次 → critical window 触发 system_server-fatal

**修复**:
- 短期:卸载 SafeGuard,重启设备
- 中期:SafeGuard 改 sepolicy 规则,移除 system_server 域限制
- 长期:OEM 在 init 启动时加 sepolicy 规则校验,避免第三方 app 引入拒绝规则

**修复原理**:
- SELinux 是 Android 4.4+ 强制启用的强制访问控制
- 任何第三方 sepolicy 模块**添加** system_server 域的规则,都可能误配
- 调试方法:`adb shell setenforce 0` 临时关闭 SELinux,验证是否是 SELinux 问题
- 注意:`setenforce 0` 只能在 userdebug 设备上用,user 设备不行

## 5. Takeaway

1. **SystemServer 启动慢的 5 类根因**:PMS 扫描阻塞(9.1 案例 1) / WMS 加载 policy 慢(9.2 案例 1) / Other 阶段服务阻塞(本节案例 1) / 第三方 sepolicy 拒绝 / 启动期 OOM——5 个 logcat 关键词直接对应。
2. **SystemServer 死锁的 3 类根因**:PMS 锁竞争(9.3 案例 1) / IMS native 死锁(9.3 案例 2) / 第三方服务持锁——3 个栈模式对应。
3. **SystemServer crash 的 4 类根因**:SELinux 拒绝(本节案例 2) / 启动期 OOM / native crash / 反复崩触发 critical window——4 个 logcat 关键词直接对应。
4. **抓栈四件套**:`SIGQUIT + DropBoxManager + tombstones + last_kmsg`——30 秒内能定位 SystemServer 任何问题。
5. **`ro.boottime.*` + `init.svc.system_server` + DropBox 文件三类来源**——分别是时间埋点、运行状态、异常落盘,三个维度配合调查。
6. **rotten tombstone(空 tombstones 文件夹)** = SystemServer 启动崩,必须从 `last_kmsg` / `pstore` 取。
7. **`critical window=system_server-fatal` 触发 4 次反复崩后整机重启**——这是设计内行为,不是 bug。
8. **9.6 与 11 章分工**:9.6 只管"已知是 SystemServer 问题,精确定位到 SystemServer 内部";11 章管"整机启动慢 5 秒,可能是 Zygote / system_server / PMS / 任何一个服务慢"。
9. **PHASE_BOOT_COMPLETED 监听者阻塞 SystemServer 主线程**——这是 AOSP 12+ 的设计局限,任何监听这个阶段的服务慢都会拖垮整机 boot。
10. **第三方 sepolicy 误配是 SystemServer 启动期最常见的"隐形问题"**——加 sepolicy 规则时**必须**在真机全路径验证 boot 流程。
