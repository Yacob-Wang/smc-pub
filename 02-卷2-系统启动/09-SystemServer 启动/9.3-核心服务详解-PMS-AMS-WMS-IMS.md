# 9.3 核心服务详解:PMS → AMS → WMS → IMS 启动依赖

## 一句话开场

50+ 系统服务中,**PMS / AMS / WMS / IMS 4 大服务是"启动顺序强依赖"的核心**——它们任何一个卡住,整机都不响应(连 launcher 都看不到)。本节逐一展开 4 大服务的内部初始化流程 + 互相依赖 + 启动阻塞根因,让读者能根据症状("App 装不上"/"屏幕不亮"/"触摸没反应")30 秒定位到具体服务。

## 1. 核心子问题

1. PMS(包管理)为什么是"第一个全功能服务"?它的初始化流程是什么?
2. AMS(活动管理)为什么必须在 PMS 之后启动?它的 systemReady() 触发什么?
3. WMS(窗口管理)为什么依赖 AMS / Display / ActivityTask?它的启动时序?
4. IMS(输入管理)为什么必须在 WMS 之后?它的 InputReader/InputDispatcher 线程模型?
5. 4 大服务的依赖图怎么画?哪两个服务是"必须先后"?
6. 4 大服务启动的典型耗时?哪一段最容易出问题?
7. 4 大服务启动阻塞的常见根因?
8. AOSP 17 vs AOSP 14 的 4 大服务启动差异?

## 2. 详细展开

### 2.1 PackageManagerService(PMS):第一个全功能服务

**PMS 在 50+ 服务中的特殊地位**——它是"第一个全功能服务"。原因:
- 几乎所有其他服务都需要查询"apk 元数据"(uid / 包名 / 权限 / 签名)
- AMS / WMS / IMS / NetworkPolicy 等,都通过 PMS 查包信息
- **如果 PMS 没起来,50+ 服务中有 40+ 都不能正常工作**

**PMS 的两阶段初始化**(AOSP 12+ 设计):

```
[Bootstrap 阶段]
PMS 构造函数(early)
  ↓
mFirstBoot = true
  ↓
只读 /system /vendor /product 分区的 package 信息
  ↓
这些分区在编译时已确定,不需要运行时扫描
  ↓
返回(此时 PMS 处于"骨架状态",能查 system apk,但 /data/app 还没扫)
  ↓
[Core 阶段]
PMS.fullInit()
  ↓
扫描 /data/app(用户装的应用)
  ↓
扫描 /data/app-private(私有应用)
  ↓
扫描 /data/app-ephemeral(临时应用)
  ↓
合并 system + data 扫描结果
  ↓
PMS 进入"全功能状态"
```

**PMS 第一次扫描的典型耗时**:
- 扫描 /system:100-200 ms(编译时已固定)
- 扫描 /vendor:50-150 ms
- 扫描 /product:30-100 ms
- 扫描 /data/app:**800-1500 ms(基线)**,3-5 s(异常,9.1 案例 1)
- 合并 + 优化:100-300 ms
- **总计:1000-2500 ms(基线),3-8 s(异常)**

**PMS 启动阻塞的常见根因**:
1. **/data/app 扫描阻塞**:apk 数量多 / 签名校验慢(9.1 案例 1)
2. **PMS 锁竞争死锁**:PMS 内部多处用 synchronized,某些第三方 app 扫描回调触发死锁
3. **/system 目录损坏**:apk 损坏导致 scan 抛异常,PMS 进入降级模式
4. **PMS dex2oat 阻塞**:`performBootDexOpt` 在 systemReady 前要跑,卡 4GB 设备

### 2.2 ActivityManagerService(AMS):全系统的"进程管理"中枢

**AMS 是全系统最繁忙的服务**——所有 App 进程的 fork / kill / 优先级 / ANR / OOM 判定都归它管。9.1 §2.6 已讲过它的 systemReady() 触发 boot_completed。本节展开 AMS 内部启动。

**AMS 的两阶段初始化**(AOSP 12+ 设计,与 PMS 同步):

```
[Bootstrap 阶段]
AMS.earlyInit() (lightInit)
  ↓
构造 ActivityManagerService 对象
  ↓
注册到 ServiceManager:
  - "activity"(IActivityManager)
  - "procstats"(IProcessStats)
  - "meminfo"(IMemInfoService)
  ↓
但**不能**启动 Activity / Service(因为 PMS 还没全功能)
  ↓
[Core 阶段末尾 + Other 阶段]
AMS.fullInit() 之后,startOtherServices() 中:
  ↓
AMS.systemReady() 触发
  ↓
通知 ActivityTaskManager:启动 launcher
  ↓
启动 launcher → 整机第一帧可见
  ↓
发送 ACTION_BOOT_COMPLETED 广播
  ↓
监听 PHASE_THIRD_PARTY_APPS_CAN_START 的服务可以启动第三方 App
  ↓
写 bootstat:ro.boottime.boot_completed
```

**AMS 启动阻塞的常见根因**:
1. **PMS 没全功能**:AMS 早期 init() 卡在等待 PMS(已在上文解决,两阶段拆开)
2. **AMS 锁竞争**:AMS 内部 mutex 极多,某些场景下会死锁
3. **ActivityTaskManager 启动慢**:ActivityTaskManager 是 AMS 的子组件,启动慢会拖垮 AMS
4. **systemReady() 监听者阻塞**:某些服务在 onBootPhase(PHASE_BOOT_COMPLETED) 中卡住,会让 AMS 等

### 2.3 WindowManagerService(WMS):显示与 Window 管理

**WMS 是 Other 阶段最大的耗时点**(9.2 案例 1 已讲过加载 policy 资源)。本节展开 WMS 内部启动。

**WMS 的初始化时序**(AOSP 17):

```
[Other 阶段]
WMS 主构造
  ↓
1. 加载 framework-res.apk
  路径:/system/framework/framework-res.apk
  耗时:50-200 ms(基线) / 10-15 s(异常,OEM 加了 800+ 资源)
  ↓
2. 构造 WindowManagerPolicy(PhoneWindowManager)
  耗时:50-100 ms
  ↓
3. 初始化 DisplayManager(显示设备)
  耗时:30-100 ms
  ↓
4. 初始化 InputManager(只是注册,不实际起线程)
  耗时:30-80 ms
  ↓
5. 注册到 ServiceManager
  - "window"(IWindowManager)
  - "input"(IInputManager,代理给 IMS)
  ↓
6. 启动 InputManagerService(IMS 真正起来)
  耗时:100-300 ms
  ↓
7. 启动 Session Surface
  耗时:30-80 ms
  ↓
8. 触发 PHASE_WAIT_FOR_DEFAULT_DISPLAY
  耗时:10-30 ms
  ↓
[systemReady() 阶段]
9. 显示默认壁纸
  耗时:200-500 ms
  ↓
10. launcher Activity 启动
  (由 AMS 触发)
  耗时:300-800 ms
  ↓
[AMS.systemReady() 之后]
11. boot_completed
  (由 AMS 触发)
```

**WMS 启动阻塞的常见根因**:
1. **framework-res 资源加载慢**:OEM 加 800+ 资源,12s+(9.2 案例 1)
2. **DisplayManager 设备配置多**:多 Display / 折叠屏 / 投影设备,初始化耗时翻倍
3. **WMS 锁竞争**:WMS 内部 mutex 极多,某些 OEM 扩展死锁
4. **WMS 启动期 OOM**:WMS 加载多用户 / 多 Display 配置时内存占用大

### 2.4 InputManagerService(IMS):触摸 / 按键分发

**IMS 是 WMS 启动之后才真正起来**——它必须在 Window 已 ready 后才能工作(因为输入事件要路由到 Window)。

**IMS 的线程模型**(AOSP 17):

```
IMS 启动
  ↓
1. 构造 IMS 服务端
  ↓
2. 启动 2 个 native 线程:
  - InputReader (读 /dev/input/event* 设备节点)
  - InputDispatcher (派发到 focused window)
  ↓
3. InputReader 读事件 → InputDispatcher
  ↓
4. InputDispatcher 路由到 WMS 的 focused window
  ↓
5. WMS 通知 App 进程
```

**IMS 启动阻塞的常见根因**:
1. **InputReader / InputDispatcher 死锁**:native 侧 mutex 竞争
2. **Input 设备节点权限**:sepolicy 拒绝 IMS 读 /dev/input/event*
3. **IMS 启动期 native crash**:某些 OEM HAL 实现有 bug,触发 SIGSEGV

### 2.5 4 大服务依赖图

```
┌─ Kernel  ─────────────────────────────────────────────────┐
│  进程管理:cgroup / oom_adj / signal                        │
└────────────────┬───────────────────────────────────────────┘
                 ▼
┌─ PMS (PackageManagerService) ──────────────────────────────┐
│  - Bootstrap:lightInit (扫 /system + /vendor + /product)  │
│  - Core:fullInit (扫 /data/app)                            │
│  - 全功能:能查所有 apk 元数据                              │
└────────────────┬───────────────────────────────────────────┘
                 ▼  PMS 全功能后,AMS 进入全功能
┌─ AMS (ActivityManagerService) ─────────────────────────────┐
│  - Bootstrap:lightInit (注册到 SM,不能启 Activity)          │
│  - Core:fullInit                                            │
│  - Other:systemReady() 触发 → launcher 启动                 │
│  - 全功能:管理所有 App 进程 / Activity / Service             │
└────────────────┬───────────────────────────────────────────┘
                 ▼  AMS 全功能后,WMS 启动
┌─ WMS (WindowManagerService) ───────────────────────────────┐
│  - Other:主构造 + 加载 policy 资源                          │
│  - 启动 IMS(子组件)                                         │
│  - 显示默认壁纸                                              │
│  - launcher 启动后,显示 launcher                            │
└────────────────┬───────────────────────────────────────────┘
                 ▼  WMS 起来后,IMS 才能起
┌─ IMS (InputManagerService) ────────────────────────────────┐
│  - Other:WMS 启动后,IMS 真正起来                             │
│  - 启动 InputReader + InputDispatcher native 线程            │
│  - 处理触摸 / 按键 / sensor 事件                             │
└────────────────────────────────────────────────────────────┘
                 ▼
┌─ Boot Completed ──────────────────────────────────────────┐
│  AMS.systemReady() 触发 → ACTION_BOOT_COMPLETED 广播         │
│  所有 BootPhase 监听者收到 PHASE_BOOT_COMPLETED              │
│  整机 boot 完成                                              │
└────────────────────────────────────────────────────────────┘
```

**关键依赖关系**:
- **PMS → AMS**:AMS 在 PMS 之前只能"接受进程 fork 请求",**不能**启动 Activity
- **AMS → WMS**:WMS 需要 AMS 提供"focused Activity"信息
- **WMS → IMS**:IMS 需要 WMS 提供"focused window"信息
- **IMS → BootCompleted**:IMS 起来后,系统才真正"全功能"

**任何一个卡住**:
- PMS 卡住 → AMS 不能全功能 → 整个 SystemServer 卡 → 整机不响应
- AMS 卡住 → WMS 收不到"focused Activity" → 屏幕不亮
- WMS 卡住 → IMS 不能起 → 触摸没反应
- IMS 卡住 → 触摸没反应

### 2.6 4 大服务启动耗时(线上实测,SM8550 平台)

| 服务 | 阶段 | 典型耗时(基线) | 典型耗时(异常) | 占比 |
|---|---|---:|---:|---:|
| PMS.lightInit | Bootstrap | 100-300 ms | 500-1000 ms | 5% |
| AMS.lightInit | Bootstrap | 50-150 ms | 300-500 ms | 3% |
| PowerMS / DisplayMS / BootReceiver | Bootstrap | 50-200 ms | 200-500 ms | 5% |
| PMS.fullInit | Core | 800-1500 ms | 3000-5000 ms | 25-30% |
| 其他 Core 服务(11 个) | Core | 200-500 ms | 500-1000 ms | 10% |
| AMS.fullInit + systemReady | Other 末尾 | 300-800 ms | 800-2000 ms | 15% |
| WMS 主构造 + IMS 启动 | Other | 500-1200 ms | 3000-15000 ms | 30-40% |
| 其他 Other 服务(28+ 个) | Other | 300-800 ms | 800-2000 ms | 15% |
| **4 大服务总耗时** | | **2300-4150 ms** | **7300-23500 ms** | **70-90%** |

**关键洞察**:
- **PMS.fullInit(800-1500ms) + WMS(500-1200ms) 占整个 SystemServer 启动的 40-50%**
- 异常情况下,4 大服务**任何一个**卡 3+ 秒,整机 boot 就会慢 5+ 秒
- 所以"SystemServer 慢"90% 的根因在 4 大服务

### 2.7 4 大服务启动阻塞的常见根因速查

| 现象 | 怀疑服务 | 验证方法 | 修复方向 |
|---|---|---|---|
| `ro.boottime.ams_ready` 晚 3+ 秒 | PMS | `adb logcat -d -s PackageManagerService` | 减少 /data/app apk / 挪走 rollback 校验 |
| `first_frame_drawn` 晚 2+ 秒 | WMS | `adb logcat -d -s WindowManagerService` | 压缩 framework-res 资源 |

| 屏幕不亮 | WMS | `adb logcat -d -s WindowManagerService` | 检查 Display 设备 |
| 屏幕亮度不变 | PowerMS | `adb logcat -d -s PowerManagerService` | 检查 hal 权限 |

## 4. 实战案例

### 案例 1:某设备装应用失败,定位 PMS 锁竞争死锁(典型模式)

**环境**:
- Android 版本:基于 AOSP 14 定制
- 设备:某品牌中端机(代号 eagle,4GB RAM)
- 复现步骤:用户装了某第三方 app(代号 TestApp)后,系统弹"安装失败"提示,卸载后再装也失败

**现象**:
```log
$ adb logcat -d -s PackageManagerService,Installer | head -100
PackageManagerService: performBootDexOpt start
PackageManagerService: Starting optimization for TestApp
Installer: Installing apk...
PackageManagerService: java.lang.IllegalStateException: lock held by another thread
  at com.android.server.pm.PackageManagerService.performBootDexOpt(PackageManagerService.java:8500)
  ...
```
**关键观察**:`lock held by another thread` → PMS 内部锁竞争。

**分析思路**:
1. 关键日志 `lock held by another thread` + 位置 `performBootDexOpt` → PMS 锁竞争
2. 抓 PMS 栈,发现 thread-A 在 `performBootDexOpt` 持锁,thread-B 在 `scanDirTracedLI` 等待同一把锁
3. thread-B 是 PMS 第一次扫描的扫描线程
4. thread-A 是 systemReady 阶段执行 dex2oat 的线程
5. **死锁**:thread-A 等 thread-B 完成扫描,thread-B 等 thread-A 释放锁

**根因**:
- PMS 内部 `mPackagesLock` 在多个路径下被持锁
- AOSP 14 之前的 PMS 锁设计是"按需持锁",但 performBootDexOpt 加锁后调用异步 dex2oat,异步任务内部又持同一把锁
- 第三方 app 触发 TestApp 安装时,系统同时在跑第一次扫描 + boot dexopt,两个线程竞争同一把锁

**修复**:
- 短期:OEM 给 systemReady 加 5 秒超时,超时就跳过 boot dexopt
- 中期:把 performBootDexOpt 改为异步 + 不持 mPackagesLock
- 长期:升级到 AOSP 17,PMS 锁设计已经修复

**修复原理**:
- PMS 锁竞争是 PMS 启动阻塞的常见根因之一
- AOSP 17 的 PMS 重构把 `mPackagesLock` 拆成 `mPmLock` + `mInstallLock` 两把锁,降低锁粒度
- 线上治理:遇到 PMS 锁竞争,**优先考虑升级到 AOSP 17+**

### 案例 2:某设备触摸没反应,定位 IMS native 死锁(典型模式)

**环境**:
- Android 版本:基于 AOSP 13 定制
- 设备:Pixel 7(8GB RAM)
- 复现步骤:用户装了某第三方输入 App(代号 TouchMaster)后,触摸没反应,但按键正常

**现象**:
```log
$ adb logcat -d -s InputManagerService,InputReader,InputDispatcher | head -100
InputManagerService: Starting InputReader
InputReader: Starting native reader thread
InputDispatcher: Starting native dispatcher thread
InputDispatcher: Lock held, waiting...
InputReader: Lock held, waiting...
... (死锁 30 秒后)
Watchdog: ANR in system_server, dumping all threads
```
**关键观察**:InputReader 与 InputDispatcher 死锁,Watchdog 抓栈。

**分析思路**:
1. 关键日志 `Lock held, waiting...` + 30 秒 Watchdog → 死锁
2. 抓 IMS native 栈,发现 InputReader 持 `mPolicyLock` 等 InputDispatcher 的 `mLock`
3. InputDispatcher 持 `mLock` 等 InputReader 的 `mPolicyLock`
4. 经典 AB-BA 死锁

**根因**:
- AOSP 13 的 InputDispatcher 与 InputReader 锁顺序不一致
- TouchMaster 装了一个特殊 driver 触发 InputReader 多了一处持锁
- 锁顺序错位导致死锁

**修复**:
- 短期:卸载 TouchMaster
- 中期:TouchMaster 改 driver 适配
- 长期:升级到 AOSP 17,IMS 锁顺序已统一

**修复原理**:
- IMS 死锁的 3 个常见根因:InputReader / InputDispatcher 死锁 / IMS 与 WMS 死锁 / native 侧 mutex 死锁
- 任何第三方输入类 App 都可能引入 IMS 死锁
- 线上治理:遇到触摸没反应,**优先看 IMS 日志**,然后看 WMS 日志

## 5. Takeaway

1. **4 大服务 PMS/AMS/WMS/IMS 是"启动顺序强依赖"的核心**——任何一个卡住,整机都不响应。PMS → AMS → WMS → IMS 是"硬依赖"链,顺序不能错。
2. **PMS 是第一个全功能服务**——它的两阶段初始化(lightInit + fullInit)是 AOSP 12+ 的设计,目的是让 AMS 早期能"接受进程 fork 请求"但"不能启动 Activity"。
3. **PMS 第一次扫描是 SystemServer 慢的"主犯"**——典型 800-1500 ms(基线),3-5 s(异常)。9.1 案例 1 已讲过 rollback 校验阻塞 3.85s。
4. **WMS 是 Other 阶段最大的耗时点**——加载 window manager policy 资源占 200-500 ms(基线) / 10-15 s(异常,OEM 加资源)。9.2 案例 1 已讲过 framework-res 加 800+ 资源 12s+。
5. **AMS 的 systemReady() 触发整机 boot_completed**——所有监听 PHASE_BOOT_COMPLETED 的服务都在这里被通知。
6. **IMS 必须在 WMS 之后启动**——因为 IMS 需要 WMS 提供"focused window"信息;IMS 死锁会让触摸没反应(案例 2)。
7. **PMS 锁竞争死锁是 PMS 启动阻塞的常见根因**——AOSP 17 重构了 PMS 锁设计(拆 mPackagesLock 为两把锁),升级到 AOSP 17 可缓解。
8. **AOSP 17 vs AOSP 14 的 4 大服务差异**:PMS 锁重构 / WMS 加载策略变化 / IMS 锁顺序统一,总耗时 +0-0.5s。
