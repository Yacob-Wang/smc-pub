## 一句话开场

init 的启动阶段不是「时间段」，而是一条**严格有序的事件触发队列**——每个阶段对应一组资源前提（设备节点、`/system`、`/data` 明文），**卡在哪个阶段，就等于哪一层资源没就位**。

## 1. 核心子问题

1. 阶段列表到底有几个？谁定义的——源码写死的还是 `init.rc` 里写的？
2. `early-init` / `init` / `late-init` 三者是 C++ 里 `QueueEventTrigger` 出来的，`post-fs` 这些却是 rc 里 `trigger` 出来的，这个分界意味着什么？
3. 每个阶段的**资源前提**是什么？在 `post-fs` 里访问 `/data` 会发生什么？
4. 为什么 `post-fs-data` 是开机卡死的最高频阶段？
5. 属性触发（`on property:`）在阶段序列里的哪一刻才开始生效？
6. `zygote-start` 为什么要按 `ro.crypto.state` 分几种写法？
7. 各阶段耗时怎么量？`ro.boottime.*` 有哪些、分别对应哪一刻？
8. 「卡在开机动画」这个现象，对应的可能是哪几个阶段？

## 2. 详细展开

### 2.1 阶段序列的两个来源

阶段列表被拆在两个地方，这是读源码时最容易迷路的一点。

**第一部分写死在 C++ 里**。`SecondStageMain()` 在进入主循环前，往 `ActionManager` 的事件队列里塞了固定的几项：

```cpp
// path: system/core/init/init.cpp
// 函数：SecondStageMain()
am.QueueEventTrigger("early-init");

// 等 ueventd 把冷插拔设备节点全部建完
am.QueueBuiltinAction(wait_for_coldboot_done_action, "wait_for_coldboot_done");
am.QueueBuiltinAction(SetMmapRndBitsAction, "SetMmapRndBits");
am.QueueBuiltinAction(SetKptrRestrictAction, "SetKptrRestrict");
am.QueueBuiltinAction(TestPerfEventSelinuxAction, "TestPerfEventSelinux");

am.QueueEventTrigger("init");

// charger 模式（关机充电）不挂载 /data、不起框架
std::string bootmode = GetProperty("ro.bootmode", "");
if (bootmode == "charger") {
    am.QueueEventTrigger("charger");
} else {
    am.QueueEventTrigger("late-init");
}

// 从这一刻起，属性触发才开始工作
am.QueueBuiltinAction(queue_property_triggers_action, "queue_property_triggers");
```

**第二部分写在 `init.rc` 里**，由 `on late-init` 用 `trigger` 命令逐个展开：

```bash
# path: system/core/rootdir/init.rc
on late-init
    trigger early-fs
    trigger fs
    trigger post-fs
    trigger late-fs
    trigger post-fs-data
    trigger load_persist_props_action
    trigger zygote-start
    trigger firmware_mounts_complete
    trigger early-boot
    trigger boot
```

所以完整序列是：

```
early-init → (coldboot 等待) → init → late-init
                                        ├─ early-fs
                                        ├─ fs
                                        ├─ post-fs
                                        ├─ late-fs
                                        ├─ post-fs-data
                                        ├─ load_persist_props_action
                                        ├─ zygote-start
                                        ├─ firmware_mounts_complete
                                        ├─ early-boot
                                        └─ boot
```

**为什么要分成两处**：C++ 里那几个是「无论什么设备都必须有」的骨架，OEM 改不了；rc 里那串是「可以按产品裁剪」的。见过 OEM 在 `on late-init` 里插自己的 `trigger vendor-early-init` 的做法，这是合法的，但插错位置（比如插在 `trigger post-fs-data` 之前却访问了 `/data`）就是典型的开机故障来源。

### 2.2 `trigger` 的排队语义：不是函数调用

这里有个反直觉的点，直接影响你对时序的判断。

`trigger x` **不是同步调用**，它只是往事件队列尾部追加一项。`on late-init` 这个 action 本身会一次性执行完 10 条 `trigger` 命令，把 10 个事件排进队列，然后才轮到队列里的 `early-fs` 开始跑。

```cpp
// path: system/core/init/builtins.cpp
static Result<void> do_trigger(const BuiltinArguments& args) {
    ActionManager::GetInstance().QueueEventTrigger(args[1]);
    return {};
}
```

推论有两条，都很实用：

- **阶段之间是严格串行的**。`post-fs` 里所有 action 执行完，才会开始 `late-fs`。所以某个阶段里有一条阻塞命令，后面全部阶段一起停摆。
- **但阶段内部不保证 rc 文件之间的顺序**。同一个 `on post-fs` 可能在 `init.rc`、`/vendor/etc/init/xxx.rc`、`/odm/etc/init/yyy.rc` 里各写一份，它们按 7.2 讲的解析顺序依次入队。跨 rc 文件的先后依赖是脆的，OEM 换个文件名就可能变。

### 2.3 逐阶段的资源前提

这张表是本节最该记住的东西——**每个阶段能碰什么、不能碰什么**。

| 阶段 | 此刻已就绪 | 此刻还没有 | 典型该做的事 |
|---|---|---|---|
| `early-init` | tmpfs、`/dev` 基本节点 | SELinux 尚未完全 enforce、无冷插拔节点 | 设 cgroup、设 init 自己的 oom_score_adj、起 ueventd |
| `init` | 冷插拔设备节点全部建完 | 分区未挂载 | 建符号链接、写内核 tunable、`mkdir` on tmpfs |
| `early-fs` | 同上 | 分区未挂载 | 起 vold 等挂载所依赖的服务 |
| `fs` | — | `/data` 未挂载 | `mount_all --early`，挂 `/vendor` `/odm` |
| `post-fs` | `/system` `/vendor` 已挂载（只读） | **`/data` 仍不可用** | 改 `/system` 下的权限、挂 tmpfs 类目录 |
| `late-fs` | keymint 等 HAL 可用 | `/data` 仍未解密 | `mount_all --late`，挂 `latemount` 条目 |
| `post-fs-data` | **`/data` 已挂载且已解密** | 框架未起 | `vold_prepare_subdirs`、建 `/data` 下目录树 |
| `zygote-start` | `/data` 可写 | — | 起 netd / statsd / zygote |
| `early-boot` | 同上 | — | 需要 zygote 之后、框架之前做的事 |
| `boot` | — | — | `class_start core`、其余服务 |

**最容易踩的一条**：`post-fs` 和 `post-fs-data` 只差三个字母，资源前提却差了整个 `/data`。在 `on post-fs` 里写 `mkdir /data/vendor/foo`，结果不是报错退出——而是**在 `/data` 挂载点被覆盖前，把目录建在了根文件系统的 tmpfs 上**。等 `/data` 真正挂上去，这个目录就被盖住了，服务启动时找不到它，表现为一个和 rc 完全无关的下游报错。这类问题排查成本极高，因为现场看不出任何 init 报错。

### 2.4 post-fs-data：开机卡死的最高频阶段

把这个阶段单拎出来讲，因为线上「开机停在动画」的案例里它占了很大比重。

它的前提链条最长：

```
/data 分区挂载
    → FBE（File-Based Encryption）密钥解封
        → 依赖 KeyMint HAL 起来
            → 依赖 vendor 分区已挂载 + HAL 进程被 init 拉起
                → 依赖 SELinux 域配对正确
```

链条上任何一环断掉，`post-fs-data` 就停在那里。而 init 是**单线程主循环**（7.1 讲过），主循环一停，后面 `zygote-start`、`boot` 全都不会发生——但屏幕上开机动画还在转，因为 bootanimation 是在更早的阶段起来的。**「动画在转」不代表系统在推进**，这是判断上最大的陷阱。

三类高频成因：

1. **`/data` 文件系统脏了**。`mount_all` 会在挂载失败时触发 fsck。`/data` 上百 GB 且损坏严重时，e2fsck 跑几分钟到十几分钟都可能，用户视角就是长时间黑屏或动画不停。
2. **KeyMint / Gatekeeper HAL 没起来**。多见于 OEM 改了 HAL 的 rc 却漏配 SELinux 域，服务被 `avc: denied` 挡住，init 反复重启它，`post-fs-data` 里的解密动作一直等不到。
3. **`vold_prepare_subdirs` 卡住**。`/data` 上文件数极多（比如某些应用留下百万级小文件）时这一步会显著变慢。

### 2.5 属性触发的生效时刻

回到 7.2 留的那个伏笔：`on property:foo=bar` 到底什么时候开始工作？

答案是 `queue_property_triggers_action` 执行的那一刻——它排在 `late-init` **之后**。

```cpp
// path: system/core/init/init.cpp
static Result<void> queue_property_triggers_action(const BuiltinArguments& args) {
    ActionManager::GetInstance().QueuePropertyChange("", "");
    return {};
}
```

`QueuePropertyChange("", "")` 用一对空字符串做一次全量匹配，把**所有当前已满足条件的属性 action** 一次性排进队列。

这带来两个必须知道的行为：

- **早期设置的属性不会「错过」触发**。哪怕 `foo=bar` 在 `early-init` 就设好了，对应的 `on property:foo=bar` 也会在这一刻补触发。
- **但它的执行时机被推迟到了 `boot` 之后**。因为此时 `late-init` 展开的那 10 个事件已经排在队列前面。所以如果你指望某个属性 action 在 `post-fs-data` 之前跑完，它不会——这是 OEM 定制里常见的时序误判。

要在指定阶段内做条件判断，正确写法不是属性触发，而是给 action 加条件：

```bash
# 在 post-fs-data 阶段内部按属性分支，而不是另起 on property:
on post-fs-data && property:ro.boot.mode=normal
    mkdir /data/vendor/foo 0770 system system
```

### 2.6 zygote-start 的多写法：按加密状态分支

`init.rc` 里 `zygote-start` 有好几个版本，按 `ro.crypto.state` 分：

```bash
on zygote-start && property:ro.crypto.state=unencrypted
    wait_for_prop odsign.verification.done 1
    start statsd
    start netd
    start zygote
    start zygote_secondary

on zygote-start && property:ro.crypto.state=encrypted && property:ro.crypto.type=file
    wait_for_prop odsign.verification.done 1
    start statsd
    start netd
    start zygote
    start zygote_secondary
```

多个 `on` 段共用一个事件名是允许的，init 会把**所有条件满足的**都排进队列。这里的分支是为了覆盖不同加密形态的设备。

注意那条 `wait_for_prop odsign.verification.done 1`：7.2 讲过 `wait_for_prop` 无超时。odsign（on-device signing）负责校验 ART 在设备上重新编译出的 artifact，OTA 后首次开机它要做的活最多。**这是一条位于关键路径上的无超时等待**——odsign 出问题，zygote 永远起不来。

### 2.7 各阶段耗时怎么量

init 会把关键时间点写成只读属性，单位是毫秒（自内核启动计时）：

```bash
adb shell getprop | grep boottime
```

常用的几个：

| 属性 | 含义 |
|---|---|
| `ro.boottime.init` | second stage init 开始的时刻 |
| `ro.boottime.init.first_stage_mount` | 一阶段挂载耗时 |
| `ro.boottime.init.selinux` | SELinux policy 加载耗时 |
| `ro.boottime.init.cold_boot_wait` | 等 ueventd 冷插拔完成的耗时 |
| `ro.boottime.<服务名>` | 该服务被启动的时刻 |

`ro.boottime.<服务名>` 是做阶段拆分的关键——它给了每个服务的启动时刻，把它们按值排序，就能看出哪一段出现了长空档。空档的位置对应的就是卡住的阶段。

补充两个交叉手段：

- `dmesg | grep "init:"`，init 的日志带内核时间戳，能看到每条 action 的执行痕迹。
- Perfetto boot trace，可视化程度最高，用法见卷 5 第 31 章。

## 3. 关键产出

### SOP：把「开机卡住」定位到具体阶段

1. 抓 `dmesg`（能进 adb 就 `adb shell dmesg`，进不去就取 `pstore`/`last_kmsg`，见卷 1 第 4 章）。
2. `grep "init:"`，找**最后一条**成功执行的 action 日志，它所在的 `on` 段就是卡住的阶段。
3. 对照 2.3 的资源前提表，确认该阶段依赖什么。
4. 若停在 `post-fs-data`：优先查 `/data` 挂载与 KeyMint HAL，`grep -E "mount_all|keymint|vold"`。
5. 若停在某个服务：`getprop init.svc.<name>` 看状态，`restarting` 说明在反复崩溃，转 SELinux 与依赖排查。

### SOP：确认一条 action 落在了正确的阶段

1. 在候选 rc 里临时加一条 `write /dev/kmsg "MARK: my-action begin"`。
2. 重启后 `dmesg | grep MARK`，比对它与 `mount_all`、`vold_prepare_subdirs` 等标志性命令的相对位置。
3. 若发现自己的 action 跑在 `/data` 就绪之前，把它从 `on post-fs` 挪到 `on post-fs-data`。

### SOP：找出拖慢启动的阶段

1. `adb shell getprop | grep ro.boottime` 全量导出。
2. 按毫秒值排序，逐项算相邻差值。
3. 差值异常大的那一段，就是要深挖的阶段——注意是**空档**而非某个大值，因为属性记的是时刻不是耗时。
4. 拿这个阶段名去 rc 里 `grep`，逐条 action 用上面的 kmsg 打点法二分。

## 4. 实战案例

### 案例 1：OEM 把目录建在了 `/data` 挂载点之下

**现象**：某项目集成 vendor 服务后，约 1/3 的机器首次开机后该服务不可用，重启一次就正常。

**排查**：服务日志报打不开 `/data/vendor/xxx/config`。但 rc 里明明写了 `mkdir /data/vendor/xxx`，且 init 没有任何报错。

**根因**：这条 `mkdir` 写在了 `on post-fs` 段。此时 `/data` 尚未挂载，目录被建在了 tmpfs 的挂载点目录上；随后 `/data` 挂载，把它盖住。第二次开机之所以正常，是因为首次开机时框架已经在真正的 `/data` 上创建过该目录了。

**修复**：`on post-fs` 改为 `on post-fs-data`。

**教训**：`/data` 相关的一切目录操作，只能在 `post-fs-data` 及之后。init 对这类错误**不会报错**，这是它最危险的地方。

### 案例 2：odsign 拖住 zygote，OTA 后首启多花 40s

**现象**：OTA 升级后首次开机比平时慢 40 秒左右，之后恢复正常。

**排查**：`ro.boottime.zygote` 明显后移，而 `ro.boottime.netd` 正常。两者都在 `on zygote-start` 里，中间隔着的正是 `wait_for_prop odsign.verification.done 1`。

**根因**：OTA 后 ART artifact 失效，odsign 需要重新校验并触发 dex2oat 重编译，这段时间 `zygote-start` 整体阻塞。

**结论**：这是**设计内的行为**，不是缺陷——但它解释了为什么 OTA 后首启必然慢，也说明启动性能基线必须区分「首启」与「常规启动」两条曲线，否则容易把正常现象当劣化追。相关的编译链路见卷 3 第 20 章。

## 5. Takeaway

- 阶段序列由两部分拼成：C++ 里写死的 `early-init` / `init` / `late-init` 骨架，加 `on late-init` 里 `trigger` 展开的十项。
- `trigger` 是入队不是调用；阶段之间严格串行，阶段内部跨 rc 文件的顺序不可依赖。
- 记住资源前提表，尤其是 `post-fs` 无 `/data`、`post-fs-data` 才有。写错**不报错**，只会在下游冒出莫名其妙的故障。
- `post-fs-data` 是开机卡死的最高频阶段，前提链条最长：`/data` 挂载 → FBE 解密 → KeyMint HAL → vendor 分区 → SELinux 域。
- 开机动画在转不代表系统在推进——动画起得比 `post-fs-data` 早。
- 属性触发在 `late-init` 之后才开始工作，别指望它在早期阶段生效；要在阶段内分支就用 `on <事件> && property:<k>=<v>`。
- 用 `ro.boottime.*` 做阶段拆分时，看**相邻差值形成的空档**，不是看单个值。
