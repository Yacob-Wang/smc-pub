## 1. 背景:内存 P0 现场不能"再压一次"

内存问题不同于 ANR/NE——**内存是"持续状态"**。当用户报"App 卡死"时:

- ANR/NE → 现场是一次性事件,traces.txt + tombstone 抓到就行
- **内存问题 → 现场是"实时水位"**——必须一次抓全,过后水位变了抓不回来

**核心原则**:**内存 P0 现场 5 件套,30 分钟内一次抓全**——超时水位变化,证据失效。

### 1.1 5 件套 vs 1 件套

| 模式 | 时间 | 证据完整度 | 工程师体验 |
|------|:----:|:----------:|----------|
| **1 件套**(只 dumpsys meminfo) | 5min | 30% | 多次往返拉数据,水位变了 |
| **5 件套**(系统+进程+时间序列+堆+bugreport) | 30min | 95% | 一次抓全,完整证据链 |

(表 1-1:5 件套 vs 1 件套)

## 3. 5 大治理动作

内存治理按优先级 3 步走(详见 [26.5 §6 治理顺序](file:///E:/smc-pub/04-卷4-诊断方法论与稳定性症状/26-内存与 OOM/05-内存压力连锁反应-GC抖动-掉帧-ANR.md))。**5 大治理动作**展开:

### 3.1 动作 1:进程级治理

| 工具 | 命令 | 适用场景 |
|------|------|----------|
| `am force-stop` | `adb shell am force-stop <pkg>` | 紧急止血(已 OOM 进程) |
| `am kill` | `adb shell am kill <pkg>` | 温和杀(后台进程) |
| `am trim-memory` | `adb shell am send-trim-memory <pkg> RUNNING_CRITICAL` | 触发 onTrimMemory |
| 调 adj | OEM 修改 `ProcessList` adj 阈值 | 长期误配 |
| 调 lmkd 阈值 | OEM 修改 `ro.lmk.*` | 调整杀进程激进度 |

(表 3-1:进程级治理 5 大工具)

### 3.2 动作 2:阈值级治理(lmkd / PSI)

| 参数 | 默认 | 调优方向 |
|------|------|----------|
| `ro.lmk.low` | 256MB(8GB 设备) | 调高到 384MB(更激进杀) |
| `ro.lmk.medium` | 384MB | 调高到 512MB |
| `ro.lmk.critical` | 768MB | 调高到 1024MB |
| `ro.lmk.swap_free_low_percentage` | 20% | 调高到 30% |
| PSI `full avg10` 阈值 | 5% | APM 监控阈值 |

(表 3-2:阈值级治理 5 大参数)

### 3.3 动作 3:ART 调优(Java 堆)

| 参数 | 默认 | 调优方向 |
|------|------|----------|
| `dalvik.vm.heapstartsize` | 16MB | 启动慢调大 |
| `dalvik.vm.heapgrowthlimit` | 192MB | 频繁 GC 调大 |
| `dalvik.vm.heapmaxfree` | 512MB | 同上 |
| `dalvik.vm.heaptargetutilization` | 0.75 | GC 频繁调低到 0.5 |
| GC 后台策略 | Sticky Young | 显式 `ConcurrentMarkSweep` |

(表 3-3:ART 调优 5 大参数)

### 3.4 动作 4:Native 治理(scudo / ION / GPU buffer)

| 参数 | 默认 | 调优方向 |
|------|------|----------|
| `SCUDO_QUARANTINE_SIZE_MB` | 64MB | 内存紧降到 16MB |
| `SCUDO_CACHE_SIZE_MB` | 32MB | 长期占用大降到 8MB |
| `SCUDO_DEAD_RATIO` | 1% | 内存紧调到 5% |
| ION heap 划分 | 系统默认 | 复审 secure buffer 大小 |
| GPU buffer 复用 | 单次 | 改 MediaCodec 输入 buffer 复用 |

(表 3-4:Native 治理 5 大参数)

详见 [26.3 §6 scudo 6 大原则](file:///E:/smc-pub/04-卷4-诊断方法论与稳定性症状/26-内存与 OOM/03-Native-内存增长与泄漏.md)。

### 3.5 动作 5:硬件级

| 维度 | 默认 | 调优方向 |
|------|------|----------|
| RAM | 6GB / 8GB | 8GB → 12GB(高端) |
| ROM | eMMC 5.1 | 切 UFS 3.1(快 3 倍) |
| 处理器 | 8 核 2.0GHz | 切 8 核 3.0GHz(GC 跑得更快) |
| GPU | Mali-G57 | 升级 Mali-G710(减少 GPU buffer) |
| 散热 | 标准 | 加强散热(防止降频) |

(表 3-5:硬件级 5 维治理)

## 4. 水位治理 5 大指标

工程师上线后**必须**监控 5 大指标(超过阈值告警):

| # | 指标 | 阈值 | 工具 | 异常动作 |
|:-:|------|:----:|------|----------|
| 1 | `MemAvailable` | > 1GB(8GB 设备) | 26.7 /proc/meminfo | < 500MB 调 lmkd 激进 |
| 2 | `allocstall_movable` 涨速 | < 100/min | 26.7 /proc/vmstat | > 200/min 调 ART 软上限 |
| 3 | 回收效率 `pgsteal/pgscan` | > 90% | 26.7 /proc/vmstat | < 70% 内存碎片 |
| 4 | `oom_kill` 计数 | = 0 | 26.7 /proc/vmstat | > 0 立即查 |
| 5 | `SwapFree / SwapTotal` 比率 | < 10% | 26.7 /proc/meminfo | zRAM 满 |

(表 4-1:5 大监控指标 + 阈值 + 异常动作)

### 4.1 指标 1:`MemAvailable` 详解

**含义**:`MemFree + Buffers + Cached + 可回收 Slab`(可被快速回收的总内存)

**0xffffff13 实测**:`MemAvailable=4.4GB / MemTotal=7.7GB` = 57% → **健康**

**异常处理**:
- < 1GB:调高 `ro.lmk.low`
- < 500MB:紧急释放 + 调 ART 软上限
- < 200MB:系统已濒临 OOM

### 4.2 指标 2:`allocstall_movable` 详解

**含义**:用户态分配触发 movable zone 回收的次数(用户态吃紧信号)

**0xffffff13 实测**:`allocstall_movable=266` → **警告**

**异常处理**:
- > 100/min:用户态分配压力
- > 200/min:必须释放 Cached 进程
- 持续涨:可能某 App 持续分配(查 dumpsys meminfo)

### 4.3 指标 3:回收效率详解

**公式**:`pgsteal_kswapd / pgscan_kswapd`(回收数 / 扫描数)

**0xffffff13 实测**:`2544671 / 2620134 = 97%` → **健康**

**异常处理**:
- < 90%:回收压力大(系统可能真紧)
- < 70%:严重碎片(查 vmallocinfo + slabinfo)
- < 50%:内核已濒临 OOM

### 4.4 指标 4:`oom_kill` 详解

**含义**:内核 OOM killer 杀进程计数(系统级最后手段)

**0xffffff13 实测**:`oom_kill=0` → **健康**

**异常处理**:
- > 0:立即拉 dumpsys + dmesg 找原因
- > 10/天:系统已严重不足,扩容硬件

### 4.5 指标 5:SwapFree 比率详解

**含义**:zRAM 块设备的剩余空间

**0xffffff13 实测**:`SwapFree=7.6GB / SwapTotal=7.7GB = 99%` → **zRAM 几乎没用**

**异常处理**:
- < 30%:zRAM 满(内存压力很大)
- < 10%:zRAM 满(系统已濒临 OOM)
- 0xffffff13 案例:`SwapFree ≈ SwapTotal` 意味着 zRAM 没工作(关注)

### 5.2 案例 B:水位治理剧本(`CmaFree=0` 链 3 治理)

**场景**:0xffffff13 抓到 `CmaFree=0`,应用层报"拍照偶发失败"。

**5 大治理动作**:
1. **动作 1(进程级)**:用 `dumpsys meminfo` 找哪个进程占 CMA
2. **动作 2(阈值级)**:调 `ro.lmk.critical` 到 1024MB(给拍照应用更多内存)
3. **动作 3(ART 调优)**:调大 `dalvik.vm.heapgrowthlimit`(让拍照应用单进程能容纳更多)
4. **动作 4(Native 治理)**:复审 ION heap 划分,secure buffer 减半
5. **动作 5(硬件)**:升级 RAM(6GB → 8GB)

**5 大监控指标**(上线后):
- `MemAvailable` < 1GB 告警(避免 CMA 再次打满)
- `CmaFree` 持续 < 50MB 告警
- `pgscan_direct` 涨速 > 100/min 告警
- `oom_kill` 计数 > 0 紧急
- `SwapFree < 10%` 紧急

## 6. 总结:5 条 Takeaway

读这篇应能回答:

1. **"5 件套采集清单怎么记?"** ——
   - 件套 1:系统级(proc/meminfo + vmstat + zoneinfo + slabinfo + vmallocinfo)= 26.7
   - 件套 2:进程级(dumpsys meminfo 单进程 + 全设备 + procstats)= 15.06 + 26.8
   - 件套 3:时间序列(mmstat2 / perfetto + ftrace)= 26.9
   - 件套 4:堆转储(am dumpheap + hprof-conv + MAT)= 26.2
   - 件套 5:跨时间窗(bugreport 4 大 buffer)= 33.03

2. **"5 大治理动作按什么顺序?"** ——
   - 动作 1:进程级(am force-stop / am kill / onTrimMemory)
   - 动作 2:阈值级(lmkd / PSI)
   - 动作 3:ART 调优(heapgrowthlimit / heapmaxfree)
   - 动作 4:Native 治理(scudo / ION / GPU buffer)
   - 动作 5:硬件级(RAM / UFS / 处理器)

3. **"5 大监控指标阈值?"** ——
   - `MemAvailable` > 1GB
   - `allocstall_movable` 涨速 < 100/min
   - 回收效率 > 90%
   - `oom_kill = 0`
   - `SwapFree > 10%`

4. **"5 件套 30 分钟时间规划?"** ——
   - 0-5 min:件套 1 + 件套 2(快速抓)
   - 5-15 min:件套 3 + 件套 4(慢抓)
   - 15-30 min:件套 5(bugreport,慢)
   - 30 min 后:解压 + 关联分析

5. **"内存 P0 与 ANR/NE 现场的最大区别?"** ——
   - ANR/NE:一次性事件,traces.txt + tombstone 抓到就行
   - 内存问题:**持续状态**,30 分钟内一次抓全,过后水位变化证据失效
   - **核心原则**:**5 件套 + 30 分钟 + 不过夜**
