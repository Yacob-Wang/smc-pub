## 1. 背景:为什么 APK 必须签名

### 1.1 APK 是什么 + 数字签名的本质

你拿到一个 `.apk` 文件(假设叫 `wechat-v8.0.50.apk`),用 `unzip -l wechat.apk` 看到的 ZIP 条目(AndroidManifest.xml、classes.dex、resources.arsc、META-INF/...),跟普通的 JAR 文件几乎完全一样。那 Android 凭什么说"这个 APK 是腾讯签发的,不是某个黑客塞了 payload 进去的"?

APK 文件 = ZIP 容器 + 数字签名 + 可选 sidecar:

```
┌──────────────────────────────────────────────────────────────┐
│  ZIP Entries (AndroidManifest.xml, classes.dex, ...)         │
│  ──────────── (entries 内部可能 V1 单独签过) ────────────     │
├──────────────────────────────────────────────────────────────┤
│  [可选 V3 only] META-INF/com/android/*(V1 时的 META-INF)     │
├──────────────────────────────────────────────────────────────┤
│  Central Directory (ZIP 中心目录,记录所有 entry 偏移)        │
├──────────────────────────────────────────────────────────────┤
│  ★ APK Signing Block (V2/V3) ★                              │
│  │ - ID-Value pairs: 长度前缀 + magic("APK Sig Block 42")    │
│  │ - signer block × N: 每个签名者(证书链 + 属性 + 签名)     │
│  │ - 整个块本身用 16 字节长度字段包裹                        │
├──────────────────────────────────────────────────────────────┤
│  EOCD (End of Central Directory Record) — ZIP 结尾标记      │
├──────────────────────────────────────────────────────────────┤
│  [V4 only] .apk.idsig (独立 sidecar 文件,与 APK 同目录)      │
└──────────────────────────────────────────────────────────────┘
```

ZIP 的 `Central Directory` 必须在 `EOCD` 之前 — 这是 ZIP 格式的硬约束。`APK Signing Block` 正好夹在两者之间,这是 Google 找到的"既能保留 ZIP 兼容性、又能追加整段签名块"的最优解。V2 时代起的 APK 校验,先找 EOCD 拿 `central_dir_offset`,往回读 APK Signing Block 的 magic,定位签名块 — 这是为什么 `ApkSignatureVerifier.findSignatureBlock()` 要做"反向扫描"。

**数字签名的本质**(3 个动作):

| 动作 | 谁做 | 产出 |
|------|------|------|
| **签名** | 开发者(用私钥) | 把 APK 内容哈希 → 用私钥加密 → 写到 Signing Block |
| **分发** | Play Store / 厂商商店 / 内部 OA | APK 文件 + 签名块原样分发 |
| **校验** | 设备(用公钥/证书) | 用证书验签 → 失败就拒绝安装;成功就信任 APK 内容未被篡改 |

签名的 3 个不可替代的承诺:

1. **身份认证**(Authenticity):这个 APK 是**持有私钥的人**签的 — 证书链验证谁能证明"我就是我"
2. **完整性**(Integrity):APK 内容**没有被篡改** — 任何字节改动都会让签名失效
3. **更新链**(Update Chain):已安装的 v1 和 v8.0.50 必须**同一个签名** — 否则是另一个 App,Android 不允许覆盖安装

### 1.2 签名在 Android 安全体系中的位置

签名是 Android 4 大安全机制之一,**位于"信任根"** — 其他 3 个机制(沙箱、权限、Verity)都建立在"我先信任这个 APK 真的来自 X"的前提上:

```
┌──────────────────────────────────────────────────────────────┐
│  Android 安全体系(自顶向下 4 层)                              │
│                                                              │
│  Layer 4: 应用层安全(应用自己做的加密/HTTPS/Cert Pinning)     │
│  ↑                                                            │
│  Layer 3: 权限沙箱(UID 隔离 + SELinux + 权限声明)             │
│  ↑                                                            │
│  Layer 2: 签名验证(PMS 校验 APK 证书链 + 身份匹配) ← 本系列  │
│  ↑                                                            │
│  Layer 1: 启动完整性(Verified Boot + vbmeta + AVB)           │
│  ↑                                                            │
│  Layer 0: 硬件信任根(TEE / StrongBox / KeyMint)              │
└──────────────────────────────────────────────────────────────┘
```

**Layer 2(签名)是 Android 安全模型的"信任锚"** —
- Layer 3 沙箱默认"不同 UID = 不同进程" — 但**前提是签名能区分"是不是同一个 App"**。如果签名是假的,沙箱连"分给谁"都搞错。
- Layer 1 Verified Boot 保护的是"系统没被 root" — 但**用户装的 App 真的来自腾讯吗**?这是签名的责任。
- Layer 0 硬件信任根给密钥做"出生证明"(Key Attestation,见 §4.4) — 但**这个 Key 真的是 App 自己的 Key 吗**?这又是签名。

**所以呢**:你在 StabilityMatrix 里遇到的"App 闪退"问题,可能根因是签名(第 2 层)出错,而不是 App 代码本身 — 比如某次 OTA 后 PMS 升级,新 PMS 拒绝旧签名的 APK,导致用户看起来"App 装不上"。

### 1.3 稳定性视角:签名的 6 大"咬人场景"

| # | 场景 | 表现 | 涉及篇章 |
|---|------|------|---------|
| 1 | **V1 绕过 + DEX 注入** | APK 看起来签名正常,实际 classes.dex 被植入恶意代码 | [02][05] |
| 2 | **升级签名不匹配** | `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | [02][03][05] |
| 3 | **vbmeta / AVB 签名断裂** | OTA 后整盘无法启动 | [04][05] |
| 4 | **Key 失窃 / 误删** | 上传密钥泄露 / 私钥文件丢失 | [02][04][05] |
| 5 | **Play Integrity 失败** | 设备被认为 root,银行/视频 App 拒绝服务 | [04][05] |
| 6 | **厂商定制签名校验差异** | 同一 APK 在 MIUI/EMUI 表现不一致 | [03][05] |

**这些场景的共同点**:都**不是 App 自己的 bug** — 但 App 在用户眼里"挂了"。架构师如果不掌握签名链,会一直追到 App 业务代码上去,根本查不到根因。

## 2. 发展史:从 V1 到 V4 的 16 年演进

每个签名方案,都是**对前一版的"已知问题"** + **新出现的需求**的回应。看历史不是为了怀旧,而是为了理解**为什么现在用 V2/V3** — 而不是"V1 + 一些补丁"。

### 2.1 V1 JAR 签名(2008,Android 1.0)

**诞生背景**:Android 1.0(2008 年 9 月)发布时,直接把 Java 的 JAR 签名机制搬过来。JAR 签名的核心是"逐文件 SHA-1 摘要 + RSA 签名",所有信息放在 `META-INF/` 目录下:

```
META-INF/
├── MANIFEST.MF         ← 每个 entry 的 SHA-1(或更强)摘要
├── *.SF                ← MANIFEST.MF 的摘要(签名 MANIFEST.MF)
└── *.RSA / *.DSA       ← *.SF 的 RSA/DSA 签名 + 证书链
```

**它解决了什么**:V1 让 Android 1.0 有了"验证 APK 来自谁 + 没被改"的能力,在当时已经足够。

**留下了什么坑(致命)**:

> **Janus 漏洞(CVE-2017-13156,2017 年 12 月披露)**:
>
> V1 签名只覆盖 **ZIP entry 内容** — 但 **classes.dex 不被 V1 视为 entry**(Android 优化后,classes.dex 可能被 mmap,而 V1 的 SHA-1 校验不强制覆盖 mmap 后的视图)。
>
> 攻击者可以在 V1 签名 APK 的**前面**塞一段字节(因为 V1 的 SHA-1 是针对单个 entry 的,不覆盖 APK 文件的整体偏移),让 Dalvik/ART 把它解释为合法的 DEX(旧版 Dalvik 允许"任意 offset 开始解析 DEX")。
>
> **结果**:APK 签名**校验通过**,但运行时执行了**完全不同的恶意代码**。
>
> **修复**(Android 7.0,2016):强制要求 **V2 或更高方案**才能在 Play Store 上架;V1 仅作为 fallback 兼容。

**V1 的另一大劣势:性能** — V1 校验需要**逐文件读 APK** + **逐文件 SHA-1**,大 APK(微信/支付宝 100MB+)校验**秒级**。

### 2.2 V2 APK Signature Scheme v2(2016,Android 7.0,API 24)

**诞生背景**:Google 在 2016 年 Android 7.0 引入**全新方案 V2**,绕开 JAR 签名的所有问题。V2 的核心变化是**整 APK 签名**(whole-APK signing):

```
APK 校验时间: V1 ~3-5s(100MB APK) → V2 ~50-150ms(同 APK)
V2 数据结构:APK Signing Block(夹在 Central Directory 和 EOCD 之间)
V2 覆盖范围:APK 全部内容(除了 Signing Block 自身)
```

**V2 的关键改进**:

| 维度 | V1 | V2 |
|------|----|----|
| 保护粒度 | 单个 ZIP entry | 整个 APK(所有 entry + Central Directory) |
| 校验性能 | 秒级 | 100ms 级(单次 SHA-256 即可) |
| DEX 完整性 | ❌ 不保护(Janus 漏洞) | ✅ 保护(整个 APK 内容都进签名) |
| 抗碰撞 | SHA-1(已不安全) | SHA-256 / SHA-512 |
| minSdkVersion | API 1+ | API 24+ |

**V2 仍然留下的坑**:**不支持密钥轮换**(key rotation) — 一旦私钥泄露,**没法升级**。只能维持现状,新版本签名强制跟旧版本一致,新装用户直接安装的 APK 是"同一个 App"。

### 2.3 V3 Key Rotation(2018,Android 9,API 28)

**诞生背景**:V2 的"不支持 key rotation"在企业场景成了大问题 — **员工离职、密钥文件丢、CI 系统被入侵** 这些场景下,开发者**必须**换密钥,但又**不能**让已安装的用户"无法升级"。

V3 的核心是引入 **Proof of Rotation struct**:

```
V3 签名块结构(简化):
┌────────────────────────────────────────────────┐
│  Signer #1:                                     │
│    Certificate chain (新密钥)                   │
│    Signed Data:                                 │
│      - digests: APK 各 part 的 SHA-256          │
│      - min/target SDK                           │
│      - additional attributes                   │
│    Signature: (新私钥签的)                      │
│  Proof of Rotation:                            │
│    - 旧证书 (#1)                                │
│    - 旧证书对"新证书 + old_attributes" 的签名   │
│    - old_attributes (旧证书的 self_binding)    │
│  ...                                            │
│  Signer #2 (可选,真正用的):                    │
│    ...                                          │
└────────────────────────────────────────────────┘
```

**Proof of Rotation 不是"新密钥的签名",而是"旧密钥声明'我信任这个新密钥'"的签名** — 只有**旧私钥持有者**能生成它。这就是"旋转"(rotation)的本意:信任链从旧 key 转到新 key,链条**不断**。

**V3 的副作用**:**签名块变大** — 多证书 + Proof of Rotation,签名块体积大约是 V2 的 1.5-2x。

### 2.4 V4 Sidecar(2020,Android 11,API 30)

**诞生背景**:V2/V3 都需要**完整 APK**才能验证 — 但 Google Play 的**增量安装**(Incremental Install,2019 年推出)需要**边下边装**。能不能"还没下载完就校验"?

V4 的答案是:**签名和 APK 解耦** — 单独的 `.apk.idsig` 文件,只含 APK 各 part 的 SHA-256 树(Merkle tree):

```
V4 文件结构:
wechat.apk        ← 正常 APK(V2/V3 签名完整)
wechat.apk.idsig  ← 独立 sidecar 文件(可单独下载,只含 hash 树)
```

**V4 的工作流**:
1. Play Store 启动增量安装(下 1MB,装 1MB,再下 1MB,再装...)
2. 每下载一个 part,用 V4 sidecar 里的 hash 树**立即校验**该 part 的完整性
3. APK 全部下完后,再用 V2/V3 做**整体签名校验**

**V4 单独**不能保证完整性(只是 hash 树) — 必须配 V2/V3 才能上线。这就是为什么 V4 总是 V2 + V3 + V4 三联签。

### 2.5 V1-V4 能力对比矩阵

| 能力 | V1 | V2 | V3 | V4 |
|------|----|----|----|----|
| 引入版本 | API 1 (2008) | API 24 (2016) | API 28 (2018) | API 30 (2020) |
| 校验性能 | 秒级(逐文件) | 100ms 级 | 100ms 级 | 100ms 级(同 V2) |
| 抗 Janus | ❌ | ✅ | ✅ | ✅(必须配 V2/V3) |
| 抗 SHA-1 碰撞 | ❌ | ✅(SHA-256+) | ✅ | ✅ |
| 密钥轮换 | ❌ | ❌ | ✅(Proof of Rotation) | ❌(继承 V2/V3) |
| 增量安装支持 | ❌ | ❌ | ❌ | ✅(sidecar) |
| 独立文件 | ❌ | ❌ | ❌ | ✅(`.apk.idsig`) |
| Play Store 上架要求 | 历史(2017 后只 V2+) | ✅ 强制 | 推荐 | 增量场景推荐 |
| 当前实际使用占比 | < 5% | ~100% | ~95% | 增量场景 ~10% |

> **架构师视角的"那么我线上应该用什么"**:
>
> - **新 App + Play Store**:V2 + V3 + V4(全开)
> - **新 App + 国内商店**:V2 + V3(V4 增量安装国内用得少)
> - **老 App(API < 24)**:V1 兜底 + V2 升级
> - **企业内部分发**:V2 + V3(走 MDM 通道,key rotation 必备)
> - **政府/银行 App**:V2 + V3 + Source Stamp(Android 13+ 的"应用商店额外签名")

## 3. 现状:V2/V3 主流 + V4 增量专用

### 3.1 minSdkVersion 与方案选择的硬性约束

`minSdkVersion` 一旦定下来,可选的签名方案**几乎被锁死**:

```
┌──────────────────────────────────────────────────────────────┐
│  minSdkVersion 选择 → 签名方案能力矩阵                       │
│                                                              │
│  minSdk = 30+ (Android 11+):                                 │
│    可选: V1 + V2 + V3 + V4                                  │
│    推荐: V2 + V3 + V4                                       │
│    实际占比: 90%+                                            │
│                                                              │
│  minSdk = 28-29 (Android 9-10):                              │
│    可选: V1 + V2 + V3                                       │
│    推荐: V2 + V3(V4 系统不识别,会被忽略)                     │
│    实际占比: ~5%                                             │
│                                                              │
│  minSdk = 24-27 (Android 7-8):                               │
│    可选: V1 + V2                                            │
│    推荐: V2(V1 仅作 fallback)                               │
│    实际占比: ~4%                                             │
│                                                              │
│  minSdk = < 24 (Android < 7):                                │
│    强制: V1(无 V2 能力)                                      │
│    注意: 2019 年后 Play Store 已停止接受 V1-only 上架        │
│    实际占比: < 1%                                            │
└──────────────────────────────────────────────────────────────┘
```

**所以呢**:你的 App 如果 minSdkVersion 还停在 21/22,**Play Store 早就不能上架了** — 这不是技术约束,是 Google 的"软强制"。**稳定性视角**:某 App 突然在某机型(系统版本低)装不上,**第一时间查 minSdkVersion + V2/V3 能力**,而不是查 App 代码。

### 3.2 Play App Signing 与密钥托管

**痛点**:2017 年前,所有 Android 开发者都要**自己保管私钥** — 私钥丢了,App 永远无法升级,得换包名重发。Google 2017 年 5 月(I/O 2017)推出 **Play App Signing**:

```
密钥角色拆分(Play App Signing):
┌─────────────────────────────────────────────────────────────┐
│  Upload Key(上传密钥,开发者持有)                             │
│    ↓ 用 Upload Key 签 APK                                    │
│  AAB (Android App Bundle) 上传到 Play                       │
│    ↓ Play 验签 OK                                            │
│  Play 内部用 App Signing Key 重新签                          │
│    ↓ (V2 + V3 + V4)                                          │
│  用户从 Play 下载的 APK                                      │
└─────────────────────────────────────────────────────────────┘
```

| 角色 | 谁持有 | 丢了怎么办 |
|------|--------|-----------|
| **Upload Key** | 开发者 | 申请 Play 团队重置(可恢复) |
| **App Signing Key** | Google Play 后台(可下载/托管) | 联系 Google(不可恢复,App 废) |

**Play App Signing 的 3 大收益**:

1. **密钥丢失可恢复** — Upload Key 丢了,App 不会废,Google 帮你重置
2. **App Bundle + Dynamic Feature** — Play 可以**根据设备特性**只下发必要 dex,优化大小
3. **Key Rotation 支持** — 升级 App Signing Key 时,**旧用户仍能升级**到新签名版本

**国内商店现状(对比)**:国内商店(华为/小米/OPPO/vivo/应用宝)**没有等价机制** — 开发者必须自己保管密钥,丢了联系商店可能也没救。**这就是为什么很多国内 App 升级"翻车"** — 他们走的是"非 Play"通道,密钥就是命。

### 3.3 工具链现状:apksigner 替代 jarsigner

**两套工具的代差**:

| 维度 | `jarsigner`(JRE 自带) | `apksigner`(Android SDK build-tools) |
|------|------------------------|--------------------------------------|
| 时代 | Java 1.0(1996) | Android 7.0 后(2016+) |
| 支持 V1 | ✅ | ✅ |
| 支持 V2/V3/V4 | ❌ | ✅ |
| KeyStore 格式 | JKS(已废弃) / PKCS12 | PKCS12 / JKS / PEM |
| 签名速度 | 慢(逐文件) | 快(整 APK) |
| 替代 | ✅ Play Store 2017 强制 apksigner | — |

> **所以呢**:新项目**用 apksigner,不要再用 jarsigner** —
>
> - `jarsigner -verify xxx.apk` 不识别 V2/V3(显示"verified" 实际只验了 V1)
> - `apksigner verify --print-certs xxx.apk` 能看到所有方案 + 证书指纹

**常用 apksigner 命令**(架构师工具箱必备):

```bash
# 1. 验证 APK 签名(线上排查必备)
apksigner verify --verbose --print-certs xxx.apk
# 输出: Verified using v1/v2/v3/v4 scheme ...

# 2. 签名(开发/CI)
apksigner sign --ks release.jks --ks-key-alias xxx   --v1-signing-enabled true --v2-signing-enabled true   --v3-signing-enabled true --v4-signing-enabled true   --out signed.apk unsigned.apk

# 3. 轮换密钥(从 old.jks 转到 new.jks,生成 Proof of Rotation)
apksigner rotate --ks new.jks --ks-key-alias newkey   --old-signer --ks old.jks --ks-key-alias oldkey   --out rotated.apk existing.apk
```

## 4. 签名生态:周边机制一览

> **关键观察**:APK 签名不是孤岛 — 它周围有 4 套机制一起工作。架构师只懂 APK 签名,会遇到"明明签名验证通过了,App 还是被拒绝"的情况,根因可能在 KeyStore / Integrity / vbmeta / Attestation 任何一个。

### 4.1 AndroidKeyStore:TEE/StrongBox 背书的密钥

**AndroidKeyStore 不是"密码学意义上的 KeyStore"** — 它是**KeyMint/Keymaster HAL 的 Java 包装**:

```
App 调用 KeyStore.getInstance("AndroidKeyStore")
  ↓
KeyStore2 服务(JNI)
  ↓
KeyMint HAL(进程内服务,Android 12 之前是 keystore daemon)
  ↓
TEE / StrongBox(Trusted Execution Environment,独立硬件)
  ↓
密钥永不出 TEE
```

**TEE vs StrongBox**:

| 维度 | TEE(ARM TrustZone) | StrongBox(独立安全芯片) |
|------|---------------------|--------------------------|
| 隔离方式 | CPU 切换到 secure world | 独立芯片(类似 SE) |
| 性能 | 中(共享主 CPU) | 较慢(独立 CPU) |
| 抗物理攻击 | 弱(同芯片) | 强(独立封装) |
| Android 要求 | API 24+ 通用 | API 28+ 可选 |
| 实际部署 | 100% 主流机型 | Pixel 3+ / Samsung Knox / 华为 inSE |

**签名场景下的 AndroidKeyStore**:
- App 用 AndroidKeyStore 生成签名密钥 → 私钥**只在 TEE 里** → App 调 `Signature.sign()` 时,TEE 在 secure world 完成签名
- 攻击者拿到设备 root,也只能看到**公钥** — 私钥从来没离开过 TEE

**所以呢**:**你做"防 Root 检测/防 hook" 时,AndroidKeyStore 是必备** — 比纯软件层的 Cert Pinning 强一个数量级。详细机制在 04 篇展开。

### 4.2 SafetyNet → Play Integrity:设备完整性证明

> **历史**:SafetyNet 是 Google 2015 年推出,2022 年开始弃用,被 **Play Integrity API** 替代。SafetyNet → Play Integrity 的迁移是 2022-2024 年的事,大多数 App 已切完。

**Play Integrity API 3 个 verdict**:

| Verdict | 含义 | 银行/支付 App 行为 |
|---------|------|-------------------|
| `MEETS_BASIC_INTEGRITY` | 设备未 root,非模拟器 | 基本通过 |
| `MEETS_DEVICE_INTEGRITY` | 设备跑的是 Google 认证的 Android | 支付/银行级通过 |
| `MEETS_STRONG_INTEGRITY` | 设备有硬件级 TEE + 启动链完整 | 最高级(罕见) |

**与 APK 签名的关系**:
- Play Integrity 校验的是**系统 + 设备**,不是 APK 本身
- 但 App 在用 Play Integrity 时,会把自己的**包名 + 签名 SHA-256** 作为请求参数 — Google 用来防"重打包绕过"

**稳定性视角**:**线上某 App 在某机型一直 Play Integrity 失败** — 常见原因:
1. 设备 root(被 SafetyNet 永久黑名单)
2. ROM 不是 GMS 认证版(国行 ROM 经常)
3. Bootloader 解锁过(就算重新锁,DRK 计数器已 +1)

### 4.3 vbmeta / AVB:与 APK 签名平行的系统级签名链

**vbmeta 不是 APK 签名 — 是系统分区签名**:

```
┌────────────────────────────────────────────────────────────┐
│  Boot 启动链(每个环节都有签名)                              │
│                                                              │
│  Boot ROM(芯片内置,信任根)                                 │
│    ↓ 验签                                                    │
│  Bootloader(Google AVB 2.0 签名)                            │
│    ↓ 验签 boot.img                                           │
│  Kernel + initramfs                                         │
│    ↓ 验签 vbmeta.img                                        │
│  /system /vendor /product 分区(每个有 hashtree 描述)       │
│    ↓ 验签                                                    │
│  init → 启动 system_server → PMS                             │
│    ↓ 验签 APK                                                │
│  App                                                         │
└────────────────────────────────────────────────────────────┘
```

**vbmeta 签名的 3 个等级**:

| 等级 | 描述 | 用户可见效果 |
|------|------|------------|
| **ENFORCE**(强制) | 任何环节验签失败 → 拒绝启动 | root + 改 system → 无法启动 |
| **WARNING**(警告) | 验签失败 → 启动 + logcat 警告 | root + 改 system → 启动但 yellow state |
| **NONE**(无) | 不验签 | 完全自由,主要用于开发 |

**与 APK 签名的关系**:
- **互不依赖** — APK 签名管"App 层",vbmeta 签名管"系统层"
- **但相互影响** — 某些定制 ROM 把 PMS 改掉,**不认 V3 签名**;或反过来,Google Play Integrity 看到 vbmeta 等级是 WARNING,直接给低 verdict

**稳定性视角**:**OTA 后整盘无法启动** — 99% 是 vbmeta 签名断裂,不是 APK 签名问题。但用户感受到的"我的 App 没了"是表象,根因是 vbmeta。

### 4.4 Key Attestation:密钥的"出生证明"

**痛点**:AndroidKeyStore 在 TEE 里生成的密钥,**App 怎么证明"这个 Key 是 TEE 签的,而不是某个 root 后的软件伪造的"**?

**Key Attestation 的解决方案**:
1. App 生成 KeyStore Key,请求 `KeyStore.getCertificateChain()` 并指定 attestation challenge
2. TEE 用**硬件级根密钥**(Google 烧录的,跟设备绑定)签一段 X.509 证书
3. 证书里包含:key 的属性(算法/用途/是否需要 unlock)+ TEE 签名 + attestation challenge(防重放)

**稳定性视角**:**银行 App 拒绝服务** — 常见原因不是"App 代码写错了",而是:
- 设备的 attestation 根证书**不在 Google 信任列表**里(国行 ROM、改版系统)
- attestation chain 中间证书**过期**(Google 2016-2024 年间发过 3 代 root key)
- 用户的 key 用了 `setUserAuthenticationRequired(true)`,但 unlock 时间超 30s

## 5. 签名在 Android 栈中的位置

### 5.1 四层抽象:同一份"签名"在四层看到什么

```
┌────────────────────────────────────────────────────────────┐
│  App 层(开发 / 构建)                                        │
│    - apksigner(签名工具,SDK build-tools)                  │
│    - keytool(密钥生成)                                      │
│    - Android Studio + Gradle(签名配置)                     │
│    - jarsigner(❌ 已过时,只懂 V1)                          │
│                                                              │
│  Framework 层(运行 / 校验)                                 │
│    - PackageManagerService(PMS)— 校验入口                  │
│    - VerifyInstaller— 安装时校验                           │
│    - PackageParser— 解析 APK + 提取签名                    │
│    - ApkSignatureVerifier— 统一校验 API                    │
│    - ApkSignatureSchemeV2/V3/V4— 方案实现                 │
│    - SigningDetails / PackageSignatures— 签名元数据         │
│                                                              │
│  Native 层(libc / 工具库)                                  │
│    - libconscrypt(JDK 移植,签名 + 证书)                    │
│    - libsigcheckaosp(apk 验证 JNI,APK Signature Block 解析)│
│    - fs_mgr(Verified Boot 链路,见 §4.3)                    │
│                                                              │
│  Kernel 层(底层)                                           │
│    - dm-verity / fs-verity(系统分区签名,见 §4.3)            │
│    - keyring(内核密钥环,与 APK 签名无关,但与 dm-verity 配合)│
└────────────────────────────────────────────────────────────┘
```

> **关键观察**:**App 层 + Framework 层是签名真正工作的地方**;Native/Kernel 层是**平行的系统完整性机制**。
>
> **所以呢**:线上排查签名问题,**先看 PMS 日志 + apksigner verify 输出**,90% 能在 App + Framework 层解决;**只有"OTA 后整盘无法启动" 才下到 Kernel 层**(dm-verity)。

### 5.3 关键调用链:从 PackageInstaller 到 PMS

**侧载安装**(adb install / 应用商店下载安装)时的签名校验主链路:

```
用户点击"安装"
    ↓
PackageInstallerActivity(系统应用)
    ↓
PackageInstallerSession.commit()
    ↓
PackageInstallerService.doInstall()
    ↓
InstallParams.handleStartCopy()
    ↓
PackageManagerService.installStage()           ← frameworks/base/services/.../PackageManagerService.java
    ↓
    ├─→ 调 verify() 准备调用
    ↓
VerifyInstaller.verify()                        ← frameworks/base/services/.../VerifyInstaller.java
    ↓
    ├─→ 构造 ApkSignatureVerifier.verify()
    ↓
ApkSignatureVerifier.verify()                   ← frameworks/base/.../apk/ApkSignatureVerifier.java
    ↓
    ├─→ 解析 APK 找 Signing Block(magic "APK Sig Block 42")
    ↓
    ├─→ 遍历所有 signer block(V2 + V3)
    ↓
    ├─→ ApkSignatureSchemeV2.verify()           ← 单个方案的 verify()
    │     ├─ 验证证书链 → 验证签名 → 验证 digest
    │     └─ 返回 result + 证书 + signer index
    ↓
    ├─→ (V3) 验证 Proof of Rotation
    ↓
    ├─→ (V4) 读 .apk.idsig → 验证 hash 树
    ↓
    ├─→ (可选) Source Stamp 验证
    ↓
返回 SigningDetails(包含所有签名 + 方案 + 证书链)
    ↓
PMS 检查"是否与已安装版本签名匹配"
    ↓
    ├─→ 升级安装: 必须匹配
    └─→ 新装: 无要求(但 signingSchemeVersion 决定 minimum 信任)
    ↓
写入 /data/system/packages.xml + /data/app/<pkg>/.../base.apk
```

**关键源码锚点**:

```java
// frameworks/base/services/core/java/com/android/server/pm/VerifyInstaller.java
// 简化后的核心入口(line ~80-120 区间)
public void verify(ParsedPackage parsedPackage, boolean isPreview) {
    // ... 省略前置检查
    ApkSignatureVerifier.Result result = ApkSignatureVerifier.verify(
        parsedPackage.getPath(),     // APK 文件路径
        minSignatureSchemeVersion,   // 来自 PMS 的 minSdkVersion 约束
        packageParserCallback        // 回调
    );
    // ... 省略错误处理
    parsedPackage.setSigningDetails(
        SigningDetails.parseResultForSigningDetails(result)  // 转成 PMS 内部数据
    );
}
```

**架构师视角的"我应该读哪几行"**:
- `ApkSignatureVerifier.verify()` 顶层方法(50 行内能看完)
- `ApkSignatureSchemeV2.verify()` 是真正的"签名验证"逻辑(200 行,核心循环)
- `PackageManagerService.installStage()` 是"签名 vs 已安装" 比较的地方(80 行)

详细走读在 [03-签名校验链路:PackageInstaller → PMS](03-签名校验链路:PackageInstaller到PMS.md)。

## 6. 风险地图:签名的 6 大"咬人场景"

> **总览篇破例规则** (总览篇可省实战案例):本节列 6 类风险场景,**不展开案例**;具体案例在 02/03/05 各讲。

| # | 场景 | 触发条件 | 关键 logcat | 默认错码 | 涉及篇章 |
|---|------|---------|------------|---------|---------|
| 1 | **V1 绕过 + DEX 注入** | minSdkVersion < 24 的老 APK,被恶意重打包 + DEX 偏移 | 无(签名通过) | 无崩溃 | [02][05] |
| 2 | **升级签名不匹配** | 用新密钥签了升级包,但旧 APK 用的是另一个密钥 | `PackageManager: Failed to parse ...` | `INSTALL_FAILED_UPDATE_INCOMPATIBLE(-25)` | [02][03][05] |
| 3 | **vbmeta / AVB 签名断裂** | OTA 后 vbmeta 与新 boot.img 不匹配 | `dm-verity failure` / `Failed to verify avb_handle` | 启动失败 | [04][05] |
| 4 | **Key 失窃 / 误删** | 私钥文件丢失,无法签新版本 | 无(开发侧) | `INSTALL_PARSE_FAILED_NO_CERTIFICATES(-103)` | [02][04][05] |
| 5 | **Play Integrity 失败** | 设备 root / ROM 不认证 / 启动链异常 | `PlayIntegrity verdict=null` | App 主动拒绝 | [04][05] |
| 6 | **厂商定制签名校验差异** | MIUI/EMUI/ColorOS 修改 PMS,加白名单或额外校验 | 厂商日志路径不同 | 各种变体 | [03][05] |

> **架构师视角的"先看哪个"**:
>
> - **"App 装不上"** → 先看 错误码 `-25 / -103`,对应场景 2/4
> - **"OTA 后整盘崩"** → 场景 3
> - **"App 闪退但 logcat 没东西"** → 场景 1(签名校验通过,运行时被劫持)
> - **"银行/视频 App 拒绝服务"** → 场景 5
> - **"同一 APK 在不同厂商表现不一"** → 场景 6

## 7. 总结:架构师视角的 5 条 Takeaway

1. **签名是 Android 安全模型的"信任锚",不是"安全特性"** — 它位于 Layer 2(见 §1.2),沙箱、权限、Verity 都建立在它之上。架构师如果只关注 App 代码,会在跨层问题上栽跟头。

2. **V2/V3 是当前事实标准,V4 是增量专用,V1 是 fallback** — 新 App 必须 V2+V3,大 App 必须 V2+V3+V4,老 App 升级必须分阶段(详见 §2.5 矩阵)。`apksigner verify --print-certs` 是排查工具箱必备。

3. **Play App Signing 是 2017 年后才有的"钥匙托管"** — 国内商店没有等价机制,这是国内 App 升级"翻车"的隐藏根因。如果你的 App 既走 Play 又走国内,**两套密钥管理流程都要做**。

4. **签名生态不止 APK 签名** — KeyStore / Play Integrity / vbmeta / Attestation 任何一个出问题,App 都会"被拒"。`§4.1-§4.4` 的 4 张表是定位"为什么 App 明明签了还装不上"的快查地图。

5. **6 大风险场景 90% 是"非 App 代码问题"** — 线上稳定性问题里,签名相关的根因通常隐藏在 PMS/KeyStore/AVB 链路,**绝不是 App 业务代码**。架构师必须有"跨 4 层"的视角,才能一次定位。
