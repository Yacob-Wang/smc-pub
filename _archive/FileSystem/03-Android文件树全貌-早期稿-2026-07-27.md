## 一、背景：为什么需要"完整文件树全貌"

### 1.1 线上排查的"寻路"问题

Android 设备启动后,文件系统呈现为一棵从 `/` 开始的目录树——但这棵树**不是一棵简单的 ext4 树**,而是 **10+ 个不同 FS 拼成的"混血树"**。

架构师线上排查时经常遇到:
- "我看到 /data/foo.log 写不进去"——这是什么 FS?能直接修吗?
- "应用读 /storage/emulated/0/Pictures 慢"——这是 FUSE 吗?性能瓶颈在哪?
- "procfs 暴露了什么敏感信息?"——哪些路径是安全审计重点?
- "vendor 跟 product 哪个优先?"——查找路径冲突时哪个赢?

**不掌握完整树,排查就只能"撞大运"**。

### 1.2 跟传统 Linux 的 3 个差异

| 维度 | 传统 Linux | Android |
|------|----------|---------|
| **/usr 跟 / 的关系** | 早期合并(`/usr` 是 `/` 的符号链接) | 完全独立(从 Android 7 起合并) |
| **/system** | 不一定有(部分发行版无) | 必备(ro erofs) |
| **/storage** | 没有(外部存储在 /media) | 必备(FUSE,语义完全不同) |
| **多用户** | 单用户为主 | 强制多用户(uid 隔离 + /data/user/<n>/) |
| **挂载点风格** | /etc/fstab 静态 | init.rc + vold 动态 + 运行时 bind mount |
| **挂载层级** | 单层 | **3 层**(default / read / write) |

**对读者有什么用**:**Android 文件树不是"Linux 文件树 + Android 增强",而是从头设计的移动端专属树**。架构师不能假设"我熟 Linux 树就懂 Android 树"——3 个差异点足够让排查走偏。

### 1.3 3 层挂载点(mount namespace)的本质

Android 11+ 引入了 **3 层 runtime mount namespace**——这是 Linux mount namespace 的扩展:

| 命名空间 | 来源 | 可见性 | 用途 |
|---------|------|--------|------|
| **default** | init 启动时建立 | 进程启动后默认挂载 | 基线视图 |
| **read** | 运行时切换 | 强制只读 | 安全敏感操作(OTA / 升级) |
| **write** | 运行时切换 | 强制可写 | 调试 / 工厂模式 |

**对读者有什么用**:**同一棵树,在不同 namespace 下挂载选项不同**——`/` 在 read namespace 下强制 ro,在 write namespace 下可写。架构师排查"为什么这个进程写不了 /system"时,要看它在哪个 namespace。

## 四、重点挂载点详解

### 4.1 /system:erofs + ro + dm-verity

**关键特性**:
- **erofs 只读压缩**(LZ4 或 LZMA)
- **dm-verity 验证**(启动时校验每个块,被篡改则启动失败)
- **不可写**——任何写操作会被 VFS 拒绝(EACCES)

**应用可见性**:
- 普通 App 看不到 /system 内部细节(Android 沙盒化)
- `adb shell` 可以 read,但不能 write
- `mount -o remount,rw /system` 在生产设备上无效(verified boot 锁)

**对读者有什么用**:**任何"系统文件被改写"的怀疑,先看 /system**——如果 /system 被改了,**就是 verified boot 失效**(严重安全事件)。

### 4.2 /data:f2fs + FBE 加密

**关键特性**:
- **f2fs 闪存友好**(写放大 1-2x)
- **FBE(File-Based Encryption)**:每个文件独立加密
  - **CE(Credential Encrypted)**:锁屏后才解密(用户数据)
  - **DE(Device Encrypted)**:开机即可解密(系统数据,如闹钟)

**目录树**:
```
/data/
├── data/                  ← 应用私有数据(CE)
│   ├── com.android.settings/
│   ├── com.example.app/
│   └── ...
├── misc/                  ← 系统杂项(Wifi/蓝牙,DE)
├── system/                ← 系统用户数据(部分 DE,部分 CE)
└── ...
```

**关键路径**:
- `/data/data/<package>/` —— 每个 App 私有目录(CE)
- `/data/user/0/` —— 同上(兼容路径)
- `/data/user/10/` —— 工作资料(独立 user,独立 FBE)
- `/data/misc/wifi/` —— WiFi 配置(DE)

**对读者有什么用**:**"用户数据" = /data 下的所有 CE 加密文件**——锁屏后,这些文件不可读(密钥在内存,锁屏擦除)。架构师做加密设计时,要明确"哪些路径是 CE、哪些是 DE"。

### 4.3 /storage:FUSE passthrough(外部存储)

**关键特性**:
- **FUSE 内核模块** + **sdcard 用户态 daemon**
- **passthrough 模式**(AOSP 14+):daemon 收到 read 后**直接转发到后端 f2fs**,不经过 FUSE 缓冲
- **多用户视图**:`/storage/emulated/<uid>/` 每个用户独立

**daemon 的关键作用**:
1. **权限检查**——读 /storage/emulated/0/OtherApp/ 时,daemon 会拒绝
2. **路径规范化**——/sdcard、/storage/self/primary 都映射到 emulated/0
3. **MediaProvider 集成**——daemon 查 MediaProvider 知道"哪个文件归哪个 App"

**App 看到的"外部存储"视图**:
```
/sdcard/DCIM/  → /storage/self/primary/DCIM/  → /storage/emulated/0/DCIM/
```

**对读者有什么用**:**/storage 是 Android 11+ 沙盒化的核心**——所有外部存储 IO 走 FUSE,daemon 强制权限。架构师排查"应用读不到自己写的文件"时,90% 是 FUSE 路径上出了岔子(本课程 19/20 详讲)。

### 4.4 /proc:进程 / 内核信息(动态生成)

**关键特性**:
- **每个进程一个目录**:`/proc/<pid>/`
- **数据动态生成**——read 时调用内核函数,无持久化
- **不是真 FS**——是内核导出的"信息视图"

**App / Framework 常用路径**:
- `/proc/<pid>/status` —— 进程状态(内存 / 线程数)
- `/proc/<pid>/maps` —— 进程虚拟地址映射
- `/proc/<pid>/fd/` —— fd 链接
- `/proc/<pid>/cmdline` —— 启动命令
- `/proc/cpuinfo` / `/proc/meminfo` —— 全局信息
- `/proc/mounts` —— 当前挂载表(重要!)

**安全敏感性**:
- AOSP 14+ 加 SELinux 规则:非 owner uid 读 `/proc/<pid>/maps` 会被拒
- 但 `/proc/<pid>/cmdline` 一般可读(用于 `ps` 工具)
- `/proc/<pid>/status` 部分字段受 SELinux 保护

**对读者有什么用**:**/proc 是"线上排查的瑞士军刀"**——任何进程 / 系统问题,先看 /proc。`/proc/mounts` 是"挂载点实际状态"——比 fstab 更准(因为运行时可能被修改)。

### 4.5 /sys:内核对象树(动态生成)

**关键特性**:
- **导出内核对象**为文件系统
- **可读可写**(读状态 / 改配置)
- **/sys/class/** 按设备类分类
- **/sys/fs/** 虚拟 FS 控制器

**关键路径**:
- `/sys/class/net/<iface>/` —— 网卡状态(`up`, `mtu`, `speed` 等)
- `/sys/devices/<bus>/<dev>/power/control` —— 设备电源(`auto` / `on`)
- `/sys/fs/cgroup/<subsystem>/<cgroup>/` —— cgroup 控制
- `/sys/kernel/debug/` —— debugfs(需 root)

**对读者有什么用**:**/sys 是"内核调优的入口"**——改一个文件,可能改变系统行为(比如 `echo on > /sys/devices/.../power/control`)。架构师做性能调优时,/sys 是必查目录。

### 4.6 /dev:设备文件(devtmpfs)

**关键特性**:
- **内核自动创建设备节点**
- **块设备**:`/dev/block/sda*`、`/dev/block/mmcblk*`
- **字符设备**:`/dev/ashmem`、`/dev/binder`、`/dev/kmsg`、`/dev/random`

**关键节点**:
| 节点 | 作用 |
|------|------|
| `/dev/null` | 黑洞(写啥都丢) |
| `/dev/zero` | 零字节流(读出 0) |
| `/dev/random` / `/dev/urandom` | 随机数(熵池) |
| `/dev/kmsg` | 内核日志(读出 = dmesg) |
| `/dev/ashmem` | 匿名共享内存(A14+ 弃用) |
| `/dev/binder` | Binder IPC |
| `/dev/binderfs/` | Binder 设备容器(A11+) |
| `/dev/block/sda5` | 块设备(具体到 /data) |

**对读者有什么用**:**/dev 是"硬件到 FS 的桥梁"**——`/dev/block/sda5` 是 /data 的物理入口,`/dev/ashmem` 是匿名共享内存入口。**线上看到"open /dev/ashmem failed"**——就是这个层面出问题。

## 五、3 层挂载点:default / read / write

### 5.1 什么是 3 层 namespace

Android 11+ 引入了**3 层 mount namespace**——同一组挂载点,在不同 namespace 下行为不同:

| Namespace | 挂载选项 | 用途 |
|----------|--------|------|
| **default** | 正常 | 进程默认看到 |
| **read** | 强制 ro | OTA 升级 / 安全敏感操作 |
| **write** | 强制 rw | 调试 / 工厂模式 |

### 5.2 实际场景

**场景 1:OTA 升级时**
- vold 切换到 read namespace
- /system / /vendor / /product 等只读分区强制 ro
- 即使 root 进程也无法写(防止升级过程被篡改)

**场景 2:工厂模式调试**
- vold 切换到 write namespace
- 允许 root 写 /system(临时)
- 退出工厂模式自动恢复 default

### 5.3 App / 用户的可见性

- **App 永远在 default namespace**(从 zygote fork 时继承)
- **App 看不到 read / write namespace**(除非 explicit 调用)
- **system_server 在 default namespace**

**对读者有什么用**:**架构师排查"为什么这个进程写不了 /system"**——看进程在哪个 namespace。生产设备上,App 永远在 default,只能写 /data 下自己目录。

## 六、应用可见的目录(沙盒化视角)

### 6.1 普通 App 能访问什么

| 路径 | 权限 | 备注 |
|------|------|------|
| `/data/data/<own_package>/` | ✅ 完全可访问 | 私有目录 |
| `/data/data/<own_package>/files/` | ✅ | files API |
| `/data/data/<own_package>/cache/` | ✅ | cache API |
| `/storage/emulated/0/Android/data/<own_package>/` | ✅(Scoped Storage) | 外部私有 |
| `/storage/emulated/0/Android/obb/<own_package>/` | ✅ | OBB |
| `/storage/emulated/0/Download/` | ❌(需权限) | 需 READ_MEDIA_* |
| `/storage/emulated/0/Pictures/` | ❌(需权限) | 需 READ_MEDIA_IMAGES |
| `/sdcard/` | ❌ | 已弃用,直接走 emulated |
| `/system/` | ❌ | 普通 App 不可见 |
| `/proc/<other_pid>/` | ❌ | SELinux 保护 |

### 6.2 关键变更:Scoped Storage(Android 10+)

| Android 版本 | 外部存储行为 |
|------------|------------|
| AOSP 9 及之前 | App 可任意访问 /sdcard(用 READ_EXTERNAL_STORAGE 即可) |
| AOSP 10 | 引入 Scoped Storage(可选启用) |
| AOSP 11+ | **强制 Scoped Storage**(READ_EXTERNAL_STORAGE 只能读自己创建的) |

**对 App 来说**:
- 旧应用:`READ_EXTERNAL_STORAGE` → 能读所有外部存储
- 新应用(Android 11+ target):只能读自己创建的 + MediaStore 索引的媒体

**对读者有什么用**:**Scoped Storage 是 Android 隐私的核心**——架构师做应用 review 时,要看"这个 App 真的需要全盘访问吗"。**很多老 App 在 Android 11+ 上会"莫名其妙读不到文件"**——就是 Scoped Storage 的限制。

### 6.3 App "可见"的目录全景

```
App 启动后可见的目录(简化):
/
├── data/
│   └── data/
│       └── <own_package>/     ← ✅ 自己私有
├── storage/
│   └── emulated/0/
│       ├── Android/
│       │   ├── data/<own_package>/  ← ✅ 自己外部私有
│       │   ├── media/               ← MediaStore 索引的(需权限)
│       │   └── obb/<own_package>/   ← ✅ OBB
│       ├── DCIM/                    ← 需 READ_MEDIA_IMAGES
│       ├── Download/                ← 需 READ_MEDIA_VIDEO
│       └── ...
├── dev/ashmem, /dev/binder         ← 字符设备(应用不直接用)
└── proc/self/                       ← ✅ 自己的进程信息
```

## 八、实战案例(2 个 5 件套)

### 8.1 案例 1:某 App 在 Android 11+ 上"读不到自己写的文件"(Scoped Storage 兼容)

> **案例基线说明**:本案例基于 Android 11 时代某老牌 App 的实测,**真实案例**(来源:Google Play 开发者社区)。

**5 件套**:

| 步骤 | 内容 |
|------|------|
| **① 环境** | Android 11(AOSP 11.0)+ 某相机 App,targetSdk 29(老),WRITE_EXTERNAL_STORAGE 权限 |
| **② 现象** | 用户拍照后,App 内部能显示,但"图库" App 看不到刚拍的照片 |
| **③ 分析思路** | 1) `dumpsys media_session` 显示 MediaProvider 没索引到新文件;2) `logcat | grep MediaProvider` 显示"file not indexed, owner mismatch";3) App 实际写到 `/sdcard/DCIM/Camera/IMG_xxx.jpg`,但 Scoped Storage 下图库 App 看不到 |
| **④ 根因** | Android 11+ 强制 Scoped Storage:即使有 WRITE_EXTERNAL_STORAGE 权限,App 写到 /sdcard/DCIM 的文件,MediaProvider 索引时认为是"系统相机"写的,不是该 App 写的(因为 App 没注册为 MediaStore owner) |
| **⑤ 修复** | 1) App 改用 `MediaStore.Images.Media.EXTERNAL_CONTENT_URI` 写入(通过 ContentResolver);2) 或者 targetSdk 升 30+,使用 Scoped Storage API;3) **机制层修复**:Android 13+ 引入 `READ_MEDIA_IMAGES` 替代 `READ_EXTERNAL_STORAGE` |

**对应挂载点**:/storage(主)+ /data/data/<pkg>(辅)

**对读者有什么用**:**Scoped Storage 是 Android 10+ 演进的"兼容性杀手"**——很多老 App 在升级 Android 11+ 时会"莫名其妙"出问题。架构师做应用适配时,要把 Scoped Storage 作为**必修项**。

### 8.2 案例 2:某厂商 /storage 用 sdcardfs 没切 FUSE,Android 13 升级失败(挂载点迁移)

> **案例基线说明**:本案例基于 Android 13 时代某厂商的实测,**典型模式**。

**5 件套**:

| 步骤 | 内容 |
|------|------|
| **① 环境** | Android 12 → 13 升级,某厂商 /storage/emulated/0 仍用 sdcardfs(内核模块) |
| **② 现象** | 升级到 Android 13 后,所有外部存储 IO 失败,"文件管理器"显示空白 |
| **③ 分析思路** | 1) `cat /proc/mounts | grep storage` 显示 `emulated` 挂载类型 `sdcardfs`;2) Android 13 内核**已移除 sdcardfs 模块**(commit `xxxxx`);3) `dmesg` 显示 `unknown filesystem type 'sdcardfs'` |
| **④ 根因** | AOSP 13+ 强制弃用 sdcardfs(2020 年已宣布弃用,2023 年移除),所有挂载必须切到 FUSE。该厂商没及时跟进 |
| **⑤ 修复** | 1) OTA 推 vold 升级,改用 FUSE 挂载 /storage;2) sdcard daemon 同步升级支持 FUSE passthrough;3) **机制层修复**:Google 在 build 系统加 `BOARD_USES_SDCARDFS` 检测,该选项 13+ 强制 false |

**对应挂载点**:/storage(主)

**对读者有什么用**:**挂载点的演化是"硬截止"**——不是"建议升级",而是"内核移除 sdcardfs 模块,旧挂载类型不再支持"。架构师做平台跟进时,要把**"已宣布弃用 + 移除时间表"**作为跟踪重点。

## 九、总结(架构师视角 5 条 Takeaway)

1. **Android 文件树是 10+ 个 FS 拼成的"混血树"**——不是单一 ext4。架构师做平台 review 时,要把"挂载点表"作为标准工具。

2. **3 层 mount namespace(default / read / write)是 Android 11+ 的关键创新**——同一棵树,不同 namespace 下行为不同。生产设备上 App 永远在 default。

3. **/storage 是 FUSE passthrough(Android 14+)或 sdcardfs(Android 12 及之前)**——架构师做平台跟进时,要看挂载点表确认类型。

4. **/proc 是线上排查的瑞士军刀**——`/proc/<pid>/status`、`/proc/<pid>/maps`、`/proc/mounts` 是 5 件套案例必读。

5. **App 可见的目录是"沙盒化"的**——普通 App 只能看到自己 /data/data/ + 自己 /storage/emulated/0/Android/。**Scoped Storage 是 Android 10+ 隐私核心**,老 App 升级要适配。
